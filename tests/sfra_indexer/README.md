# SFRA: тестовый стенд структурного Markdown-индексатора

Независимый набор pytest-тестов для этапа 1 SFRA. Он проверяет сегментацию Markdown, исходные фрагменты, координаты, Content Hash, родительский контекст и границы индексируемого Vault. Поиск, ранжирование и retrieval здесь намеренно отсутствуют.

## Структура

- `fixtures/` — небольшие автономные Markdown-документы, каждый воспроизводит отдельный класс разметки.
- `test_fixtures.py` — проверка корпуса и интеграционные проверки сегментации фикстур.
- `test_live_vault.py` — профиль семи реальных документов из `ГП/`, проверка сканирования, разбора и экспорта.
- `adapter.py` — единственная точка привязки неизвестной пока структуры результата SFRA к стабильному тестовому представлению.
- `SCENARIOS.md` — матрица сценариев и критические случаи для аудита.

## Запуск

Из корня репозитория:

```bash
python -m pip install -r tests/sfra_indexer/requirements.txt
python -m pytest tests/sfra_indexer -ra
```

Пока модуль индексатора отсутствует, автономные проверки корпуса и профиля реальных исходников выполняются, а интеграционные тесты отмечаются как skipped. Это ожидаемо: тестовый стенд не подменяет индексатор самодельным парсером.

Когда реализация будет готова, укажите её импортируемый Python-модуль:

```bash
SFRA_INDEXER_MODULE=package.module python -m pytest tests/sfra_indexer -ra
```

По умолчанию используется модуль `sfra_indexer`. Он должен предоставлять три публичные функции из согласованного задания:

- `scan_vault(root_path)`
- `parse_document(path, root_path)`
- `export_index(result, output_path)`

В тестах `root_path` — абсолютный путь непосредственно к директории `ГП/`, а `path` — абсолютный путь к Markdown-файлу внутри неё. Если реальная реализация трактует пути иначе, измените вызовы в тестах или оформите это преобразование в отдельном адаптере, не меняя сценарии.

## Адаптация результата

Формат результата SFRA пока не опубликован. Поэтому тесты не предполагают названия полей, формат сериализации, тип контейнера или вложенную схему. После появления реализации заполните две функции в `adapter.py`:

1. `iter_nodes(result)` — преобразует результат `parse_document` в последовательность `NodeView`.
2. `iter_document_paths(result, root_path)` — извлекает пути документов из результата `scan_vault`.

`NodeView` — внутренний контракт только этого тестового стенда, а не требование к публичному API SFRA:

- `node_id` — уникальный идентификатор узла в документе;
- `parent_id` — идентификатор непосредственного родителя либо `None`;
- `kind` — нормализованный тип: `heading`, `list_item`, `table`, `quote`, `callout`, `code_block`, `paragraph` или другой тип;
- `source_text` — точный исходный фрагмент без нормализации;
- `char_start`, `char_end` — смещения в Python Unicode code points, 0-based, полуоткрытый диапазон `[start, end)`;
- `utf8_byte_start`, `utf8_byte_end` — смещения в исходных UTF-8 байтах, 0-based, полуоткрытый диапазон;
- `line_start`, `line_end_exclusive` — номера строк с единицы, конечная граница не включается;
- `content_hash` — Content Hash этого точного фрагмента;
- `level` и `label` — уровень/текст заголовка или пункта, если они доступны.

Адаптер обязан переводить координаты реализации в три согласованные системы: 1-based линии с исключающей конечной границей, 0-based Python code points и 0-based UTF-8 байты. Принцип взят из исследования в `research/markdown-parser/README.md`; при этом схема результата SFRA остаётся неизвестной до реализации.

## Content Hash

В стенде исходное ожидаемое значение по умолчанию — SHA-256 от UTF-8-байтов точного фрагмента. Алгоритм не был задан в спецификации индексатора, а исследовательский прототип пока не экспортирует Content Hash. Если SFRA v1 закрепит другой алгоритм или способ кодирования, измените только `expected_content_hash()` в `adapter.py` и зафиксируйте решение в отчёте; не ослабляйте проверку до простого сравнения непустых строк.

## Что проверяется

Интеграционные тесты проверяют:
- каждый фрагмент точно соответствует срезу исходного файла;
- диапазоны находятся внутри документа, а строки согласованы со смещениями;
- все содержательные символы (включая NBSP) покрыты точными исходными фрагментами; пустые ASCII-разделители между блоками не обязаны становиться отдельными узлами;
- Content Hash вычислен от того же сырого фрагмента;
- все ссылки на родителей разрешаются, нет циклов, а диапазон родителя охватывает диапазон потомка;
- структурные типы и уровни распознаются в специально подготовленных фикстурах;
- сканирование возвращает документы только из `ГП/`;
- реальные документы разбираются тем же контрактом;
- `export_index` создаёт результат по указанному пути.

Проверки не требуют точного внутреннего JSON или конкретной сериализации. Это позволяет менять реализацию, не переписывая корпус сценариев.
