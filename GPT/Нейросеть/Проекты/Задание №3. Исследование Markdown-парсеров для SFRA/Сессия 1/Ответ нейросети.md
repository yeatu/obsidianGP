Задание №3. Исследование Markdown-парсеров для SFRA

Главный архитектурный вывод: AST не должен становиться источником текста для индексатора. Источником истины должен оставаться исходный Markdown-файл, а AST должен использоваться для определения структуры и границ фрагментов.

Это принципиально важно для SFRA. Если парсер преобразовал Markdown в AST, а затем сериализовал его обратно, он может изменить отступы, пробелы, окончания строк, форматирование и другие детали. Полученный текст будет семантически похож на исходный, но уже не будет его точной копией.

Для этой задачи я рассматриваю два независимых результата разбора:

Структурное представление документа: заголовки, списки, цитаты, таблицы и другие элементы.

Координаты элементов в оригинальном файле, позволяющие извлечь исходный текст обычным срезом строки.

Рабочую директорию ГП/ и исходные заметки следует оставить нетронутыми. Исследование и прототип будут изолированы в отдельной папке репозитория.

2. Координаты: рекомендуемая модель

Рекомендую хранить три независимых диапазона.

Поле

	

Единицы

	

Назначение

Строки

	

Навигация по документу




char_start, char_end

	

Unicode code points

	

Срез Python str




byte_start, byte_end

	

UTF-8 bytes

	

Точное извлечение исходных байтов

Все диапазоны должны быть полуоткрытыми: начало включено, конец исключён.

Например, кириллическая буква обычно занимает один индекс Python-строки, но два байта UTF-8. Emoji могут занимать четыре байта UTF-8.

Нельзя взаимозаменять эти координаты.

Отдельно важно: файлы необходимо читать с сохранением оригинальных окончаний строк. Обычное преобразование CRLF в LF изменит все последующие смещения.

Прототип учитывает это через:

Python
with path.open("r", encoding="utf-8", newline="") as stream:
    source = stream.read()

Для окончательного индексатора я рекомендую хранить исходные байты и вычислять символьные координаты дополнительно.

3. Практическая проверка исходных заметок

Я просмотрела содержимое трёх заданных файлов через GitHub.

Рэддл.md

В документе многоуровневые списки, вложенность с использованием табуляции, длинные цепочки зависимых пунктов.

Основной тест для корректного определения родительских и дочерних элементов.

Перси Уизли.md

Есть Obsidian Callout:

Markdown
> [!NOTE] Уизли
> Маги крови...

Хороший тест на сохранение цитат и распознавание Callout без потери исходных маркеров.

Генрих Фауст.md

Сочетание заголовков, больших текстовых блоков и цитат, используемых в качестве визуальных разделителей.

Хороший тест на смешанную структуру документа.

Выполнена также локальная проверка механизма координат на примере с кириллицей, вложенным списком, Callout и таблицей. Все полученные срезы совпали с соответствующими диапазонами исходной строки.

Ограничение проверки: запустить прототип непосредственно на трёх заметках в этой среде не удалось: клонирование репозитория в локальную среду выполнения оказалось недоступно. Поэтому я не буду выдавать неподтверждённые результаты за реальные тесты корпуса.

Для воспроизводимой проверки подготовлена команда:

Bash
python -m pip install -r research/markdown-parser/requirements.txt

python research/markdown-parser/prototype.py \
  "ГП/фракции/Рэддл.md" \
  "ГП/персонажи/ученики/Иное/Перси Уизли.md" \
  "ГП/персонажи/ученики/Молодая кровь/Генрих Фауст.md" \
  --output /tmp/sfra-markdown-spans.json

В JSON для каждого файла будет поле all_round_trip_exact. Оно проверяет, что извлечённые UTF-8 байты соответствуют исходному текстовому фрагменту.

5. Итоговые рекомендации исполнителю №1

Моя рекомендация для первой версии SFRA:

markdown-it-py + собственная система координат
Рекомендуемая архитектура

Markdown-it-py отвечает за структуру.

Исходный файл отвечает за содержимое.

Собственная таблица смещений отвечает за координаты.

AST никогда не используется для восстановления оригинального текста.

Последовательность обработки одного файла:

Прочитать оригинальные UTF-8 байты.

Сохранить их хеш.

Построить таблицу начал строк.

Выполнить Markdown-разбор.

Получить структурные токены и диапазоны строк.

Перевести диапазоны строк в символьные и байтовые offsets.

Извлечь оригинальные фрагменты.

Проверить точное совпадение байтов.

Сохранить координаты вместе с идентификатором версии файла.

Особенно важно: не делать текст заголовка идентификатором узла. Два одинаковых заголовка в одном документе должны иметь разные идентификаторы, основанные на положении и структуре.

Что пока не нужно делать

Подключать сразу несколько Markdown-парсеров.

Писать собственный универсальный Markdown-парсер.

Преобразовывать AST обратно в Markdown.

Пытаться нормализовать все Obsidian-конструкции.

Строить систему разрешения ссылок и полноценный индексатор.

Это исследование подтверждает практическую основу для первой версии, но не заменяет прогон прототипа на полном корпусе.

Главный вывод для SFRA: структурная корректность и точность извлечения должны проверяться независимо. Парсер может ошибиться в классификации элемента, но система координат всё равно должна позволять получить исходные байты без единого изменения. Именно это свойство стоит сделать обязательным инвариантом индексатора.
