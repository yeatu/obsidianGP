# Задание для Исполнителя 2: разработка локального поискового индекса SFRA


## 1. Цель


Разработать второй обязательный компонент архитектуры SFRA: локальный поисковый индекс, обеспечивающий поиск по содержимому Markdown-документов, структурным узлам и сущностям.


Основная задача — обеспечить точное обнаружение необходимых фрагментов Vault по словам, словоформам, числам, заголовкам, именам персонажей и другим сущностям.


**Главный принцип: поисковый индекс помогает найти источник, но не заменяет его.**


Поисковая система не должна создавать новые факты, самостоятельно устанавливать связи между персонажами или определять, какая из нескольких версий информации является правильной.


Разработай рабочую основу, которую можно будет проверить и позднее подключить к структурному индексатору.

## 4. Независимость от Исполнителя 1


Структурный индексатор разрабатывается параллельно. Поэтому ты не должен ожидать его завершения.


Для разработки создай собственный тестовый набор структурных узлов и используй согласованный входной контракт.


Ожидаемый формат входного узла:
```
{
  "node_id": "node_00421",
  "source_path": "персонажи/Генрих Фауст.md",
  "node_type": "section",
  "parent_node_id": "node_00012",
  "heading_path": [
    "Поведение",
    "Конфликтное поведение"
  ],
  "line_start": 310,
  "line_end": 337,
  "content_hash": "sha256:...",
  "raw_text": "Оригинальный текст структурного узла"
}
```


Это предварительный контракт обмена данными, а не требование к внутренней реализации Исполнителя 1.


При необходимости создай собственный JSONL-формат для импорта и тестирования.


Обязательно предусмотрите отдельный адаптер, который позволит в дальнейшем подключить результаты структурного индексатора без переписывания поискового движка.


Если обнаружишь, что для интеграции требуется изменение входного контракта, опиши предложение и обоснуй его. Не меняй чужую реализацию самостоятельно.


## 5. Требования к поисковому движку


### 5.1. SQLite и FTS5


Используй SQLite в качестве локального хранилища.


Для полнотекстового поиска используй FTS5.


Поисковый индекс должен поддерживать поиск по:


- оригинальному содержимому;
- нормализованному тексту;
- заголовкам;
- названиям документов;
- путям к источникам;
- именам и алиасам сущностей.


Не теряй оригинальные написания. Нормализованный текст используется только для обнаружения результатов, а не для замены исходного содержания.


Предусмотри возможность расширения схемы базы данных.


### 5.2. Русская морфологическая нормализация


Используй `pymorphy3` либо обоснуй выбор альтернативы.


Поиск должен учитывать различные словоформы.


Например, запросы:


- «маг»
- «мага»
- «маги»
- «магами»


должны находить релевантные фрагменты с соответствующими формами слова.


При этом нормализация не должна уничтожать точные совпадения, имена, специальные термины и числовые значения.


Проверь работу на кириллице, дефисах, апострофах и составных именах.


### 5.3. Точный поиск


Обязательно реализуй поиск по точным словам и числам.


Особенно важно корректно обрабатывать числовые значения.


Например, запрос по числу `18 518` должен находить именно источники с таким значением.


Не допускай случайного смешивания чисел, которые отличаются значением или разрядностью.


При обработке разделителей разрядов учитывай обычные пробелы и неразрывные пробелы.


Точное совпадение должно сохранять преимущество перед приблизительным морфологическим совпадением.


### 5.4. Реестр сущностей


Реализуй отдельный механизм хранения сущностей и их алиасов.


Источниками кандидатов для сущностей могут быть:


- имена файлов;
- заголовки документов;
- явно заданные алиасы;
- повторяющиеся имена в тексте.


Для сущности должны храниться:


- уникальный идентификатор;
- каноническое имя;
- список алиасов;
- статус подтверждения алиасов;
- связанные Node ID.


Предусмотри возможность ручного подтверждения и отклонения неоднозначных алиасов.


**Не объединяй сущности автоматически, если их тождество не доказано.**


Примеры неоднозначностей из проекта:


- Хогвартс / Хоггвартс;
- Рэбекка Блэе / Рэбекка Блэк;
- Долохов / Александр Долохов / Антонин Долохов.


Это кандидаты на проверку, а не готовые решения.


Реестр сущностей нужен для поиска упоминаний. Он не должен превращаться в граф знаний или автоматически устанавливать отношения между персонажами.


### 5.5. Карта упоминаний


Для каждой подтверждённой сущности необходимо хранить сведения о том, в каких структурных узлах она встречается.


Пример:
```
ENTITY: character_daphne


Canonical:
Дафна Гринграсс


Aliases:
Дафна
Daphne Greengrass


Mentions:
node_001
node_028
node_104
```


Поиск по сущности должен возвращать:


1. Основной документ сущности, если он существует.
2. Другие документы, содержащие подтверждённые упоминания.
3. Конкретные структурные узлы с этими упоминаниями.


Не создавай утверждений о характере, отношениях или действиях сущности на основании одного факта упоминания.


### 5.6. Базовое ранжирование


Реализуй первоначальную систему ранжирования результатов.


Приоритеты:


1. Точное совпадение сущности.
2. Совпадение имени в названии документа.
3. Совпадение имени или термина в заголовке.
4. Точное совпадение слов и фраз.
5. Морфологические совпадения.
6. Совпадения в остальном тексте.


Зоны Vault не должны автоматически понижать или повышать авторитетность источников.


Наличие авторских вопросов и заметок не должно автоматически уменьшать релевантность документа.


Не пытайся определять, какой источник является каноничным.


Для каждого результата возвращай причину, по которой он был найден, и доступные координаты исходного узла.


## 6. Формат поискового результата


Разработай программный интерфейс поиска.


Например:
```
search(
    query="Особенности речи Генриха Фауста",
    entities=["Генрих Фауст"],
    limit=20
)
```


Точный интерфейс выбери самостоятельно, но он должен быть документирован и пригоден для подключения к будущему Context Builder.


Результат должен содержать:


- Node ID;
- путь к исходному файлу;
- заголовок или heading path;
- Content Hash;
- координаты исходного узла;
- причину совпадения;
- оценку релевантности;
- тип совпадения;
- информацию о найденной сущности, если применимо.


Поисковик может возвращать оригинальные фрагменты для проверки, но не должен самостоятельно формировать адаптивный Context Pack.


Не подменяй первоисточник нормализованным текстом.


## 7. Инкрементальное обновление


Предусмотри возможность обновления поискового индекса при изменении входных данных.


Минимальные требования:


- повторная загрузка неизменённого узла не создаёт дубликат;
- изменение Content Hash обновляет поисковую запись;
- удаление узла удаляет либо помечает соответствующие поисковые записи;
- изменения алиасов отражаются в поиске;
- изменения одного документа не требуют полной пересборки всего индекса, если это технически возможно.


Операции обновления должны быть транзакционными.


Не допускай состояния, в котором поисковик видит частично обновлённую базу.


## 8. Ограничения архитектуры


Обязательные правила:


1. Поисковый индекс хранит производные данные отдельно от Vault.
2. Исходные документы не изменяются.
3. Нормализация не заменяет оригинальный текст.
4. Поисковые аннотации не являются доказательствами фактов.
5. Реестр упоминаний не является графом знаний.
6. Неоднозначные алиасы не объединяются без подтверждения.
7. Параллельные источники сохраняются независимо.
8. Семантический поиск не внедряется на этом этапе.
9. Отсутствие результата поиска не означает отсутствия информации в Vault.


Особенно внимательно отнесись к параллельным источникам.


Например, два документа `Демография.md` из разных папок могут содержать пересекающиеся, но не идентичные сведения.


Нельзя удалять один из них только потому, что второй содержит похожие данные.

## **3. Что считаю правильным и менять не рекомендую**


Несколько решений исполнителя стоит сохранить без существенных изменений.


**1. Индекс не является источником знаний.**


Оригинальный текст хранится отдельно, а нормализация, леммы и алиасы используются только для поиска. Это соответствует основному принципу SFRA.


**2. Документ определяется полным путём.**


Два файла `Демография.md` из разных каталогов должны оставаться самостоятельными источниками. Объединять их нельзя.


**3. Алиасы не подтверждаются автоматически.**


Примеры с Долоховыми, Рэбеккой и вариантами написания Хогвартса действительно требуют неоднозначной обработки.


**4. История версий сохраняется.**


Пара `node_id + content_hash` позволяет отличать структурную идентичность узла от конкретной версии его содержания.


**5. Отсутствие совпадения не считается отсутствием информации.**


Статус `not_found_in_retrieval` выбран правильно.


Эти положения не нужно пересматривать ради демонстрации активности.


## **4. Замечания к проектному решению**


До написания кода рекомендую закрепить несколько технических деталей.


**4.1. Контракт импорта**


Исполнитель предлагает JSONL с Node v1 и отдельный манифест обновления. Это разумно, но необходимо зафиксировать:


- SHA-256 рассчитывается по UTF-8 байтам ровно того `raw_text`, который поступает на импорт.
- Координаты строк начинаются с единицы и включают обе границы.
- Пути относительны к Vault и используют `/`.
- Повторный импорт неизменённого узла не создаёт новую версию.
- Частичный пакет `delta` никогда не вызывает удаление отсутствующих узлов.


Пока совместимость с индексатором Исполнителя 1 фактически не подтверждена. Поэтому тестирование следует начать на искусственных JSONL-файлах, соответствующих согласованному контракту.


**4.2. Внутренняя согласованность БД**


Нужно закрепить тип и идентичность `version_id`. В частности, если FTS5 использует `rowid = version_id`, идентификатор должен иметь однозначное соответствие целочисленному SQLite `rowid`.


Также необходимо проверить, что обычный поиск возвращает только актуальные версии узлов, а старые версии доступны исключительно через отдельный запрос истории.


**4.3. Индекс чисел**


Для целых чисел можно использовать нормализованное целое значение. Для десятичных значений следует использовать точное представление, исключающее ошибки плавающей арифметики.


Например, поиск `18 518` должен находить варианты с обычным, неразрывным и узким неразрывным пробелом, но не `185180` или `118518`.


**4.4. FTS5 и пользовательский запрос**


Нужно реализовать безопасную подготовку запросов. Пользовательский текст не должен случайно интерпретироваться как управляющий синтаксис FTS5.


Нужно также закрепить направление сортировки BM25 и правила разрешения равных результатов.


**4.5. Реестр сущностей**


В проекте одновременно присутствуют `primary_source_path` в таблице `entities` и таблица `entity_sources` с ролью `primary_document`.


Лучше выбрать один основной механизм хранения этой связи. Иначе возникнет риск расхождения двух представлений одной настройки.
