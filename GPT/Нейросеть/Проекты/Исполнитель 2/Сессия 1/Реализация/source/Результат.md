## 1. Реализованная функциональность

Основной пакет `sfra_search` предоставляет:

- SQLite FTS5 exact и morphology channels;
- русский морфологический поиск: `pymorphy3` как штатный механизм и NLTK Snowball как резерв;
- точную нормализацию чисел через `Decimal`, включая пробелы группировки;
- Entity Registry, алиасы `candidate` / `confirmed` / `rejected`, разрешение неоднозначных алиасов и карту Mentions;
- ранжирование по уровням релевантности, BM25 внутри уровня и детерминированный tie-break;
- версии узлов, транзакционный импорт, `delta` / `replace_documents` / `full_snapshot`;
- API, CLI, адресное получение полного текста узла по `node_id + content_hash`.

## 2. Дополнение координатора: архитектура запуска

Добавлен новый путь `run-once` для GitHub Actions:

1. Получает путь к структурной SQLite-базе Исполнителя 1.
2. Открывает её через SQLite URI `mode=ro` и включает `PRAGMA query_only=ON`.
3. Читает только текущие узлы активных документов; неактуальные и удалённые документы исключаются.
4. Требует существующие `node_id` и `content_hash` от Исполнителя 1. При пропуске этих полей выполнение завершается ошибкой; Исполнитель 2 не генерирует и не переписывает ID.
5. Проверяет SHA-256 точных UTF-8 байтов `raw_text` и сохраняет `documents.source_sha256` как `document_hash`.
6. Создаёт отдельный производный FTS5/Entity Registry индекс в общей in-memory SQLite базе. Он не добавляется к структурной БД и не записывается на диск.
7. Возвращает JSON с поисковыми попаданиями, в каждом из которых сохраняются исходные `node_id` и `content_hash`.

Поиск запускается командой:

```bash
sfra run-once \
  --source-db "$RUNNER_TEMP/sfra-search-index/structure.sqlite3" \
  --query "остановка кровообращения" \
  --limit 20
```

Полный исходный узел извлекается отдельной командой по паре, полученной из результата поиска:

```bash
sfra get-source \
  --source-db "$RUNNER_TEMP/sfra-search-index/structure.sqlite3" \
  --node-id "node_..." \
  --content-hash "sha256:..."
```

Тот же контракт открыт как Python API: `search_structural_database(...)`, `load_current_nodes(...)` и `get_source_node(database_path, node_id, content_hash)`.

## 5. Что уже подтверждено на реальном Vault

В Issue №4 репозитория опубликован отдельный экспериментальный прогон прежнего smoke harness: **66 документов**, **9 080 текущих узлов**, точный поиск фразы «остановка кровообращения», проверка точных срезов и SHA-256. Второй прогон выбрал один наиболее конкретный узел и подавил два совпавших узла-предка. Эксперимент использовал временную SQLite FTS5 и не изменял исходный Vault.

Этот результат подтверждает работоспособность структурного индекса и базового FTS5 сценария на Vault. Он **не является** end-to-end проверкой нового модуля `sfra_search`: тот пока проверен на тестовой SQLite-базе по опубликованной схеме.

## 6. Ограничения и честный статус

- Основной путь `pymorphy3` не запускался в текущей изолированной среде: PyPI недоступен. 56 тестов выполнялись на NLTK Snowball fallback. В Actions установщик должен иметь доступ к пакетам, чтобы проверить основной путь.
- Workflow, который вызывает `sfra run-once`, ещё не добавлен. Текущий `sfra-search-kernel-test.yml` остаётся прежним smoke-тестом Исполнителя 1 и не является интеграцией нового модуля.
- Новый runtime ещё не запускался на фактической `structure.sqlite3`, созданной Исполнителем 1 для всего Vault.
- `document_hash` передаётся из `documents.source_sha256`. Если поле отсутствует в варианте входной схемы, адаптер вернёт `null`, не станет подделывать hash всего документа по одному узлу.
- Задача и этап 1 не объявляются принятыми до проверки аналитиком.
