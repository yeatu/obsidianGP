# Уточнения после аналитической проверки и совместимости с Executor 3

## 1. SQLite и FTS5 rowid

- `node_versions.version_id` — `INTEGER PRIMARY KEY AUTOINCREMENT`.
- FTS5 `rowid` напрямую соответствует `node_versions.version_id`.
- `nodes.current_version_id` указывает на текущую активную версию.
- Обычный поиск ограничен текущими версиями. История возвращается только при явном запросе версии по Content Hash.

## 2. Хранение primary_document

Роль `primary_document` хранится только в `entity_sources`. Поле `primary_source_path` не дублируется в `entities`.

## 3. Node v1 import contract

- `content_hash` вычисляется по точным UTF-8 байтам входного `raw_text`, без trim, Unicode rewrite и нормализации.
- `line_start` / `line_end`: 1-based inclusive.
- `source_path`: относительный путь от Vault, POSIX-разделитель `/`, Unicode и регистр сохраняются.
- Повторная пара `node_id + content_hash` не создаёт новую content-version.
- `delta` не удаляет узлы, отсутствующие в пакете.
- Удаления выполняются только явным `deleted_node_ids` либо внутри указанной полной области `replace_documents` / `full_snapshot`.

## 4. Числа и запрос FTS5

- Цифры исключены из обычного FTS выражения; числовой канал использует точные ключи.
- Группировочные пробелы U+0020, U+00A0 и U+202F дают один ключ для целого числа.
- Десятичные значения представлены точным Decimal-строковым значением, без binary float.
- Запрос пользователя разбивается на токены и каждый токен экранируется как FTS phrase; пользовательская пунктуация/операторы не исполняются как управляющий FTS синтаксис.
- BM25 FTS5: меньшее значение лучше; внутри tier сортировка по возрастанию.
- Tie-break: `source_path`, `line_start`, `node_id` по возрастанию.

## 5. Search hit и get_node для Executor 3

Search hit содержит: `node_id`, `source_path`, `heading_path`, `line_start`, `line_end`, `content_hash`, `excerpt`, `match_type`, `match_reasons`, `relevance.tier`, `relevance.bm25`.

`excerpt` — ограниченная поисковая подсказка, не полный первоисточник и не может быть подставлен в Context Pack как raw_text.

`get_node(node_id, content_hash)` возвращает полный точный `raw_text` выбранной версии, locator fields, `index_generation` и `document_hash`.

## 6. Ограничение document_hash

Схема Executor 3 `executor2_get_node.response.schema.json` в текущей опубликованной версии требует строковый `document_hash`. Входной Node v1 от Executor 1 содержит hash структурного узла, а не hash всего Markdown-документа. Прототип не подделывает document hash: если поле не передано в payload, возвращается `null`.

Для интеграции нужно одно из двух:
1. Executor 1 добавляет в экспорт узла/document metadata SHA-256 всего исходного Markdown-файла; или
2. Executor 3 согласует nullable `document_hash` до тех пор, пока whole-document hash не будет предоставляться.

Это единственный выявленный schema-level integration blocker на уровне данных; он не скрывается и не решается ложным хешированием.

## 7. Фактическая проверка

- 47 pytest-тестов прошли на искусственных Node v1 фикстурах.
- compileall прошёл.
- CLI smoke test прошёл; SQLite check: `integrity=ok`, 3 активных узла, 0 пропусков FTS, 0 dangling current versions.
- Тестовый запуск использовал NLTK Snowball fallback, так как pymorphy3 не был доступен для установки через PyPI в изолированной среде.
- Реальный экспорт Executor 1 и весь Vault не проверялись.
