## Запуск

В GitHub откройте **Actions → SFRA search integration (Executor 2) → Run workflow**. Workflow также запускается при изменении собственного YAML-файла.

Сценарий:

1. Получает state/structure.sqlite3 и state/manifest.json из sfra-state.
2. Проверяет наличие файлов, SHA-256 базы, SQLite integrity и версию схемы.
3. Проверяет, что checkout E1 соответствует source_commit в manifest.
4. Не запускает индексатор E1. Структурная база открывается E2 только для чтения.
5. Устанавливает pymorphy3, собирает исходный пакет и запускает его тесты.
6. Дважды запускает sfra run-once с отдельными запросами; FTS5 создаётся в памяти процесса.
7. Получает исходные узлы через sfra get-source --node-id ... --content-hash ....
8. Сверяет SHA исходных фрагментов, стабильность адресов, неизменность ГП и sfra-state.
9. Публикует JSON, Результат.md и Actions artifact.

Запуски сериализованы через concurrency, чтобы параллельные workflow не мешали публикации результатов. Постоянного поискового сервера нет; поисковая SQLite не сохраняется.

## Важная оговорка

Workflow подтверждает интеграционный сценарий на конкретном снимке E1, записанном в manifest. При следующей проверке используется актуальная ветка sfra-state; если manifest указывает на иной commit, workflow проверяет соответствующий commit E1 и не подменяет его HEAD-версией.

Найденная особенность E1: для пустого исходного диапазона координаты могут иметь вид line_end = line_start - 1 (например, 1, 0). E2 сохраняет исходные координаты, разрешая такой интервал только при пустом raw_text; прочие некорректные диапазоны по-прежнему отклоняются. В БД E1 ничего не исправляется.

**Статус:** интеграционная контрольная точка опубликована; окончательное решение остаётся за Аналитиком 2.
