## 1. Назначение и границы решения

Компонент — локальный поисковый индекс Sidecar Index для обнаружения структурных узлов Vault по исходным словам, словоформам, числам, заголовкам, путям и подтверждённым сущностям.

Основной принцип: **индекс указывает на источник, но не заменяет его**. Индекс может хранить поисковые представления и технические аннотации. Единственным содержательным первоисточником остаётся исходный Markdown-фрагмент, адресуемый парой `node_id + content_hash`.

В Этап 2 входят SQLite, FTS5, морфологическая нормализация, точный числовой поиск, реестр сущностей и алиасов, карта упоминаний, базовое ранжирование, адаптер входных узлов и инкрементальное обновление.

Вне границ: Markdown AST, сегментация, генерация Node ID, Context Builder, токеновый бюджет, MCP, векторный и семантический поиск, LLM-реранжирование, определение каноничности источников и построение графа знаний.

На Этапе А не создаются поисковый движок, база данных или тестовый исполняемый модуль. Этот документ фиксирует решения, которые должны быть проверены до реализации.

## 2. Что обнаружено в исходных материалах

Изучены архитектура SFRA, `dump.md`, дерево `ГП`, а также задача сессии Исполнителя 1 и его входной контракт. В проекте уже есть отдельная папка Исполнителя 2 и `Сессия 1`; в ней сохранён исходный промпт сессии. В папке Исполнителя 1 обнаружена его задача, но никаких файлов его реализации я не менял.

Архитектура описывает 62 Markdown-документа, в том числе 16 без Markdown-заголовков. Для поискового слоя это означает, что заголовок и имя файла должны индексироваться как самостоятельные поля, а поиск по тексту не может зависеть от наличия заголовков.

В фактическом `dump.md` обнаружены важные тестовые случаи:

- Два самостоятельных источника `Демография.md`: `иное/Демография.md` и `разобрать/Демография.md`. Пути различаются, содержание пересекается, поэтому их нельзя объединять по имени файла или похожести текста.
- Значение `18 518` встречается в нескольких местах, в том числе в демографических расчётах.
- Материал о Рэбекке находится в каталоге `Теодор Нотт и Рэбекка Блэе`, а имя файла — `Рэбекка Блэк.md`. Это пример несовпадения вариантов написания, но не основание автоматически подтверждать алиас.
- В исходных путях есть `Александр Долохов.md`, а в тексте встречается фамилия `Долоховы`. Короткий алиас «Долохов» нельзя автоматически закреплять за единственной сущностью.
- В архитектуре отдельно отмечены варианты «Хогвартс / Хоггвартс» как требующие проверки.
- В дампе присутствуют внешние ссылки, авторские вопросы, черновые пометки и материалы разной структуры. Они остаются частью исходного текста и не получают автоматического понижающего коэффициента.

Вывод: базовая идентичность документа — полный относительный путь, а не имя файла. Все варианты написания и повторяющиеся имена первоначально являются кандидатами на проверку, а не фактами об идентичности.

## 3. Выбранный технический стек

| Компонент | Решение | Обоснование |
|---|---|---|
| Язык | Python 3.11+ | Совместимая базовая версия для локального CLI и библиотечного API; `pymorphy3` заявляет поддержку Python 3.9–3.14. |
| Хранилище | Встроенный модуль `sqlite3` | Не требует отдельного сервера или ORM; транзакции и внешние ключи доступны в стандартной библиотеке. |
| Полнотекстовый индекс | SQLite FTS5 | Локальный полнотекстовый поиск; Unicode61 понимает кириллицу и разбивает дефисы/апострофы как разделители. |
| Морфология | `pymorphy3==2.0.6` | Продолжение pymorphy2; анализатор для русского и украинского языков. |
| Словарь | `pymorphy3-dicts-ru==2.4.417150.4580142` | Отдельный пакет русских словарей, который требуется анализатору. |
| CLI | `argparse` | Встроенная библиотека Python, достаточная для требуемых команд. |
| Тесты | `pytest` | Изолированные unit- и интеграционные проверки; это dev-зависимость. |
| Модели и сериализация | `dataclasses`, `typing`, `json`, `jsonlines` через стандартный построчный ввод | Не вводить Pydantic/ORM без необходимости; не усложнять контракт. |

Важные оговорки по зависимостям:

1. PyPI указывает для `pymorphy3` версию 2.0.6 и официальную поддержку Python 3.9–3.14; сам пакет отмечен как Beta. Это не отменяет выбор, но требует тестов на нашем корпусе.
2. Русский словарь устанавливается отдельно. Его данные имеют отдельные условия лицензирования (CC BY-SA); при дальнейшем распространении сборки это следует учитывать.
3. FTS5 не лемматизирует русский текст. Поэтому леммы будут вычисляться Python-кодом до записи в индекс, а FTS5 будет выполнять поиск по подготовленным токенам.
4. При запуске обязательна проверка доступности FTS5 реальным созданием временной виртуальной таблицы. Если сборка SQLite не поддерживает FTS5, приложение должно завершаться с понятной ошибкой, а не незаметно переключаться на поиск `LIKE`.

Прямой `sqlite3` выбран вместо SQLAlchemy: у проекта одна локальная БД, небольшой объём исходных материалов, требуется прозрачная схема и контроль транзакций. ORM здесь добавит слой абстракции, но не решит отдельной задачи.

## 4. Предлагаемая структура Sidecar Index

Файл БД по умолчанию: `.ai-index/sfra-search.sqlite3`. Путь должен переопределяться параметром CLI или настройкой. Сам каталог Sidecar исключается из сканирования Vault и не должен попадать в исходные документы.

Схема развивается миграциями (`schema_migrations` или `PRAGMA user_version`). Никакие миграции не изменяют Markdown-файлы.

| Таблица | Назначение и ключевые поля |
|---|---|
| `documents` | Реестр исходных путей: `source_path` (PK), хеш файла при наличии, состояние, время последней синхронизации, поколение индекса. Полный путь хранится без потери регистра и Unicode. |
| `nodes` | Стабильная идентичность узла: `node_id` (PK), `current_version_id`, состояние active/deleted. Node ID создаёт структурный индексатор, не этот модуль. |
| `node_versions` | Неизменяемые версии: `version_id`, `node_id`, `content_hash`, `source_path`, `node_type`, `parent_node_id`, `heading_path_json`, координаты, `raw_text`, производные поля поиска, время импорта. Ограничение `UNIQUE(node_id, content_hash)`. |
| `node_fts` | FTS5-индекс полей названия документа, пути, заголовков, исходного текста и отдельных лемматизированных полей. `rowid = version_id`. |
| `node_numbers` | Числа как точные значения: `version_id`, `value_key`, исходное написание, позиция в исходном фрагменте. Индекс по `value_key`. |
| `entities` | Ручной реестр сущностей: `entity_id` (PK), каноническая подпись, необязательный тип, необязательный явно подтверждённый `primary_source_path`. |
| `entity_aliases` | Алиасы: `alias_id`, `entity_id`, исходное написание, ключ сравнения, статус candidate/confirmed/rejected, происхождение, отметки проверки. Один и тот же нормализованный алиас может относиться к нескольким сущностям: глобальная уникальность запрещена. |
| `entity_candidates` | Неразрешённые кандидаты из имён файлов, заголовков и повторяющихся именных последовательностей. Кандидат не участвует в entity search до ручного подтверждения. |
| `mentions` | Карта подтверждённых упоминаний: версия узла, Node ID, Entity ID, Alias ID, найденная поверхность, позиции и метод сопоставления. Не содержит отношений между сущностями. |
| `entity_sources` | Явная привязка сущности к документу/пути с ролью, например `primary_document`; роль устанавливается конфигурацией или человеком, а не эвристикой похожести. |
| `index_meta` | Поколение индекса, версия схемы и служебные параметры. |

### 4.1. Версии узлов

`nodes` хранит текущий указатель, а `node_versions` — историю версий. Пара `node_id + content_hash` идентифицирует конкретную версию источника.

- Повторный импорт той же пары не создаёт новую запись версии.
- Новый Content Hash для существующего Node ID создаёт новую строку `node_versions` и меняет текущий указатель.
- Предыдущая версия остаётся доступной для диагностики и явного запроса истории, но стандартный поиск возвращает только текущую.
- Удаление узла помечает его как deleted и снимает текущий указатель. Старые версии не становятся результатами обычного поиска.

Так поисковый модуль не подменяет старый текст новым и не выдаёт старую версию как актуальную.

### 4.2. Поля FTS5

В FTS5 предлагаются отдельные поля:

- `title_original` — имя файла без расширения;
- `path_original` — полный относительный путь;
- `heading_original` — элементы `heading_path` в исходном порядке;
- `raw_text` — оригинальный текст узла;
- `title_lemmas`, `heading_lemmas`, `raw_lemmas` — отдельное поисковое представление из лемм.

Для таблицы выбирается токенизатор `unicode61 remove_diacritics 0`. Дефис, апостроф и пробел будут разделителями токенов; составные имена ищутся как последовательность слов. Это снижает зависимость от конкретного вида дефиса/апострофа. Оригинальная строка и её пунктуация при этом сохраняются в `node_versions.raw_text`.

FTS5 используется как навигационный индекс, а не как источник фрагмента. После получения совпадения результат всегда собирается из `node_versions.raw_text` и метаданных той же версии.

Для базы такого размера допустим внешний-content FTS5, связанный с `node_versions`, с триггером добавления неизменяемой версии. Нужно покрыть согласованность индекса интеграционными тестами и командой диагностики/перестроения FTS. Если конкретная сборка SQLite создаёт проблемы с external-content, резервный простой вариант — обычная contentful FTS5-таблица; схема поиска от этого не меняется.

## 5. Нормализация текста и точные числа

### 5.1. Общая нормализация

Оригинальный текст не переписывается и не заменяется нормализованным. Алгоритм формирует дополнительные поисковые поля:

1. Unicode-нормализация NFC для ключей сопоставления; исходный текст остаётся побайтно/символьно неизменным в переданном JSON-тексте.
2. Разбиение на токены с сохранением границ и исходных смещений.
3. Для кириллических слов — `pymorphy3.MorphAnalyzer(lang="ru")`; на первом этапе используется наиболее вероятный разбор (`parse(token)[0].normal_form`).
4. Для латиницы, чисел, неизвестных слов и специальных обозначений сохраняется исходная токенная форма.
5. Результат лемматизации записывается отдельно от оригинальных полей.

Поиск выполняется в двух независимых каналах: точный — по исходным словам/фразам, морфологический — по леммам. Точное совпадение имеет более высокий приоритет. Словари и эвристические разборы pymorphy3 не могут заменять точный поиск.

Для имён, редких фамилий и специальных терминов лемматизация может ошибаться. Поэтому исходные написания всегда индексируются; нормализация не является основанием для объединения Entity ID.

### 5.2. Дефисы, апострофы и составные имена

Для лексического поиска дефисы, варианты тире, прямой/типографский апостроф и пробел рассматриваются как границы токенов. Запрос «Генрих-Фауст» может находить последовательность «Генрих Фауст», но результат должен ссылаться на оригинальный узел с исходной пунктуацией.

Ключи алиасов строятся отдельно: Unicode NFC, casefold и токенизация последовательности. Варианты «е/ё» и орфографические опечатки не сливаются автоматически. Если понадобятся дополнительные правила, они должны быть явной конфигурацией с тестами, а не скрытой нормализацией.

### 5.3. Числовой индекс

Для чисел создаётся отдельная таблица `node_numbers`. Она нужна, чтобы исключить подстрочные совпадения и случайное смешивание разрядности.

- Группировка целых чисел распознаётся только при корректных группах по три цифры.
- Разделителями группировки считаются обычный пробел, неразрывный пробел U+00A0 и узкий неразрывный пробел U+202F.
- `18 518`, `18 518`, `18 518` и `18518` получают один ключ целого значения `18518`.
- Исходное написание и диапазон символов сохраняются отдельно.
- Сравнение выполняется по равенству числового ключа, а не через `LIKE`, префикс или совпадение отдельных цифр.
- `18`, `18518`, `118518` и `185180` являются разными значениями.
- Десятичная часть не удаляется; десятичные числа не должны превращаться в целые после снятия разделителей. Для неоднозначных форматов в первой реализации приоритет получает точное текстовое совпадение, а не догадка о разрядности.

Тестовый эталон: запрос `18 518` должен находить узлы со значением 18 518 во всех разрешённых форматах пробела, но не числа с другой разрядностью/значением.

## 6. Реестр сущностей и карта упоминаний

### 6.1. Разделение сущности и кандидата

Сущности создаются явно из конфигурации или после ручного подтверждения. Автоматическое извлечение формирует только `entity_candidates`.

Источники кандидатов:

- имена файлов и заголовки;
- повторяющиеся последовательности слов с признаками имени;
- вручную добавленные предложения.

Эвристическое обнаружение имён может ошибочно принимать начало предложения, заголовок или название организации за персонажа. Поэтому кандидат сопровождается источником обнаружения и числом/примерами совпадений, но сам по себе не участвует в выдаче как подтверждённая сущность.

### 6.2. Статусы алиаса

У каждого алиаса один из статусов:

- `candidate` — предложен системой или человеком, но не подтверждён; не используется для автоматической привязки Mentions;
- `confirmed` — подтверждён человеком и может использоваться в Entity Search и карте упоминаний;
- `rejected` — отклонён и исключён из сопоставления.

Каноническая подпись сущности добавляется как подтверждённая форма этой Entity ID. Алиас может повторяться у разных Entity ID. Если один подтверждённый алиас соответствует нескольким сущностям, поисковик обязан вернуть неоднозначную выдачу, а не выбирать одну.

Примеры из задания остаются неразрешёнными до проверки:

- «Хогвартс» / «Хоггвартс»;
- «Рэбекка Блэе» / «Рэбекка Блэк»;
- «Долохов» / «Александр Долохов» / «Антонин Долохов».

Запрещено автоматическое склеивание сущностей по похожести строки, общему фрагменту имени, частоте упоминаний или нахождению в одном документе.

### 6.3. Поиск упоминаний

После подтверждения алиаса индексатор упоминаний просматривает активные версии узлов и записывает совпадения с символьными смещениями. Сопоставление выполняется по границам токенов и последовательностям слов. Морфологический вариант имени может учитываться отдельным методом, но точное написание сохраняется в `matched_text`.

При изменении содержимого узла пересчитываются упоминания только для новой версии этого узла. При изменении статуса или написания алиаса пересчитываются зависимые упоминания по активным версиям узлов. Оба действия транзакционны.

Entity Search возвращает:
1. явно заданный `primary_document`, если он существует;
2. другие документы и узлы с подтверждёнными упоминаниями;
3. для каждого узла — его собственные координаты и Content Hash.

Привязка `primary_document` — навигационная настройка. Она не означает, что источник каноничнее остальных. Mentions не содержат рёбер «родственник», «враг», «действовал вместе» и подобных связей.

## 7. Ранжирование

Ранжирование выполняется детерминированно по лучшему типу совпадения. Внутри одной категории порядок уточняется FTS5 BM25 и числом/качеством лексических совпадений.

| Приоритет | Тип совпадения |
|---:|---|
| 1 | Точное совпадение подтверждённой сущности или её подтверждённого алиаса |
| 2 | Совпадение имени/термина в имени документа |
| 3 | Совпадение в заголовке или `heading_path` |
| 4 | Точное слово или точная фраза в исходном тексте; точное числовое значение |
| 5 | Морфологическое совпадение в лемматизированном поле |
| 6 | Остальные лексические совпадения в тексте |

Рекомендуемая реализация — целочисленный `rank_tier` плюс BM25 как вторичный показатель внутри одного уровня. Не следует складывать BM25 из разных полей и позволять большому числу слабых совпадений обойти более высокий приоритет.

Зона Vault, расположение в `разобрать`, наличие авторских вопросов и предполагаемая «проработанность» не влияют на ранг. Эти данные могут отображаться как метаданные, но не являются оценкой достоверности или авторитетности.

Каждый результат содержит список причин (`match_reasons`), а не только итоговый балл. Если найдена сущность, результат также возвращает Entity ID, каноническую подпись, фактически совпавший алиас и его статус.

## 8. Интерфейс и формат результата

Поисковый модуль предоставляется как обычная Python-библиотека без сетевого сервера и MCP.

Предлагаемый интерфейс:

```python
engine.search(
    query="Особенности речи Генриха Фауста",
    entities=["Генрих Фауст"],
    limit=20,
    include_history=False,
)
```

Отдельные методы:

- `search(query, entities=None, limit=20)` — объединённый лексический и Entity Search;
- `search_entity(name, limit=20)` — разрешение подтверждённой сущности/алиаса и поиск узлов упоминаний;
- `get_node(node_id, content_hash=None)` — получение метаданных и оригинального текста текущей или указанной версии;
- `list_entity_aliases(entity_id)` — просмотр реестра и статусов;
- `confirm_alias(...)` / `reject_alias(...)` — явное ручное решение.

Скелет одного результата:

```json
{
  "node_id": "node_00421",
  "source_path": "персонажи/Генрих Фауст.md",
  "node_type": "section",
  "parent_node_id": "node_00012",
  "heading_path": ["Поведение", "Конфликтное поведение"],
  "line_start": 310,
  "line_end": 337,
  "content_hash": "sha256:...",
  "excerpt": "Оригинальный фрагмент из raw_text",
  "match_type": "exact_heading",
  "match_reasons": ["heading_exact", "body_morphology"],
  "relevance": {"tier": 3, "bm25": -4.21},
  "entity": null
}
```

Число BM25 здесь иллюстративное, не результат измерения. Финальный контракт результата будет зафиксирован тестами в Этапе Б.

Обязательные поля ответа: Node ID, source path, заголовок/heading path, Content Hash, координаты, причина совпадения, релевантность, тип совпадения и Entity metadata при наличии. Оригинальный excerpt извлекается из сохранённого `raw_text` текущей версии. Нормализованный текст никогда не возвращается как цитата источника.

При отсутствии совпадений API возвращает пустую выдачу со статусом `not_found_in_retrieval`. Это означает только, что текущий поисковый индекс не обнаружил совпадение; это не утверждение об отсутствии информации в Vault.

## 9. Контракт импорта и адаптер Исполнителя 1

### 9.1. Входной узел v1

Адаптер принимает JSONL, одна запись на структурный узел. Поля соответствуют согласованному предварительному контракту:

```json
{
  "node_id": "node_00421",
  "source_path": "персонажи/Генрих Фауст.md",
  "node_type": "section",
  "parent_node_id": "node_00012",
  "heading_path": ["Поведение", "Конфликтное поведение"],
  "line_start": 310,
  "line_end": 337,
  "content_hash": "sha256:...",
  "raw_text": "Оригинальный текст структурного узла"
}
```

Адаптер:
- валидирует типы и обязательные поля;
- проверяет положительность и порядок координат;
- приводит разделители `source_path` к POSIX `/`, но не меняет регистр и Unicode;
- проверяет формат SHA-256 и, при согласованном определении хеша, сверяет его с UTF-8 представлением `raw_text`;
- сохраняет неизвестные дополнительные поля в диагностике/metadata либо игнорирует их с предупреждением;
- не строит AST, не пересегментирует исходный текст и не генерирует Node ID.

Имя документа для поиска по умолчанию — basename `source_path` без расширения. Если у документа может быть отдельное отображаемое название, это можно добавить необязательным полем `document_title`, не меняя базовый контракт.

### 9.2. Что нужно уточнить для безопасной синхронизации

Сам узел v1 достаточен для upsert, но не сообщает, какие другие узлы документа были удалены из нового снимка. Поэтому предлагается не менять структуру узла, а добавить внешний манифест пакета импорта:

```json
{
  "schema": "sfra-node-batch/v1",
  "mode": "replace_documents",
  "replace_source_paths": [
    "персонажи/Генрих Фауст.md"
  ],
  "deleted_node_ids": []
}
```

Семантика:
- `delta` — импортировать/обновить только переданные узлы; отсутствие узла в пакете ничего не удаляет;
- `replace_documents` — пакет содержит полный список узлов для перечисленных source_path; отсутствующие в пакете узлы этих документов помечаются deleted;
- `deleted_node_ids` — явные удаления;
- полный снимок всего Vault разрешён только с явным `mode=full_snapshot` и перечнем управляемых путей.

Это предотвращает случайное удаление узлов при передаче частичного JSONL. Пустой документ также можно корректно отметить в `replace_source_paths`, не придумывая фиктивный узел.

### 9.3. Проверки совместимости, требующие согласования

До интеграции нужно согласовать с Исполнителем 1:

1. `content_hash` — SHA-256 UTF-8 байтов ровно того `raw_text`, который передаётся в JSONL; без скрытой нормализации пробелов/переводов строк. Если выбран другой алгоритм, его необходимо явно описать и версионировать.
2. Координаты `line_start` / `line_end` — строки с единицы, границы включительные.
3. `source_path` — путь относительно корня Vault, с разделителем `/`, без абсолютных префиксов.
4. `node_id` — стабилен при обновлении содержимого, если индексатор смог сопоставить структурный узел; новая версия текста отличается Content Hash.
5. Удаление узлов и документов передаётся через манифест/явный список, а не выводится из неполного пакета.

Предлагаемые уточнения не требуют изменения обязательных полей Node v1. Опциональный `document_title` — единственное расширение самого узла, если basename не всегда является правильным названием.

## 10. Инкрементальное обновление и транзакции

Все операции записи выполняются в одной транзакции SQLite:

1. валидировать пакет и его область действия до начала записи;
2. начать `BEGIN IMMEDIATE`;
3. зарегистрировать документ/узел;
4. проверить пару Node ID + Content Hash;
5. создать новую immutable-версию только при изменении;
6. обновить FTS и числовые записи;
7. пересчитать Mentions для затронутых версий;
8. обновить current pointer и статусы удалённых узлов;
9. увеличить `index_generation`;
10. commit.

При любой ошибке выполняется rollback всего пакета. Индекс не должен видеть частичное состояние.

Параметры SQLite:
- `PRAGMA foreign_keys = ON`;
- `PRAGMA journal_mode = WAL` для одновременных читателей и одного писателя;
- ограниченный `busy_timeout`;
- параметризованные SQL-запросы;
- транзакционные обновления FTS и обычных таблиц.

Команды синхронизации должны быть идемпотентны. Повторная передача неизменённого узла не создаёт новую версию, FTS-строку или повторные Mentions. Изменение одного документа пересобирает только его узлы и зависимые поисковые записи; полная пересборка допускается отдельной диагностической командой.

История узлов сохраняется. Удаление документа не удаляет параллельный документ с другим source_path, даже если basename совпадает.

## 13. План тестирования

### Этап Б — SQLite и FTS5
- создание схемы, проверка миграций и FTS5;
- импорт тестовых узлов из JSONL;
- точный поиск по слову, фразе, имени файла, пути и заголовку;
- поиск по кириллице, составным именам, дефисам и апострофам;
- сохранение исходного `raw_text`, Node ID, координат и Content Hash;
- отдельная проверка двух одноимённых документов из разных source_path.

### Этап В — морфология и числа
- «маг», «мага», «маги», «магами»;
- несколько падежей существительных и формы глаголов;
- неизвестные слова и имена: морфология не должна скрывать точное совпадение;
- обычный пробел, U+00A0 и U+202F в `18 518`;
- `18 518` находит точный ключ 18518, но не 18, 18517, 118518 и 185180;
- дефис, прямой и типографский апостроф, кириллица/латиница.

### Этап Г — сущности
- подтверждённый алиас находит нужные узлы;
- candidate и rejected не формируют подтверждённые Mentions;
- повторяющийся алиас у нескольких сущностей возвращает неоднозначный результат;
- отдельные сущности Александра и Антонина Долоховых не объединяются;
- карта упоминаний возвращает конкретные Node ID и версии;
- нет таблиц или результатов с автоматически созданными отношениями между сущностями.

### Этап Д — обновление и интеграционная устойчивость
- повторный импорт неизменённого узла идемпотентен;
- изменение Content Hash создаёт новую версию и обновляет текущую;
- удаление узла/документа по явному манифесту снимает его с обычного поиска;
- ошибка посреди batch приводит к rollback;
- изменение алиаса обновляет Mentions;
- параллельные источники с одинаковым basename не теряются и не объединяются;
- `sfra check` выявляет рассогласование FTS/основных таблиц.

Отдельно должны быть unit-тесты нормализации, интеграционные тесты SQLite/FTS5, тесты адаптера контракта и регрессионные тесты полного набора требований.

### Реальные материалы и тестовые данные

Текущий этап использовал реальные сведения из архитектуры и `dump.md` для анализа структуры и фиксации тестовых примеров. **Автоматические тесты не запускались**, потому что реализация начинается только после одобрения Этапа А.

На Этапах Б–Д искусственный JSONL-набор будет основным детерминированным набором регрессионных тестов. Проверка реальных материалов будет выполняться через JSONL-экспорт структурных узлов Исполнителя 1. Самостоятельно разбирать Markdown и создавать Node ID в рамках этой задачи нельзя. Если экспорт Исполнителя 1 к тому времени недоступен, это будет отдельно отмечено как непроведённая интеграционная проверка, а не выдано за успешный тест реального Vault.

## 14. Риски и решения, вынесенные на согласование

| Вопрос | Предлагаемое решение | Почему важно |
|---|---|---|
| Hash и переводы строк | Зафиксировать точный алгоритм для `raw_text` | Иначе один и тот же фрагмент может получить разные Content Hash у двух компонентов. |
| Удаление отсутствующих узлов | Внешний manifest с областью replace/delete | Неполный JSONL не должен случайно удалить весь документ/Vault. |
| Название документа | Выводить из basename, необязательное `document_title` разрешить позднее | Текущий Node v1 отдельного поля названия не содержит. |
| Неоднозначные имена | Не объединять; возвращать кандидатов/множественное соответствие | Совпадение строки не доказывает идентичность. |
| Неизвестная морфология | Всегда искать по исходной форме параллельно | Имена, термины и неологизмы часто отсутствуют в словаре. |
| FTS5 на целевой системе | Проверка при старте с явной ошибкой | Не все сборки SQLite одинаково скомпилированы. |
| Лицензия словаря | Сохранить сведения об CC BY-SA и проверить перед распространением | Лицензия словарных данных отличается от лицензии кода анализатора. |

Ни один из этих пунктов не требует вмешательства в реализацию Исполнителя 1. Контракт Node v1 сохраняется; предложены только внешняя оболочка пакета импорта и необязательное поле заголовка.

## 15. Последовательность реализации и контрольные точки

Работа будет продолжена только после проверки текущего этапа аналитиком.

- **Этап А — текущий:** проектное решение и контракт интеграции. После публикации документа остановиться.
- **Этап Б:** SQLite, FTS5, миграции, Node v1 adapter, тестовые JSONL-узлы, точный лексический поиск и заголовки. Передать на проверку.
- **Этап В:** pymorphy3, числовой индекс, тесты словоформ и точных чисел. Передать на проверку.
- **Этап Г:** Entity Registry, alias review, Mentions и неоднозначность. Передать на проверку.
- **Этап Д:** атомарная инкрементальная синхронизация, CLI, документация, полный набор проверок и отчёт. Передать на итоговую проверку.

К следующему этапу не переходить, пока аналитик не проверил результат текущего этапа и не закрыты замечания.

## 16. Итог Этапа А

**Принято проектное решение:** Python + SQLite/FTS5 + pymorphy3; неизменяемая история Node Version; раздельные исходные и лемматизированные поля; отдельный точный числовой индекс; ручное подтверждение алиасов; Mentions без графа отношений; ранжирование по фиксированным приоритетам; транзакционный импорт с явной областью обновления; адаптер к Node v1 без изменения его обязательных полей.
