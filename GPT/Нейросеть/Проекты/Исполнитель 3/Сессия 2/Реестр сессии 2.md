## 5. Context Builder


### 5.1. Общий принцип


Context Builder получает:


- исходную задачу;
- поисковый запрос;
- найденные структурные узлы;
- необходимые сущности и фасеты, если они заданы;
- бюджет токенов;
- сведения о ранее полученных версиях узлов.


На основании этих данных он формирует Context Pack.


При этом он не должен самостоятельно придумывать недостающие аспекты задачи.


### 5.2. Покрытие задачи


Реализуй механизм контроля покрытия задачи.


Запрос может содержать несколько независимых аспектов.


Например:


«Написать сцену конфликта между Дафной и Теодором».


Для такого запроса можно выделить следующие аспекты:


| Аспект    | Что требуется обнаружить                      |
| --------- | --------------------------------------------- |
| Дафна     | Характер, мотивация, поведение                |
| Теодор    | Характер, мотивация, поведение                |
| Речь      | Особенности речи обоих персонажей             |
| Отношения | Прямые описания взаимодействия                |
| Сюжет     | Обстоятельства конфликта, если они уже заданы |


Context Builder должен учитывать каждый аспект отдельно.


Допускается использовать переданные клиентом аспекты или явный список `focus`.


Не создавай обязательную сложную систему автоматической декомпозиции любого запроса. Для MVP достаточно управляемого механизма покрытия.


Для каждого аспекта предусмотрите статус:


- `found` — найдены подходящие источники;
- `deferred` — источники найдены, но не помещены в текущий пакет;
- `not_found_in_retrieval` — среди обработанных результатов подходящий материал не обнаружен.


Последний статус не означает, что информация отсутствует в Vault.


**Запрещено превращать результат поиска «не найдено» в утверждение «такой информации нет».**


### 5.3. Ранжирование


Используй результаты поискового движка как основу.


Учитывай следующие приоритеты:


1. Точное совпадение сущности.
2. Совпадение имени в названии документа и заголовке.
3. Точное совпадение терминов и фраз.
4. Морфологическое совпадение.
5. Совпадение функциональных фасетов.
6. Дополнительная релевантность, указанная поисковым движком.


Зона Vault и наличие авторских вопросов отображаются как дополнительные сведения, но не должны автоматически определять достоверность или каноничность источника.


Не создавай собственную систему смыслового анализа, подменяющую поисковый движок.


### 5.4. Контроль бюджета токенов


Реализуй механизм ограничения объёма Context Pack.


Входной параметр:


`budget_tokens`


При отборе узлов необходимо учитывать:


- размер исходного фрагмента;
- его релевантность;
- необходимость сохранения контекста родителя;
- покрытие аспектов задачи;
- возможные повторы;
- наличие обязательных правил и ограничений.


Используй реальный токенизатор, если это оправдано и доступно для выбранного стека. В противном случае реализуй отдельный модуль оценки объёма и явно укажи его погрешность.


Не используй необоснованную формулу `len(text) / 3` как точный подсчёт токенов.


Если весь важный материал не помещается в бюджет, система должна честно сообщить об этом.


**Нельзя удалять критические ограничения, правила или исключения только ради соблюдения бюджета.**


### 5.5. Устранение повторов


Устраняй повторы внутри одного источника, если они действительно не добавляют новой информации.


При этом учитывай:


- различия Content Hash;
- разные структурные положения;
- разные версии узлов;
- параллельные документы.


Похожие фрагменты из разных источников не должны автоматически удаляться.


### 5.6. Параллельные источники


Особое внимание удели нескольким документам, содержащим сведения об одной сущности или теме.


Пример из Vault — два документа `Демография.md` в разных папках.


Они могут пересекаться по значениям, но содержать разные модели и допущения.


Context Builder должен:


- сохранить оба источника;
- показать их отдельными результатами;
- при необходимости отметить возможное пересечение;
- не объявлять их противоречащими друг другу без доказательств;
- не выбирать один источник как правильный.


### 5.7. Формат Context Pack


Результат должен состоять из следующих блоков.


**Included**


Источники, включённые в текущий пакет:


- оригинальный текст;
- Node ID;
- Content Hash;
- путь;
- заголовок;
- координаты;
- зона;
- дополнительные признаки, если доступны.


**Coverage**


Информация о покрытии задачи:


- найденные аспекты;
- отложенные аспекты;
- ненайденные аспекты.


**Deferred**


Источники, которые были найдены, но не помещены в текущий бюджет:


- Node ID;
- заголовок;
- путь;
- Content Hash;
- причина откладывания;
- оценка объёма.


**Parallel Sources**


Похожие или параллельные источники:


- Node ID;
- путь;
- описание характера пересечения;
- причина, по которой источники сохранены отдельно.


**Statistics**


Общая статистика:


- число найденных узлов;
- число включённых узлов;
- число отложенных узлов;
- число ненайденных аспектов;
- использованный бюджет;
- оценка или фактическое число токенов;
- полнота покрытия задачи.


Context Pack должен формироваться в структурированном формате, пригодном для передачи через MCP.


## 6. Инструмент №1: search_vault


Реализуй обязательный MCP-инструмент:


`search_vault`


Его задача — выполнить поиск через подключённый поисковый адаптер и сформировать Context Pack.


### Входные параметры


Обязательный параметр:


- `query` — поисковый запрос.


Дополнительные параметры:


- `entities` — список сущностей;
- `facets` — список функциональных категорий;
- `budget_tokens` — бюджет Context Pack;
- `known` — Node ID и Content Hash, уже известные клиенту;
- `zones` — необязательное ограничение по зонам;
- `focus` — список аспектов, которые необходимо покрыть.


Пример:
```
{
  "query": "Особенности речи Генриха Фауста",
  "entities": ["Генрих Фауст"],
  "facets": ["VOICE"],
  "budget_tokens": 3000,
  "known": [],
  "focus": [
    "Общий стиль речи",
    "Типичные фразы"
  ]
}
```


### Выходные данные


Возвращай полный Context Pack с разделами:


- Included;
- Coverage;
- Deferred;
- Parallel Sources;
- Statistics.


Если результатов нет, верни корректный пустой результат со статусами покрытия, а не ошибку и не выдуманный ответ.


## 7. Инструмент №2: read_source


Реализуй второй обязательный MCP-инструмент:


`read_source`


Его задача — адресно получать оригинальный текст из источника.


### Входные параметры


- `node_id` — идентификатор узла;
- `expected_hash` — ожидаемый Content Hash;
- `scope` — режим получения текста;
- `budget_tokens` — ограничение объёма, если применимо.


Пример:
```
{
  "node_id": "node_00421",
  "expected_hash": "sha256:...",
  "scope": "parent",
  "budget_tokens": 2500
}
```


### Режимы чтения


| Scope       | Результат                         |
| ----------- | --------------------------------- |
| `node`      | Сам структурный узел              |
| `parent`    | Узел вместе с контекстом родителя |
| `neighbors` | Соседние структурные элементы     |
| `document`  | Полный исходный документ          |


Результат должен включать оригинальный текст, путь и сведения о версии.


### Устаревший Node ID


Если Node ID не найден или его Content Hash отличается от ожидаемого:


- не подменяй его другим узлом;
- не возвращай похожий фрагмент как будто это запрошенный;
- сообщай о несовпадении или устаревании;
- возвращай диагностическую информацию, позволяющую клиенту повторить поиск.


Молчаливая подмена источников запрещена.


## 8. Stateless-протокол


MCP-сервер не должен хранить состояние диалога.


Клиент самостоятельно передаёт список известных ему узлов:
```
{
  "known": [
    {
      "node_id": "node_00421",
      "content_hash": "sha256:..."
    }
  ]
}
```


Если Content Hash не изменился, сервер может не передавать этот фрагмент повторно.


Если содержимое изменилось, сервер должен вернуть новую версию узла.


Важно: сервер не знает, сохранил ли клиент ранее полученный материал в своём контексте.


Не создавай скрытую систему памяти или предположений о содержимом окна контекста модели.


## 9. Защита от prompt injection


Исходный текст Vault является недоверенным содержимым.


В документах могут присутствовать инструкции, цитаты, внешние материалы или фрагменты, которые выглядят как команды для нейросети.


Обязательно соблюдай следующие правила:


1. Исходный текст передаётся как данные, а не как системные инструкции.
2. Не выполняй указания, обнаруженные внутри извлечённых документов.
3. Передавай оригинальный текст в отдельных структурированных полях.
4. Не считай XML-обёртку самостоятельной защитой от prompt injection.
5. Не изменяй содержимое источников ради удаления потенциально опасных фраз.


Твоя ответственность — корректно структурировать выдачу и обеспечить разделение данных и инструкций.

## 2. Принципиальные решения


Особенно тщательно проработаны следующие вопросы:


1. **Сохранность информации.** Исходные узлы передаются целиком. Если они не помещаются в бюджет, откладываются полностью, без обрезания текста.
2. **Критические ограничения.** Предусмотрены метки обязательности и зависимости между узлами. Context Builder не пытается самостоятельно угадывать смысловую критичность.
3. **Параллельные источники.** Разные документы не объединяются, в том числе два документа `Демография.md`.
4. **Покрытие.** `not_found_in_retrieval` не превращается в утверждение об отсутствии сведений в Vault.
5. **Stateless.** Повторная передача контролируется парой Node ID + Content Hash.
6. **Prompt injection.** Оригинальный текст остаётся неизменным и передаётся как недоверенные данные.


Для реализации выбран официальный MCP Python SDK 2.3.0 и tiktoken 0.14.0. Версии сверены с актуальными публикациями на момент проектирования. 【turn327144search3】【turn327144search2】

**Первое.** Context Builder не пытается самостоятельно угадывать смысловую важность материала. Критические связи передаются техническими метками `preservation` и `required_with`. Это соответствует ограничению архитектуры: навигационный слой не должен притворяться смысловым аналитиком.


**Второе.** Два документа `Демография.md` остаются разными источниками, даже если содержат пересекающиеся данные. Это важный случай из реального Vault, и спецификация учитывает его.


**Третье.** `read_source` не пытается найти похожий узел, когда исходный ID устарел. При несовпадении хеша предусмотрен статус `stale`, а не выдача приблизительно подходящего текста. Это принципиально важно для достоверности.


Документирование `Known` и `Version Changes` также оправдано: обе секции расширяют stateless-протокол, не создавая серверной памяти.


## **3. Блокирующие замечания**


### **Блокер №1. Ошибка в расчёте покрытия Included**


**Файлы:** `Спецификация.md`, раздел 6; `Контракты/context_pack.schema.json`.


Сейчас спецификация определяет `found` так:


> Источник включён в Included либо клиент сообщил, что та же версия уже имеется через known.


Но `coverage_included_ratio` считается как доля аспектов со статусом `found`.


Получается, что материал, который вообще не попал в Included, засчитывается как включённый только потому, что клиент сообщил о его наличии в `known`.


Это разные показатели.


**Поправка:**


- `coverage_available_ratio` — доля аспектов, для которых найден подходящий источник: Included, Known или Deferred.
- `coverage_included_ratio` — доля аспектов, у которых `included_node_ids` содержит хотя бы один узел.
- `known_node_ids` не должны увеличивать показатель Included.


Добавить отдельный пример и проверочный сценарий: аспект имеет только Known, но ни одного Included. В таком случае доступность покрытия должна быть положительной, а покрытие Included — нулевым.


### **Блокер №2. Не завершена логика обязательных узлов и зависимостей**


**Файлы:** `Спецификация.md`, разделы 2.3, 4.3 и 5.2; `Контракты/search_adapter.batch.schema.json`.


В схеме уже существуют поля:


- `preservation`;
- `required_with`;
- `parent_node_id`;
- `parent_context_required`.


Однако алгоритм сборки подробно описывает только группы `required_with`.


Не определено, что происходит, если:


- у узла стоит `preservation: required`, но он не связан с другими узлами через `required_with`;
- `parent_context_required = true`, но родитель сам не попал в поисковую выдачу;
- зависимость образует цепочку из нескольких узлов;
- один из участников обязательной группы отсутствует в SearchBatch;
- в зависимостях обнаружен цикл.


Сейчас схема содержит необходимые поля, но их наличие ещё не гарантирует, что алгоритм их правильно использует. Бумажная защита от потери важных условий без алгоритма остаётся декоративной.


**Поправка:**


Определить детерминированный алгоритм:


1. Выделить все узлы с `preservation: required`.
2. Построить транзитивное замыкание зависимостей `required_with`.
3. Для узлов с `parent_context_required = true` определить обязательное включение родительского контекста.
4. Обрабатывать получившиеся обязательные группы целиком.
5. Если группа не помещается в бюджет, отложить всю группу, не разделяя её.
6. Если зависимый узел отсутствует, зафиксировать `unresolved_required_dependency`.
7. Определить поведение при циклических зависимостях.


Обязательные группы должны обрабатываться до обычного ранжированного заполнения бюджета. Иначе обычные кандидаты способны занять бюджет раньше обязательных материалов.


### **Блокер №3. Не закреплена обязательная проверка Content Hash**


**Файлы:** `Спецификация.md`, разделы 4, 5.2, 11 и 12; `Контракты/search_adapter.batch.schema.json`; `Контракты/read_source.response.schema.json`.


В спецификации сказано, что неверный хеш должен регистрироваться в диагностике. Но не закреплено достаточно строго, что сервер обязан самостоятельно пересчитывать SHA-256 по полученному `raw_text`.


**Поправка:**


Для каждого кандидата SearchBatch:


1. Получить точный `raw_text`.
2. Вычислить SHA-256 от его UTF-8-представления.
3. Сравнить результат с `content_hash`.
4. При несовпадении зарегистрировать ошибку целостности.
5. Не передавать такой фрагмент в Included как проверенный источник.


Аналогичную проверку предусмотреть для фрагментов `read_source`.


Дополнительно зафиксировать, что `parent`, `neighbors` и `document` в `read_source` читаются из одного согласованного снимка источника. Нельзя проверить хеш узла в одной версии документа, а затем вернуть родителя или соседей уже из другой версии.


Для этого должны использоваться согласованные `document_hash` и/или `index_generation`.


Важно: точную семантику хеша пока нельзя считать окончательно согласованной с Исполнителем 1.
 В его реализации индексатора в репозитории пока нет, а Исполнитель 2 только проектирует импорт узлов.
 Поэтому сейчас нужно закрепить предлагаемый контракт, но не объявлять межмодульную совместимость подтверждённой.

### **Блокер №5. Противоречие в статусах пакета**


**Файлы:** `Спецификация.md`, разделы 2.3, 5.3 и 7.3; `Примеры/context_pack.response.json`.


В разделе 5.3 сказано: если хотя бы один кандидат отложен из-за бюджета, статус пакета — `budget_limited`.


В разделе 7.3 для обязательной группы, не поместившейся в бюджет, указан `partial`.


В ADR-03 используется формулировка `partial/budget_limited`.


Наконец, в примере `context_pack.response.json` две записи Deferred имеют причину `budget_limit`, но статус всего пакета указан как `partial`.


Это три варианта одного правила. Нужно оставить один.


**Поправка:**


Установить единое правило:


- `integrity_warning` — нарушена целостность данных;
- `empty` — завершённый поиск не дал кандидатов;
- `budget_limited` — хотя бы один кандидат или обязательная группа отложены из-за бюджета;
- `partial` — бюджет не ограничил выдачу, но поиск неполон либо есть непокрытые аспекты;
- `complete` — поиск завершён, нет ошибок целостности, бюджетных отложений и непокрытых аспектов.


Исправить пример на `budget_limited` и привести ADR-03 и раздел 7.3 в соответствие с этим правилом.

## 2. Обработка запроса


GitHub Actions должен:


1. Получить событие создания Issue.
2. Проверить автора и префикс `[SFRA]` в заголовке.
3. Проверить версию и JSON-схему запроса.

## 5. Права GitHub Actions

- `issues: write` для публикации результатов;

- `contents: write` только там, где действительно требуется обновление постоянного состояния.


Не выдавай workflow права записи во весь репозиторий без необходимости.

## 2. Принятые архитектурные решения


**Разделение ядра и транспорта.** Context Builder не зависит от GitHub Actions или MCP SDK. Оба транспорта вызывают одни и те же Python application services.


**Протокол Issue.** Введён `sfra.issue.v1` с UUID v4 в `request_id` и закрытым списком операций.


**Идемпотентность.** Результат связан с Issue number и request_id. Повторный запуск после DONE не должен создавать второй несовместимый ответ.


**Постоянство индекса.** Предложена отдельная публичная ветка `sfra-index-state` с SQLite и manifest. Issue worker читает её только для чтения.


**Права.** Issue worker получает `contents: read` и `issues: write`. `contents: write` выделяется отдельному workflow публикации sidecar.


**Очередь.** Используются `queue: max` и восстановление незавершённых запросов через recovery sweep. Одного concurrency недостаточно для гарантии сохранения всех запросов: GitHub ограничивает такую очередь 100 ожидающими запусками. <Cite refs={["turn107507search1","turn107507search2"]}/>

Это отражено в дополнении. Я не стал объявлять существующий smoke test готовым рабочим интерфейсом или временную базу постоянным хранилищем.

Базовая архитектура Context Builder остаётся состоятельной.

- Обязательные зависимости образуют неделимые группы.
- Параллельные источники сохраняются, а не объявляются автоматически противоречащими друг другу.
- Проверка SHA-256 выполняется над точным UTF-8 представлением `raw_text`.

## **2. Найденные замечания**


### **Блокирующие для реализации транспорта**


**1. Не согласовано постоянное хранилище E1.**


В документах E3 до сих пор фигурирует:


- ветка `sfra-index-state`;
- каталог `.sfra-state/`;
- файлы `.sfra-state/structure.sqlite3` и `.sfra-state/manifest.json`.


Но E1 реализовал другую схему:


- ветка `sfra-state`;
- `state/structure.sqlite3`;
- `state/manifest.json`;
- workflow `.github/workflows/sfra-state-persistence.yml`.


Кроме того, реальная база пока не инициализирована: первый production-запуск должен выполняться с `initialize_state=true`.


В E3 устарели не только названия. Различаются и поля manifest: E1 использует `source_commit`, `database_sha256`, `indexer_version`, а E3 ожидает сведения о Vault snapshot и версии индексатора в своей модели.


**Требование:** Исполнитель 3 должен обновить §6 дополнения, согласовать соответствие полей manifest и исправить `sidecar_branch` в примерах. Нельзя писать worker под несуществующую структуру.


**2. Несовпадение&#x20;**`document_hash`**&#x20;в контракте E2 и E3.**


В контракте E3 `executor2_get_node.response.schema.json` поле `document_hash` обязательно и допускает только строку SHA-256.


При этом в документе E2 «Уточнения после аналитической проверки» прямо указано, что `document_hash` может возвращаться как `null`, если его нет в исходных данных.


Это не косметическое различие. E3 использует `document_hash` для проверки целостности чтения родительских узлов, соседей и целого документа.


**Требование:** согласовать реальный ответ `get_node` на SQLite E1. Если E1 предоставляет hash целого документа, E2 должен возвращать его. Если нет, E3 должен явно определить поведение для `null`, включая ограничения на допустимые `scope`. Подставлять hash узла вместо hash документа запрещено.


### **Замечания к транспортному протоколу**


**3. Неоднозначен формат result-комментариев.**


В `sfra.issue.result-part.schema.json` результат описан как JSON-объект с полями `protocol_version`, `request_id`, `attempt_no`, `marker`, `content`.


Пример `issue.result.part.json` соответствует именно такому объекту.


Но в дополнении §4.4 написано, что тело комментария состоит из HTML marker на отдельной строке и следующего за ним content.


Это два разных формата передачи. Разработчик worker не должен самостоятельно выбирать между ними.


**Требование:** зафиксировать один wire format и привести к нему схему, пример и описание. Я бы предпочла единый JSON-объект целиком в теле комментария.


**4. Статус RUNNING не гарантирует закреплённый snapshot.**


В `sfra.issue.status.schema.json` проверяется, что у RUNNING есть `lease_expires_at`, но `source_snapshot` при этом всё ещё может быть `null`.


Это противоречит спецификации: RUNNING означает, что запрос уже проверен и snapshot закреплён.


**Требование:** добавить условие схемы, требующее `source_snapshot` типа object для `status=RUNNING`.

### **Блокер №1. Неправильный расчёт бюджета**


**Файл:** `src/sfra_context_builder/budget.py`, строка 54.


В принятой спецификации Этапа А, ADR-07, установлено:


`budget_tokens` ограничивает включаемый материал и его provenance.


Служебная структура ответа, в частности Coverage, Deferred и Diagnostics, учитывается отдельно через `response_tokens_estimated`.


Но сейчас реализация считает:
```
payload = {
    "Included": list(included),
    "Coverage": list(coverage),
}
return token_counter.count(compact_json(payload))
```


Таким образом, Coverage расходует бюджет, предназначенный для включённых источников.


**Почему это проблема:**


Предположим, что исходный узел вместе с provenance помещается в бюджет. Но клиент передал большое количество focus-аспектов. Объём Coverage увеличился, и тот же узел теперь может быть отклонён.


Получается, что увеличение количества аспектов способно лишить клиента исходного текста, который раньше помещался в бюджет.


Это противоречит принятому ADR-07.


**Что исправить:**


1. Разделить подсчёт `Included + provenance` и подсчёт полного ответа.
2. `tokens_used` должен отражать именно расход бюджета Included.
3. Coverage, Deferred и Diagnostics учитывать в `response_tokens_estimated`.

### **Блокер №2. Неверный статус при неразрешённой зависимости известного узла**


**Файлы:**


- `builder.py`, строки 174–190;
- `builder.py`, строки 338–353.


Здесь более неприятная проблема.


Рассмотрим сценарий:


- Клиент передал узел A в `known`.
- Узел A имеет `required_with = ["M"]`.
- Узел M отсутствует в SearchBatch.
- DependencyResolver отсутствует либо не может разрешить M.


Код правильно обнаруживает неразрешённую зависимость.


Однако в обработке группы есть следующий механизм:
```
new_members = [
    member for member in group.members
    if member.node_id not in known_ids
]
```


После этого Deferred формируется только для `new_members`.


Поскольку A уже находится в Known, список оказывается пустым.


Диагностика `unresolved_required_dependency` добавляется, но в дальнейшем итоговый статус вычисляется по наличию соответствующей записи в Deferred.


В результате система может вернуть:


`status = complete`


хотя обязательная зависимость не разрешена.


**Это ошибка функциональной логики.**


Known означает, что клиент уже располагает конкретной версией исходного узла. Это не доказывает, что клиент располагает всеми обязательными зависимостями.


**Что исправить:**


1. Ввести отдельный признак наличия неразрешённых обязательных групп.
2. Учитывать его при вычислении статуса независимо от наличия Deferred.
3. Не повторять текст Known в Included.
4. Сохранять диагностическую информацию о недостающих узлах.
5. При любой неразрешённой обязательной зависимости устанавливать `partial`, если нет более приоритетной ошибки целостности.
