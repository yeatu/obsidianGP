# E3. Интегрировать Search Engine, Structural Indexer и Context Builder


**Цель:** превратить уже реализованное ядро Context Builder (этап Б1) в работающую систему, которая принимает поисковые результаты E2, собирает Context Pack и умеет получать дополнительные оригинальные фрагменты из E1.


## 1. Что уже существует


Этап Б1 слит в `main`. Ядро включает:


- SearchRequest, SearchBatch, RetrievalCandidate, SnapshotRef;
- проверку входных данных и точного SHA-256 `raw_text`;
- дедупликацию и обработку конфликтующих версий;
- ранжирование;
- dependency resolver;
- coverage, deferred и parallel sources;
- атомарное бюджетирование и Context Pack;
- token counter на `tiktoken`.


См. `Этап Б1/Передача аналитику.md`.


Не переписывать ядро и не менять его публичные модели без отдельного обоснования и обновления схем.


## 2. Реализовать SearchAdapter


Создать адаптер между реальным E2 и типами Context Builder.


Он должен:


1. Вызывать существующий интерфейс E2, не копировать поисковую логику в E3.
2. Преобразовывать реальные результаты E2 в `SearchBatch`.
3. Корректно передавать Node ID, Content Hash, raw_text, tier, BM25, source path и доступные метаданные.
4. Сохранять исходное направление сортировки score.
5. Не создавать новые идентификаторы и не подменять отсутствующие поля.
6. Обрабатывать пустой результат, ошибку поиска и частичную выдачу явно.


## 3. Реализовать SourceReader


Создать реализацию resolver/reader для Context Builder, использующую API E1.


Нужен адресный вызов по `node_id + content_hash` с закреплённым snapshot.


Поддержать режимы `read_source` из архитектуры:


- `node`;
- `parent`;
- `neighbors`;
- `document`.


Текст должен поступать из проверенного оригинального Markdown. Не считать сохранённый в поисковом индексе текст E2 самостоятельным первоисточником.


Если E1 не предоставляет необходимую операцию для конкретного scope, не дублировать молча внутреннюю логику индексатора. Сначала согласовать недостающий интерфейс и зафиксировать его контракт.


Устаревший или неоднозначный адрес должен приводить к явной ошибке/диагностике, а не к автоматической подмене другим узлом.


## 4. Snapshot consistency


Использовать `SnapshotRef`, предусмотренный Б1.


В рамках одного запроса должны быть закреплены:


- `vault_commit_sha`;
- `sidecar_commit_sha`;
- SHA-256 manifest.


Все поисковые результаты, зависимости и чтение дополнительных фрагментов должны относиться к одному snapshot.


Нельзя при рекурсивном разрешении зависимостей переключаться на текущую ветку или более новое состояние `sfra-state`. При несовпадении snapshot возвращать явную ошибку целостности.


Отдельно документировать, как `manifest.source_commit` сопоставляется с `SnapshotRef.vault_commit_sha`.
