# Передача аналитику — E3 Integration C1

**Статус:** C1 подготовлен в отдельной ветке и ожидает независимой проверки.  
**Объём:** E2 SearchAdapter boundary, Snapshot binding, E1 source-reader port, fixture tests и контрактное предложение E1. Не заявляется как сквозная интеграция.

## 1. Реальный E2 API

Используемый callable: `sfra_search.runtime.search_structural_database(source_database, query, entities=..., limit=..., entity_config=...)`.

Ответ содержит `search.status` (`ok` или `not_found_in_retrieval`) и `search.results`. Hit содержит locator поля, `excerpt`, `match_type`, `match_reasons` и `relevance.tier/bm25`.

Ограничения:
- `excerpt` не заменяет полный исходный узел;
- E2 не выдаёт `total_count` или `cursor`;
- E2 `index_generation` — generation производного E2 search index, не E1 document-local generation;
- E2 API не предоставляет facet filtering или явный facet-match signal;
- E2 не предоставляет preservation/dependency flags как подтверждённые поля своего API.

Поэтому C1 консервативно отмечает выдачу размером ровно limit как potentially truncated, не выдумывает пагинацию, сохраняет match reasons как unmapped и не строит facet signal по факту запроса.

## 2. Source of truth

E2 hit используется для поиска, locator и ранжирования. Полный `raw_text` запрашивается только у injected `E1NodeReader` по точной паре `node_id + content_hash` и pinned `SnapshotRef`.

При несовпадении ID/hash/path/coordinates/heading или source hash кандидат исключается и сопровождается диагностикой. `excerpt` никогда не используется как fallback.

Важное ограничение: опубликованный E1 API design в ветке E1 всё ещё помечает реализацию как не начатую и покрывает только `node`. Поэтому C1 реализует порт и fake-reader tests, но не E1-backed SourceReader.

## 3. Snapshot binding

Предлагаемое отображение:
- `SnapshotRef.vault_commit_sha` = фактический Git HEAD checkout Vault, совпадающий с `manifest.source_commit`;
- `SnapshotRef.sidecar_commit_sha` = фактический Git HEAD checkout `sfra-state`;
- `SnapshotRef.manifest_sha256` = SHA-256 точных байтов `state/manifest.json`.

Snapshot binder требует официальный callback E1 `verify_state_directory` для проверки SQLite/schema/FK и дополнительно сверяет manifest/database digest. E2 и E1 reads в одном запросе получают один и тот же immutable snapshot reference.

E1 `documents.generation` — document-local generation. Его нельзя сравнивать между разными source_path или путать с E2 generation.

## 4. Что проверяют fixtures

- source raw_text exact UTF-8/CRLF и SHA-256;
- exact mapping E2 locator → E1 source;
- tier/BM25 и сортировочное направление;
- unmapped match reasons без эвристической интерпретации;
- excerpt isolation;
- empty retrieval vs E2 runtime exception;
- stale/deleted/ambiguous/not_found/integrity_error;
- locator metadata mismatch и source hash mismatch;
- limit truncation, facet signal absence, exact zone post-filter;
- manifest.source_commit binding и manifest SHA over raw bytes.

## 5. Незакрытые зависимости перед real-Vault stage

1. E1 должен принять и реализовать scope API для `node`, `parent`, `neighbors` и `document`.
2. E1 должен вернуть E1 document-local generation, whole-document hash, metadata и точный raw_text.
3. E1/E2 должны согласовать источник `preservation`, `required_with`, `parent_context_required`.
4. После этого E3 реализует SourceReader/DependencyResolver через публичный E1 API и проводит fixtures end-to-end.
5. Только затем проводится real-Vault test: immutable pinned checkouts, E1 SQLite и Vault read-only, контроль digest до/после.

## 6. Просьба аналитику

Проверить:
- соответствует ли SearchAdapter фактическому E2 runtime API;
- корректна ли conservative truncation при len(results) == limit;
- корректно ли отображается manifest.source_commit в SnapshotRef;
- принять/отклонить предложение E1 scope API и определить источник dependency metadata.

C2, C3 и C4 не начинаются автоматически до проверки C1 и согласования E1 API.
