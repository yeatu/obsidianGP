## 4. Изменение транспортного решения

По дополнению координатора:
- основной MVP transport — GitHub Issue → GitHub Actions → Issue Comment;
- ядро предоставляет две независимые операции search_vault и read_source;
- MCP не является обязательным транспортом MVP;
- MCP, если будет нужен, остаётся отдельным optional adapter, не обязательной зависимостью ядра;
- каждое Issue содержит request_id и protocol_version;
- новое read_source создаётся отдельным Issue;
- комментарии workflow не являются командами и не триггерят обработчик;
- статусы транспорта PENDING/RUNNING/DONE/FAILED отделены от бизнес-статуса Context Pack/SourceReadResult;
- повторный запуск одного Issue/request_id идемпотентен;
- contents: write не выдаётся Issue worker. Запись постоянного sidecar выделяется отдельному publish job.

## 5. Что выяснено в репозитории

Проверены существующие Actions и реализация Исполнителя 1:

1. .github/workflows/sfra-issue-bridge-smoke.yml — только транспортный smoke test. Он проверяет автора yeatu, специальный тестовый префикс и строку-пробу; Vault не читает и операции search_vault/read_source не вызывает.
2. .github/workflows/sfra-search-kernel-test.yml — отдельный smoke test поискового ядра, не общий Issue protocol handler.
3. В Actions run 43966494886 bridge smoke workflow был пропущен (skipped), поскольку заголовок тестового Issue имел префикс [SFRA-SEARCH-KERNEL], а не [SFRA-BRIDGE-TEST]. Это не ошибка поиска: соответствующее ядро отработало в run 43966494822 со статусом success.
4. Реализация Исполнителя 1 находится в ветке executor-1/sfra-indexer-session-1. Её workflow создаёт SQLite в /tmp/sfra-vault-sidecar; .gitignore исключает *.sqlite3 и *.db. Это подтверждает тестовую индексацию, но не сохраняет Node ID и историю версий между независимыми Actions runs.
5. Предлагаемая ветка sfra-index-state ещё не создана. Это проектное решение, а не уже существующая инфраструктура.
6. Репозиторий yeatu/obsidianGP публичный. Ветка sidecar также будет публичной, если будет создана. Она должна содержать только производное состояние индекса для уже публичного Vault, без секретов и приватных материалов.

Следовательно, текущий Issue bridge не выдаётся за готовый SFRA transport, а временная SQLite не выдаётся за постоянное хранилище.

## 6. Предлагаемая схема эксплуатации

- Отдельный Issue worker получает открытый Issue, проверяет allowlist автора, префикс [SFRA], envelope и payload schema; получает фиксированный Vault commit и sidecar snapshot; вызывает Python application service; публикует результат в Issue Comment.
- Worker имеет только contents: read и issues: write; он не меняет main, Vault или sidecar.
- Отдельный sidecar refresh workflow сериализован общей concurrency group и обновляет постоянную ветку sfra-index-state.
- Issue worker читает sidecar read-only. FTS5 и временные поисковые структуры строятся в каталоге runner.
- Manifest связывает sidecar с Vault commit и содержит SHA-256 SQLite-файлов. Несовпадающий snapshot не используется: запрос остаётся PENDING с INDEX_NOT_READY до синхронизации.
- queue: max и cancel-in-progress: false уменьшают риск вытеснения запросов; recovery sweep повторно подбирает открытые Issues без terminal status. GitHub ограничивает очередь concurrency group максимумом 100 ожидающих запусков, поэтому recovery sweep остаётся необходимой страховкой.

## 7. Исправления предыдущего аудита Context Builder

| Замечание | Реализация в проектной спецификации |
|---|---|
| Coverage Included смешивал Included и Known | coverage_available_ratio считает found + deferred; coverage_included_ratio считает только непустые included_node_ids |
| Не был формализован граф обязательных узлов | Транзитивный required_with, standalone preservation=required, parent context, SCC-обработка циклов, atomic include/defer |
| SHA-256 не был обязательной проверкой | Пересчёт SHA-256 точных UTF-8 байтов raw_text на границах SearchAdapter, ContextBuilder и SourceReader |
| Контракт не соответствовал Исполнителю 2 | excerpt остаётся поисковой подсказкой; полный raw_text читается через get_node(node_id, content_hash); tier/BM25 сортируются по возрастанию |
| Статусы пакета противоречили друг другу | Установлена единая последовательность integrity_warning → empty → budget_limited → partial → complete |

Остались тесты интеграции на фактических модулях E1/E2, когда их доступные API будут готовы.

## 8. Проверочные сценарии нового транспорта

В Дополнение_GitHub_Issues_Actions.md определены I-01—I-23, включая:
- разрешённый/запрещённый автор;
- корректный и невалидный JSON;
- неизвестную версию протокола и operation;
- защиту от запуска по комментариям и pull request;
- повторную обработку после DONE;
- параллельные Issues и обновление sidecar;
- несовпадение manifest checksum;
- восстановление RUNNING/PENDING после прерванного runner через reusable workflow;
- запуск одного worker по issues.opened и через workflow_call из scheduled matrix;
- переполнение concurrency queue;
- FAILED retryable=true с повтором того же request_id до трёх попыток;
- FAILED retryable=false как терминальное состояние;
- многочастный JSON result с контрольным SHA-256;
- stale при повторном чтении старого Content Hash;
- prompt injection в Issue body.

Полный end-to-end сценарий (search_vault → Context Pack → новый Issue read_source → оригинальный фрагмент или stale) задан как критерий последующей реализации. Сейчас он не объявляется выполненным.
