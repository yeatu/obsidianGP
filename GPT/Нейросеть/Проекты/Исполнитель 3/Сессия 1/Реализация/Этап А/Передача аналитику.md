## 2. Исправления пяти блокирующих замечаний

| Замечание | Исправление |
|---|---|
| 1. Coverage Included смешивал Included и Known | \`coverage_available_ratio\` считает found + deferred; \`coverage_included_ratio\` считает только аспекты с непустым included_node_ids. Known-only пример показывает 1.0 доступности и 0.0 Included |
| 2. Не был формализован граф обязательных узлов | Добавлен транзитивный граф \`required_with\`, standalone \`preservation=required\`, обязательный parent context, разрешение отсутствующих узлов, SCC-обработка циклов, atomic include/defer |
| 3. SHA-256 не был обязательной проверкой | Пересчёт SHA-256 точных UTF-8-байтов raw_text закреплён для SearchAdapter, Context Builder и каждого фрагмента SourceReader |
| 4. Контракт не соответствовал Исполнителю 2 | Добавлены upstream-схемы Search Hit и get_node. excerpt используется только для поиска, полный raw_text получается через get_node(node_id, content_hash). tier сортируется ascending, BM25 ascending |
| 5. Статусы пакета противоречили друг другу | Введено единое правило integrity_warning → empty → budget_limited → partial → complete. Основной пример исправлен на budget_limited |

## 3. Интеграция с Исполнителем 2

Сверено с его [Проектным решением](../../../../Исполнитель%202/Сессия%201/Реализация/Проектное%20решение.md).

Его проектный API:
- \`engine.search(query, entities=None, limit=20, include_history=False)\`;
- \`engine.get_node(node_id, content_hash=None)\`.

Его search hit:
- \`excerpt\`;
- \`relevance.tier\`;
- \`relevance.bm25\`;
- \`match_reasons\`;
- \`match_type\`;
- путь, координаты, Node ID и Content Hash.

Адаптер Исполнителя 3 не подменяет excerpt полным текстом. Он разрешает конкретную версию через get_node, сверяет Node ID + Content Hash и только затем получает raw_text. В спецификации есть таблица отображения match_reasons и правила для неизвестных причин.

По ранжированию:
- меньший tier лучше;
- меньший BM25 лучше;
- сортировка по возрастанию обоих показателей;
- score не применяется поверх E2 relevance и не используется без явного score_direction.

Метод get_node сам по себе не обещает соседние узлы и полный документ. Поэтому SourceReader определён как составной адаптер: E2 get_node для конкретного узла/parent, структурный snapshot Indexer для neighbors, оригинальный источник от Indexer/согласованного file reader для document. Недостающая capability приводит к source_unavailable, не к имитации чтения.

## 5. Оставшиеся открытые интеграционные вопросы

Они не блокируют архитектурное описание, но требуют проверки на реализации модулей 1 и 2:

1. Исполнитель 1 должен подтвердить точный byte-scope Content Hash, координаты и доступность snapshot чтения parent/neighbors/document.
2. Исполнитель 2 должен подтвердить, что get_node возвращает полный raw_text запрошенной версии, а также index_generation/document_hash или эквивалентный immutable snapshot token.
3. Фактические значения match_reasons нужно подтвердить тестами. Неизвестные коды сохраняются, но не получают выдуманного ранга.
4. В проектном интерфейсе Исполнителя 2 есть limit, но отдельный cursor/offset пока не закреплён. Поэтому MVP не притворяется, что выдача полная при достижении лимита: SearchAdapter выставляет complete=false/truncated_by_limit=true, если API не подтвердил исчерпание результатов. Публичный search_vault cursor не добавляется.
5. Целевой MCP host координатора должен подтвердить транспорт/совместимость выбранной версии SDK при реализации.
