## Исполнитель 3 · Context Builder и MCP-интерфейс

**Статус:** проектирование, передано на проверку аналитику  
**Версия контракта:** 1.0-draft  
**Дата:** 16.11.2026  
**Область:** только Этап 3 SFRA. Код и реализация MCP-инструментов в этом этапе не создаются.

## 1. Назначение и границы

Компонент принимает результаты Retrieval Engine и собирает Context Pack из оригинальных фрагментов Vault. Он не становится второй базой знаний и не меняет исходные документы.

В область реализации входят:

- нормализация результата поискового адаптера во внутреннюю модель;
- детерминированное ранжирование по переданным поисковиком признакам;
- управляемое покрытие явно заданных аспектов;
- бюджетирование без обрезания исходных узлов;
- исключение только доказанных технических дублей;
- сохранение параллельных источников;
- передача отложенных результатов и диагностик;
- адресное чтение первоисточников;
- два MCP-инструмента: search_vault и read_source;
- stateless-протокол по паре Node ID + Content Hash.

Вне области реализации: Markdown AST, сегментация, FTS5, морфология, реестр сущностей, граф знаний, эмбеддинги, LLM-реранжирование, долговременная память и UI.

**Правило доверия:** содержательным доказательством является только raw_text, полученный из первоисточника. Score, фасеты, сигналы, зоны и авторские пометки являются метаданными навигации и не должны превращаться в факты о мире.

## 2. Основные архитектурные решения

### ADR-01. Context Builder не ищет самостоятельно

Context Builder получает SearchBatch от интерфейса SearchAdapter. Он не выполняет SQL/FTS, не лемматизирует запросы и не пытается заменить Retrieval Engine. Результаты поиска и их score остаются ответственностью Исполнителя 2.

### ADR-02. Оригинальный узел является атомом отбора

Нельзя обрезать raw_text по символам, предложениям, абзацам или токенам. Включается весь узел либо он откладывается целиком. Текст в Included должен побайтно соответствовать UTF-8-представлению оригинального среза, согласованному с индексатором.

Если узел слишком велик, клиент получает Deferred + причину и может вызвать read_source с другим scope или увеличить бюджет. Context Builder не делает пересказ и не создаёт «сжатую версию».

### ADR-03. Критичность не выводится из смысла

Context Builder не имеет смыслового анализатора и не устанавливает критичность содержания по тексту. Сохранность обеспечивается явными метками индексатора/поискового адаптера и детерминированным алгоритмом зависимостей.

Поддерживаются:
- \`preservation = required|normal\`;
- \`required_with\` — список Node ID, которые необходимы вместе с узлом;
- \`parent_node_id\` и \`parent_context_required\`;
- \`matched_focus_ids\`;
- \`index_generation\` и \`document_hash\` для проверки согласованного снимка.

Все зависимости рассматриваются как обязательство передавать связанный материал вместе. Из графа зависимостей строятся неделимые компоненты. В них включаются:
1. сам кандидат с \`preservation=required\`;
2. транзитивное замыкание всех ссылок \`required_with\`;
3. родительский узел, если \`parent_context_required=true\`;
4. обязательные зависимости уже добавленных узлов, рекурсивно.

Если родителя/зависимый узел нет в SearchBatch, адаптер пытается получить точную запись через SourceReader.resolve_node() в том же index_generation. Такой узел включается как required dependency context, а не как самостоятельно найденный поисковый результат. Если источник недоступен или его снимок отличается, вся зависимая группа откладывается с причиной \`unresolved_required_dependency\`. Дочерний узел без обязательного родительского контекста отдельно не включается.

Группы формируются до бюджетирования. Сначала обрабатываются все обязательные группы, затем кандидаты для покрытия focus, затем остальные результаты по рангу. Группа включается полностью или целиком откладывается. Если группа не помещается, применяется \`required_group_budget_limit\` и статус пакета \`budget_limited\`.

Циклы в графе зависимостей обнаруживаются алгоритмом SCC (strongly connected components). Каждая циклическая SCC сворачивается в один атомарный компонент; транзитивные зависимости этого компонента добавляются к нему. Цикл не вызывает бесконечный обход и не приводит к произвольному разрыву связей. Выдаётся диагностика \`required_dependency_cycle_collapsed\` уровня warning. Если из-за цикла или отсутствующего участника нельзя построить полный компонент, он откладывается целиком с диагностикой.

Узел \`preservation=required\` без \`required_with\` и без родителя образует обязательную группу из одного элемента. Следовательно, флаг не является декоративным и учитывается сам по себе.

Эти правила не означают, что Context Builder распознаёт смысловые исключения. Если индексатор не передал preservation/dependency metadata, Context Builder не может гарантировать специальную защиту неизвестного ему условия и честно фиксирует отсутствие такого сигнала.

### ADR-04. Покрытие управляется клиентом

Context Builder не декомпозирует произвольную задачу самостоятельно. Источником списка аспектов является focus. Поддерживаются:
1. короткая форма — строка с названием аспекта; для неё назначается локальный ID focus_001, focus_002 и т. д. в порядке запроса. Такой ID стабилен только при неизменном порядке списка;
2. расширенная форма — объект с явно заданными id, label и entities/facets/terms. Для межзапросного known/сопоставления клиенту следует использовать расширенную форму.

Поиск может возвращать matched_focus_ids. Если этих меток нет, расширенный focus сопоставляется только по переданным структурным признакам и точным текстовым фразам. Это детерминированное сопоставление, а не семантический вывод.

Если aspect не сопоставлен ни одному обработанному кандидату, его статус — not_found_in_retrieval. Это означает только «не обнаружено в обработанных результатах этого поиска», а не «материала нет в Vault».

### ADR-05. Параллельные источники не разрешаются

Потенциальное пересечение можно отметить, например, по одинаковому имени файла при разных source_path либо по явной метке overlap_group_id от поискового слоя.

Наличие совпадающих чисел, имён или слов не является доказательством противоречия. Context Builder:
- сохраняет каждый Node ID отдельно;
- указывает конкретный сигнал пересечения;
- не выбирает источник как канонический;
- не присваивает статус «противоречие»;
- не сливает фрагменты разных документов.

Два файла Демография.md в папках иное/ и разобрать/ являются обязательным будущим тестовым случаем, а не основанием для объединения.

### ADR-06. Устранение повторов ограничено доказуемой идентичностью

Безопасно объединяются повторные появления одной и той же версии того же узла: одинаковые node_id + content_hash. Для противоречащих друг другу версий одного Node ID в одном SearchBatch возвращается диагностика целостности, а не произвольный выбор.

Похожие тексты, одинаковые названия заголовков и перекрывающиеся диапазоны не удаляются автоматически. Разные структурные положения и разные source_path сохраняются.

### ADR-07. Бюджет не подменяет полноту

budget_tokens — лимит на материал, включаемый в Included. Узлы атомарны. Context Builder сначала проверяет зависимости/обязательные группы, затем обеспечивает покрытие focus, затем добавляет оставшиеся кандидаты в порядке ранжирования.

Токены считаются отдельным TokenCounter. Предлагается tiktoken с конфигурируемой encoding; начальное значение — o200k_base. Это точный подсчёт для выбранной кодировки, но не гарантия точного совпадения с неизвестной моделью MCP-клиента. Поэтому в Statistics обязательно указываются токенизатор, кодировка и область точности.

budget_tokens ограничивает именно включённый контент и его provenance-метаданные. Отложенные записи, диагностики и компактная структура ответа являются служебными метаданными и учитываются отдельно в response_tokens_estimated. Это разделение предотвращает ситуацию, когда из-за длинного списка Deferred исчезают ссылки на найденные материалы.

Если метаданные ответа сами становятся чрезмерными, это фиксируется отдельным предупреждением. На этапе MVP нельзя молча отбрасывать Deferred ради формального попадания в бюджет.

### ADR-08. Сервер stateless

Сервер не хранит контекст диалога, историю доставленных фрагментов, состояние окна модели или список известных источников. Клиент передаёт known при каждом search_vault.

- совпали Node ID и Content Hash — исходный текст не повторяется, запись помещается в блок Known;
- Node ID найден, но Content Hash изменился — новая версия включается в выдачу, а разница фиксируется в Version Changes;
- Node ID не найден — сервер не заменяет его похожим узлом.

Known — доказательство только того, что клиент сообщил о наличии версии у себя. Сервер не может проверить, сохранилась ли она после компрессии контекста.

### ADR-09. Prompt injection

Исходный текст — недоверенные данные. Сервер:
- передаёт его отдельным raw_text-полем;
- не исполняет содержащиеся в нём команды;
- не удаляет подозрительные фразы;
- не меняет исходный текст ради «очистки»;
- добавляет trust_label = untrusted_source_data как метаданные.

Метка и JSON-структура помогают разделять данные и инструкции, но не являются самостоятельной защитой. Клиент обязан сохранять соответствующее системное правило и рассматривать raw_text как цитируемый материал.

## 3. Внутренняя архитектура

Рекомендуемое разделение модулей:

    contracts/
      models.py
      validation.py
    adapters/
      executor2_search.py       # преобразование search() + get_node()
      source_reader.py          # составной SourceReader
      snapshot_reader.py        # чтение исходника/снимка от Indexer
    context/
      ranking.py

      coverage.py
      budget.py
      dedup.py
      parallel_sources.py
      builder.py
    mcp_server.py
    fixtures/
    tests/

\`ContextBuilder.build(request, batch, dependency_resolver)\` остаётся чистым и независимо тестируемым. \`dependency_resolver\` — узкий интерфейс для точного разрешения Node ID, отсутствующих в поисковой выдаче, но нужных для обязательных зависимостей. MCP-обработчики валидируют запрос, вызывают адаптеры, затем Context Builder и сериализуют результат.

### 3.1. SearchAdapter и мост к Исполнителю 2

Внешний Python API Исполнителя 2 в его проектном решении:

    engine.search(
        query: str,
        entities: list[str] | None = None,
        limit: int = 20,
        include_history: bool = False
    )

и

    engine.get_node(node_id: str, content_hash: str | None = None)

Результат search() содержит поисковую запись с:
- \`node_id\`, \`source_path\`, \`node_type\`, \`parent_node_id\`;
- \`heading_path\`, \`line_start\`, \`line_end\`;
- \`content_hash\`;
- \`excerpt\` — поисковый фрагмент, который **не считается полным узлом**;
- \`match_type\`, \`match_reasons\`;
- \`relevance.tier\`, \`relevance.bm25\`;
- \`entity\`, если присутствует.

Адаптер Исполнителя 3 работает в два шага:

1. Вызывает \`engine.search(..., include_history=False)\`. \`excerpt\` используется только как объяснение совпадения/поисковая подсказка и никогда не передаётся в Included вместо полного узла.
2. Для каждого результата вызывает \`engine.get_node(hit.node_id, hit.content_hash)\`. Только возвращённый этой операцией \`raw_text\` конкретной версии может стать нормализованным \`RetrievalCandidate.raw_text\`.

Адаптер обязан проверить, что get_node вернул ту же пару \`node_id + content_hash\`, что была в hit. Он также сверяет source_path, координаты и heading_path, если эти поля возвращены обеими сторонами. Если get_node не возвращает полного оригинального текста, версия не найдена или метаданные расходятся, кандидат не допускается в Included и регистрируется диагностика. Подстановка \`excerpt\` вместо недостающего \`raw_text\` запрещена.

Нормализованный интерфейс:

    async def search(request: SearchRequest) -> SearchBatch
    async def resolve_node(
        node_id: str,
        expected_hash: str | None,
        snapshot_generation: int | None
    ) -> ResolvedNode | ResolveFailure

SearchRequest передаёт query, entities, facets, zones и focus. SearchBatch содержит candidates, complete, inspected_count и внутренний cursor. Для каждого candidate обязательны полный raw_text, node_id, source_path, heading_path, координаты, content_hash и match_type; дополнительно сохраняются relevance, match_reasons, entity metadata, сигналы и зависимости.

\`resolve_node\` использует \`engine.get_node(node_id, content_hash)\`. Для поиска текущей версии обязательной зависимости допускается \`content_hash=None\`, но версия должна иметь тот же \`index_generation\`, что и исходный кандидат/снимок. Для узлов одного source_path дополнительно проверяется общий \`document_hash\`.

### 3.2. SourceReader и составной адаптер

Интерфейс:

    async def resolve_node(
        node_id: str,
        expected_hash: str | None = None,
        snapshot: SnapshotRef | None = None
    ) -> ResolvedNode | ResolveFailure

    async def read(
        node_id: str,
        expected_hash: str,
        scope: ReadScope,
        budget_tokens: int | None
    ) -> SourceReadResult

Базовый способ получить точную версию структурного узла — \`engine.get_node(node_id, expected_hash)\` Исполнителя 2. Это покрывает \`scope=node\` и даёт metadata для адресации контекста.

Четыре режима реализуются составным адаптером:
- \`node\`: точный get_node по паре Node ID + Content Hash;
- \`parent\`: точный target плюс parent_node_id из той же версии/генерации, затем получение родительского узла;
- \`neighbors\`: Indexer/SourceSnapshotReader разрешает соседние структурные элементы по метаданным структуры и возвращает их исходные срезы;
- \`document\`: SourceSnapshotReader читает полный исходный Markdown-документ из согласованного snapshot.

Метод get_node Исполнителя 2 сам по себе не обещает выдачу соседей или полного документа. Поэтому SourceReader не имитирует эти режимы из одного excerpt. Для neighbors/document требуется возможность чтения структурного снимка/исходного файла, которую предоставляет Исполнитель 1 либо согласованный файловый адаптер. Если такой возможности пока нет, возвращается \`source_unavailable\` с указанием недостающей capability; ложная успешная выдача запрещена.

Каждый SourceReadResult должен содержать единый snapshot reference. Все фрагменты scope должны относиться к одной генерации индекса и версии исходного документа. Если проверить единство версии невозможно, текст не выдаётся как проверенный: возвращается \`integrity_error\` или \`source_unavailable\`.

## 4. Контракт поискового кандидата

### 4.1. Обязательные поля нормализованного кандидата

| Поле | Тип | Значение |
|---|---|---|
| node_id | string | Node ID от индексатора |
| source_path | string | Путь относительно Vault |
| heading_path | string[] | Иерархия заголовков |
| line_start / line_end | integer | Координаты исходного узла |
| content_hash | string | sha256 от точного UTF-8 среза raw_text |
| raw_text | string | Полный оригинальный Markdown-срез узла, полученный через get_node |
| match_type | string | Тип совпадения, переданный поисковым модулем |
| relevance | object | tier и bm25 от Исполнителя 2, если доступны |
| match_reasons | string[] | Причины совпадения от Исполнителя 2 |

### 4.2. Поля ранжирования и отображение E2

Нормализованный SearchBatch может дополнительно содержать zone, has_author_notes, entity, signals, matched_focus_ids, matched_entities, matched_facets, matched_terms, preservation, required_with, parent_node_id, parent_context_required, overlap_group_id, index_generation и document_hash.

Для контракта Исполнителя 2 используется явное преобразование:

| Поле Исполнителя 2 | Поле нормализованного кандидата | Правило |
|---|---|---|
| relevance.tier | relevance.tier / rank_priority | Меньшее значение выше: 1 лучше 2, 2 лучше 3 и т.д. |
| relevance.bm25 | relevance.bm25 | Вторичная сортировка по возрастанию: более низкий (в том числе более отрицательный) BM25 идёт раньше |
| match_reasons | match_reasons + signals | Только точное отображение известных кодов; неизвестные строки сохраняются отдельно |
| match_type | match_type | Передаётся без переименования и смысловой интерпретации |
| excerpt | match_excerpt | Только поисковая подсказка; никогда не raw_text |
| get_node(node_id, content_hash).raw_text | raw_text | Полный узел требуемой версии; единственный текст для Included |
| get_node metadata | source_path, heading_path, coordinates, parent_node_id, index_generation, document_hash | Источник истины для верификации узла |

Реестр отображения известных match_reasons:

| match_reason Исполнителя 2 | Нормализованный сигнал |
|---|---|
| entity_exact, entity_alias_exact | entity_exact=true |
| filename_exact, document_name_exact | document_name_match=true |
| heading_exact | heading_match=true |
| body_exact, exact_phrase, exact_number | exact_terms=true |
| body_morphology | morphology=true |
| facet_match, facet_exact | facet_match=true |

Неизвестные причины сохраняются в \`unmapped_match_reasons\` и диагностике \`unknown_match_reason\`; они не получают придуманного веса. Если Исполнитель 2 не возвращает facet_match, поле отсутствует/неизвестно, а не выставляется в false. Совпадение фасета из самого факта передачи facets в запросе не выводится.

### 4.3. Совместимость с исходным входным примером

Если другой поисковый адаптер поставляет \`score\` без структуры E2 relevance, он обязан передать \`score_direction = asc|desc\`. Context Builder не угадывает направление. В таком варианте первыми применяются доступные отдельные сигналы, затем score с явно указанным направлением. Если есть \`relevance.tier\` и \`relevance.bm25\`, они являются авторитетным ранжированием E2; score не должен их переопределять.

Поля из исходного задания (\`score\`, \`match_type\`, \`raw_text\`) остаются поддерживаемым внешним форматом, но для подключения Исполнителя 2 используется relevance mapping, а не неявное предположение, что любой score сортируется по убыванию.

### 4.4. Поля сохранности и зависимости

- \`preservation=required\` — обязательная группа, даже если \`required_with\` пуст.
- \`required_with\` — Node ID узлов, обязательных вместе с данным кандидатом.
- \`parent_node_id\` — родитель, записанный индексатором.
- \`parent_context_required=true\` — родитель обязан быть включён вместе с ребёнком.
- \`index_generation\` и \`document_hash\` — метки согласованного снимка.

Неизвестные дополнительные поля не должны молча превращаться в обязательную семантику. Источник и значения preservation/dependency metadata согласуются с Исполнителем 1 и передаются через импорт/индекс Исполнителя 2.

## 5. Ранжирование и отбор

### 5.1. Детерминированное ранжирование

Для выдачи Исполнителя 2 используется его документированный порядок:
1. relevance.tier по возрастанию (tier 1 — наивысший приоритет);
2. BM25 по возрастанию внутри одного tier;
3. исходный порядок поисковика как стабильный tie-breaker, если tier и BM25 равны.

Не инвертировать BM25 и не сортировать его по убыванию. Внутри E2 не пересчитывается новая формула score. Сигналы match_reasons показываются в provenance и используются для прозрачного покрытия focus, но не должны менять первичное ранжирование вопреки tier.

Для другого SearchAdapter без E2 relevance применяются приоритеты SFRA: точная сущность; имя документа; заголовок; точные термины; морфология; фасет; score с обязательным явным score_direction. Веса и смысловой reranking не вводятся.

### 5.2. Детерминированная обработка обязательных зависимостей

До заполнения бюджета строится граф зависимостей.

1. Проверить каждую запись и хеш, затем дедуплицировать только идентичные пары node_id + content_hash.
2. Создать вершины из всех проверенных SearchBatch candidates.
3. Для каждого узла добавить ребро к каждому Node ID из required_with.
4. При parent_context_required=true добавить ребро к parent_node_id.
5. Для недостающих вершин вызвать SourceReader.resolve_node(node_id, expected_hash=None, snapshot=current_snapshot). Добавленная запись должна быть полным проверенным узлом из того же index_generation. Для родителя из того же документа должен совпасть document_hash.
6. Если зависимый Node ID не может быть разрешён или найденная версия относится к другой генерации/документу, зафиксировать unresolved_required_dependency. Узел-владелец и вся зависящая от него группа не могут быть включены без этого участника.
7. Вычислить strongly connected components (SCC), чтобы обнаружить циклы. Каждая SCC рассматривается как атом, а затем компоненты объединяются в неделимые dependency groups по транзитивным связям. Цикл сворачивается детерминированно и получает warning \`required_dependency_cycle_collapsed\`; повторный обход не зацикливается.
8. Группа считается обязательной, если любой её участник имеет preservation=required или группа была необходима для удовлетворения обязательной зависимости другого обязательного узла.
9. Обязательные группы сортируются по лучшему relevance участника; внутри группы сохраняется детерминированный порядок: исходный кандидат, затем dependency, с сортировкой по Node ID.
10. Каждая обязательная группа целиком включается до обычных результатов, если она помещается. Иначе целиком Deferred с \`required_group_budget_limit\`. При unresolved dependency группа целиком Deferred с \`unresolved_required_dependency\`, не зависимо от того, поместилась бы она по размеру или нет.

Это покрывает standalone preservation=required, цепочки, родительские контексты, отсутствующих участников и циклы. Нельзя сначала заполнять бюджет обычными узлами, а затем пытаться найти место обязательным.

### 5.3. Выбор кандидатов после обязательных групп

После обязательных групп:

1. Для каждого focus по порядку выбрать лучший dependency group, содержащий хотя бы один подходящий узел и ещё не учтённый в Included/Known.
2. Если группа не помещается, отложить её целиком; не включать часть для формального покрытия аспекта.
3. Добавлять остальные группы/узлы в порядке ранжирования, не вытесняя уже включённое.
4. Все не включённые проверенные результаты сохраняются в Deferred с причиной.
5. Формировать Coverage, Parallel Sources, Known, Version Changes, Statistics и Diagnostics.

Если focus не передан, автоматические аспекты не создаются: Coverage=[], ratios=null.

### 5.4. Единое правило статуса Context Pack

Статус вычисляется строго по следующему приоритету:

1. \`integrity_warning\` — есть ошибка целостности: несовпадение SHA-256, конфликт версий одного Node ID, смешение поколений/документных снимков либо другая ошибка, из-за которой материал нельзя считать проверенным.
2. \`empty\` — SearchBatch.complete=true и после проверки целостности не осталось пригодных кандидатов.
3. \`budget_limited\` — хотя бы один проверенный кандидат или неделимая группа отложены именно из-за бюджета.
4. \`partial\` — бюджет не ограничил выдачу, но поиск неполон, есть unresolved dependency либо аспект имеет deferred/not_found_in_retrieval.
5. \`complete\` — поиск завершён, ошибки целостности отсутствуют, бюджетных отложений и непокрытых аспектов нет.

Если одновременно присутствуют бюджетное ограничение и иная неполнота, статус будет budget_limited, а остальные причины останутся в Coverage/Diagnostics. Цикл, успешно свёрнутый в атомарную группу, сам по себе не меняет статус на integrity_warning; отсутствующая зависимость — partial.

## 6. Статусы Coverage

Каждый focus аспект получает один из статусов:

- \`found\` — существует хотя бы один соответствующий узел в Included или точная пара Node ID + Content Hash уже известна клиенту через Known;
- \`deferred\` — подходящий узел найден и отложен, но нет ни одного подходящего узла в Included или Known;
- \`not_found_in_retrieval\` — подходящий кандидат не обнаружен среди обработанных результатов.

\`found\` через Known не означает, что сервер доставил этот материал в текущем ответе. Поэтому статусы используются для доступности материала, но не подменяют метрику Included.

У каждого аспекта возвращаются included_node_ids, known_node_ids, deferred_node_ids, basis и diagnostic_note.

### 6.1. Точное сопоставление focus

Сначала используется \`matched_focus_ids\` от поискового адаптера. Если соответствующий ID присутствует, узел подходит к аспекту.

Если ID отсутствует, допустим fallback только по явно переданным данным:
- entities сопоставляются с matched_entities или подтверждёнными entity metadata кандидата;
- facets сопоставляются с matched_facets или явным signals.facet_match, но не из факта передачи facets в запросе;
- terms сопоставляются по точному вхождению после Unicode NFC + casefold в basename/source_path, heading_path или raw_text; морфологическое или смысловое сходство не используется.

Для каждого непустого поля-категории (entities, facets, terms) достаточно совпадения любого элемента внутри данной категории. Далее:
- match_mode=any: достаточно совпадения хотя бы одной непустой категории;
- match_mode=all: должны совпасть все непустые категории;
- пустые категории игнорируются;
- если все три категории пусты, сопоставление выполняется только по matched_focus_ids или точной фразе label.

Для короткой формы focus (строка) локальный aspect_id формируется как focus_001, focus_002 и т.д. по порядку запроса. Для повторного использования идентификаторов между запросами клиенту рекомендуется объект focus с явным id.

basis фиксирует adapter_match, explicit_entities_facets_terms или exact_phrase_fallback. Это основание сопоставления, а не смысловое доказательство.

### 6.2. Формулы Coverage

- \`coverage_available_ratio\` = число аспектов со статусом found или deferred / общее число аспектов.
- \`coverage_included_ratio\` = число аспектов, у которых массив included_node_ids непустой / общее число аспектов.
- \`known_node_ids\` не увеличивают coverage_included_ratio.
- \`deferred_node_ids\` увеличивают coverage_available_ratio, но не coverage_included_ratio.
- \`not_found_aspect_count\` = число аспектов со статусом not_found_in_retrieval.

Пример Known-only: у аспекта один matching Node ID присутствует в Known, included_node_ids=[], known_node_ids=[...], статус found. Тогда coverage_available_ratio=1.0, coverage_included_ratio=0.0. Это намеренно показывает, что источник клиенту уже известен, но не был передан в текущем Included.

Если focus пуст, обе доли равны null. Если search_complete=false, not_found_in_retrieval относится только к уже обработанным кандидатам и никогда не означает отсутствие информации во Vault.

## 7. Бюджет токенов

### 7.1. TokenCounter

Интерфейс:

    count(text: str) -> TokenCount

TokenCount содержит:
- value;
- tokenizer_name;
- tokenizer_version;
- encoding;
- exact_for_encoding;
- exact_for_client_model.

Предлагаемая реализация MVP: tiktoken 0.14.0, начальная кодировка o200k_base, задаваемая конфигурацией. Если MCP-клиент использует модель с другой токенизацией, encoding переключается конфигурацией и точность относительно неизвестной модели не заявляется.

Не использовать len(text)/3 как точный токенизатор. Если поддерживаемая кодировка недоступна, сборка должна завершаться явной ошибкой конфигурации или использовать отдельный оценщик, который маркирует результат как estimate и сообщает метод/погрешность. Молчаливое переключение на неподтверждённую формулу запрещено.

### 7.2. Что считается в budget_tokens

В budget_tokens включаются:
- оригинальный raw_text;
- provenance-метаданные Included;
- обязательная структура контекстной части Included/Coverage.

Отложенные записи, Known, Parallel Sources и diagnostics не вытесняют оригинальные фрагменты из Included. Их объём учитывается отдельно как response_tokens_estimated. Таким образом Statistics различает tokens_used и полный размер ответа.

### 7.3. Неприкосновенность текста

- raw_text никогда не обрезается;
- строка/предложение/список не удаляются из узла;
- при нехватке места весь узел (или required_with-группа) откладывается;
- при блокировке required-группы пакет помечается partial и получает предупреждение required_material_deferred;
- Deferred содержит координаты, hash, оценку размера и причину.

Возможные причины Deferred:
- budget_limit;
- required_group_budget_limit;
- lower_priority_budget_limit;
- unresolved_required_dependency;
- known_version_not_repeated не является Deferred и отражается отдельно.

## 8. Дедупликация и параллельные источники

### 8.1. Дедупликация

Безопасное правило: совпали node_id + content_hash — одна и та же версия узла; повторную запись можно свернуть, объединяя поисковые сигналы и matched_focus_ids.

Одинаковый текст при разных Node ID или разных координатах не считается дублем автоматически. Разные source_path всегда сохраняются отдельно.

Если один Node ID приходит с двумя Content Hash в одном SearchBatch, результат помечается version_conflict. Выбирать «последний» или «лучший» хеш нельзя.

### 8.2. Parallel Sources

Группа создаётся по одному из явных оснований:
- одинаковый basename, разные source_path;
- общий overlap_group_id, переданный поисковым адаптером;
- явный overlap_hint поискового движка.

Для каждого источника указываются Node ID, путь, hash и signal. Текст разных источников не объединяется. Описание характера пересечения должно быть нейтральным, например «совпадает имя файла, пути различаются». Ни «противоречие», ни «канонический источник» автоматически не присваиваются.

## 9. known и версии

Вход known — список пар node_id + content_hash.

- Совпала пара: не включать raw_text повторно; добавить компактную запись в Known.
- Node ID совпал, hash отличается: текущий результат не подавлять; включить новую версию по бюджету и добавить Version Changes с old_hash/new_hash.
- Node ID не найден в результатах: не генерировать вывод об изменении. Неизвестность не равна устареванию.
- В одном ответе конфликтуют две версии одного ID: сообщить integrity diagnostic, не подменять версии.

Сервер не ведёт собственный реестр known между вызовами и не помнит результаты прошлого диалога.

## 10. Контракт MCP: search_vault

Единственный обязательный параметр — query. Дополнительные:
- task — описание исходной задачи для трассировки, не для автодекомпозиции;
- entities;
- facets;
- budget_tokens;
- known;
- zones;
- focus.

search_vault выполняет один вызов SearchAdapter, затем ContextBuilder.build и возвращает структурированный ContextPack:
- Included;
- Coverage;
- Deferred;
- Parallel Sources;
- Known;
- Version Changes;
- Statistics;
- Diagnostics.

Known и Version Changes — дополнительные технические секции, необходимые для stateless-протокола; они не заменяют обязательные блоки.

### Пример входа

    {
      "query": "Особенности речи Генриха Фауста",
      "entities": ["Генрих Фауст"],
      "facets": ["VOICE"],
      "budget_tokens": 3000,
      "known": [],
      "focus": [
        {
          "id": "voice_style",
          "label": "Общий стиль речи",
          "entities": ["Генрих Фауст"],
          "facets": ["VOICE"],
          "terms": ["общий стиль речи"],
          "match_mode": "any"
        },
        "Типичные фразы"
      ]
    }

### Пустой ответ

Пустой SearchBatch — корректный ответ со статусом empty, пустыми Included/Deferred/Parallel Sources, нулевыми счётчиками и focus со статусом not_found_in_retrieval. Это не ошибка инструмента.

## 11. Контракт MCP: read_source

Вход:
- node_id;
- expected_hash;
- scope ∈ {node, parent, neighbors, document};
- budget_tokens — необязательный целый положительный лимит.

expected_hash всегда относится к запрошенному целевому Node ID, включая scope=document. Сначала разрешается и проверяется точная версия target. Затем все дополнительные фрагменты читаются из того же согласованного snapshot.

### 11.1. Обязательная проверка хешей

Для каждого фрагмента SourceReadResult:
1. Получить exact raw_text из исходного источника/снимка.
2. Вычислить SHA-256 по UTF-8 байтам raw_text без NFC/NFKC, trim, нормализации CRLF/LF, удаления пробелов или иных преобразований.
3. Сформировать строку \`sha256:<64 lowercase hex>\`.
4. Сравнить её с content_hash фрагмента.
5. Только при совпадении разрешить выдачу.

Для target дополнительно сравнить content_hash с expected_hash. Несовпадение приводит к status=stale и fragments=[]. Несовпадение хеша любого дополнительного фрагмента приводит к integrity_error и fragments=[]. Ни один частично проверенный пакет не выдаётся.

### 11.2. Единый snapshot для четырёх scope

У target_source и каждого fragment должны совпадать:
- index_generation;
- source_path и document_hash для всех фрагментов одного документа;
- snapshot identity, если используемый источник её предоставляет.

Для scope parent и neighbors все элементы должны быть получены из того же document_hash и index_generation, что target. Для scope=document полный текст файла должен иметь SHA-256, совпадающий с document_hash того же snapshot; target должен принадлежать этому документу в том же index_generation.

Если документ или индекс изменился между получением target и дополнительных частей, не пытаться смешивать данные: вернуть integrity_error, fragments=[] и diagnostic snapshot_generation_mismatch или document_hash_mismatch.

### 11.3. Формат и режимы чтения

SourceReadResult содержит:
- status: ok / stale / not_found / budget_exceeded / source_unavailable / integrity_error;
- requested;
- target_source с content_hash, document_hash и index_generation;
- fragments — массив оригинальных срезов, каждый со своей ролью, координатами и content_hash;
- token_accounting;
- trust_label=untrusted_source_data;
- diagnostics.

Режимы:
- node: один target node;
- parent: target и прямой parent context раздельными фрагментами;
- neighbors: target и соседние структурные элементы, определённые Indexer;
- document: полный исходный Markdown-документ.

MCP адаптер не должен самостоятельно резать файл или реконструировать структуру. Для parent/neighbor используются node hierarchy и координаты Indexer, для document — оригинальный файл. Если upstream API не предоставляет соответствующую capability, status=source_unavailable и fragments=[]. get_node Исполнителя 2 достаточен для exact node, но сам по себе не обещает соседей или документ.

### 11.4. Ошибки и бюджет

- неизвестный Node ID: status=not_found, fragments=[];
- target найден, но expected_hash отличается: status=stale, actual_hash и current locator в diagnostics, fragments=[];
- нарушена целостность любого фрагмента или snapshot смешан: status=integrity_error, fragments=[];
- запрошенный scope целиком превышает budget_tokens: status=budget_exceeded, fragments=[].

Никакого усечения текста, частичной выдачи или подмены похожим Node ID. Клиент повторяет запрос с другим scope или увеличенным бюджетом.

## 12. Протокол хеширования и совместимость

### 12.1. Content Hash

Предлагаемое и принимаемое как контракт Этапа А соглашение:
- алгоритм SHA-256;
- префикс sha256:;
- хешируются точные UTF-8 байты raw_text;
- никаких Unicode normalization, trim, замены переводов строк, схлопывания пробелов, удаления Markdown-разметки или иных преобразований до хеширования;
- формат hex lowercase; при сравнении допускается lowercase-normalization самой hex-строки после проверки формата.

Контроль обязателен как минимум на двух границах:
1. SearchAdapter после получения полного raw_text из get_node и до передачи кандидата в Context Builder.
2. Context Builder непосредственно перед сборкой Context Pack — повторная защитная проверка кандидата, чтобы доверять не только адаптеру.
3. SourceReader для каждого фрагмента read_source до ответа MCP.

Если SHA-256(raw_text.encode("utf-8")) не совпал с указанным content_hash:
- candidate отвергается и не попадает ни в Included, ни в обычный Deferred;
- появляется Diagnostic content_hash_mismatch с expected/actual;
- status Context Pack становится integrity_warning;
- SourceReader возвращает integrity_error с пустым fragments.

Это правило действует и для зависимостей, которые адаптер разрешил через get_node.

### 12.2. Snapshot и защита от смешения поколений

Каждый нормализованный кандидат и результат get_node должен по возможности содержать index_generation и document_hash. Для одного поискового batch адаптер фиксирует snapshot generation. Dependency resolve и дочитывание выполняются на той же generation.

Для одного source_path все связанные узлы обязаны иметь одинаковый document_hash в рамках одного snapshot. Для разных source_path document_hash закономерно различаются, но index_generation должна оставаться общей.

SourceReader не может проверять target в одной generation, а потом читать parent/neighbor/document из другой. При любом несовпадении выдача отменяется целиком. Если API Исполнителя 2 пока не предоставляет исторический read на определённую generation, adapter обязан fail closed (source_unavailable/integrity_error), а не получить текущую версию под видом старой.

### 12.3. Контракт с Исполнителем 2: явный адаптер, без переписывания его модуля

Проектное решение Исполнителя 2 (Этап А) фиксирует:
- \`engine.search(query, entities=None, limit=20, include_history=False)\`;
- \`engine.get_node(node_id, content_hash=None)\`;
- search hit: \`excerpt\`, \`match_type\`, \`match_reasons\`, \`relevance.tier\`, \`relevance.bm25\`, entity metadata;
- приоритет tier 1..6, меньшее значение — более высокий приоритет;
- BM25 — вторичный показатель внутри tier. Для SQLite FTS5 меньшее значение считается лучшим, поэтому сортировка ascending.

Таблица нормализации:

| E2 | SearchAdapter Executor 3 | Примечание |
|---|---|---|
| search hit node_id | node_id | Не генерировать заново |
| source_path | source_path | Сохранить полный путь, не использовать basename как identity |
| heading_path | heading_path | Передать без потери уровней |
| line_start/end | line_start/end | Согласовать базу/границы координат |
| content_hash | content_hash | Должен совпасть с SHA-256 полного get_node.raw_text |
| excerpt | match_excerpt | Не передавать как original text |
| get_node(...).raw_text | raw_text | Полный оригинальный узел точной версии |
| relevance.tier | relevance.tier | Ascending; tier=1 выше tier=2 |
| relevance.bm25 | relevance.bm25 | Ascending внутри одного tier |
| match_reasons | match_reasons/signals | Только документированное отображение |
| match_type | match_type | Передавать буквально |
| parent_node_id | parent_node_id | Вход в граф обязательных зависимостей |

Адаптер не требует добавления в Executor 2 полей, которые он не обещал. Missing facet signal остаётся unknown; нельзя синтезировать facet_match из запроса. Якщо E2 возвращает только excerpt, адаптер делает get_node по точной паре и получает полный raw_text. Если get_node не вернул полный текст или версию, candidate отклоняется.

### 12.4. Контракт SourceReader с Исполнителями 1 и 2

- Для exact node, метаданных версии и parent_node_id используется \`engine.get_node(node_id, content_hash)\` Исполнителя 2.
- Для parent можно получить parent_node_id из exact node и затем разрешить parent через get_node, при условии общей generation/document_hash.
- Для neighbors требуется информация о соседстве из структурного дерева Indexer Исполнителя 1 либо эквивалентная read-only операция.
- Для document требуется оригинальный source snapshot/file read от Исполнителя 1 или согласованный файловый адаптер, привязанный к document_hash.
- Если Исполнитель 1/2 реализует другие сигнатуры, меняется только адаптер. Нельзя заставлять соседний компонент реализовывать чужой интерфейс без отдельного согласования.

### 12.5. Открытые интеграционные подтверждения

До реализации необходимо подтвердить на реальном коде:
1. get_node возвращает полный raw_text и exact version по content_hash.
2. Возвращаются index_generation и document_hash либо эквивалентный immutable snapshot token.
3. Доступны данные для parent, neighbors и document.
4. Соглашение хеширования/координат Исполнителя 1 совпадает с этим контрактом.
5. match_reasons Исполнителя 2 соответствует документированному справочнику. Неизвестные причины сохраняются, но не получают ранга по догадке.
6. Поисковый API предоставляет pagination либо полный result list в пределах configured limit.

Это точки интеграционного подтверждения. Спецификация не объявляет совместимость подтверждённой до появления работающих модулей и контрактных тестов.

## 13. Технологический стек реализации

Предлагаемая база:
- Python 3.11+;
- официальный MCP Python SDK, пакет mcp 2.3.0;
- tiktoken 0.14.0 для настраиваемого подсчёта токенов;
- стандартные dataclasses/typing либо Pydantic-модели, только если они упрощают валидацию входа;
- pytest для модульных и интеграционных тестов на следующем этапе.

Почему так:
- SDK mcp является официальной реализацией MCP и поддерживает stdio, Streamable HTTP и прочие стандартные транспорты;
- для локального MVP достаточно stdio, без отдельного HTTP-сервера и внешнего брокера;
- Python 3.11+ соответствует требованиям актуальной ветки SDK;
- tiktoken — реальный BPE-токенизатор, а не оценка по длине строки;
- поисковая и источниковая инфраструктура подключается через Protocol, поэтому тестовые fake-адаптеры не требуют запуска настоящих компонентов.

Версии зафиксированы как проектная отправная точка на 16.11.2026. Перед реализацией версии должны быть проверены в lock-файле. Если библиотека несовместима с выбранной средой, изменение фиксируется отдельным решением, не маскируется.

## 14. Stateless и структура ответа

Каждый вызов полностью определяется входным JSON и текущим snapshot поискового индекса/источника. Сервер не хранит:
- conversation_id → историю фрагментов;
- сведения о текущем окне контекста;
- автоматически обновляемый known;
- результаты предыдущего поиска.

Если клиент хочет избежать повторной передачи, он отправляет known повторно. Контекстный пакет не кэшируется как диалоговая память.

## 15. Критерии проверки Этапа А

Этап А принимается, если:
- описаны отдельные SearchAdapter и SourceReader;
- зафиксирован внешний контракт двух MCP-инструментов;
- определено внутреннее представление кандидата и Context Pack;
- определены статусы Coverage и ограничения их трактовки;
- бюджетирование не подразумевает обрезание исходных узлов;
- определено поведение для обязательных правил/зависимостей, которые не помещаются;
- описана безопасная дедупликация;
- параллельные документы сохраняются и не арбитрируются;
- known не требует серверной памяти;
- все четыре scope read_source описаны;
- устаревший hash приводит к stale без подмены источника;
- исходный текст помечен как недоверенные данные, но не модифицируется;
- есть примеры JSON и JSON Schema;
- перечислены точки согласования с Исполнителями 1 и 2.

## 16. Сценарии повторной проверки Этапа А

Следующие сценарии передаются как тест-кейсы для следующего этапа; исполняемый код на Этапе А не создаётся.

| ID | Входная ситуация | Ожидаемое поведение |
|---|---|---|
| A-01 Known-only | Аспект имеет подходящий узел только в known, raw_text не передаётся | Coverage status=found; coverage_available_ratio=1.0; coverage_included_ratio=0.0 |
| A-02 Required singleton | preservation=required, required_with=[] | Узел становится обязательной singleton-группой и обрабатывается до обычного ранжирования |
| A-03 Required chain | A required_with B, B required_with C | Транзитивная группа A+B+C включается целиком или целиком Deferred |
| A-04 Parent absent in batch | A.parent_context_required=true, parent_node_id=P, P отсутствует в SearchBatch | resolve_node(P) в том же snapshot; при успехе P включается как required_parent_context, иначе A+его группа Deferred |
| A-05 Required group exceeds budget | A+B неделимая обязательная группа больше бюджета | Ни A, ни B не включаются; оба Deferred reason=required_group_budget_limit; status=budget_limited |
| A-06 Missing dependency | A.required_with=[M], M нельзя разрешить | A/вся группа Deferred reason=unresolved_required_dependency; Diagnostic с M; status=partial |
| A-07 Dependency cycle | A→B→A | SCC сворачивается в одну группу; цикл не вызывает бесконечный обход; diagnostic required_dependency_cycle_collapsed |
| A-08 SearchBatch hash mismatch | SHA-256(raw_text) != content_hash | Кандидат не Included и не ordinary Deferred; diagnostic content_hash_mismatch; status=integrity_warning |
| A-09 read_source hash mismatch | Один из fragments имеет неверный content_hash | status=integrity_error; fragments=[] |
| A-10 Mixed index generations | target index_generation=7, parent/neighbor generation=8 | Выдача отменяется целиком; integrity_error; fragments=[] |
| A-11 Different document hash | Фрагменты одного source_path имеют разные document_hash | Выдача отменяется целиком; integrity_error; fragments=[] |
| A-12 Stale node | Node ID есть, expected_hash не равен current version | status=stale; fragments=[]; actual_hash и locator в diagnostics |
| A-13 Incomplete retrieval | SearchBatch.complete=false, аспект не обнаружен среди проверенных кандидатов | aspect=not_found_in_retrieval; status=partial; формулировка ограничена обработанной выдачей |
| A-14 Budget deferral | Проверенный необязательный candidate не помещается | Он остаётся в Deferred; status=budget_limited; raw_text не обрезается |
| A-15 Executor 2 excerpt | search hit содержит excerpt, get_node возвращает полный raw_text | В Included попадает только полный проверенный raw_text; excerpt остаётся match_excerpt |
| A-16 Executor 2 get_node missing | get_node не возвращает текст указанной версии | Candidate отвергается; excerpt не используется как замена; diagnostic exact_node_unavailable |

Дополнительные проверки:
- tier сортируется по возрастанию;
- bm25 сортируется по возрастанию внутри tier;
- неизвестный match_reason не получает веса;
- match_mode=all требует совпадения каждой непустой категории, а не каждого отдельного значения внутри категории;
- different source_path никогда не сливаются дедупликацией;
- недоверенный исходный текст передаётся без изменений.
