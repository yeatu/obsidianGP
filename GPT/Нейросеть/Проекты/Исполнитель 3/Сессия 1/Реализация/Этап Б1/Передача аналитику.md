# Передача аналитику — Этап Б1: ядро Context Builder

**Статус:** реализация ядра опубликована в отдельной ветке; unit-тесты проходят в GitHub Actions.  
**Границы:** только transport-independent core. GitHub Issue worker, recovery и интеграционные адаптеры не входят в Б1.

## 1. Что реализовано

Пакет `sfra_context_builder` находится в `src/sfra_context_builder/` и включает:

- типизированные модели SearchRequest, SearchBatch, RetrievalCandidate, SnapshotRef;
- строгую проверку и нормализацию входных структур;
- SHA-256 точных UTF-8 байтов `raw_text`, без нормализации переносов, Unicode или пробелов;
- дедупликацию по паре Node ID + Content Hash, объединение search metadata; конфликтующие версии одного Node ID исключаются с `version_conflict`;
- детерминированное ранжирование E2 tier/BM25 по возрастанию;
- точный NFC + casefold matching для focus, с поддержкой `any` / `all`, без морфологического или смыслового вывода;
- построение required dependency groups, рекурсивное разрешение отсутствующих узлов через внедряемый resolver, SCC для циклов и атомарное включение/отложение;
- Known, Version Changes, Coverage и Parallel Sources без склейки параллельных документов;
- бюджетирование сериализованной структуры Included/Coverage и оригинальных фрагментов; узлы и required-группы не усекаются;
- Context Pack со статусами complete / partial / empty / budget_limited / integrity_warning и проверкой вложенной структуры;
- TokenCounter на `tiktoken==0.14.0`, encoding по умолчанию `o200k_base`; fallback на длину строки отсутствует.

## 2. Контрактные особенности

- `SnapshotRef` фиксирует `vault_commit_sha`, `sidecar_commit_sha` и SHA-256 manifest. Resolver получает этот snapshot в каждом вызове; рекурсивные зависимости не должны переключаться на текущую ветку или поколение.
- `documents.generation` сравнивается только для узлов одного `source_path`. Междокументная идентичность определяется закреплённым snapshot.
- `document_hash=null` не подменяется Node Content Hash. Ограничения read_source scope остаются в контракте Этапа А.
- `coverage_available_ratio` считает found/deferred; `coverage_included_ratio` считает только аспекты с Included. Known не считается текущей доставкой.
- `response_tokens_estimated` отдельно оценивает полный сериализованный Context Pack; `tokens_used` относится к Included + Coverage.

## 3. API ядра

```python
from sfra_context_builder import ContextBuilder, TiktokenCounter

builder = ContextBuilder(token_counter=TiktokenCounter("o200k_base"))
context_pack = builder.build(search_request, search_batch)
```

Для разрешения обязательных зависимостей передаётся объект с методом `resolve_node(node_id, snapshot)`. Если resolver подключён, snapshot обязателен. Само ядро не читает GitHub, SQLite, Vault или E2 runtime.

## 4. Тесты

Тесты покрывают валидацию, exact UTF-8 hashing, dedup/conflicting versions, ранжирование, required dependency chains/cycles, pinned snapshot, budget atomicity, focus any/all, Known-only Coverage, Version Changes, параллельные источники, truncated search и production TokenCounter.

CI workflow: `.github/workflows/sfra-context-builder-b1-tests.yml`.  
Команда локального запуска:

```bash
python -m pip install -e ".[test]"
python -m pytest -q
```

Подтверждённый Actions run на текущем ядре до последнего TokenCounter regression test: [43991195764](https://github.com/yeatu/obsidianGP/actions/runs/43991195764), 38 passed. Итоговый CI для этой ревизии указан в PR после выполнения теста TokenCounter.

## 5. Что намеренно не реализовано

- E2 SearchAdapter и подключение к фактической SQLite E1;
- SourceReader/read_source и чтение scope parent/neighbors/document;
- GitHub Issue parser/renderer/status store;
- reusable Issue worker, recovery sweep и retry orchestration;
- MCP adapter;
- end-to-end search_vault → Context Pack → read_source на реальном Vault.

Это отдельные последующие этапы. Аналитику передаётся только ядро с unit-тестами, без заявления об интеграционной готовности.
