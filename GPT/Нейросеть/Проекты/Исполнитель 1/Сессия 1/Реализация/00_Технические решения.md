## 2. Markdown-парсер

Выбран **markdown-it-py 4.3.0** с включённым правилом таблиц.

Причины:

1. Возвращает структурные токены Markdown, а не только HTML.
2. У блочных токенов есть source map вида `[line_begin, line_end)`, пригодный для восстановления исходного фрагмента по строкам.
3. Поддерживает CommonMark и включаемые расширения. Таблицы в CommonMark выключены по умолчанию, поэтому правило таблиц будет включено явно.
4. Позволяет анализировать дочерние inline-токены ссылок, не переписывая исходный Markdown.
5. Не требует отдельного сервиса или тяжёлой инфраструктуры.

AST используется исключительно для определения типа блока, вложенности и границ. Для выдачи текста AST не сериализуется.

### Obsidian Callout

Callout синтаксически является разновидностью blockquote. Парсер увидит blockquote, а индексатор дополнительно проверит исходную строку на шаблон `> [!TYPE]` и присвоит блоку `node_type=callout`. Всё содержимое Callout останется одной неделимой структурной единицей на первом уровне.

### Markdown-ссылки

Ссылки анализируются парсером как inline-токены, но не превращаются в самостоятельные индексные узлы. Они сохраняются внутри точного исходного текста содержащего их абзаца, списка или Callout. Это не поисковый этап и не реестр ссылок.

## 3. Система координат

Для каждого узла сохраняются:

- `line_start`: первая строка, нумерация с 1;
- `line_end`: последняя строка включительно;
- `char_start`, `char_end`: смещения Python-строки в Unicode code points, диапазон полуоткрытый `[start, end)`;
- `byte_start`, `byte_end`: смещения UTF-8 в байтах, диапазон полуоткрытый;
- `raw_text`: исходный срез `source[char_start:char_end]`.

Парсер предоставляет построчные границы. Символьные позиции вычисляются накоплением длин исходных строк, байтовые — кодированием префикса в UTF-8. Файл читается с `newline=""`, чтобы не нормализовать CRLF/LF. Хеш считается от UTF-8-представления точного среза.

## 4. Модель сегментации

Индекс строится как `Document → Structural Node → Passage`.

### Документы с заголовками

Заголовок создаёт узел типа `heading`. Узел охватывает заголовок и весь его раздел до следующего заголовка того же или более высокого уровня. Вложенные заголовки становятся дочерними узлами.

Узлы секций намеренно могут иметь перекрывающиеся диапазоны: родительская секция покрывает всё поддерево, а дочерний узел адресует более узкий участок. Это нужно для двух режимов извлечения — целиком раздел и конкретный вложенный фрагмент.

Абзацы, списки, цитаты, Callout, таблицы, кодовые блоки и прочие блочные конструкции создаются как дочерние узлы ближайшей активной секции.

### Документы без заголовков

Структурными узлами становятся самостоятельные блочные конструкции. Короткие соседние абзацы не объединяются автоматически в этой версии: отдельные точные границы проще проверять, а объединение может скрыть источник ошибки. Объединение можно добавить позже по результатам эталонных тестов.

### Вложенные списки

Список образует узел `list`. Каждый пункт образует дочерний `list_item`. Вложенный пункт становится дочерним узлом ближайшего родительского пункта. Диапазон родительского пункта включает его поддерево, поэтому контекст условия не теряется при извлечении ветви.

### Таблицы, цитаты и код

Таблица, blockquote/Callout и fenced code block индексируются цельным блоком. Они не разрезаются по произвольным символам или строкам. Если безопасного разделения крупного узла по дочерним структурным узлам нет, он сохраняется целиком и получает предупреждение о превышении мягкого порога.

### Passage и размер

Оценка токенов будет эвристической (лексические токены/слова), а не точным подсчётом токенизатором конкретной модели. Диапазон 400–900 — мягкий ориентир, не гарантия. Большой узел делится только по границам непосредственных дочерних узлов. Контекст заголовка родителя сохраняется отдельно в Passage. Если безопасных границ нет, Passage не создаётся, а превышение явно отмечается.

## 5. Node ID и Content Hash

- `content_hash` — `sha256:` + SHA-256 точного исходного текста узла.
- `node_id` — отдельный непрозрачный идентификатор `node_<uuid4>`, назначаемый и хранимый в SQLite.

При переиндексации изменённого файла сопоставление выполняется только внутри того же документа и внутри уже сопоставленного родителя:

1. Совпадение типа узла и структурного ключа (заголовок, либо нормализованный короткий ведущий текст блока).
2. Если в группе несколько кандидатов — уникальное совпадение Content Hash может разрешить конкретную пару.
3. ID сохраняется только при однозначном соответствии 1:1.
4. При нескольких равноправных кандидатах новый узел получает новый ID и статус `ambiguous_new`; прежние узлы переводятся в `stale`. Событие сопоставления сохраняет список кандидатов.
5. При изменившемся содержимом узла, но устойчивом уникальном структурном ключе, Node ID сохраняется, а новая версия Content Hash записывается отдельно в `node_versions`.

Не используется глобальный ordinal или позиция строки как единственное основание для сохранения ID: вставка выше по документу иначе могла бы незаметно переназначить адресацию.

## 6. SQLite и синхронизация

Планируются таблицы:

- `documents` — один ряд на путь источника, его SHA-256 и поколение индекса;
- `nodes` — текущие и устаревшие структурные узлы, parent link и исходные координаты;
- `node_versions` — снимки предыдущих версий узлов;
- `node_match_events` — результат сопоставления, в том числе неоднозначные случаи;
- `passages` — точные фрагменты крупных узлов с координатами и контекстом.

FTS5, сущности, фасеты и прочие этапы не создаются.

При повторном обходе Vault SHA-256 файла сравнивается с предыдущим значением. Неизменённые файлы пропускаются. Изменённый файл переиндексируется в одной транзакции SQLite. Исчезнувшие из файловой системы документы и их узлы получают состояние deleted/stale, физически исходные файлы не затрагиваются.

Файлы индекса создаются только в переданном `index_dir`. Реализация будет отклонять `index_dir`, вложенный в Vault, чтобы исключить обратную индексацию производных данных.

## 7. План этапов и контрольные точки

1. **Этап A — анализ и проектные решения.** Этот документ. Отдельный коммит для проверки архитектуры.
2. **Этап B — парсер и модель узлов.** Исходный код, схема SQLite и API извлечения. Тесты структуры и координат.
3. **Этап C — устойчивые ID, версии и инкрементальная индексация.** Тесты повторного запуска, изменения, неоднозначного сопоставления и неизменности Vault.
4. **Этап D — документация и проверка реальных файлов.** README, CLI, полный отчёт с результатами, ограничениями и примерами.

После каждого этапа изменения остаются отдельными коммитами внутри папки реализации. Исходные файлы `ГП/` не изменяются.
