# Этап A — проектирование API адресного чтения структурного узла

Статус: **этап A принят; E1 API реализован в отдельной PR-ветке и передан аналитику на проверку.**  
Рабочая ветка: `executor-1/sfra-indexer-session-1`.  
Базовая версия кода: этапы B/C и Persistence, принятые ранее; SQLite schema v2.

## 1. Цель и границы API

В публичном пакете `sfra_indexer` реализована функция:

```python
get_node_by_id(
    db_path,
    node_id: str,
    expected_hash: str,
    vault_root,
) -> NodeLookupResult
```

Функция возвращает только текущую, однозначно идентифицированную версию структурного узла и только после подтверждения её соответствия актуальному файлу Markdown. Node ID задаёт идентичность узла; Content Hash задаёт конкретное содержимое этой версии.

API не выполняет поиск по содержимому, не выбирает похожие узлы и не возвращает историческую версию вместо текущей. Если передан старый Hash, API сообщает `stale_source` и не возвращает новую версию под старым адресом.

В этой части реализуется только адресное чтение одного Structural Node. У Passage в schema v2 нет собственного Node ID; Passage API в этот контракт не входит. `context_text` Passage не добавляется к `raw_text` структурного узла.

## 2. Фактическая опора на SQLite schema v2

Новая таблица или миграция не требуются. Чтение строится на существующих сущностях:

| Таблица | Поля, используемые API | Назначение |
|---|---|---|
| `schema_info` | `schema_version` | Проверка совместимости: ожидается версия 2 |
| `structural_nodes` | `node_pk`, `document_pk`, `node_id`, `parent_node_pk`, `node_type`, `content_hash`, `status`, `stale_generation`, `line_start/end`, `char_start/end`, `byte_start/end`, `raw_text`, `heading_path_json`, `metadata_json` | Текущая или сохранённая адресация узла |
| `documents` | `document_pk`, `source_path`, `source_sha256`, `source_size_bytes`, `status`, `generation` | Относительный путь, контрольная сумма файла и состояние документа |
| `node_versions` | `node_pk`, `version_no`, `content_hash`, `source_path`, `node_type`, `parent_node_id`, координаты, `raw_text`, `heading_path_json`, `metadata_json`, `warnings_json` | Неизменяемые снимки версий; проверка текущего снимка и сохранение истории |
| `node_match_events` | `event_pk`, `document_pk`, `generation`, `event_type`, `node_id`, `candidate_node_ids_json`, `details_json` | Доказательство результата сопоставления, удаления или неоднозначности |

В `structural_nodes` нет отдельного `source_path`: он получается через `structural_nodes.document_pk → documents.document_pk`. Родительский Node ID при необходимости проверки получается через `parent_node_pk`; историческое значение родителя также записывается в `node_versions.parent_node_id`.

Node ID в существующей реализации имеет формат `node_<UUID4>`. Content Hash имеет формат `sha256:<64 lowercase hex>` и вычисляется как SHA-256 от UTF-8 байтов точного `raw_text`. Хеш документа в `documents.source_sha256` вычисляется от полного UTF-8 содержимого файла.

Координаты schema v2:
- `line_start` / `line_end`: строки с 1, обе границы включены;
- `char_start` / `char_end`: 0-based полуоткрытые смещения в Unicode code points Python;
- `byte_start` / `byte_end`: 0-based полуоткрытые смещения в UTF-8 байтах.

## 3. Типизированный результат

Предлагаемые публичные типы:

```python
from dataclasses import dataclass
from enum import Enum


class NodeLookupStatus(str, Enum):
    OK = "ok"
    STALE_SOURCE = "stale_source"
    DELETED = "deleted"
    AMBIGUOUS = "ambiguous"
    NOT_FOUND = "not_found"
    INVALID_REQUEST = "invalid_request"
    INTEGRITY_ERROR = "integrity_error"


@dataclass(frozen=True)
class NodeRecord:
    node_id: str
    content_hash: str
    source_path: str
    raw_text: str
    line_start: int
    line_end: int
    char_start: int
    char_end: int
    byte_start: int
    byte_end: int


@dataclass(frozen=True)
class NodeLookupResult:
    status: NodeLookupStatus
    node: NodeRecord | None = None
    error_code: str | None = None
    message: str | None = None
```

Контракт результата:
- при `status == ok`: `node` заполнен, `error_code` и `message` отсутствуют;
- при любом другом статусе: `node is None`; содержимое, отрывки, контекст и координаты узла в ответе отсутствуют;
- `to_dict()`/JSON-представление должно явно выдавать `"node": null` для ошибочного результата;
- сообщение ошибки не должно включать `raw_text`, содержимое файла или абсолютный путь к нему.

### Успешный JSON

```json
{
  "status": "ok",
  "node": {
    "node_id": "node_<uuid4>",
    "content_hash": "sha256:<64-hex>",
    "source_path": "folder/note.md",
    "raw_text": "Exact source slice",
    "line_start": 10,
    "line_end": 12,
    "char_start": 120,
    "char_end": 145,
    "byte_start": 140,
    "byte_end": 165
  }
}
```

Пример иллюстрирует форму ответа, а не реальные координаты из Vault.

### Ошибочный JSON

```json
{
  "status": "stale_source",
  "node": null,
  "error": {
    "code": "expected_hash_mismatch",
    "message": "The requested node version is no longer current."
  }
}
```

Для остальных статусов используется та же безопасная оболочка. Нельзя включать скрытое поле с содержимым в ошибочный ответ, исключение, лог API или диагностическую метаинформацию.

## 4. Семантика статусов и приоритет

До выбора любого терминального статуса API выполняет полный **DB-only integrity preflight**: проверяет SQLite/schema/FK и уникальность адресуемой записи, допустимые статусы и внутреннюю согласованность полей, всю релевантную историю `node_match_events`, Hash сохранённого `raw_text`, соответствие текущей строки последней `node_versions` и синтаксическую безопасность `documents.source_path` как относительного POSIX-пути. Эти проверки используют только БД и не открывают исходный Markdown. Любое нарушение даёт `integrity_error` и имеет приоритет над `deleted` и `ambiguous`. Только после успешного DB-only preflight разрешается терминальное состояние документа/узла. Проверки canonical path, symlink, полного Hash файла и координат относительно исходного текста выполняются отдельно и требуют чтения источника; они нужны только для активного однозначного узла.

| Статус | Условие | Содержимое |
|---|---|---|
| `ok` | Узел активен и однозначен; документ активен; текущая версия, Hash, файл и все координаты проверены; `expected_hash` совпадает | Возвращается только точный проверенный фрагмент |
| `stale_source` | Полный Hash найденного исходного файла отличается от `documents.source_sha256`; корректно сформированный `expected_hash` не совпадает с проверенным текущим Content Hash; либо файл активного документа отсутствует в переданном checkout, идентичность которого не подтверждена | Не возвращается |
| `deleted` | `documents.status == 'deleted'` или валидное событие `document_deleted`, если все DB-only integrity checks (включая историю событий, `raw_text`, `node_versions` и синтаксис `source_path`) успешно пройдены; валидное событие `stale` подтверждает удаление отдельного узла после тех же проверок | Не возвращается |
| `ambiguous` | Для документа, не помеченного `deleted`, текущий узел имеет статус `ambiguous` либо старый Node ID зафиксирован как кандидат неоднозначного сопоставления, если все DB-only integrity checks успешно пройдены | Не возвращается |
| `not_found` | После синтаксической валидации Node ID в `structural_nodes` нет такой записи | Не возвращается |
| `invalid_request` | Неверный формат Node ID/Hash или некорректный `vault_root` (например, путь не существует или не является каталогом) | Не возвращается |
| `integrity_error` | DB-only: ошибка SQLite/schema/FK/уникальности; неизвестный статус или внутренне противоречивые поля; неизвестное событие/повреждённый payload; Hash сохранённого `raw_text` не совпадает; текущая строка не совпадает с последней `node_versions`; `documents.source_path` синтаксически небезопасен. При чтении источника: unsafe canonical target/symlink, невозможность безопасного открытия, координаты или срез противоречат исходному файлу | Не возвращается |

Приоритет разрешения статусов:
1. некорректные входные параметры или `vault_root` — `invalid_request`;
2. нарушение целостности SQLite/schema/FK/уникальности либо любого DB-only preflight поля (статусы и поля, история событий и payload, Hash `raw_text`, последняя `node_versions`, синтаксис `source_path`) — `integrity_error`;
3. отсутствие Node ID после проверки общей целостности БД — `not_found`;
4. `documents.status == 'deleted'` или валидное событие `document_deleted` — `deleted`, только если весь DB-only preflight успешно завершён;
5. текущая или исторически зафиксированная неоднозначность узла в документе, не помеченном `deleted`, — `ambiguous`, только если весь DB-only preflight успешно завершён;
6. подтверждённое удаление отдельного узла валидным событием `stale` — `deleted` после DB-only preflight;
7. отсутствие/изменение исходного файла в checkout с неподтверждённой идентичностью либо несовпавший ожидаемый Hash — `stale_source`;
8. нарушение координат/среза относительно уже прочитанного исходного файла — `integrity_error`;
9. только после всех необходимых для активного узла проверок — `ok`.

Таким образом, все ошибки DB-only preflight обнаруживаются до `deleted` или `ambiguous`. Если запись документа помечена `deleted`, но небезопасен её `source_path`, не совпадает Hash `raw_text` или текущая строка расходится с последней `node_versions`, итогом будет `integrity_error`. Если весь DB-only preflight прошёл, `deleted` возвращается без canonical-разрешения пути, открытия или чтения исходного Markdown.

События сопоставления сначала проверяются на известный тип и корректность payload. Неизвестное релевантное событие не пропускается и не считается подтверждением активного состояния: результат — `integrity_error`.

Текущая сигнатура API получает `vault_root`, но не получает доверенный `vault_ref` или `source_commit`. Поэтому отсутствие файла в этом checkout само по себе не доказывает удаление. В рамках текущего контракта оно даёт `stale_source`. Статус `deleted` по фактическому отсутствию файла допустим только после того, как этап D установит доверенную идентичность версии Vault и подтвердит удаление в этой версии; такая интеграция не входит в этап A и не подразумевает изменения schema v2.

Это означает, например, что старый Node ID, отмеченный как кандидат неоднозначного сопоставления, возвращает `ambiguous`, а не обычный `deleted`. Если весь документ помечен удалённым в самой БД, `deleted` имеет приоритет над состоянием его прежних узлов.

## 5. Последовательность проверки

Функция обязана выполнять проверки в следующем порядке. Любая ошибка немедленно завершает обработку без возврата содержимого.

### 1. Формат запроса

- Node ID проверяется по формату `node_<canonical UUID4>`: префикс, каноническая запись UUID, версия UUID 4 и допустимый variant.
- `expected_hash` должен строго соответствовать `sha256:[0-9a-f]{64}`.
- `vault_root` должен быть путём к существующему каталогу.
- Синтаксически неверные параметры возвращают `invalid_request`.

### 2. Поиск Node ID и базовая целостность SQLite

- Открыть только существующую базу в read-only режиме, проверить schema v2.
- Выполнить `PRAGMA integrity_check` и `PRAGMA foreign_key_check`; ошибка SQLite, неверная schema version или нарушение FK — `integrity_error`.
- Найти узел по точному `structural_nodes.node_id`, присоединить строку `documents`.
- Проверить уникальность адресуемой записи; более одной строки для одного Node ID — `integrity_error`, поскольку schema v2 предусматривает уникальный частичный индекс на непустом `node_id`.
- Если запись отсутствует в целой и совместимой БД — `not_found`.
- API использует read-only соединение и транзакцию согласованного чтения.

### 3. Проверка структурных статусов и полей (DB-only)

- Допустимые статусы документа: `active`, `deleted`; допустимые статусы узла: `active`, `ambiguous`, `stale`.
- Для актуального `active` узла ожидается `stale_generation IS NULL`; неизвестные статусы и внутренне противоречивые комбинации полей — `integrity_error`.
- Проверить типы и базовые инварианты сохранённых координат: значения должны быть целыми; char/byte диапазоны неотрицательными и полуоткрытыми (`start <= end`); `line_start >= 1`; для пустого char-диапазона допускается `line_end == line_start - 1`, для непустого — `line_end >= line_start`.
- Эти проверки подтверждают только внутреннюю корректность сохранённых полей. Сопоставление координат с реальным Markdown выполняется позже, только после чтения исходного файла.
- На шаге 3 не выбирается терминальный статус: `documents.status == 'deleted'` только фиксируется как значение БД.

### 4. Полная проверка истории событий сопоставления документа (DB-only)

До любого терминального решения, включая `deleted` и `ambiguous`, загрузить и проверить **всю релевантную историю** `node_match_events` для `document_pk`, а не только последнее событие для запрошенного Node ID.

Известные типы событий, создаваемые текущим кодом:
- текущие/успешные сопоставления: `document_root`, `unique_content_hash`, `unique_heading_key`, `unique_sibling_heading_key`, `unique_sibling_slot`, `new`;
- неоднозначность: `ambiguous`;
- потеря прежней адресации: `stale`, `stale_ambiguous_candidate`;
- удаление документа: `document_deleted`.

Для каждой строки истории:
- `event_type` должен входить в указанный allowlist; неизвестный тип в любой позиции истории даёт `integrity_error`, даже если другие события известны;
- все JSON-поля события, присутствующие в схеме (`candidate_node_ids_json`, `details_json`), должны успешно разбираться; `NULL` допускается только там, где он допустим контрактом соответствующего типа события;
- разобранный payload должен соответствовать форме и типам полей, ожидаемым для этого `event_type` (например, `candidate_node_ids_json` для события неоднозначности должен быть массивом корректных Node ID; некорректная форма/значение дают `integrity_error`);
- проверка выполняется приложением и не зависит от необязательного SQLite JSON1 extension.

Любой неизвестный `event_type`, невалидный JSON или payload, не соответствующий контракту события, завершает запрос с `integrity_error` и `node is None`. Это правило действует при любом статусе документа, включая `deleted`.

После проверки всей истории выбрать последнее относящееся к Node ID событие по `node_match_events.event_pk DESC`, а не только по времени: временные метки могут совпадать.

### 5. DB-only integrity gate до выбора терминального статуса

Этот этап не обращается к файловой системе Vault и обязателен для всех состояний узла, включая `deleted` и `ambiguous`.

**5.1. Проверка сохранённого raw_text и Content Hash**
- Проверить формат `structural_nodes.content_hash`.
- Вычислить `sha256:` + SHA-256 от `structural_nodes.raw_text.encode('utf-8')`.
- Результат должен точно совпасть с `structural_nodes.content_hash`.
- Несовпадение, некорректный Hash или невозможность корректно закодировать сохранённый текст — `integrity_error`, даже если запросный Hash совпадает с повреждённой строкой.

**5.2. Сверка текущей строки с последней node_versions**
- Для `node_pk` должна существовать хотя бы одна версия; выбрать запись с максимальным `version_no`.
- Сравнить текущий снимок с последней версией по `content_hash`, `raw_text`, `source_path`, `node_type`, `parent_node_id`, `heading_path_json`, всем line/char/byte координатам, `content_spans_json`, `metadata_json` и `warnings_json`.
- Для проверки `parent_node_id` использовать текущего родителя из `parent_node_pk`; `source_path` текущей строки сверять с `documents.source_path`.
- Отсутствие последней версии или расхождение любого поля — `integrity_error`.
- История `node_versions` служит аудитом и проверкой согласованности. API не ищет старую версию по `expected_hash` и не возвращает исторический `raw_text`.

**5.3. Синтаксическая безопасность documents.source_path**
- Путь берётся только из `documents.source_path`; он должен быть непустым относительным POSIX-путём, соответствующим формату индексатора `relative_to(vault).as_posix()`.
- Запрещены абсолютные пути, пустые компоненты, `.`, `..`, обратная косая черта, Windows drive/UNC-формы, NUL и любые формы, не соответствующие относительному POSIX-пути.
- Нарушение этого лексического контракта — повреждение записи SQLite и `integrity_error`, не `invalid_request`.
- Это только синтаксическая проверка строки пути. Canonical resolution, symlink containment и безопасное открытие — отдельные проверки файловой системы на шаге 7.

**Все DB-only проверки шагов 2–5 должны завершиться успешно до выбора `deleted`, `ambiguous` или любого другого результата, зависящего от статуса записи.** Ошибки этих проверок имеют приоритет и всегда дают `integrity_error`, `node is None`; исходный Markdown не открывается.

### 6. Разрешение терминального состояния по проверенным DB-записям

Этот шаг выполняется только после успешного DB-only integrity gate:
- если `documents.status == 'deleted'` либо валидная история содержит `document_deleted`, вернуть `deleted` без canonical-разрешения пути, открытия или чтения исходного Markdown-файла;
- для документа со статусом `active`: `structural_nodes.status == 'ambiguous'` — `ambiguous`;
- для документа со статусом `active`: `status == 'stale'` вместе с событием `stale_ambiguous_candidate`, либо Node ID присутствует в списке кандидатов валидного актуального неоднозначного события, — `ambiguous`;
- для документа со статусом `active`: валидное событие `stale` для отдельного узла — `deleted`; событие должно однозначно подтверждать удаление узла индексатором;
- `stale` без события, позволяющего подтвердить удаление или неоднозначность, — `integrity_error`;
- противоречие статуса узла последнему валидному событию удаления/неоднозначности — `integrity_error`.

Старый Node ID не переназначается на новый узел и никогда не выбирается по сходству текста. Для активного узла отсутствие события допустимо только как совместимость с мигрированными записями этапа B.

### 7. Безопасное разрешение source_path относительно canonical Vault root

Лексическая безопасность `documents.source_path` уже проверена на DB-only шаге 5. Здесь выполняются только проверки, требующие файловой системы:
- `vault_root` нормализуется через canonical resolve и должен существовать как каталог; некорректный пользовательский `vault_root` относится к `invalid_request`.
- Разрешить путь относительно canonical root и проверить, что фактическая canonical target остаётся внутри canonical `vault_root`. Symlink наружу или невозможность доказать containment дают `integrity_error`.
- Вызов `Path.resolve()` до открытия может использоваться только как предварительная диагностика, но не как защита от TOCTOU и не как доказательство идентичности уже открытого объекта.
- Symlink, ведущий внутрь Vault, допустим только на платформе/через API, где безопасное открытие с ограничением корнем Vault доказуемо (см. следующий шаг). В fallback-режиме symlink любого направления запрещается.

Если canonical target небезопасен или его принадлежность Vault нельзя доказать, содержимое не читается и не возвращается.

### 8. Проверка наличия и чтение файла (только после DB-only gate и выбора active/однозначного узла)

Этот шаг и последующие source-dependent проверки не выполняются для уже определённых `deleted` или `ambiguous`.

- Отсутствующий файл при `documents.status == 'active'` в переданном checkout возвращает `stale_source`, а не `deleted`: сигнатура не подтверждает, что checkout соответствует версии Vault, по которой создан индекс.
- `deleted` для физически отсутствующего файла допускается только после отдельного доверенного подтверждения версии Vault на этапе D. В текущем API такого подтверждения нет. `documents.status == 'deleted'` и `document_deleted` остаются достаточными подтверждениями удаления со стороны самого индекса.
- Файл должен быть обычным читаемым файлом. Ошибка прав/чтения или невозможность безопасного открытия — fail-closed `integrity_error`; отсутствие файла — `stale_source`.
- Canonical `vault_root` открывается как каталоговый дескриптор (`root_fd`); его идентичность фиксируется через `fstat` и проверяется повторно после чтения.
- Обычная последовательность `resolve()` → обычный `open()` не является защитой: symlink может измениться между этими вызовами. Открытие должно быть привязано к `root_fd` и выполняться одной из следующих безопасных схем:
  1. **Linux с `openat2`:** открыть относительный `source_path` относительно `root_fd` с `RESOLVE_BENEATH | RESOLVE_NO_MAGICLINKS`. Ядро должно отклонять разрешение, которое выходит за `root_fd` через `..`, symlink или magic link. Внутренний symlink допускается только если эта операция успешно доказывает containment. Фактическую цель уже открытого дескриптора дополнительно проверить через `/proc/self/fd/<fd>` (readlink + canonical resolve) и убедиться, что она находится внутри canonical `vault_root`. Если `/proc/self/fd` или требуемая проверка недоступны, чтение не выполняется и возвращается `integrity_error`.
  2. **POSIX fallback без `openat2`:** пошагово открывать каждый компонент пути относительно уже открытого родительского directory FD; для промежуточных каталогов использовать `dir_fd` + `O_DIRECTORY | O_NOFOLLOW`, для конечного файла — `dir_fd` + `O_NOFOLLOW`. Такой режим намеренно запрещает все symlink, включая внутренние, поскольку безопасно доказать их разрешение данным fallback нельзя. При отсутствии `dir_fd`, `O_NOFOLLOW` или `O_DIRECTORY` нужной семантики fallback недоступен.
- Если платформа не поддерживает ни один из перечисленных режимов безопасного открытия, API не делает небезопасный fallback через обычный `open()` и возвращает `integrity_error` без чтения содержимого.
- Сразу после открытия проверить через `fstat(fd)`, что объект является обычным файлом. Зафиксировать как минимум `st_dev`, `st_ino`, `st_size`, `st_mtime_ns` и `st_ctime_ns`; подтвердить, что фактическая цель открытого FD находится внутри canonical root (для `openat2` — проверкой FD target, для POSIX fallback — цепочкой descriptor-relative открытий без symlink).
- Прочитать bytes только один раз из этого FD. После чтения повторить `fstat(fd)` и сравнить идентичность и метаданные; повторно безопасно открыть путь от того же `root_fd`, проверить цель и сравнить `st_dev`/`st_ino` нового FD с исходным. Повторно проверить идентичность `root_fd` и, где доступна canonical FD target, её принадлежность Vault root.
- При изменении размера/mtime/ctime во время чтения вернуть `stale_source` без данных. При смене inode/цели, изменении symlink/пути, выходе за root, изменении root directory или невозможности повторить проверку вернуть `integrity_error` без данных. Любое расхождение отменяет результат: прочитанный буфер не декодируется и `NodeRecord` не формируется.
- Если symlink изменился между предварительной проверкой и открытием, проверка только строкового canonical path недостаточна: `openat2` должен атомарно отклонить выход за root; POSIX fallback с `O_NOFOLLOW` отклонит сам symlink. Если symlink изменился после открытия, повторное безопасное разрешение пути и сравнение идентичности FD обнаружит замену; данные отбрасываются.

Реализация должна использовать единственный проверенный byte buffer и для хеширования, и для декодирования. Нельзя хешировать одну версию файла, а извлекать текст повторным чтением другой версии.

### 9. SHA-256 всего исходного Markdown

- Вычислить SHA-256 от всех прочитанных байтов файла и представить как `sha256:<hex>`.
- Сравнить с `documents.source_sha256`.
- Если хеш файла отличается, вернуть `stale_source` до извлечения фрагмента.
- `source_size_bytes` также сверяется с фактическим числом байтов; несогласованность индексных метаданных — `integrity_error`.
- После успешного совпадения файл строго декодируется как UTF-8 без преобразования LF/CRLF. Ошибка декодирования при совпавшей сохранённой контрольной сумме рассматривается как `integrity_error`.

### 10. Проверка координат и оригинального среза

Используя один декодированный текст:
1. Проверить границы: `0 <= char_start <= char_end <= len(source)`.
2. Проверить `source[char_start:char_end] == raw_text`.
3. Пересчитать ожидаемые UTF-8 byte offsets из префиксов строки:
   `len(source[:char_start].encode('utf-8'))` и `len(source[:char_end].encode('utf-8'))`.
4. Проверить, что они равны сохранённым `byte_start` / `byte_end`.
5. Проверить, что байтовый срез `source_bytes[byte_start:byte_end]` равен `raw_text.encode('utf-8')` и декодируется без ошибки.
6. Пересчитать line_start/line_end по фактическому алгоритму `_Offsets.span_from_chars()` в `parser.py`: `line_starts` начинается с `[0]`, затем содержит позиции сразу после каждого `\\n`; строки считаются с 1, а `bisect_right(line_starts, offset)` определяет номер строки.
7. Для непустого диапазона (`char_start < char_end`) ожидаются обычные включительные координаты строк: `line_start = max(1, bisect_right(line_starts, char_start))`, `line_end = max(1, bisect_right(line_starts, char_end - 1))`.
8. Для пустого диапазона (`char_start == char_end`) допустим специальный результат парсера: `raw_text == ""`, `byte_start == byte_end`, `line_start = max(1, bisect_right(line_starts, char_start))`, `line_end = line_start - 1`. Это не повреждённые координаты и не основание для `integrity_error`. Для пустого Markdown-файла корневой узел `document` имеет `char_start = char_end = 0`, `byte_start = byte_end = 0`, `line_start = 1`, `line_end = 0`.
9. Проверить совпадение пересчитанных координат с БД.

Пустой диапазон нельзя нормализовать к `line_end == line_start`: это изменит фактическую семантику `_Offsets.span_from_chars()` и будет ошибочно отвергать/искажать пустой исходник.

Любое иное расхождение при совпавшем Hash всего файла — `integrity_error`, а не `stale_source`.

### 11. Сравнение expected_hash

Только после проверки источника и координат сравнить `expected_hash` с проверенным текущим `structural_nodes.content_hash`.

- Совпадение — можно сформировать ответ `ok`.
- Несовпадение — `stale_source`; новую версию возвращать запрещено.
- API не должен искать `expected_hash` в `node_versions` и подставлять исторический фрагмент вместо текущего. Для этого потребуется отдельный явно спроектированный контракт исторического чтения, которого в данном задании нет.

### 12. Возврат результата

Только после прохождения всех проверок сформировать `NodeRecord` из проверенной строки и вернуть `NodeLookupResult(status=ok, node=...)`.

`raw_text` должен быть именно тем текстом, который получен срезом исходного буфера по координатам. Запрещена сериализация AST, реконструкция Markdown, нормализация пробелов или окончаний строк.

## 6. Read-only поведение и согласованность SQLite

API не должен вызывать `connect_database()`: эта функция создаёт каталог/таблицы и запускает миграцию, то есть имеет write-поведение.

Предлагается:
- открыть уже существующий `db_path` в SQLite URI-режиме `mode=ro`;
- включить `PRAGMA query_only=ON` и `foreign_keys=ON`;
- проверить schema version = 2;
- выполнить `PRAGMA integrity_check` и `PRAGMA foreign_key_check` (для первой версии — при каждом API-вызове; при последующей оптимизации допускается кэширование только в рамках неизменяемой read-only сессии);
- начать согласованную read transaction, прочитать узел, документ, историю и события, затем закрыть соединение;
- не выполнять DDL, миграции, записи, обновления статусов и исправление повреждённых строк.

Если база отсутствует, повреждена, несовместима или недоступна для чтения, возвращается fail-closed результат `integrity_error`; новая пустая база автоматически не создаётся.

## 7. Правила использования node_versions и node_match_events

### node_versions

- `node_versions` — журнал снимков, а не альтернативный индекс для подстановки текста.
- Максимальный `version_no` подтверждает, что текущая строка `structural_nodes` не разошлась с последним сохранённым снимком.
- Предыдущие версии остаются доступными для аудита и будущего отдельного исторического API.
- Запрос с прошлым Hash всегда возвращает `stale_source`, если Node ID сейчас существует с другим проверенным Hash.
- Отсутствующая либо противоречивая последняя версия — `integrity_error`.

### node_match_events

- Последнее событие определяется по монотонному `event_pk`.
- События `stale` и `document_deleted` подтверждают прекращение адресации прежнего узла.
- `stale_ambiguous_candidate` и `ambiguous` подтверждают, что старую идентичность нельзя безопасно назначить новому фрагменту.
- Массив `candidate_node_ids_json` читается как доказательство неопределённости, но никогда не используется для выбора кандидата.
- События не переписываются и не удаляются при чтении.

## 8. Ошибки, исключения и fail-closed

Предлагаемые безопасные error codes (это поля результата, не дополнительные статусы):
- `node_id_invalid`, `expected_hash_invalid`, `vault_root_invalid` → `invalid_request`;
- `node_not_found` → `not_found`;
- `document_deleted`, `node_deleted` → `deleted`; `node_ambiguous` → `ambiguous`;
- `source_file_missing`, `source_hash_mismatch`, `expected_hash_mismatch` → `stale_source` для текущего checkout-контракта;
- `source_unreadable`, `source_path_unsafe`, `source_target_outside_root`, `secure_open_unavailable`, `file_identity_changed`, `match_event_type_unknown`, `match_event_payload_invalid`, `raw_text_hash_mismatch`, `version_snapshot_mismatch`, `source_size_mismatch`, `char_span_mismatch`, `byte_span_mismatch`, `line_span_mismatch`, `sqlite_integrity_failure`, `schema_version_unsupported`, `foreign_key_failure` → `integrity_error`.

Пользовательское сообщение должно быть коротким и не содержать текста источника. В логах допускаются Node ID, error code и безопасный относительный путь только при необходимости; содержимое, excerpt и полный абсолютный путь не логируются.

Неожиданное исключение не должно превращаться в частично успешный ответ. Оно либо преобразуется в безопасный `integrity_error`, либо поднимается как внутреннее исключение до границы транспортного адаптера, который обязан удалить любые промежуточные данные и не сериализовать NodeRecord.

## 9. Предлагаемая внутренняя архитектура

Без изменения текущих B/C модулей предлагается добавить изолированный модуль, например `sfra_indexer/lookup.py`, содержащий:
- enum статусов и dataclass результата/узла (либо разместить типы в `models.py`, если аналитик подтвердит это предпочтительным);
- валидаторы Node ID и Hash;
- read-only SQLite loader;
- status resolver по документу/узлу/последним событиям;
- path resolver с проверкой canonical root и symlink;
- координатный валидатор, согласованный с правилами `parser.py`;
- публичную функцию `get_node_by_id`.

После одобрения этапа A функция и типы будут экспортированы из `sfra_indexer/__init__.py`. Существующие `storage.py`, `identity.py`, `parser.py`, `indexer.py` и schema v2 не переписываются. Использование новых таблиц или изменение существующих полей не требуется.

Вызов API должен получать `db_path` от уже действующего механизма восстановления Persistence и `vault_root` от конкретного checkout исходного Vault. Сам API не загружает GitHub Actions артефакты, не запускает workflow и не управляет ветками состояния.

## 10. Потенциальные проблемы и меры предотвращения

| Риск | Мера |
|---|---|
| Старый Hash передан для существующего Node ID | Сверить только с проверенной текущей версией; вернуть `stale_source`, не читать исторический текст |
| Повторяющиеся или неоднозначные блоки | Использовать node status и match events; не выбирать candidate ID |
| Удалённый узел и узел-кандидат могут оба иметь stale status | Различать `stale` и `stale_ambiguous_candidate` по последнему event |
| Документ удалён или ещё не переиндексирован после удаления | В неподтверждённом checkout отсутствие файла даёт `stale_source`; `deleted` требует статуса/события удаления в индексе либо доверенного подтверждения версии Vault на этапе D |
| DB current row расходится с последней версией | Сверить поля current row с последним `node_versions`; вернуть `integrity_error` |
| DB `raw_text` изменён вместе или отдельно от Hash | Сначала независимо пересчитать SHA-256 raw_text, затем сверить последнюю версию |
| `documents.source_path` содержит `../` или абсолютный префикс | Считать повреждением адресации SQLite: `integrity_error`; не открывать файл |
| Symlink ведёт за пределы Vault или target невозможно проверить | Отказать с `integrity_error`; не возвращать данные |
| TOCTOU между проверкой пути и открытием | Использовать root directory FD и `openat2` с `RESOLVE_BENEATH` либо POSIX descriptor walk с `O_NOFOLLOW`; проверить target/`fstat` до и после чтения и повторно открыть путь для сравнения inode |
| CRLF, кириллица, emoji, UTF-8 | Сверить одновременно char, byte и line offsets на исходном буфере без newline normalization |
| API случайно запускает миграцию | Использовать исключительно SQLite `mode=ro`, не вызывать `connect_database()` |
| Передан другой Vault checkout с тем же relative path | Проверять полный file SHA; выбор доверенного `vault_ref` и фиксация source commit относятся к отдельному этапу D |

Ограничение schema v2: таблица `documents` хранит относительный `source_path` и hash файла, но не уникальный абсолютный корень Vault или Git ref. Поэтому API может доказать, что байты по указанному относительному пути в переданном `vault_root` совпадают с индексированными байтами, но не может самостоятельно установить Git-ветку этого checkout. Для доказательства ветки/коммита нужен доверенный выбор `vault_root` и зафиксированный source commit на этапе D; ради этого этапа менять schema v2 не предлагается.

## 11. Предлагаемый набор тестов для этапа B

### Положительные

1. Активный документ + активный узел + совпавший expected hash → `ok`.
2. Проверить точное равенство возвращаемого raw_text исходному срезу.
3. Узел с кириллицей, emoji, LF и CRLF: правильные char/byte/line coordinates.
4. Документный root и обычный дочерний структурный узел.
5. Пустой Markdown-документ: корневой узел `document` с `raw_text == ""`, `char_start == char_end == 0`, `byte_start == byte_end == 0`, `line_start == 1`, `line_end == 0`; адресное чтение такого узла при корректном Hash возвращает `ok`.
6. Успешный read-only вызов не изменяет содержимое или schema version SQLite.

### Статусы и негативные случаи

| Сценарий | Ожидаемый статус |
|---|---|
| Некорректный Node ID | `invalid_request` |
| Неправильный формат expected Hash | `invalid_request` |
| Валидный Node ID отсутствует | `not_found` |
| Документ помечен deleted (`documents.status == 'deleted'`) и все DB-only проверки пройдены: история событий валидна, `raw_text` Hash верен, последняя `node_versions` совпадает, `source_path` синтаксически безопасен | `deleted`; исходный файл не открывается |
| Документ помечен deleted (`documents.status == 'deleted'`), но история содержит неизвестный `event_type` | `integrity_error`; исходный файл не открывается |
| Документ помечен deleted (`documents.status == 'deleted'`), но `documents.source_path` содержит `../`, абсолютный или иной небезопасный путь | `integrity_error`; исходный файл не открывается |
| Документ помечен deleted (`documents.status == 'deleted'`), но текущая строка `structural_nodes` не совпадает с последней `node_versions` | `integrity_error`; исходный файл не открывается |
| Документ помечен deleted (`documents.status == 'deleted'`), но Hash сохранённого `raw_text` не совпадает с `content_hash` | `integrity_error`; исходный файл не открывается |
| Файл активного документа отсутствует в checkout с неподтверждённой идентичностью | `stale_source` |
| Удаление файла подтверждено в доверенно установленной версии Vault (после интеграции этапа D) | `deleted` |
| Узел удалён при обновлении документа, событие `stale` | `deleted` |
| Текущий узел ambiguous | `ambiguous` |
| Старый ID с событием `stale_ambiguous_candidate` | `ambiguous` |
| Hash всего файла изменился после индексации | `stale_source` |
| Передан прежний expected Hash при существующей новой версии | `stale_source` |
| В `documents.source_path` записан `../`, абсолютный или иной небезопасный путь | `integrity_error` |
| Symlink ведёт за пределы Vault либо цель FD нельзя подтвердить | `integrity_error` |
| Внутренний symlink при поддержке безопасного `openat2` | Допустим; дальнейшие проверки обязательны |
| Внутренний symlink в POSIX fallback с `O_NOFOLLOW` | `integrity_error` (fallback запрещает все symlink) |
| Symlink меняется между предварительной проверкой и открытием/повторной проверкой | `integrity_error`, содержимое не возвращается |
| Платформа не поддерживает безопасное descriptor-relative открытие | `integrity_error`, обычный `open()` запрещён |
| Hash raw_text не равен structural_nodes.content_hash | `integrity_error` |
| Последняя node_version не совпадает с текущим снимком | `integrity_error` |
| Нарушены char offsets | `integrity_error` |
| Нарушены UTF-8 byte offsets | `integrity_error` |
| Нарушены line coordinates | `integrity_error` |
| source_size_bytes противоречит исходному файлу | `integrity_error` |
| Неизвестный `event_type` в истории сопоставления данного `document_pk` | `integrity_error` |
| Повреждённый `candidate_node_ids_json` или иной event payload | `integrity_error` |
| Пустой Markdown-документ с валидным пустым root span (`line_start=1`, `line_end=0`) | `ok` |
| Повреждена SQLite, schema version не 2 или нарушены FK | `integrity_error` |

Для каждого ошибочного случая отдельное утверждение должно проверять одновременно:
- `result.node is None`;
- JSON не содержит ключа `raw_text` и не содержит исходного фрагмента ни в одном другом поле;
- в логах и сообщении об ошибке нет фрагмента источника.

Дополнительные тесты:
- узел stale без объясняющего match event → `integrity_error`;
- противоречивое сочетание node status и последнего события → `integrity_error`;
- `documents.status == 'deleted'` + неизвестный `event_type` в любой позиции истории этого документа → `integrity_error`, `node is None`, исходный файл не открывается;
- `documents.status == 'deleted'` + небезопасный синтаксис `documents.source_path` → `integrity_error`, `node is None`, исходный файл не открывается;
- `documents.status == 'deleted'` + несовпадение текущей строки с последней `node_versions` → `integrity_error`, `node is None`, исходный файл не открывается;
- `documents.status == 'deleted'` + несовпадение Hash `raw_text` с `content_hash` → `integrity_error`, `node is None`, исходный файл не открывается;
- `documents.status == 'deleted'` + полностью пройденный DB-only integrity gate → `deleted`, `node is None`, исходный файл не открывается;
- один Node ID с несколькими строками в тестовой повреждённой БД → `integrity_error`;
- файл меняется между проверкой пути и чтением → fail-closed;
- symlink меняется между pre-resolve и descriptor-relative open; symlink меняется после open до повторной проверки → `integrity_error`, `node is None`;
- для платформ без безопасного open API обычный `open()` не используется;
- неизвестный тип события в том же `document_pk` → `integrity_error`;
- ожидаемый старый Hash не приводит к чтению из `node_versions`.

## 14. Фактическая реализация E1

Модуль реализации: `sfra_indexer/lookup.py`.

Публичные экспорты:
- `get_node_by_id(db_path, node_id, expected_hash, vault_root)`;
- `NodeLookupResult`;
- `NodeLookupStatus`;
- `NodeRecord`.

Возвращаемый `raw_text` берётся исключительно из `source_text[char_start:char_end]` текущего файла. `structural_nodes.raw_text` не используется как ответ: он участвует только в DB-only проверке сохранённого Content Hash и сверке с последним снимком `node_versions`.

Безопасное открытие использует Linux `openat2` с ограничением корнем и запретом symlink; при недоступности syscall применяется POSIX descriptor-relative обход с `O_NOFOLLOW`. Открытый объект проверяется через `fstat` до/после чтения, его путь сверяется с canonical Vault root (когда доступен `/proc/self/fd`), а путь повторно открывается и сравнивается по device/inode. Если платформенные гарантии недоступны, запрос завершается fail-closed.

Тесты E1 находятся в `tests/test_lookup.py`. Workflow `sfra-stage-b-tests.yml` запускает полный pytest набор и проверку реального Vault как для push в рабочую ветку, так и для pull request в `main`; checkout в PR закрепляется на SHA самого PR head.

### Явная идентичность Vault

Persistence workflow принимает параметр `vault_ref`; его значение по умолчанию — `executor-1/sfra-indexer-session-1`, а не `main`. Исходные заметки извлекаются отдельным checkout в `vault/ГП`. Фактический commit фиксируется через `git rev-parse HEAD`.

Новые manifest содержат:
- `vault_ref` — явно выбранную ветку, тег или commit ref;
- `vault_commit_sha` — фактический commit SHA checkout;
- `source_branch` и `source_commit` — совместимые алиасы для существующих readers.

Формат manifest остаётся version 1; чтение ранее созданных manifest с `source_branch/source_commit` сохранено. Выбор Vault ref не выводится из ветки реализации и не переключается автоматически на `main`.

### Фактические границы реализации

- SQLite schema v2 не изменена.
- Модули `parser.py`, `identity.py`, `storage.py` и `indexer.py` не переписывались.
- `get_node_by_id` открывает только существующую SQLite в read-only/query-only режиме.
- Тесты не используют production `sfra-state` и не изменяют Vault.
- Production Persistence workflow остаётся ограниченным своей рабочей веткой; E1 changes are prepared in a separate PR branch to avoid unintended production publication before review.
