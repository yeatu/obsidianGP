# Аналитика совместимости SFRA с GitHub Actions

**Статус:** архитектурное решение одобрено аналитиком; внесены пять уточнений для повторной проверки. Реализация механизма сохранения состояния и API чтения узла не начиналась.

**Проверенная ветка реализации:** `executor-1/sfra-indexer-session-1`.

## 1. Итог

Этапы B и C совместимы с восстановлением существующей SQLite-базы в новом GitHub Actions runner. Переписывать парсер, алгоритм сопоставления Node ID или схему хранения ради переноса между runner не требуется.

Необходимы два новых слоя:

1. Workflow persistence: загрузка SQLite из отдельной ветки состояния до индексации и публикация обновлённой базы после индексации.
2. Адресный read API: поиск по `node_id` с обязательной проверкой `expected_hash` и целостности исходного фрагмента.

Текущий workflow не реализует ни один из этих двух слоёв. Сейчас он создаёт базу в `/tmp/sfra-vault-sidecar`, выполняет два прохода в пределах одного job, а после завершения runner база исчезает.

Ветка `sfra-state` при проверке не обнаружена. Её следует создать в будущем как настоящую orphan-ветку с независимым корневым коммитом без родителя. Она не должна наследовать историю `main` или любой другой ветки с исходным Vault.

## 2. Проверка совместимости с существующим кодом

Проверены текущие файлы `sfra_indexer/storage.py`, `indexer.py`, `cli.py`, `__init__.py`, `models.py`, тесты идентичности и workflow `.github/workflows/sfra-stage-b-tests.yml`.

| Требование | Результат | Основание |
|---|---|---|
| Открыть ранее созданную БД | Совместимо | `index_vault()` открывает `<index_dir>/structure.sqlite3` через `connect_database()` |
| Сохранить Node ID между запусками | Совместимо при восстановлении той же БД | `structural_nodes.node_id`, уникальный индекс `idx_nodes_node_id` |
| Сохранить версии | Совместимо | `node_versions` хранит снимки с Content Hash и `raw_text` |
| Сохранить историю сопоставления | Совместимо | `node_match_events` |
| Пропустить неизменённый документ | Совместимо | Сверка `documents.source_sha256` до парсинга |
| Создать новую версию после изменения | Совместимо | Повторное сопоставление и добавление записи в `node_versions` |
| Восстановить состояние на другом runner | Пока не реализовано | Текущий workflow не скачивает/не публикует БД |
| Получить узел по Node ID и expected Hash | Пока не реализовано | В публичном Python API нет соответствующей функции |
| Проверить межзапусковой сценарий | Пока не реализовано | Текущий повторный проход использует ту же локальную БД в одном job |

### Почему текущий API можно сохранить

`index_vault(vault_path, index_dir)` не требует, чтобы БД была создана в текущем процессе. Достаточно заранее разместить восстановленный файл по адресу:

```text
<index_dir>/structure.sqlite3
```

Затем `connect_database()` откроет эту БД и выполнит проверку/миграцию схемы. Текущая версия схемы — v2. В коде уже предусмотрен переход со схемы v1 на v2.

Для восстановления непрерывности идентификаторов важно передавать именно прежнюю SQLite-базу. Создание новой пустой базы выдаст новые UUID и не может считаться продолжением предыдущей индексации.

### Существующее поведение при изменении источника

При изменении Markdown-файла индексатор повторно обрабатывает документ. Если узел однозначно сопоставлен, он сохраняет прежний Node ID, обновляет Content Hash и создаёт новую запись в `node_versions`. Предыдущая версия остаётся в истории.

Это уже обеспечивает основную часть критического сценария. Не хватает постоянного хранения самой БД между runner и внешнего API проверки Hash.

## 3. Предлагаемый формат ветки состояния

Предлагается отдельная ветка `sfra-state` в том же репозитории, с независимой историей и только файлами состояния:

```text
sfra-state
├── README.md
└── state/
    ├── structure.sqlite3
    └── manifest.json
```

### Создание ветки и проверка изоляции

Ветка должна быть создана как **настоящая orphan-ветка**: первый коммит является корневым и не имеет родительского коммита. Нельзя создавать её от `main` с последующим удалением файлов: это оставит связь с историей исходного репозитория. При создании необходимо использовать orphan-механизм Git и сформировать новое дерево только из разрешённых файлов.

После создания обязательны две проверки:

1. Проверить, что у первого коммита `sfra-state` нет родителя (root commit / orphan history).
2. Проверить полный список файлов в дереве ветки и убедиться, что там находятся только `README.md`, `state/structure.sqlite3` и `state/manifest.json`. Ветка не должна содержать `ГП/`, Markdown-заметки Vault, исходный код или посторонние файлы.

Допустимый allowlist для публикации: `README.md`, `state/structure.sqlite3`, `state/manifest.json`. Любой файл вне allowlist должен блокировать публикацию.

### Состав файлов

- `structure.sqlite3` — актуальное состояние индексатора, включая Node ID, Content Hash, версии и события сопоставления.
- `manifest.json` — метаданные снимка и проверка целостности SQLite.
- `README.md` — описание формата, правил обновления, восстановления и границы доступа.

Пример `manifest.json`:

```json
{
  "format_version": 1,
  "database": "state/structure.sqlite3",
  "database_sha256": "sha256:<hash>",
  "sqlite_schema_version": 2,
  "source_repository": "yeatu/obsidianGP",
  "source_branch": "executor-1/sfra-indexer-session-1",
  "source_commit": "<commit-sha>",
  "indexer_version": "0.2.0",
  "workflow_run_id": "<run-id>",
  "updated_at": "<UTC timestamp>"
}
```

Manifest не дублирует содержимое базы. Он позволяет до открытия SQLite проверить целостность загруженного файла и установить, какой версией индексатора и на каком коммите было сформировано состояние.

Git-история ветки дополнительно сохраняет предыдущие снимки файла базы. Внутренняя таблица `node_versions` остаётся основным источником истории конкретных структурных узлов.

### Граница доступа и конфиденциальность

Отдельная orphan-ветка физически отделяет файлы состояния от дерева исходного Vault и его истории Git, но **не создаёт отдельную границу прав доступа**. Пользователь, имеющий доступ к репозиторию, сможет получить содержимое ветки `sfra-state` наравне с другими доступными ветками.

SQLite содержит исходный текст заметок в `structural_nodes.raw_text`, а также исторические снимки в `node_versions.raw_text`. Git-история ветки сохраняет предыдущие версии файла базы. Поэтому исходный текст заметок будет доступен пользователям, имеющим доступ к репозиторию и этой ветке.

Если содержимое Vault нельзя раскрывать всем пользователям репозитория, одной отдельной ветки недостаточно. Потребуется отдельный приватный репозиторий или внешнее хранилище с независимыми ACL. В рамках предлагаемой архитектуры это ограничение должно быть явно принято владельцем данных.

## 4. Предлагаемый жизненный цикл GitHub Actions

Индекс и исходный Vault должны физически находиться в разных каталогах runner. Рекомендуемый временный путь:

```text
$RUNNER_TEMP/sfra-state/state/structure.sqlite3
```

Предлагаемая последовательность:

1. Checkout ветки с кодом и исходным Vault.
2. Получить ветку `sfra-state` и восстановить `state/structure.sqlite3` в каталог индекса вне Vault.
3. Проверить SHA-256 из manifest и выполнить SQLite `PRAGMA integrity_check` для восстановленной базы.
4. Запустить существующий `sfra-index index`, передав каталог восстановленной базы через `--index-dir`.
5. После завершения индексации создать согласованный снимок SQLite через SQLite Backup API (`Connection.backup()`), а не копированием файла базы из файловой системы.
6. Для готового файла-снимка выполнить `PRAGMA integrity_check`, убедиться, что результат равен `ok`, затем вычислить SHA-256 именно этого готового файла и записать его в manifest.
7. Зафиксировать только `state/structure.sqlite3` и `state/manifest.json` в ветке `sfra-state`.
8. Выполнить обычный fast-forward push. Не использовать принудительную перезапись ветки.

### Требования к снимку SQLite

SQLite Backup API должен копировать состояние из открытого соединения с рабочей БД в отдельное временное соединение/файл назначения. После завершения `Connection.backup()` оба соединения закрываются. Проверка целостности выполняется на готовом файле-снимке, который затем будет опубликован.

Публиковать исходный рабочий файл SQLite простым файловым копированием не следует: при режиме WAL отдельные актуальные данные могут находиться в WAL-файле. Backup API формирует согласованный снимок и не требует вручную собирать пару DB/WAL.

Порядок контрольных проверок перед коммитом:

- снимок завершён и соединения с ним закрыты;
- `PRAGMA integrity_check` возвращает ровно `ok`;
- SHA-256 рассчитывается после формирования и закрытия файла-снимка;
- `manifest.json` содержит SHA-256 этого файла;
- повторное чтение снимка/manifest перед публикацией подтверждает совпадение контрольной суммы.

Для workflow потребуются `permissions: contents: write` и группа `concurrency`, исключающая одновременную запись нескольких job в одну ветку состояния. Дополнительно push должен отклоняться при конфликте с новым head ветки, а не затирать чужое состояние.

Запись состояния не должна запускать повторный workflow индексации: действующий workflow реагирует только на изменения своей ветки реализации, а не на push в `sfra-state`.

Если ветка состояния или база неожиданно отсутствует при обычном восстановлении, workflow должен завершаться ошибкой. Создание пустой базы допустимо только в отдельном явно заданном режиме первичной инициализации.

## 5. API адресного чтения узла

Предлагаемая сигнатура:

```python
get_node_by_id(
    db_path,
    node_id: str,
    expected_hash: str,
    vault_root,
) -> NodeLookupResult
```

`expected_hash` — полный Content Hash в формате `sha256:<64 hex>`, вычисленный для `raw_text` конкретного узла. Это не SHA-256 всего Markdown-документа: последний уже хранится отдельно в `documents.source_sha256`.

### Порядок проверок

1. Найти узел по `node_id`. Идентификатор должен однозначно соответствовать одной записи.
2. Определить статус документа и узла, включая последние события в `node_match_events`. Неоднозначный или удалённый узел не может быть возвращён как актуальный.
3. Проверить формат `expected_hash`.
4. Вычислить SHA-256 от сохранённого `structural_nodes.raw_text.encode("utf-8")` и сравнить его с сохранённым `structural_nodes.content_hash`. Несовпадение означает повреждённую/неконсистентную запись SQLite и должно завершаться статусом `integrity_error` без содержимого.
5. Безопасно разрешить `source_path` относительно `vault_root`: получить canonical/absolute path, проверить, что итоговый путь находится внутри canonical `vault_root` (например, через `Path.is_relative_to`), и отклонить выход за пределы корня, в том числе через symlink. Путь, который выходит за пределы корня, не должен читаться.
6. Проверить, что исходный файл существует и доступен. Отсутствующий файл означает удалённый источник.
7. Прочитать исходный Markdown без нормализации переводов строк, вычислить SHA-256 всего файла и сравнить с `documents.source_sha256`. Если SHA-256 исходного файла отличается от сохранённого в базе, вернуть `stale_source`.
8. Проверить координаты узла относительно текущего исходного файла: `source[char_start:char_end] == raw_text`; аналогично проверить байтовый срез `source.encode("utf-8")[byte_start:byte_end]`, декодируя его как UTF-8 и сравнивая с `raw_text`. Проверить согласованность границ строк с координатами. Если Hash всего исходного файла совпадает с `documents.source_sha256`, но фрагмент или координаты не совпадают, вернуть `integrity_error`: сохранённая запись не соответствует тому исходнику, который был проиндексирован.
9. Сравнить `expected_hash` с проверенным Content Hash узла. Если он не совпадает, вернуть `stale_source`: вызывающая сторона запрашивает не ту версию узла.
10. Только после всех успешных проверок вернуть узел и координаты.

### Статусы ответа

API должен различать как минимум следующие статусы:

| Статус | Условие | Содержимое узла |
|---|---|---|
| `ok` | Узел однозначен, активен, Hash и исходный фрагмент подтверждены | Возвращается |
| `stale_source` | Проверенный актуальный Hash узла не совпадает с `expected_hash`; либо SHA-256 исходного файла отличается от `documents.source_sha256` | Не возвращается |
| `deleted` | Исходный документ удалён, файл отсутствует либо событие/статус показывает, что узел удалён из текущей структуры | Не возвращается |
| `ambiguous` | Узел находится в состоянии неоднозначного сопоставления или является кандидатом неоднозначного события | Не возвращается |
| `not_found` | Node ID отсутствует в базе | Не возвращается |
| `invalid_request` | Некорректный Node ID/Hash или путь нарушает ограничение корня Vault | Не возвращается |
| `integrity_error` | SHA-256 сохранённого `raw_text` не совпадает с `structural_nodes.content_hash`; либо координаты/срез не соответствуют исходному файлу при совпадающем SHA-256 всего файла и `documents.source_sha256`; либо обнаружена иная ошибка целостности БД | Не возвращается |

Статус `deleted` означает, что адрес больше не соответствует актуальному узлу. Статус `stale_source` означает, что узел/его источник существует, но запрошенное состояние не совпадает с подтверждённой актуальной версией. Для старого Node ID, который остался в БД со статусом stale из-за удаления узла при переиндексации, API должен определить последнее событие и классифицировать его как `deleted`, кроме случаев неоднозначного сопоставления, которые должны давать `ambiguous`.

**Правило безопасности ответа:** при любом статусе, кроме `ok`, поле `node` равно `null` или отсутствует. Нельзя возвращать `raw_text`, координаты, новый Node ID или иной фрагмент в качестве замены запрошенного узла.

Успешный ответ:

```json
{
  "status": "ok",
  "node": {
    "node_id": "node_<uuid>",
    "content_hash": "sha256:<hash>",
    "source_path": "folder/note.md",
    "raw_text": "Exact source slice",
    "line_start": 10,
    "line_end": 12,
    "char_start": 120,
    "char_end": 145,
    "byte_start": 140,
    "byte_end": 165
  }
}
```

Ответ при несовпадении Hash:

```json
{
  "status": "stale_source",
  "node_id": "node_<uuid>",
  "expected_hash": "sha256:<expected>",
  "actual_hash": "sha256:<current>",
  "node": null
}
```

Для случая изменения файла после последней индексации причина должна быть обозначена отдельно, например `reason: "source_file_changed_since_index"`. В ответе нельзя возвращать новый `raw_text`, координаты или другой Node ID вместо запрошенной версии.

Таким образом, Node ID определяет адрес структурной сущности, а expected Hash закрепляет конкретную версию содержимого. Несовпадение означает отказ в выдаче узла как актуального, а не разрешение незаметно заменить его новой версией.

Исторический поиск по старому Hash можно добавить отдельно позднее. Он не должен смешиваться с API получения актуального узла.

## 6. Критический интеграционный тест: два независимых запуска

Для проверки предлагается выделенный workflow с `workflow_dispatch` и двумя режимами. Проверочный источник — маленький временный fixture Vault, а не рабочая папка `ГП`. Каждый тестовый запуск должен использовать отдельную тестовую SQLite-базу, размещённую вне Vault, например:

```text
$RUNNER_TEMP/sfra-integration-test/structure.sqlite3
```

Тестовая БД не должна открывать, изменять, заменять или переиспользовать рабочую SQLite. Тестовые данные должны передаваться между запусками A/B через отдельную тестовую ветку состояния, например `sfra-state-test`, либо эквивалентный изолированный тестовый канал. Workflow интеграционного теста не должен иметь шага публикации в `sfra-state` и не должен изменять рабочую базу или рабочий manifest.

Использование отдельной тестовой ветки позволяет проверить настоящий перенос состояния между двумя независимыми runner, не смешивая тестовые fixture с производственными документами.

### Запуск A: первичная индексация

- Новый runner создаёт временный fixture Vault с одним заголовком и одним абзацем.
- В отдельной тестовой директории создаётся тестовая SQLite.
- Индексатор строит тестовую базу.
- Тест сохраняет в тестовый manifest исходный Node ID и Content Hash абзаца.
- Тестовая база и manifest публикуются в `sfra-state-test`, а не в `sfra-state`.

Ожидание: один стабильный Node ID, один Content Hash, одна версия узла. Рабочее состояние не затронуто.

### Запуск B: восстановление на новом runner

Это отдельный запуск workflow, а не повторный шаг того же job.

- Новый runner восстанавливает тестовое состояние только из `sfra-state-test`.
- Проверяет контрольную сумму manifest и `PRAGMA integrity_check`.
- Создаёт тот же fixture без изменений в отдельной временной директории и запускает индексатор с восстановленной тестовой SQLite.
- Сравнивает Node ID и Content Hash с контрольными значениями из manifest запуска A.

Ожидание после неизменённого прохода:

- Node ID полностью совпадает с запуском A;
- Content Hash полностью совпадает с запуском A;
- новая версия узла не создана;
- generation документа не увеличивается из-за неизменённого файла;
- рабочая SQLite и ветка `sfra-state` не изменены.

Затем в том же изолированном fixture изменяется текст абзаца и индексатор запускается повторно.

Ожидание после изменения:

- Node ID остаётся прежним, поскольку узел однозначно сопоставляется в том же родительском структурном слоте;
- Content Hash отличается;
- `node_versions` содержит версии 1 и 2 с прежним и новым Hash;
- запрос с прежним `expected_hash` возвращает `stale_source` и не содержит поля `node`;
- запрос с новым Hash возвращает `ok` и актуальный узел;
- новая версия тестовой БД публикуется только в `sfra-state-test`.

Этот сценарий доказывает перенос идентичности через границу двух workflow runs и сохранение истории при последующем редактировании, не затрагивая рабочее состояние.

## 7. Риски и меры защиты

| Риск | Защита |
|---|---|
| Пустая БД вместо старого состояния | Fail-closed, отдельный режим первичной инициализации |
| Повреждённый или неполный файл SQLite | SHA-256 manifest, `PRAGMA integrity_check` |
| Одновременные записи в state branch | `concurrency`, fast-forward push, отказ при конфликте |
| Попадание Vault или посторонних файлов в state branch | Настоящая orphan-история, root commit без родителя, allowlist файлов и проверка полного дерева |
| Разглашение текста заметок | Учитывать, что ветка не ограничивает доступ участников репозитория; использовать отдельный репозиторий/ACL, если содержимое конфиденциально |
| SQLite WAL/SHM при публикации | Закрыть соединения; создавать согласованный снимок через SQLite Backup API (`Connection.backup()`) |
| Повреждение готового снимка | `PRAGMA integrity_check` и SHA-256 уже сформированного файла перед публикацией |
| Загрязнение производственного состояния тестами | Выделенная тестовая SQLite, отдельный fixture Vault и `sfra-state-test`; запрет записи интеграционного workflow в `sfra-state` |
| Незамеченное изменение исходного файла | Сверять текущий SHA-256 файла с `documents.source_sha256` в адресном API |
| Подмена новой версии при старом Hash | Возвращать `stale_source` без содержимого узла |
| Выход за пределы Vault через путь или symlink | Разрешать canonical path и проверять принадлежность `vault_root` до чтения |

Отдельно следует следить за размером SQLite в Git. Если база существенно вырастет, нужно будет пересмотреть способ хранения бинарных снимков. Для текущего этапа обычная SQLite-база в отдельной ветке проще и прозрачнее внешнего хранилища.

## 8. Результаты проверки и границы текущего этапа

Подтверждено статической проверкой:

- Существующая схема v2 уже хранит требуемые ID, Hash, версии и события.
- Существующий `index_vault()` может продолжить работу с восстановленной БД без изменения алгоритма.
- Текущий алгоритм C предусматривает сохранение ID при однозначном сопоставлении и новую версию при изменении узла.
- В текущем публичном API нет `get_node_by_id(..., expected_hash)`.
- Workflow сейчас не сохраняет SQLite вне временного каталога runner.
- Ветка `sfra-state` на момент анализа отсутствует.
- Тестовая БД и тестовая ветка состояния должны быть изолированы от рабочего состояния.

Базовый CI этапов B/C ранее проходил с 23 тестами. Эти тесты подтверждают локальную работу SQLite и идентичности, но не подтверждают загрузку/публикацию между runner: такого интеграционного сценария пока нет.

**Новые механизмы не реализованы, межзапусковой тест не запускался, ветка `sfra-state` не создавалась.** Это аналитическое решение с уточнениями для повторной проверки. Следующий шаг должен быть отдельным этапом после вердикта аналитика.
