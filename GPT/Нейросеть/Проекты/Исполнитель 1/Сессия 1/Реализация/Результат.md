## 1. Краткое описание

Реализован Python-модуль структурной индексации Markdown для Obsidian Vault. Индексатор разбирает исходные Markdown-файлы с помощью AST, строит дерево Document → Structural Node → Passage, сохраняет точные координаты и исходные фрагменты, хранит индекс отдельно в SQLite, присваивает устойчивые Node ID, вычисляет независимые SHA-256 Content Hash, сохраняет версии узлов и инкрементально обновляет только изменённые документы.

**Основной принцип:** индекс указывает, источник говорит. AST определяет структуру, но извлекаемый текст всегда получается срезом исходной строки. Авторский Markdown не сериализуется из AST и не меняется.

Реализация не включает FTS5, лемматизацию, реестр сущностей, алиасы, фасеты, Context Builder, MCP, эмбеддинги или автоматическое определение каноничности.

Выбран `markdown-it-py`: блочные AST-токены имеют source map с координатами исходных строк, а встроенное правило таблиц включается явно. AST используется для структуры; текст возвращается исключительно исходным срезом.

Obsidian Callout распознаётся как blockquote с маркером `> [!TYPE]`. Внешние и локальные Markdown-ссылки сохраняются внутри исходных блоков; target-ы ссылок регистрируются в metadata, но внешние страницы не загружаются.

Проверено на markdown-it-py 4.3.0 в GitHub Actions.

## 4. Алгоритм сегментации

### Заголовки

H1–H6 формируют вложенные узлы `heading`. Диапазон узла и его `raw_text` охватывают заголовок и полное поддерево до следующего заголовка того же или более высокого уровня.

Собственное содержимое родителя отделено в `content_spans`: заголовочная строка и непосредственные блоки секции, без дочерних heading-секций. Это позволяет различать полный диапазон секции и её собственный текст.

### Вложенные списки

Модель: `list → list_item → nested list / block`. Диапазон родительского пункта включает дочерние ветви, но его `content_spans` содержат только непосредственные блоки самого пункта.

### Остальные блоки

- Абзацы — самостоятельные блоки.
- Callout и цитаты — цельные блоки.
- Таблицы — цельный блок с сохранённой Markdown-разметкой.
- Fenced и indented code — цельные блоки.
- Ссылки остаются в исходном блоке.
- Документы без заголовков строятся как набор блоков под корнем Document.
- Пустые файлы регистрируются как документы с пустым root.
- Соседние короткие абзацы не объединяются автоматически.

### Passage и родительский контекст

Passage создаётся только при превышении мягкого размера и только по уже существующим дочерним границам. Неразделимый крупный блок остаётся цельным с предупреждением.

`Passage.raw_text` и его координаты соответствуют только точному срезу источника. Контекст хранится отдельно в `context_text` и `context_spans`.

Контекст включает исходные строки заголовков и прямое содержимое всех родительских `list_item`. Вложенная ветвь, возвращённая самостоятельно, сохраняет условие родительского пункта без добавления этого условия в `raw_text` или диапазон Passage.

Оценка размера — приблизительный подсчёт Unicode-слов, не количество токенов модели.

## 5. Координаты и контроль первоисточника

У каждого узла и Passage хранятся:

- `source_path` — относительный путь;
- `line_start` / `line_end` — строки с 1, включительно;
- `char_start` / `char_end` — 0-based полуоткрытый диапазон Python Unicode code points;
- `byte_start` / `byte_end` — 0-based полуоткрытый диапазон UTF-8 bytes;
- `raw_text` — точный оригинальный текстовый срез.

Файлы читаются с `newline=""`, чтобы не нормализовать LF/CRLF. Автоматическая проверка сверяет символьные и байтовые границы с исходным текстом. Тесты покрывают кириллицу, emoji, специальные символы, латиницу с диакритикой и оба типа окончаний строк.

Пример:

~~~markdown
# Профиль
Текст описания.

## Характер
Спокойный и наблюдательный.
~~~

Пример дерева:

~~~text
Document
└── heading: Профиль
    ├── paragraph: Текст описания.
    └── heading: Характер
        └── paragraph: Спокойный и наблюдательный.
~~~

Извлечение абзаца «Текст описания.»:

| Координата | Значение |
|---|---:|
| line_start | 2 |
| line_end | 2 |
| char_start | 10 |
| char_end | 26 |
| byte_start | 17 |
| byte_end | 46 |

Извлекаемый фрагмент:

~~~python
source[10:26]  # "Текст описания.\n"
~~~

Символьный срез и UTF-8-байтовый срез возвращают одинаковый оригинальный текст. Дополнительный контекст не включён в эти координаты.

## 6. Node ID и Content Hash

Это независимые поля:

- **Node ID** — непрозрачный `node_<UUID4>`, идентифицирующий структурную сущность;
- **Content Hash** — `sha256:<hex>` от точного UTF-8 текста `raw_text`, идентифицирующий конкретную версию содержимого.

Алгоритм сопоставления выполняется внутри одного документа:

1. Уникальное совпадение `node_type + content_hash` может сохранить ID при переносе неизменённого узла.
2. Уникальное совпадение заголовка по точным `level + title` сохраняет ID при изменении тела секции и при однозначном переносе заголовка.
3. Внутри уже сопоставленного родителя единственная пара старого и нового узлов одного типа может сопоставляться как уникальный структурный слот. Это позволяет сохранить ID при изменении текста единственного абзаца или пункта в секции.
4. Если остаётся несколько кандидатов, новый узел получает новый ID и статус `ambiguous`; старые адреса становятся `stale`. Событие сохраняет candidate Node IDs. Молчаливой подмены нет.
5. Если предыдущего кандидата нет, создаётся новый узел со статусом `active`.

Проверены повторная индексация, изменение текста, перемещение заголовка, неоднозначные повторяющиеся блоки, локальное разрешение дублирующихся заголовков родительским контекстом и удаление узлов.

### Версии

`node_versions` хранит каждый уникальный снимок узла: Content Hash, исходный текст, тип, родителя, heading_path, координаты, content_spans и metadata. Версия добавляется при изменении текста, координат или структурного родителя. Неизменённая версия не дублируется.

`node_match_events` хранит причины сопоставления: exact hash, heading key, unique sibling slot, новый узел, stale, ambiguous и удаление документа.

## 7. SQLite

Текущая схема — версия 2.

| Таблица | Содержание |
|---|---|
| `schema_info` | Версия схемы |
| `documents` | Путь, размер, SHA-256 файла, поколение, статус |
| `structural_nodes` | Текущие и stale узлы, Node ID, Content Hash, parent, координаты, raw Markdown, статус |
| `passages` | Точные фрагменты и отдельный контекст |
| `node_versions` | История снимков узлов |
| `node_match_events` | Результаты и причины сопоставления |

Предусмотрена миграция схемы этапа B (v1) в v2: существующие узлы получают UUID и SHA-256, для них записывается версия 1, а SHA-256 документа рассчитывается из текста сохранённого корневого узла.

FTS5 и таблицы следующих этапов не создаются.

## 8. Инкрементальная синхронизация

Для каждого файла вычисляется SHA-256 всего исходного Markdown.

- Если hash совпадает с активной версией документа, файл не парсится и его SQLite-записи не обновляются.
- Если hash изменился, переиндексируется только этот документ в транзакции SQLite.
- Исчезнувший файл не удаляется физически: документ получает статус `deleted`, его актуальные узлы — `stale`, история версий сохраняется.
- Файл, появившийся снова после состояния deleted, начинает новую активную линию адресации; stale ID не оживляются автоматически.

~~~bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -e . pytest
python -m pytest
~~~

~~~bash
sfra-index parse path/to/note.md
~~~

~~~bash
sfra-index index --vault /path/to/Vault --index-dir /path/outside/Vault/.sfra-index
~~~

Сводка индекса:

~~~bash
sfra-index info --db /path/outside/Vault/.sfra-index/structure.sqlite3
~~~

Python API:

~~~python
from sfra_indexer import index_vault, get_database_summary

result = index_vault("/path/to/Vault", "/path/outside/Vault/.sfra-index")
print(result.documents_indexed, result.documents_skipped)
print(get_database_summary(result.database_path))
~~~

## 12. Ограничения и известные проблемы

1. Сопоставление намеренно консервативно. Некоторые неоднозначные изменения требуют нового ID вместо рискованного наследования старого.
2. Переименование заголовка без уникального совпадения по прежнему содержимому не считается тождеством.
3. Перенос узла с одновременным изменением текста и родителя не имеет надёжного якоря; алгоритм не пытается угадать соответствие.
4. Callout, blockquote, table и code остаются атомарными блоками; внутренние элементы Callout не индексируются отдельными дочерними узлами.
5. Wikilinks, embeds, frontmatter/properties и сторонние Obsidian-конструкции сохраняются как исходный текст, но не получают отдельной семантической модели.
6. Индексатор при каждом сканировании обходит дерево файлов для вычисления hash; неизменённые документы не парсятся и не переписываются в БД. File watcher пока не реализован.
7. При потере или ручном удалении sidecar SQLite постоянные Node ID теряются; базу следует резервировать отдельно от Vault.
8. Проверка производительности на больших многопользовательских Vault не проводилась. Оптимизация скорости не была целью этапов B/C.

## 13. Что требуется следующим этапам

Этапы B и C обеспечивают структурную основу и адресуемую историю источников. Следующим этапам SFRA предстоит независимо реализовать:

- FTS5 и полнотекстовый поиск;
- русскую лемматизацию;
- Entity Registry и aliases;
- facets;
- Retrieval Engine;
- Context Builder;
- MCP-интерфейс;
- опциональный семантический слой после оценки необходимости.

Эти подсистемы не входят в текущую реализацию и не должны менять правило: индекс служит навигации, доказательством остаётся оригинальный фрагмент.
