# Этап C — идентификаторы, версии и инкрементальная синхронизация

Статус: техническая спецификация перед реализацией.  
Ветка: executor-1/sfra-indexer-session-1.

## 1. Независимые идентификаторы

- Node ID — постоянная идентичность структурного узла, создаётся как `node_<UUID4>` и хранится в SQLite.
- Content Hash — `sha256:<hex>` от UTF-8 байтов точного `raw_text` узла. Он меняется при изменении исходного Markdown-фрагмента независимо от Node ID.
- Node Version — последовательный снимок содержимого и координат узла с отдельным номером версии.

## 2. Алгоритм сопоставления

Сопоставление выполняется только внутри одного документа и консервативно:

1. Уникальное совпадение пары `node_type + content_hash` в документе. Это позволяет безопасно пережить перенос неизменённого блока.
2. Уникальное совпадение заголовка по паре `level + exact title` в документе. Это сохраняет Node ID при изменении тела секции и при переносе однозначно узнаваемого заголовка.
3. Внутри уже сопоставленного родителя, если для одного node_type осталась ровно одна старая и одна новая структурная единица, пара сопоставляется по уникальному структурному слоту. Это покрывает изменение текста единственного абзаца/пункта в секции.
4. Если остаётся несколько старых и/или новых кандидатов одного типа, старые узлы получают состояние `stale`, новые узлы — `ambiguous` и новые Node ID. Событие сохраняет все старые candidate IDs. Никакой старый ID не назначается одному из кандидатов наугад.
5. Если кандидатов для нового узла нет, это новый узел со статусом `active`. Старые несопоставленные узлы получают статус `stale`.

Сначала сопоставляется корень документа, затем дочерние узлы уже сопоставленных родителей. Глобальные уникальные совпадения по хешу и уникальные заголовки обрабатываются до локального сопоставления.

### Что не делается автоматически

- Переименование заголовка не считается доказательством тождества: если нет точного уникального совпадения по содержимому, создаётся новый ID.
- Два одинаковых абзаца нельзя различить только по одинаковому тексту, если их несколько.
- При переносе блока с одновременным изменением содержимого и сменой родителя нет надёжного структурного якоря. Такое соответствие не угадывается.

## 3. Версии и статусы

`node_versions` сохраняет каждый подтверждённый снимок узла: номер версии, hash, текст, parent Node ID, heading_path, source locator и metadata. Новая версия создаётся, если изменился текст, координаты или структурный родитель. При неизменённом снимке версия не дублируется.

`node_match_events` сохраняет результат сопоставления для каждого узла: точное совпадение, заголовок, уникальный слот, новый узел, неоднозначность, устаревший/удалённый узел. Для ambiguous записывается массив candidate Node ID.

Текущие узлы имеют `active` или `ambiguous`; прежние адреса, больше не являющиеся текущими, имеют `stale`. Неоднозначный новый Node ID можно использовать как текущую provisional-адресацию, но его происхождение остаётся явно помеченным в событии и версии.

## 4. Инкрементальная синхронизация

Для каждого пути вычисляется SHA-256 всего исходного файла. Если hash совпадает с последней активной версией документа, парсинг и запись пропускаются.

Если файл изменился:

1. Парсится только он.
2. Его структурные узлы сопоставляются с предыдущим активным поколением.
3. В одной транзакции сохраняются новые снимки, версии, события сопоставления, Passage и file hash.
4. Остальные документы не затрагиваются.

Исчезнувший файл не удаляется из SQLite физически: Document получает статус `deleted`, его текущие узлы — `stale`, а история версий сохраняется. Индексный каталог всегда остаётся вне Vault.

## 5. Обратная совместимость

Схема этапа B имеет версию 1. Миграция создаёт поля Node ID, Content Hash, статусы и таблицы версий/событий, назначает UUID текущим узлам этапа B и записывает для каждого начальную версию. Полный текст источника для миграционного SHA-256 берётся из сохранённого корневого узла документа.
