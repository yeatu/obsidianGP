Задание для Исполнителя 1: разработка структурного индексатора SFRA
1. Цель

Разработать первую рабочую версию структурного индексатора для Obsidian Vault в соответствии с архитектурным документом проекта.

Индексатор должен читать Markdown-файлы, определять их структуру и создавать отдельное индексное представление, которое позволяет адресно извлекать оригинальные фрагменты документов.

Главный принцип: индекс указывает, источник говорит.

Индексатор не должен пересказывать, переписывать или интерпретировать авторские материалы. Его задача — корректно находить структурные границы и сохранять связь каждого фрагмента с первоисточником.

Речь идёт о рабочей основе для тестирования, а не о попытке создать идеальный промышленный продукт с первого захода.

4. Требования к индексатору
4.1. Разбор Markdown

Используй Python и Markdown AST-парсер, сохраняющий координаты исходных блоков.

Индексатор должен распознавать:

заголовки H1–H6;
абзацы;
вложенные списки;
цитаты;
Obsidian Callout;
таблицы;
Markdown-ссылки;
кодовые блоки;
обычные текстовые блоки без заголовков.

Выбранную библиотеку и причины выбора зафиксируй в документации.

4.2. Структура индекса

Реализуй трёхуровневую модель:

Document → Structural Node → Passage

Где:

Document — исходный Markdown-файл.
Structural Node — самостоятельная структурная единица: секция, ветвь списка, таблица или текстовый блок.
Passage — часть крупного узла, если его невозможно эффективно передать целиком.

Каждый дочерний узел должен сохранять связь с родителем.

У каждого узла должны быть предусмотрены поля:

node_id;
source_path;
node_type;
parent_node_id;
heading_path;
line_start;
line_end;
content_hash;
raw_text.

Допускаются дополнительные технические поля, если они действительно необходимы.

4.3. Правила сегментации

Реализуй следующие правила.

Документы с заголовками

Заголовок вместе с собственным содержимым образует структурный узел. Вложенные заголовки становятся дочерними узлами.

Вложенные списки

Родительский пункт и его дочерние элементы должны сохранять смысловую связь. Не превращай каждый элемент списка в независимый фрагмент.

Документы без заголовков

Используй абзацы и самостоятельные структурные блоки как первичные границы. Соседние короткие абзацы допускается объединять.

Таблицы

Сохраняй таблицы целиком, пока их размер позволяет. При разделении повторяй заголовки столбцов.

Callout, цитаты и кодовые блоки

Не разрывай эти конструкции произвольно.

Крупные узлы

Используй мягкий ориентир 400–900 токенов, но не жертвуй смысловой целостностью ради размера. При необходимости разделяй узел по дочерним структурам с сохранением контекста родителя.

Если безопасное разделение невозможно, лучше сохранить крупный узел и сообщить о превышении размера.

4.4. Координаты и исходный текст

Каждый узел должен однозначно указывать на соответствующий участок исходного Markdown.

Обязательно сохраняй:

относительный путь к файлу;
начальную и конечную строки;
при возможности символьные смещения;
точный исходный текст фрагмента.

При выдаче текста запрещено восстанавливать его сериализацией AST. Нужно возвращать исходный текстовый срез.

Проверяй, что извлечённый фрагмент побайтно или посимвольно соответствует исходному участку с учётом выбранной системы координат.

4.5. Node ID и Content Hash

Эти понятия должны быть независимыми.

Node ID идентифицирует структурный узел.

Content Hash идентифицирует конкретное содержимое узла.

Для Content Hash используй SHA-256.

Node ID должен сохраняться при повторной индексации, если старый и новый узел удалось однозначно сопоставить.

При неоднозначном сопоставлении запрещено молча присваивать старый идентификатор другому содержимому. Такой узел должен получить статус, позволяющий определить, что прежняя адресация устарела или требует проверки.

Опиши алгоритм сопоставления старых и новых узлов. Не выдавай ненадёжное совпадение за достоверное.

4.6. Хранение индекса

Используй SQLite.

На этом этапе достаточно базовой структуры для хранения:

документов;
структурных узлов;
иерархии узлов;
версий и состояния сопоставления идентификаторов.

Не создавай пока FTS-таблицы и механизмы поиска.

Предусмотри возможность расширения схемы на следующих этапах без необходимости полностью переписывать индексатор.

Индекс должен храниться отдельно от исходного Vault.

5. Неизменность Vault

Это обязательное требование.

Индексатор работает только на чтение исходных материалов.

Запрещено:

изменять Markdown-файлы;
добавлять комментарии или метаданные в заметки;
добавлять YAML frontmatter;
переименовывать или перемещать документы;
исправлять авторские ошибки;
удалять дубликаты или параллельные источники.

Все производные данные должны находиться вне исходного Vault.

7. Тестирование

Создай тестовые Markdown-файлы, покрывающие как минимум следующие случаи:

Документ с несколькими уровнями заголовков.
Документ без заголовков.
Вложенные списки.
Obsidian Callout.
Таблицы.
Кодовые блоки и цитаты.
Кириллица и специальные символы.
Очень большой структурный узел.

Проверь следующие свойства:

повторная индексация неизменённого документа даёт одинаковую структуру;
Content Hash корректно отражает содержимое;
исходный текст фрагментов сохраняется без искажений;
родительские и дочерние связи корректны;
Node ID не меняется при повторной индексации неизменённого узла;
изменение содержимого отражается в Content Hash;
неоднозначное сопоставление не приводит к молчаливой подмене идентификатора;
исходные файлы остаются неизменными.

По возможности проведи дополнительную проверку на реальных материалах из папки ГП. Если фактическая структура файлов недоступна и имеется только dump.md, отдельно зафиксируй это ограничение. Не подменяй проверку реального Vault проверкой одного искусственного файла.

8. Критерии приёмки

Работа считается выполненной, если:

Индексатор запускается локально по инструкции.
Он способен обработать набор Markdown-документов.
Строит иерархию структурных узлов.
Возвращает оригинальные фрагменты с координатами источника.
Сохраняет независимые Node ID и Content Hash.
Не изменяет исходные документы.
Повторная индексация работает предсказуемо.
Автоматические тесты проходят.
Документация позволяет другому разработчику запустить и проверить модуль.
Результат можно передать следующему этапу разработки без необходимости переписывать его с нуля.

Не скрывай ограничения реализации. Если конкретная конструкция Markdown обрабатывается упрощённо, это должно быть явно указано.
