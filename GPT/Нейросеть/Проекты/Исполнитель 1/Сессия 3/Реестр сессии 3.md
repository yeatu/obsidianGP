# E1. Реализовать публичное API точного чтения первоисточника


**Цель:** завершить недостающую часть Structural Indexer. По паре `Node ID + Content Hash` система должна уметь получить точный фрагмент актуального Markdown-файла, а не просто вернуть сохранённый в SQLite текст.


## 1. Исходное состояние


Ветка реализации: `executor-1/sfra-indexer-session-1`.


Этапы B/C и persistence уже реализованы. В документации этапа Persistence прямо указано, что API `get_node_by_id(..., expected_hash)` не входило в его объём.


Ориентироваться на:


- архитектурный документ SFRA, разделы об идентификаторах, `read_source` и проверке первоисточника;
- `02_Проектирование_этапа_C.md`;
- `05_Результат_этапа_1_Persistence.md`.


## 2. Реализовать


Добавить и экспортировать публичный API чтения узла. Ожидаемый контракт:
```
get_node_by_id(
    node_id: str,
    expected_hash: str,
    vault_root: Path,
)
```


Сохранять эту форму, если она уже предусмотрена текущей реализацией или спецификацией. Если для подключения к SQLite требуется дополнительный параметр, сначала зафиксировать это в документации и тестах, не создавать скрытую глобальную конфигурацию.


API должен:


1. Найти узел по точной паре `node_id + expected_hash`.
2. Принимать только узлы со статусом `active`.
3. Отвергать `ambiguous`, `stale`, `deleted` и отсутствующие узлы.
4. Проверить, что исходный файл существует внутри переданного `vault_root`.
5. Проверить соответствие текущего файла сохранённому `documents.source_sha256`.
6. Восстановить фрагмент по исходным координатам, учитывая систему координат `char_start/char_end`.
7. Вычислить SHA-256 точных UTF-8-байтов полученного фрагмента.
8. Сравнить результат с `expected_hash`.
9. Вернуть дословный фрагмент из текущего Markdown-файла вместе с метаданными адресации.


Нельзя считать `raw_text` из SQLite достаточным доказательством актуальности первоисточника. Его допустимо использовать для сверки, но возвращаемый текст должен быть проверен относительно самого файла.


Если файл изменился после индексации, узел неоднозначен, хеш не совпадает или координаты невалидны, API должен завершаться явной ошибкой/статусом устаревшего адреса. Не возвращать старый фрагмент и не подбирать похожий узел автоматически.


## 3. Безопасность и неизменность


- Открывать SQLite только для чтения.
- Не изменять Vault.
- Проверять, что `source_path` не позволяет выйти за пределы `vault_root`, в том числе через символические ссылки.
- Не нормализовать переносы строк, Unicode, пробелы или Markdown-разметку до вычисления хеша.
- Не путать символьные смещения Python-строки с байтовыми смещениями UTF-8.


## 4. Обязательные тесты


Проверить как минимум:


- успешное чтение актуального активного узла;
- неправильный `expected_hash`;
- отсутствующий Node ID;
- статусы `ambiguous`, `stale`, `deleted`;
- изменение исходного файла после индексации;
- изменение целевого фрагмента;
- изменение другой части документа с последующим устареванием индекса;
- Unicode, кириллицу и emoji;
- LF и CRLF;
- некорректные координаты;
- отсутствующий файл;
- попытку чтения пути за пределами Vault;
- отсутствие записи в SQLite и изменения исходного файла.


## 5. Отдельно зафиксировать источник Vault


Сейчас нельзя оставлять неявным, из какой ветки репозитория индексируются заметки.


Добавить явную фиксацию `vault_ref` и фактического `vault_commit_sha` в конфигурацию запуска и manifest. Не переключать источник на `main` автоматически. Сохранить текущую совместимость и описать, какой ref использовался в каждом запуске.


## 6. Критерии приёмки


- Публичный API доступен через пакет `sfra_indexer`.
- Возвращается проверенный исходный фрагмент, а не непроверенная копия из SQLite.
- Устаревшие, неоднозначные и изменившиеся источники отклоняются без подмены.
- Все тесты проходят локально и в CI.
- Vault и production SQLite не изменены тестами.
- Документация содержит сигнатуру, формат результата и перечень возможных ошибок.


**Результат:** отдельный PR в `main`, тесты, описание API, commit SHA и ссылки на CI. Не объединять эту работу с переработкой схемы SQLite, если для неё нет доказанной необходимости.

```
read_source_scope(
    db_path,
    vault_root,
    node_id,
    expected_hash,
    *,
    scope,
    snapshot_id,
) -> SourceScopeResult
```


Поддерживаемые значения `scope`:


- `node` — точный целевой узел.
- `parent` — целевой узел и его непосредственный родитель.
- `neighbors` — целевой узел и его непосредственные соседние узлы в порядке следования в документе, с учетом того же родителя.
- `document` — полный оригинальный Markdown-документ из Vault.


Существующие публичные методы чтения по возможности сохранить как совместимые обёртки над новым API. Не дублировать и не поддерживать две независимые реализации логики чтения.


### 2. Обеспечить атомарность чтения


В рамках одного вызова `read_source_scope()`:


- использовать одно SQLite-соединение;
- открыть одну read-транзакцию;
- выполнять все необходимые SQL-чтения в рамках этой транзакции;
- не открывать дополнительные соединения для получения родителя, соседей или документа;
- обеспечить согласованность всех возвращаемых записей по одной версии индексного состояния.


Чтение исходных файлов должно выполняться из переданного `vault_root`. При этом необходимо сохранять существующие проверки безопасности: безопасный путь, отсутствие обхода через symlink, проверку целостности файла и соответствие исходного текста сохранённым координатам.


### 3. Проверять согласованность каждого фрагмента


Для каждого возвращаемого фрагмента обеспечить проверку и возврат следующих данных:


- `node_id`;
- `content_hash`;
- `source_path`;
- `document_hash` — значение `documents.source_sha256`;
- `index_generation` — значение `documents.generation`;
- точный `raw_text`.


Необходимо проверять, что узел и его родитель/соседи принадлежат одному документу и одной актуальной генерации индекса. Проверять не только статус узла, но и согласованность его привязки к записи документа.


Необходимо исключить возврат узлов со статусами `ambiguous`, `stale`, `deleted` и других неактивных состояний. Не возвращать исторические или неоднозначные записи в качестве текущих.


### 4. Соблюдать правила возврата исходного текста


- `raw_text` должен точно соответствовать первоисточнику.
- Документная область должна возвращать полный оригинальный Markdown-файл, а не реконструкцию из `node_versions`.
- Не обрезать текст по токенам или размеру.
- Не подменять `document_hash` хешем узла.
- Не подставлять отсутствующие значения из других хешей или полей.


Если проверка хеша, поколения, пути, координат, статуса или согласованности не проходит, метод должен вернуть ошибку и пустой список фрагментов. Частичный результат недопустим.


### 5. Добавить разрешение актуального узла


Реализовать публичный метод:
```
resolve_current_node(
    db_path,
    node_id,
    *,
    snapshot_id,
) -> CurrentNodeAddress
```


Метод должен возвращать адрес актуального узла и его текущий `content_hash`, необходимые E3 для последующего точного чтения.


Требования:


- искать только актуальную запись;
- не использовать fuzzy matching;
- не возвращать исторические версии;
- не подменять отсутствующий узел похожим;
- при неоднозначности или отсутствии актуальной записи возвращать явный отказ.


### 6. Учесть Snapshot binding


`E1` принимает `snapshot_id` от вызывающей стороны и возвращает тот же идентификатор в результате каждого вызова `read_source_scope()` и `resolve_current_node()`.


Важное разделение ответственности:


- E3 отвечает за проверку `SnapshotRef`, привязку Vault и sidecar к конкретным Git-коммитам, проверку manifest и вычисление его SHA-256.
- E1 использует переданные `db_path`, `vault_root` и `snapshot_id`.
- E1 не выполняет git fetch, checkout, переключение веток или самостоятельный поиск актуального snapshot.
- E1 не должен изображать проверку Git-привязки, которую фактически выполняет E3.


`Snapshot ID` для E1 является непрозрачным идентификатором контекста чтения: принять, использовать в результате и вернуть без изменений.


### 7. Метаданные и бюджет


Не добавлять самостоятельно значения `preservation`, `required_with`, `parent_context_required` и не выводить их из эвристик.


Передавать только те значения, которые действительно присутствуют в существующих метаданных узла. Эти поля относятся к политике Context Builder, а не к структурным фактам первоисточника.


Не реализовывать токенный бюджет и не обрезать выдачу. E1 возвращает полный проверенный текст. Контроль бюджета находится на стороне E3.
