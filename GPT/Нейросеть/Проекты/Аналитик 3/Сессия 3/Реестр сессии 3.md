### 3. Snapshot consistency


Это наиболее важная часть будущей реализации.


Недостаточно просто записать три SHA в объект `SnapshotRef`. Нужно гарантировать, что все операции одного запроса действительно используют один снимок:


1. Фиксируется `vault_commit_sha`.
2. Фиксируется `sidecar_commit_sha`.
3. Фиксируется `manifest_sha256`.
4. Проверяется соответствие `manifest.source_commit` и `vault_commit_sha`.
5. Поиск, разрешение зависимостей и чтение оригинала используют именно эти закреплённые версии.


В противном случае можно получить поисковый результат из одной версии Vault, а исходный текст из другой. Формально система ответит, но фактически это будет уже другой источник.

**1. SearchAdapter**


Начать реализацию адаптера поверх фактического интерфейса E2.


Обязательные условия:
- не копировать поисковую логику E2;

- корректно отображать `tier`, BM25 и направление сортировки;

- корректно учитывать достижение лимита результатов.


Добавить unit-тесты на реальные формы ответов E2 и искусственные фикстуры.


**2. SourceReader**


Создать транспортно-независимый интерфейс SourceReader с поддержкой всех четырёх scope:
- node;
- parent;
- neighbors;
- document.


Не писать собственные SQL-запросы к внутренней SQLite E1. Не извлекать соседние узлы самостоятельным разбором Markdown.


PR №9 Исполнителя 1 пока предоставляет API точного чтения одного узла. Для остальных scope необходимо согласовать расширение публичного API E1.


В частности, требуется возможность получить проверенные данные родителя, соседних узлов и полного документа с контрольными хешами и принадлежностью к одному снимку.


До появления такого API допускается разработка через тестовую реализацию SourceReader. Реальную интеграцию нельзя объявлять завершённой.


**3. Snapshot consistency**


Реализовать закрепление трёх компонентов SnapshotRef:
- vault_commit_sha;
- sidecar_commit_sha;
- manifest_sha256.


Все последующие операции поиска и чтения должны использовать один и тот же снимок. При несовпадении версии возвращать явную ошибку целостности.


Добавить тесты, подтверждающие отказ при попытке получить зависимость или исходный фрагмент из другого поколения.


**4. Интеграционные тесты**


Сначала реализовать полный сценарий на фикстурах:


search → SearchAdapter → SearchBatch → ContextBuilder → ContextPack → SourceReader.


Проверить:
- дедупликацию;
- tier/BM25;
- точный SHA-256;
- все четыре scope;
- stale и ambiguous;
- обязательные зависимости;
- бюджет;
- единый SnapshotRef на всём протяжении запроса.


Все тесты Б1 должны продолжать проходить без переписывания принятого ядра.


После появления пригодного API E1 провести сквозной тест на реальном Vault. Не изменять Vault и SQLite E1.


**5. Организация работы**


1. Синхронизировать ветку `executor-3/context-integration-stage-c1` с актуальным `main`.
2. Вносить реализацию в отдельные логические коммиты.

Не включать в этот PR GitHub Issue worker, recovery workflow и MCP adapter. Это отдельный этап.


**Приоритет:** сначала рабочий SearchAdapter и тестовое ядро интеграции, параллельно согласование полного read API с E1. Затем реальный SourceReader и сквозной прогон.

## 3. Найденные замечания


Здесь уже начинается собственно аналитическая работа.


### Блокер №1. E1 пока не предоставляет интерфейс в требуемом E3 формате


У Исполнителя 1 теперь есть [PR №11](https://github.com/yeatu/obsidianGP/pull/11).


Положительный момент: в нём появились публичные функции:


- `get_node_by_id`;
- `get_parent_by_id`;
- `get_neighbors_by_id`;
- `get_document_by_id`.


То есть предыдущая ситуация, когда существовало только чтение одного узла, изменилась.


Но я проверила фактические модели E1. `NodeRecord` сейчас не содержит:


- `index_generation`;
- `metadata` с `preservation`;
- `required_with`;
- `parent_context_required`.


Также E1 использует `source_sha256`, тогда как E3 ожидает `document_hash`.


Кроме того, ответы новых функций E1 пока имеют другую структуру, чем контракт `E1ScopeAPI`, ожидаемый E3.


Это не означает, что функции E1 плохие. Это означает, что адаптер между двумя публичными контрактами ещё не реализован.


**Особенно важно:** без явных dependency metadata Context Builder не может гарантировать сохранение обязательных ограничений и связей.


### Блокер №2. Недостаточно строгая проверка связей в SourceReader


Нашла конкретный недостаток в `source_reader.py`.


Сейчас проверяется наличие фрагмента `parent_context`, если у целевого узла указан родитель.


Но не проверяется, что:


`parent_context.node_id == target_source.parent_node_id`


То есть тестовый или ошибочный E1 provider теоретически может вернуть другой узел того же документа, и проверка его пропустит.


Аналогично для соседей:


- не проверяется совпадение `parent_node_id`;
- не проверяется порядок соседей относительно целевого узла;
- не исключается повторение одного Node ID под разными ролями.


Это нужно исправить до принятия SourceReader.


### Блокер №3. Потеря dependency metadata


В `search_adapter.py` при отсутствии metadata устанавливаются значения по умолчанию:


- `preservation = normal`;
- `required_with = []`;
- `parent_context_required = false`.


Добавляется предупреждение `dependency_metadata_unavailable`.


Но предупреждение не передаётся непосредственно в `ContextBuilder.build()`. Pipeline сохраняет его отдельно в `SearchAdapterResult.diagnostics`.


В результате Context Pack потенциально может иметь статус `complete`, хотя важные зависимости не были получены.


Это опасная ситуация: система не должна считать отсутствие сведений о обязательности доказательством отсутствия обязательных связей.


Требуется fail-closed поведение либо явный статус неполной выдачи.


### Дополнительное замечание. Snapshot binder


Основная логика проверки manifest и SQLite реализована хорошо.


Но `bind_pinned_snapshot()` получает `vault_commit_sha` и `sidecar_commit_sha` как аргументы и самостоятельно не подтверждает, что они действительно совпадают с HEAD соответствующих Git checkout.


Нужно закрепить это в запускающем коде через реальные результаты `git rev-parse HEAD` и добавить интеграционную проверку.
