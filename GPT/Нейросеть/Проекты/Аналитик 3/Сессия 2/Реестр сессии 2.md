## 2. Найденные дефекты


### Блокер №1. Неправильный расчёт бюджета


**Файл:** `src/sfra_context_builder/budget.py`, строка 54.


В принятой спецификации Этапа А, ADR-07, установлено:


`budget_tokens` ограничивает включаемый материал и его provenance.


Служебная структура ответа, в частности Coverage, Deferred и Diagnostics, учитывается отдельно через `response_tokens_estimated`.


Но сейчас реализация считает:


```python
payload = {
    "Included": list(included),
    "Coverage": list(coverage),
}
return token_counter.count(compact_json(payload))
```


Таким образом, Coverage расходует бюджет, предназначенный для включённых источников.


**Почему это проблема:**


Предположим, что исходный узел вместе с provenance помещается в бюджет. Но клиент передал большое количество focus-аспектов. Объём Coverage увеличился, и тот же узел теперь может быть отклонён.


Получается, что увеличение количества аспектов способно лишить клиента исходного текста, который раньше помещался в бюджет.


Это противоречит принятому ADR-07.


**Что исправить:**


1. Разделить подсчёт `Included + provenance` и подсчёт полного ответа.
2. `tokens_used` должен отражать именно расход бюджета Included.
3. Coverage, Deferred и Diagnostics учитывать в `response_tokens_estimated`.
4. Не удалять служебные сведения ради искусственного соблюдения бюджета.


Добавить тест, в котором Included помещается в бюджет, но Coverage существенно увеличивает размер результата. Включение источника не должно зависеть от объёма Coverage.


### Блокер №2. Неверный статус при неразрешённой зависимости известного узла


**Файлы:**
- `builder.py`, строки 174–190;
- `builder.py`, строки 338–353.


Здесь более неприятная проблема.


Рассмотрим сценарий:


- Клиент передал узел A в `known`.
- Узел A имеет `required_with = ["M"]`.
- Узел M отсутствует в SearchBatch.
- DependencyResolver отсутствует либо не может разрешить M.


Код правильно обнаруживает неразрешённую зависимость.


Однако в обработке группы есть следующий механизм:


```python
new_members = [
    member for member in group.members
    if member.node_id not in known_ids
]
```


После этого Deferred формируется только для `new_members`.


Поскольку A уже находится в Known, список оказывается пустым.


Диагностика `unresolved_required_dependency` добавляется, но в дальнейшем итоговый статус вычисляется по наличию соответствующей записи в Deferred.


В результате система может вернуть:


`status = complete`


хотя обязательная зависимость не разрешена.


**Это ошибка функциональной логики.**


Known означает, что клиент уже располагает конкретной версией исходного узла. Это не доказывает, что клиент располагает всеми обязательными зависимостями.


**Что исправить:**


1. Ввести отдельный признак наличия неразрешённых обязательных групп.
2. Учитывать его при вычислении статуса независимо от наличия Deferred.
3. Не повторять текст Known в Included.
4. Сохранять диагностическую информацию о недостающих узлах.
5. При любой неразрешённой обязательной зависимости устанавливать `partial`, если нет более приоритетной ошибки целостности.


Добавить два теста:


| Сценарий | Ожидаемый результат |
|---|---|
| Known A требует отсутствующий M | `partial` |
| Known A требует отсутствующий родительский контекст M | `partial` |


Проверить, что при этом A не дублируется в Included.

<text color="secondary" size="xs" weight="medium">Проверенное состояние на момент аудита</text>


| Поле | Текущее значение |
|---|---|
| `manifest.source_commit` | `2a3c54fa7a9e910f4c9621c8fe00f41a061fc158` |
| HEAD `sfra-state` | `fb0b45ae0e5043e342c790d43e2b341ca65d7f2b` |
| SHA-256 SQLite из manifest | `2a6d792d5e5c458ffa87df32a082229fc548c42dab2d91a5cc8fa1195bcf6674` |
| Schema SQLite | 2 |


Следовательно, правило сопоставления должно быть таким:


```text
SnapshotRef.vault_commit_sha  = manifest.source_commit
SnapshotRef.sidecar_commit_sha = pinned sfra-state commit SHA
SnapshotRef.manifest_sha256    = SHA-256 точных байтов manifest.json
```


При старте операции нужно закрепить оба Git SHA, проверить hash SQLite по manifest и использовать именно эти checkout для E2 и E1. Ни поиск, ни рекурсивное разрешение зависимостей, ни последующее чтение не должны повторно обращаться к именам веток, чтобы получить «самую свежую» версию.


Особенно важно: проектируемый E1 `get_node_by_id` сам по себе не устанавливает Git identity переданного `vault_root`. Следовательно, SourceReader должен проверять соответствие checkout заявленному `vault_commit_sha` и не допускать смены закреплённых путей или коммитов в течение запроса.


## 4. Дополнительные замечания к SearchAdapter


Есть ещё две особенности E2, которые стоит учесть сразу:


1.
 E2 не возвращает в поисковом ответе явного `complete`, `inspected_count` или `has_more`.
 При установленном `limit` адаптер не должен объявлять выдачу полной только потому, что получил несколько результатов.
 Без изменения E2 можно использовать запрос с дополнительным результатом (`limit + 1`) для обнаружения усечения, учитывая максимальный предел E2 в 500.
2.
 Текущий `main` E2 допускает в загрузку структурные узлы со статусом `ambiguous`.
 В отдельной ветке [e2/active-node-source-filter](https://github.
com/yeatu/obsidianGP/tree/e2/active-node-source-filter) уже есть исправление на выбор только `active`, но эта ветка пока не слита и отдельного PR нет.
 При интеграции нужно согласовать с E2, какая версия является целевой.


Ошибку поиска нельзя превращать в пустой `SearchBatch` с `complete=true`. Пустая выдача, частичная выдача и технический сбой должны оставаться разными исходами. Если для передачи диагностик адаптера потребуется расширить контракт, это следует делать только после явного обоснования и обновления схем.
