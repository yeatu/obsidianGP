## 2. Главная цель следующего этапа


Реализовать надёжный API адресного чтения структурного узла по его Node ID с проверкой ожидаемого Content Hash.


Функция должна обеспечивать следующий сценарий:


1. Поисковый движок нашёл узел и вернул его Node ID и Content Hash.
2. ChatGPT создал отдельный запрос на получение этого узла.
3. Новый GitHub Actions runner восстановил сохранённое состояние.
4. API нашёл именно запрошенный Node ID.
5. Проверил актуальность версии и соответствие оригинальному Markdown.
6. Вернул исходный фрагмент без искажений либо сообщил, почему его нельзя безопасно вернуть.


**Молчаливая подмена одного узла другим запрещена.**


## 3. Этап A. Проектирование API


Сначала подготовь техническую спецификацию, не переходя сразу к программированию.


Предлагаемая сигнатура:
```
get_node_by_id(
    db_path,
    node_id: str,
    expected_hash: str,
    vault_root,
) -> NodeLookupResult
```


Она должна использовать существующую SQLite-схему v2 и имеющиеся поля:


- `structural_nodes.node_id`;
- `structural_nodes.content_hash`;
- `structural_nodes.raw_text`;
- координаты узла;
- `documents.source_path`;
- `documents.source_sha256`;
- статусы узлов и документов;
- `node_versions`;
- `node_match_events`.


Не создавай альтернативный механизм идентификации.


### Обязательные статусы ответа


| Статус            | Значение                                                       |
| ----------------- | -------------------------------------------------------------- |
| `ok`              | Источник и версия проверены, узел можно вернуть                |
| `stale_source`    | Источник изменён либо Hash не соответствует запрошенной версии |
| `deleted`         | Документ или узел удалён                                       |
| `ambiguous`       | Узел или его прежняя адресация неоднозначны                    |
| `not_found`       | Node ID отсутствует                                            |
| `invalid_request` | Некорректный запрос или недопустимый путь                      |
| `integrity_error` | Обнаружено нарушение целостности БД или координат              |


При любом статусе, кроме `ok`, содержимое узла не возвращается.


В частности, запрещено возвращать новый текст под видом старой версии.


### Формат успешного ответа
```
{
  "status": "ok",
  "node": {
    "node_id": "node_<uuid>",
    "content_hash": "sha256:<hash>",
    "source_path": "folder/note.md",
    "raw_text": "Exact source slice",
    "line_start": 10,
    "line_end": 12,
    "char_start": 120,
    "char_end": 145,
    "byte_start": 140,
    "byte_end": 165
  }
}
```


### Порядок проверок


1. Проверить формат Node ID и ожидаемого Hash.
2. Найти узел по Node ID.
3. Определить актуальность узла по его статусу, состоянию документа и последним событиям сопоставления.
4. Отличить удаление от неоднозначного сопоставления.
5. Проверить SHA-256 сохранённого `raw_text` относительно `content_hash`.
6. Безопасно разрешить `source_path` относительно `vault_root`.
7. Проверить canonical path и запретить чтение файлов за пределами Vault, включая выход через symlink.
8. Проверить наличие исходного файла.
9. Вычислить SHA-256 всего исходного Markdown и сравнить с `documents.source_sha256`.
10. Проверить соответствие символьного и UTF-8-байтового срезов сохранённому `raw_text`.
11. Проверить согласованность координат строк.
12. Сравнить проверенный Content Hash с `expected_hash`.
13. Только после всех успешных проверок вернуть исходный узел.


Если ожидаемый Hash старый, а текущая версия узла существует, результат `stale_source`. Если узел удалён, результат `deleted`. Если соответствие неоднозначно, результат `ambiguous`.


Не смешивай устаревание источника с повреждением индексной базы.


Подготовь документ с проектным решением и передай его аналитику.

### Обязательные статусы API


| Статус | Условие |
|---|---|
| `ok` | Источник и версия проверены, узел можно вернуть |
| `stale_source` | Исходный файл изменился либо Hash не соответствует запрошенной версии |
| `deleted` | Документ или узел удалён |
| `ambiguous` | Узел или его прежняя адресация неоднозначны |
| `not_found` | Node ID отсутствует |
| `invalid_request` | Некорректный запрос или недопустимый путь |
| `integrity_error` | Нарушена целостность БД или координат |


При любом статусе, кроме `ok`, содержимое узла возвращаться не должно.


### Успешный ответ


Используй следующий формат:


```json
{
  "status": "ok",
  "node": {
    "node_id": "node_<uuid>",
    "content_hash": "sha256:<hash>",
    "source_path": "folder/note.md",
    "raw_text": "Exact source slice",
    "line_start": 10,
    "line_end": 12,
    "char_start": 120,
    "char_end": 145,
    "byte_start": 140,
    "byte_end": 165
  }
}
```


Фактические форматы идентификаторов и координат должны соответствовать существующей схеме проекта.


### Обязательная последовательность проверок


Опиши в спецификации следующий порядок:


1. Проверка формата Node ID и ожидаемого Hash.
2. Поиск узла по Node ID.
3. Проверка актуального статуса узла и документа.
4. Анализ последних событий сопоставления.
5. Различение удалённого и неоднозначно сопоставленного узла.
6. Проверка соответствия SHA-256 сохранённого `raw_text` полю `content_hash`.
7. Безопасное разрешение `source_path` относительно `vault_root`.
8. Проверка canonical path и невозможности выхода за пределы Vault, в том числе через symlink.
9. Проверка наличия исходного файла.
10. Вычисление SHA-256 всего исходного Markdown и сравнение с `documents.source_sha256`.
11. Проверка соответствия символьного и UTF-8-байтового срезов сохранённому `raw_text`.
12. Проверка координат строк.
13. Сравнение проверенного Content Hash с `expected_hash`.
14. Возврат оригинального узла только после успешного прохождения всех проверок.


Важно правильно разделить ошибки:


- `stale_source` — источник изменился либо запрошена неактуальная версия.
- `integrity_error` — сохранённая запись или координаты повреждены либо противоречат друг другу.
- `deleted` — подтверждено удаление документа или узла.
- `ambiguous` — сопоставление не позволяет однозначно установить идентичность узла.


Если запрошен старый Hash, но актуальная версия существует, возвращай `stale_source`, а не новую версию.


Если соответствие неоднозначно, не пытайся самостоятельно выбирать наиболее похожий узел.

### 2. Замечания, требующие исправления


**Критическое замечание №1. Ошибочная классификация отсутствующего файла.**


В спецификации отсутствие файла при активной записи документа сразу означает `deleted`.


Но API получает `vault_root`, а не подтверждённый `vault_ref` или `source_commit`.


Представим ситуацию: индекс создан по `main`, а API получил checkout рабочей ветки, где этого документа нет. Файл будет отсутствовать, хотя автор его не удалял.


Нужно разделить:


- `documents.status = deleted` или подтверждённое событие удаления → `deleted`;
- активная запись в БД, но исходник отсутствует в переданном checkout → `stale_source`, пока не подтверждена идентичность checkout;
- удаление в достоверно установленной версии Vault → `deleted`.


Иначе API будет выдавать ложные сведения об удалении источников.


**Критическое замечание №2. Неверная семантика `invalid_request`.**


`source_path` не приходит от пользователя. Он извлекается из SQLite.


Поэтому обнаружение `../`, абсолютного пути или повреждённого пути в БД не обязательно означает некорректный пользовательский запрос.


Предлагаю разграничить:


- неправильный `vault_root` или входные параметры → `invalid_request`;
- повреждённый или небезопасный `documents.source_path` → `integrity_error`;
- корректный путь, но несоответствие содержимого исходного файла → `stale_source`.


Тесты также нужно привести в соответствие с этим разграничением.


**Критическое замечание №3. Недостаточно определена защита от TOCTOU.**


Сейчас предлагается разрешить путь, открыть файл, прочитать его, а затем повторно проверить canonical target.


Этого недостаточно как строгой гарантии: между разрешением пути и открытием файла символическая ссылка может измениться.


Необходимо дополнить спецификацию:


- проверкой фактической цели открытого файлового дескриптора до чтения;
- проверкой нахождения этой цели внутри canonical Vault root;
- сравнением идентичности файлового объекта через `fstat`;
- повторной проверкой после чтения;
- запретом возвращать содержимое при любом расхождении.


Нужно также определить допустимость внутренних symlink и поведение на платформах, где безопасную проверку нельзя гарантировать.


**Замечание №4. Не описана обработка пустых структурных узлов.**


В существующем `parser.py` пустой диапазон может иметь:


`line_end = line_start - 1`.


Это видно непосредственно в `_Offsets.span_from_chars()`.


Спецификация считает координаты строк включительными, но не описывает этот частный случай. В результате корректный пустой документ может быть ошибочно признан повреждённым.


Нужно добавить явное правило и тест пустого Markdown-документа.


**Замечание №5. Неизвестные события сопоставления.**


Для известных типов событий правила описаны хорошо. Но не определено поведение при появлении неизвестного `event_type`.


Рекомендую установить правило: неизвестное событие, способное повлиять на идентичность узла, приводит к `integrity_error`. API не должен молча считать такой узел активным.
