<WritingBlock id="73184" variant="document"># Задание для Исполнителя 1: разработка структурного индексатора SFRA


## 1. Цель


Разработать первую рабочую версию структурного индексатора для Obsidian Vault в соответствии с архитектурным документом проекта.


Индексатор должен читать Markdown-файлы, определять их структуру и создавать отдельное индексное представление, которое позволяет адресно извлекать оригинальные фрагменты документов.


**Главный принцип: индекс указывает, источник говорит.**


Индексатор не должен пересказывать, переписывать или интерпретировать авторские материалы. Его задача — корректно находить структурные границы и сохранять связь каждого фрагмента с первоисточником.


Речь идёт о рабочей основе для тестирования, а не о попытке создать идеальный промышленный продукт с первого захода.


## 2. Исходные материалы


Изучи перед началом работы:

- 15. Этапы реализации;
- 16. Технический стек;
- 17. Окончательная архитектурная спецификация.


Учитывай реальные особенности Vault: документы разного размера, отсутствие заголовков в части файлов, вложенные списки, Obsidian Callout, таблицы, внешние ссылки и параллельные источники.


## 3. Границы ответственности


Твоя задача — только **Этап 1. Структурный индексатор**.


В неё входят:
1. Чтение Markdown-файлов.
2. Разбор Markdown-структуры.
3. Построение дерева структурных узлов.
4. Детерминированная сегментация.
5. Сохранение координат исходного текста.
6. Генерация и сохранение Node ID.
7. Вычисление Content Hash.
8. Сохранение оригинального Markdown без изменений.
9. Базовая проверка корректности индексации.


Не реализовывай:
- FTS5 и полнотекстовый поиск;
- русскую лемматизацию;
- реестр сущностей и алиасов;
- фасеты;
- Context Builder;
- MCP;
- семантический поиск и эмбеддинги;
- автоматическое определение каноничности материалов.


Не расширяй задачу на соседние этапы. Важно получить законченный модуль, а не шесть недоделанных подсистем.


## 4. Требования к индексатору


### 4.1. Разбор Markdown


Используй Python и Markdown AST-парсер, сохраняющий координаты исходных блоков.


Индексатор должен распознавать:


- заголовки H1–H6;
- абзацы;
- вложенные списки;
- цитаты;
- Obsidian Callout;
- таблицы;
- Markdown-ссылки;
- кодовые блоки;
- обычные текстовые блоки без заголовков.


Выбранную библиотеку и причины выбора зафиксируй в документации.


### 4.2. Структура индекса


Реализуй трёхуровневую модель:


`Document → Structural Node → Passage`


Где:


- **Document** — исходный Markdown-файл.
- **Structural Node** — самостоятельная структурная единица: секция, ветвь списка, таблица или текстовый блок.
- **Passage** — часть крупного узла, если его невозможно эффективно передать целиком.


Каждый дочерний узел должен сохранять связь с родителем.


У каждого узла должны быть предусмотрены поля:


- `node_id`;
- `source_path`;
- `node_type`;
- `parent_node_id`;
- `heading_path`;
- `line_start`;
- `line_end`;
- `content_hash`;
- `raw_text`.


Допускаются дополнительные технические поля, если они действительно необходимы.


### 4.3. Правила сегментации


Реализуй следующие правила.


**Документы с заголовками**


Заголовок вместе с собственным содержимым образует структурный узел. Вложенные заголовки становятся дочерними узлами.


**Вложенные списки**


Родительский пункт и его дочерние элементы должны сохранять смысловую связь. Не превращай каждый элемент списка в независимый фрагмент.


**Документы без заголовков**


Используй абзацы и самостоятельные структурные блоки как первичные границы. Соседние короткие абзацы допускается объединять.


**Таблицы**


Сохраняй таблицы целиком, пока их размер позволяет. При разделении повторяй заголовки столбцов.


**Callout, цитаты и кодовые блоки**


Не разрывай эти конструкции произвольно.


**Крупные узлы**


Используй мягкий ориентир 400–900 токенов, но не жертвуй смысловой целостностью ради размера. При необходимости разделяй узел по дочерним структурам с сохранением контекста родителя.


Если безопасное разделение невозможно, лучше сохранить крупный узел и сообщить о превышении размера.


### 4.4. Координаты и исходный текст


Каждый узел должен однозначно указывать на соответствующий участок исходного Markdown.


Обязательно сохраняй:


- относительный путь к файлу;
- начальную и конечную строки;
- при возможности символьные смещения;
- точный исходный текст фрагмента.


При выдаче текста запрещено восстанавливать его сериализацией AST. Нужно возвращать исходный текстовый срез.


Проверяй, что извлечённый фрагмент побайтно или посимвольно соответствует исходному участку с учётом выбранной системы координат.


### 4.5. Node ID и Content Hash


Эти понятия должны быть независимыми.


**Node ID** идентифицирует структурный узел.


**Content Hash** идентифицирует конкретное содержимое узла.


Для Content Hash используй SHA-256.


Node ID должен сохраняться при повторной индексации, если старый и новый узел удалось однозначно сопоставить.


При неоднозначном сопоставлении запрещено молча присваивать старый идентификатор другому содержимому. Такой узел должен получить статус, позволяющий определить, что прежняя адресация устарела или требует проверки.


Опиши алгоритм сопоставления старых и новых узлов. Не выдавай ненадёжное совпадение за достоверное.


### 4.6. Хранение индекса


Используй SQLite.


На этом этапе достаточно базовой структуры для хранения:
- документов;
- структурных узлов;
- иерархии узлов;
- версий и состояния сопоставления идентификаторов.


Не создавай пока FTS-таблицы и механизмы поиска.


Предусмотри возможность расширения схемы на следующих этапах без необходимости полностью переписывать индексатор.


Индекс должен храниться отдельно от исходного Vault.


## 5. Неизменность Vault


Это обязательное требование.


Индексатор работает только на чтение исходных материалов.


Запрещено:
- изменять Markdown-файлы;
- добавлять комментарии или метаданные в заметки;
- добавлять YAML frontmatter;
- переименовывать или перемещать документы;
- исправлять авторские ошибки;
- удалять дубликаты или параллельные источники.


Все производные данные должны находиться вне исходного Vault.

## 7. Тестирование


Создай тестовые Markdown-файлы, покрывающие как минимум следующие случаи:


1. Документ с несколькими уровнями заголовков.
2. Документ без заголовков.
3. Вложенные списки.
4. Obsidian Callout.
5. Таблицы.
6. Кодовые блоки и цитаты.
7. Кириллица и специальные символы.
8. Очень большой структурный узел.


Проверь следующие свойства:


- повторная индексация неизменённого документа даёт одинаковую структуру;
- Content Hash корректно отражает содержимое;
- исходный текст фрагментов сохраняется без искажений;
- родительские и дочерние связи корректны;
- Node ID не меняется при повторной индексации неизменённого узла;
- изменение содержимого отражается в Content Hash;
- неоднозначное сопоставление не приводит к молчаливой подмене идентификатора;
- исходные файлы остаются неизменными.


По возможности проведи дополнительную проверку на реальных материалах из папки `ГП`. Если фактическая структура файлов недоступна и имеется только `dump.md`, отдельно зафиксируй это ограничение. Не подменяй проверку реального Vault проверкой одного искусственного файла.


## 8. Критерии приёмки


Работа считается выполненной, если:


1. Индексатор запускается локально по инструкции.
2. Он способен обработать набор Markdown-документов.
3. Строит иерархию структурных узлов.
4. Возвращает оригинальные фрагменты с координатами источника.
5. Сохраняет независимые Node ID и Content Hash.
6. Не изменяет исходные документы.
7. Повторная индексация работает предсказуемо.
8. Автоматические тесты проходят.
9. Документация позволяет другому разработчику запустить и проверить модуль.
10. Результат можно передать следующему этапу разработки без необходимости переписывать его с нуля.


Не скрывай ограничения реализации. Если конкретная конструкция Markdown обрабатывается упрощённо, это должно быть явно указано.


## 9. Итоговый отчёт

## 5. Требования к поисковому движку


### 5.1. SQLite и FTS5


Используй SQLite в качестве локального хранилища.


Для полнотекстового поиска используй FTS5.


Поисковый индекс должен поддерживать поиск по:


- оригинальному содержимому;
- нормализованному тексту;
- заголовкам;
- названиям документов;
- путям к источникам;
- именам и алиасам сущностей.


Не теряй оригинальные написания. Нормализованный текст используется только для обнаружения результатов, а не для замены исходного содержания.


Предусмотри возможность расширения схемы базы данных.


### 5.2. Русская морфологическая нормализация


Используй `pymorphy3` либо обоснуй выбор альтернативы.


Поиск должен учитывать различные словоформы.


Например, запросы:


- «маг»
- «мага»
- «маги»
- «магами»


должны находить релевантные фрагменты с соответствующими формами слова.


При этом нормализация не должна уничтожать точные совпадения, имена, специальные термины и числовые значения.


Проверь работу на кириллице, дефисах, апострофах и составных именах.


### 5.3. Точный поиск


Обязательно реализуй поиск по точным словам и числам.


Особенно важно корректно обрабатывать числовые значения.


Например, запрос по числу `18 518` должен находить именно источники с таким значением.


Не допускай случайного смешивания чисел, которые отличаются значением или разрядностью.


При обработке разделителей разрядов учитывай обычные пробелы и неразрывные пробелы.


Точное совпадение должно сохранять преимущество перед приблизительным морфологическим совпадением.


### 5.4. Реестр сущностей


Реализуй отдельный механизм хранения сущностей и их алиасов.


Источниками кандидатов для сущностей могут быть:


- имена файлов;
- заголовки документов;
- явно заданные алиасы;
- повторяющиеся имена в тексте.


Для сущности должны храниться:


- уникальный идентификатор;
- каноническое имя;
- список алиасов;
- статус подтверждения алиасов;
- связанные Node ID.


Предусмотри возможность ручного подтверждения и отклонения неоднозначных алиасов.


**Не объединяй сущности автоматически, если их тождество не доказано.**


Примеры неоднозначностей из проекта:


- Хогвартс / Хоггвартс;
- Рэбекка Блэе / Рэбекка Блэк;
- Долохов / Александр Долохов / Антонин Долохов.


Это кандидаты на проверку, а не готовые решения.


Реестр сущностей нужен для поиска упоминаний. Он не должен превращаться в граф знаний или автоматически устанавливать отношения между персонажами.


### 5.5. Карта упоминаний


Для каждой подтверждённой сущности необходимо хранить сведения о том, в каких структурных узлах она встречается.


Пример:


```text
ENTITY: character_daphne


Canonical:
Дафна Гринграсс


Aliases:
Дафна
Daphne Greengrass


Mentions:
node_001
node_028
node_104
```


Поиск по сущности должен возвращать:


1. Основной документ сущности, если он существует.
2. Другие документы, содержащие подтверждённые упоминания.
3. Конкретные структурные узлы с этими упоминаниями.


Не создавай утверждений о характере, отношениях или действиях сущности на основании одного факта упоминания.


### 5.6. Базовое ранжирование


Реализуй первоначальную систему ранжирования результатов.


Приоритеты:


1. Точное совпадение сущности.
2. Совпадение имени в названии документа.
3. Совпадение имени или термина в заголовке.
4. Точное совпадение слов и фраз.
5. Морфологические совпадения.
6. Совпадения в остальном тексте.


Зоны Vault не должны автоматически понижать или повышать авторитетность источников.


Наличие авторских вопросов и заметок не должно автоматически уменьшать релевантность документа.


Не пытайся определять, какой источник является каноничным.


Для каждого результата возвращай причину, по которой он был найден, и доступные координаты исходного узла.


## 6. Формат поискового результата


Разработай программный интерфейс поиска.


Например:


```python
search(
    query="Особенности речи Генриха Фауста",
    entities=["Генрих Фауст"],
    limit=20
)
```


Точный интерфейс выбери самостоятельно, но он должен быть документирован и пригоден для подключения к будущему Context Builder.


Результат должен содержать:


- Node ID;
- путь к исходному файлу;
- заголовок или heading path;
- Content Hash;
- координаты исходного узла;
- причину совпадения;
- оценку релевантности;
- тип совпадения;
- информацию о найденной сущности, если применимо.


Поисковик может возвращать оригинальные фрагменты для проверки, но не должен самостоятельно формировать адаптивный Context Pack.


Не подменяй первоисточник нормализованным текстом.


## 7. Инкрементальное обновление


Предусмотри возможность обновления поискового индекса при изменении входных данных.


Минимальные требования:


- повторная загрузка неизменённого узла не создаёт дубликат;
- изменение Content Hash обновляет поисковую запись;
- удаление узла удаляет либо помечает соответствующие поисковые записи;
- изменения алиасов отражаются в поиске;
- изменения одного документа не требуют полной пересборки всего индекса, если это технически возможно.


Операции обновления должны быть транзакционными.


Не допускай состояния, в котором поисковик видит частично обновлённую базу.


## 8. Ограничения архитектуры


Обязательные правила:


1. Поисковый индекс хранит производные данные отдельно от Vault.
2. Исходные документы не изменяются.
3. Нормализация не заменяет оригинальный текст.
4. Поисковые аннотации не являются доказательствами фактов.
5. Реестр упоминаний не является графом знаний.
6. Неоднозначные алиасы не объединяются без подтверждения.
7. Параллельные источники сохраняются независимо.
8. Семантический поиск не внедряется на этом этапе.
9. Отсутствие результата поиска не означает отсутствия информации в Vault.


Особенно внимательно отнесись к параллельным источникам.


Например, два документа `Демография.md` из разных папок могут содержать пересекающиеся, но не идентичные сведения.


Нельзя удалять один из них только потому, что второй содержит похожие данные.

## 5. Context Builder


### 5.1. Общий принцип


Context Builder получает:


- исходную задачу;
- поисковый запрос;
- найденные структурные узлы;
- необходимые сущности и фасеты, если они заданы;
- бюджет токенов;
- сведения о ранее полученных версиях узлов.


На основании этих данных он формирует Context Pack.


При этом он не должен самостоятельно придумывать недостающие аспекты задачи.


### 5.2. Покрытие задачи


Реализуй механизм контроля покрытия задачи.


Запрос может содержать несколько независимых аспектов.


Например:


«Написать сцену конфликта между Дафной и Теодором».


Для такого запроса можно выделить следующие аспекты:


| Аспект | Что требуется обнаружить |
|---|---|
| Дафна | Характер, мотивация, поведение |
| Теодор | Характер, мотивация, поведение |
| Речь | Особенности речи обоих персонажей |
| Отношения | Прямые описания взаимодействия |
| Сюжет | Обстоятельства конфликта, если они уже заданы |


Context Builder должен учитывать каждый аспект отдельно.


Допускается использовать переданные клиентом аспекты или явный список `focus`.


Не создавай обязательную сложную систему автоматической декомпозиции любого запроса. Для MVP достаточно управляемого механизма покрытия.


Для каждого аспекта предусмотрите статус:


- `found` — найдены подходящие источники;
- `deferred` — источники найдены, но не помещены в текущий пакет;
- `not_found_in_retrieval` — среди обработанных результатов подходящий материал не обнаружен.


Последний статус не означает, что информация отсутствует в Vault.


**Запрещено превращать результат поиска «не найдено» в утверждение «такой информации нет».**


### 5.3. Ранжирование


Используй результаты поискового движка как основу.


Учитывай следующие приоритеты:


1. Точное совпадение сущности.
2. Совпадение имени в названии документа и заголовке.
3. Точное совпадение терминов и фраз.
4. Морфологическое совпадение.
5. Совпадение функциональных фасетов.
6. Дополнительная релевантность, указанная поисковым движком.


Зона Vault и наличие авторских вопросов отображаются как дополнительные сведения, но не должны автоматически определять достоверность или каноничность источника.


Не создавай собственную систему смыслового анализа, подменяющую поисковый движок.


### 5.4. Контроль бюджета токенов


Реализуй механизм ограничения объёма Context Pack.


Входной параметр:


`budget_tokens`


При отборе узлов необходимо учитывать:


- размер исходного фрагмента;
- его релевантность;
- необходимость сохранения контекста родителя;
- покрытие аспектов задачи;
- возможные повторы;
- наличие обязательных правил и ограничений.


Используй реальный токенизатор, если это оправдано и доступно для выбранного стека. В противном случае реализуй отдельный модуль оценки объёма и явно укажи его погрешность.


Не используй необоснованную формулу `len(text) / 3` как точный подсчёт токенов.


Если весь важный материал не помещается в бюджет, система должна честно сообщить об этом.


**Нельзя удалять критические ограничения, правила или исключения только ради соблюдения бюджета.**


### 5.5. Устранение повторов


Устраняй повторы внутри одного источника, если они действительно не добавляют новой информации.


При этом учитывай:


- различия Content Hash;
- разные структурные положения;
- разные версии узлов;
- параллельные документы.


Похожие фрагменты из разных источников не должны автоматически удаляться.


### 5.6. Параллельные источники


Особое внимание удели нескольким документам, содержащим сведения об одной сущности или теме.


Пример из Vault — два документа `Демография.md` в разных папках.


Они могут пересекаться по значениям, но содержать разные модели и допущения.


Context Builder должен:


- сохранить оба источника;
- показать их отдельными результатами;
- при необходимости отметить возможное пересечение;
- не объявлять их противоречащими друг другу без доказательств;
- не выбирать один источник как правильный.


### 5.7. Формат Context Pack


Результат должен состоять из следующих блоков.


**Included**


Источники, включённые в текущий пакет:


- оригинальный текст;
- Node ID;
- Content Hash;
- путь;
- заголовок;
- координаты;
- зона;
- дополнительные признаки, если доступны.


**Coverage**


Информация о покрытии задачи:


- найденные аспекты;
- отложенные аспекты;
- ненайденные аспекты.


**Deferred**


Источники, которые были найдены, но не помещены в текущий бюджет:


- Node ID;
- заголовок;
- путь;
- Content Hash;
- причина откладывания;
- оценка объёма.


**Parallel Sources**


Похожие или параллельные источники:


- Node ID;
- путь;
- описание характера пересечения;
- причина, по которой источники сохранены отдельно.


**Statistics**


Общая статистика:


- число найденных узлов;
- число включённых узлов;
- число отложенных узлов;
- число ненайденных аспектов;
- использованный бюджет;
- оценка или фактическое число токенов;
- полнота покрытия задачи.


Context Pack должен формироваться в структурированном формате, пригодном для передачи через MCP.


## 6. Инструмент №1: search_vault


Реализуй обязательный MCP-инструмент:


`search_vault`


Его задача — выполнить поиск через подключённый поисковый адаптер и сформировать Context Pack.


### Входные параметры


Обязательный параметр:


- `query` — поисковый запрос.


Дополнительные параметры:


- `entities` — список сущностей;
- `facets` — список функциональных категорий;
- `budget_tokens` — бюджет Context Pack;
- `known` — Node ID и Content Hash, уже известные клиенту;
- `zones` — необязательное ограничение по зонам;
- `focus` — список аспектов, которые необходимо покрыть.


Пример:


```json
{
  "query": "Особенности речи Генриха Фауста",
  "entities": ["Генрих Фауст"],
  "facets": ["VOICE"],
  "budget_tokens": 3000,
  "known": [],
  "focus": [
    "Общий стиль речи",
    "Типичные фразы"
  ]
}
```


### Выходные данные


Возвращай полный Context Pack с разделами:


- Included;
- Coverage;
- Deferred;
- Parallel Sources;
- Statistics.


Если результатов нет, верни корректный пустой результат со статусами покрытия, а не ошибку и не выдуманный ответ.


## 7. Инструмент №2: read_source


Реализуй второй обязательный MCP-инструмент:


`read_source`


Его задача — адресно получать оригинальный текст из источника.


### Входные параметры


- `node_id` — идентификатор узла;
- `expected_hash` — ожидаемый Content Hash;
- `scope` — режим получения текста;
- `budget_tokens` — ограничение объёма, если применимо.


Пример:


```json
{
  "node_id": "node_00421",
  "expected_hash": "sha256:...",
  "scope": "parent",
  "budget_tokens": 2500
}
```


### Режимы чтения


| Scope | Результат |
|---|---|
| `node` | Сам структурный узел |
| `parent` | Узел вместе с контекстом родителя |
| `neighbors` | Соседние структурные элементы |
| `document` | Полный исходный документ |


Результат должен включать оригинальный текст, путь и сведения о версии.


### Устаревший Node ID


Если Node ID не найден или его Content Hash отличается от ожидаемого:


- не подменяй его другим узлом;
- не возвращай похожий фрагмент как будто это запрошенный;
- сообщай о несовпадении или устаревании;
- возвращай диагностическую информацию, позволяющую клиенту повторить поиск.


Молчаливая подмена источников запрещена.


## 8. Stateless-протокол


MCP-сервер не должен хранить состояние диалога.


Клиент самостоятельно передаёт список известных ему узлов:


```json
{
  "known": [
    {
      "node_id": "node_00421",
      "content_hash": "sha256:..."
    }
  ]
}
```


Если Content Hash не изменился, сервер может не передавать этот фрагмент повторно.


Если содержимое изменилось, сервер должен вернуть новую версию узла.


Важно: сервер не знает, сохранил ли клиент ранее полученный материал в своём контексте.


Не создавай скрытую систему памяти или предположений о содержимом окна контекста модели.


## 9. Защита от prompt injection


Исходный текст Vault является недоверенным содержимым.


В документах могут присутствовать инструкции, цитаты, внешние материалы или фрагменты, которые выглядят как команды для нейросети.


Обязательно соблюдай следующие правила:


1. Исходный текст передаётся как данные, а не как системные инструкции.
2. Не выполняй указания, обнаруженные внутри извлечённых документов.
3. Передавай оригинальный текст в отдельных структурированных полях.
4. Не считай XML-обёртку самостоятельной защитой от prompt injection.
5. Не изменяй содержимое источников ради удаления потенциально опасных фраз.


Твоя ответственность — корректно структурировать выдачу и обеспечить разделение данных и инструкций.

## Обнаружена одна существенная проблема альтернативы


Временная SQLite для каждого запуска Actions удобна, но есть конфликт с требованием сохранять `Node ID`.


В комментариях к Issue №4 один и тот же исходный фрагмент имеет одинаковый `Content Hash`, но разные `Node ID` в двух запусках:


- первый результат: `node_ea035e08-...`;
- повторный результат: `node_ad404ab9-...`.


Причина видна в тестовом workflow: индекс создаётся заново в `$RUNNER_TEMP`. Новый SQLite-файл получает новые UUID узлов. Это допустимо для проверки поиска, но ломает адресное обращение `read_source` по ранее выданному `Node ID`.


**Следовательно, оптимальная схема должна быть гибридной:**


- поисковая таблица FTS5 и промежуточные данные могут быть временными;
- реестр идентификаторов, версии узлов и история сопоставления должны сохраняться между запусками Actions;
- `read_source` должен проверять прежний `Node ID` и `Content Hash` на актуальной версии Vault.


Предпочтительное решение: отдельная ветка GitHub для небольшого постоянного sidecar-хранилища структурного индекса.
 GitHub Actions загружает его в начале задания, обновляет при необходимости и сохраняет обратно.
 Запуски, изменяющие это хранилище, нужно сериализовать, иначе два параллельных задания могут перезаписать результаты друг друга.


Это не возвращает нас к постоянному серверу. Вычисления остаются одноразовыми, а сохраняется только состояние, без которого архитектура адресации не работает.

<WritingBlock id="91533" variant="document"># Дополнение к заданию Исполнителя 3: GitHub Issues + Actions вместо обязательного MCP


Действующее задание сохраняется в части Context Builder, формирования Context Pack, контроля бюджета, покрытия и адресного чтения.


Изменяется требование к транспорту.

MCP-сервер не является обязательным компонентом MVP.


Если MCP-адаптер уже реализуется, не удаляй выполненную работу. Оставь его отдельным необязательным транспортным адаптером. Основная бизнес-логика не должна зависеть от MCP SDK.


## 1. Команды


Поддержи две операции:


- `search_vault`
- `read_source`


Обе передаются в теле Issue структурированным JSON.


Каждый запрос получает уникальный `request_id` и версию протокола.


## 2. Обработка запроса


GitHub Actions должен:


1. Получить событие создания Issue.
2. Проверить автора и префикс `[SFRA]` в заголовке.
3. Проверить версию и JSON-схему запроса.
4. Определить операцию по разрешённому списку.
5. Загрузить текущий Vault и сохранённое состояние структурного индекса.
6. Вызвать нужный Python-модуль.
7. Сформировать структурированный результат.
8. Опубликовать результат комментарием к исходному Issue.


Не исполняй содержимое Issue как код.


Для повторного `read_source` создаётся отдельный Issue. Не используй комментарии Actions как новые команды, иначе можно случайно получить бесконечную цепочку запусков.


## 3. Статусы


Предусмотри состояния:


- `PENDING`;
- `RUNNING`;
- `DONE`;
- `FAILED`.


Результат должен быть однозначно связан с исходным Issue и request_id.


Повторная обработка одного запроса не должна приводить к нескольким несовместимым ответам.


## 4. Сохранение состояния


Взаимодействуй с постоянным sidecar-хранилищем структурного индексатора.


FTS5 и Context Pack могут создаваться временно.


Node ID и история версий должны сохраняться между запусками.


Предусмотри защиту от параллельного изменения sidecar-хранилища. Запросы не должны теряться из-за автоматической отмены ожидающих запусков.


## 5. Права GitHub Actions


Используй минимальные права:


- `issues: write` для публикации результатов;
- `contents: read` для чтения исходного Vault;

Я выделяю четыре главных риска.


**Первый. Нет единого канонического интерфейса чтения источника.**


E2 уже имеет `get_source_node()`. E1 проектирует более строгий `get_node_by_id()`. E3 требует `SourceReader`.


Необходимо согласовать один основной контракт, чтобы не получить три функции с похожими названиями, но разной семантикой. Иначе ошибки начнут путешествовать между слоями, как бесхозный кот по подъезду.


**Второй. Не согласована реализация закреплённого snapshot.**


E3 использует `SnapshotRef`, содержащий:
- commit исходного Vault;
- commit sidecar;
- Hash manifest.


E1 manifest содержит `source_commit`, `database_sha256`, `source_branch` и другие данные, но не готовый объект E3 `SnapshotRef`.


Нужен небольшой адаптер, который однозначно преобразует manifest E1 и commit ветки `sfra-state` в `SnapshotRef` E3. Все зависимости при сборке контекста должны читаться из одной закреплённой версии, без переключения на более свежую базу посреди операции.


**Третий. GitHub Issue bridge не является рабочим транспортом.**


Workflow `sfra-issue-bridge-smoke.yml` только проверяет получение события Issues и возможность опубликовать комментарий. Он прямо не выполняет чтение Vault.


Поэтому пока не подтверждены:
- разбор настоящего запроса ChatGPT;
- резервирование запроса и состояния RUNNING;
- выполнение поиска и сборки Context Pack;
- публикация результата;
- повторы при сбоях;
- восстановление зависших запросов.


**Четвёртый. Нужно определить источник истины для Vault.**


E1 сейчас индексирует `ГП` из своей ветки `executor-1/sfra-indexer-session-1`. E2 умеет восстановить именно тот commit, который записан в manifest.


Это обеспечивает воспроизводимость текущей интеграции. Но до начала постоянной эксплуатации нужно определить, какая ветка является авторитетной для исходных заметок: `main` или отдельная ветка реализации. Изменения в другой ветке не должны оставаться незамеченными.

## Поручение E1


<WritingBlock id="13501" variant="document"># E1. Реализовать публичное API точного чтения первоисточника


**Цель:** завершить недостающую часть Structural Indexer. По паре `Node ID + Content Hash` система должна уметь получить точный фрагмент актуального Markdown-файла, а не просто вернуть сохранённый в SQLite текст.


## 1. Исходное состояние


Ветка реализации: `executor-1/sfra-indexer-session-1`.


Этапы B/C и persistence уже реализованы. В документации этапа Persistence прямо указано, что API `get_node_by_id(..., expected_hash)` не входило в его объём.


Ориентироваться на:
- архитектурный документ SFRA, разделы об идентификаторах, `read_source` и проверке первоисточника;
- `02_Проектирование_этапа_C.md`;
- `05_Результат_этапа_1_Persistence.md`.


## 2. Реализовать


Добавить и экспортировать публичный API чтения узла. Ожидаемый контракт:


```python
get_node_by_id(
    node_id: str,
    expected_hash: str,
    vault_root: Path,
)
```


Сохранять эту форму, если она уже предусмотрена текущей реализацией или спецификацией. Если для подключения к SQLite требуется дополнительный параметр, сначала зафиксировать это в документации и тестах, не создавать скрытую глобальную конфигурацию.


API должен:


1. Найти узел по точной паре `node_id + expected_hash`.
2. Принимать только узлы со статусом `active`.
3. Отвергать `ambiguous`, `stale`, `deleted` и отсутствующие узлы.
4. Проверить, что исходный файл существует внутри переданного `vault_root`.
5. Проверить соответствие текущего файла сохранённому `documents.source_sha256`.
6. Восстановить фрагмент по исходным координатам, учитывая систему координат `char_start/char_end`.
7. Вычислить SHA-256 точных UTF-8-байтов полученного фрагмента.
8. Сравнить результат с `expected_hash`.
9. Вернуть дословный фрагмент из текущего Markdown-файла вместе с метаданными адресации.


Нельзя считать `raw_text` из SQLite достаточным доказательством актуальности первоисточника. Его допустимо использовать для сверки, но возвращаемый текст должен быть проверен относительно самого файла.


Если файл изменился после индексации, узел неоднозначен, хеш не совпадает или координаты невалидны, API должен завершаться явной ошибкой/статусом устаревшего адреса. Не возвращать старый фрагмент и не подбирать похожий узел автоматически.


## 3. Безопасность и неизменность


- Открывать SQLite только для чтения.
- Не изменять Vault.
- Проверять, что `source_path` не позволяет выйти за пределы `vault_root`, в том числе через символические ссылки.
- Не нормализовать переносы строк, Unicode, пробелы или Markdown-разметку до вычисления хеша.
- Не путать символьные смещения Python-строки с байтовыми смещениями UTF-8.


## 4. Обязательные тесты


Проверить как минимум:


- успешное чтение актуального активного узла;
- неправильный `expected_hash`;
- отсутствующий Node ID;
- статусы `ambiguous`, `stale`, `deleted`;
- изменение исходного файла после индексации;
- изменение целевого фрагмента;
- изменение другой части документа с последующим устареванием индекса;
- Unicode, кириллицу и emoji;
- LF и CRLF;
- некорректные координаты;
- отсутствующий файл;
- попытку чтения пути за пределами Vault;
- отсутствие записи в SQLite и изменения исходного файла.


## 5. Отдельно зафиксировать источник Vault


Сейчас нельзя оставлять неявным, из какой ветки репозитория индексируются заметки.


Добавить явную фиксацию `vault_ref` и фактического `vault_commit_sha` в конфигурацию запуска и manifest. Не переключать источник на `main` автоматически. Сохранить текущую совместимость и описать, какой ref использовался в каждом запуске.


## 6. Критерии приёмки


- Публичный API доступен через пакет `sfra_indexer`.
- Возвращается проверенный исходный фрагмент, а не непроверенная копия из SQLite.
- Устаревшие, неоднозначные и изменившиеся источники отклоняются без подмены.
- Все тесты проходят локально и в CI.
- Vault и production SQLite не изменены тестами.
- Документация содержит сигнатуру, формат результата и перечень возможных ошибок.


**Результат:** отдельный PR в `main`, тесты, описание API, commit SHA и ссылки на CI. Не объединять эту работу с переработкой схемы SQLite, если для неё нет доказанной необходимости.</WritingBlock>
