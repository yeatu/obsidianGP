<list connector="solid" marker="number" gap={2}>

    **Переписать PROJECT_TASKS.md**

  </list-item>
  <list-item>
    **Проверить результат**


    Убедиться, что нет задач без Issue, старых владельцев, противоречий между Markdown и GitHub, а также несанкционированного возобновления завершённых работ.

Исполнители / Аналитики сами могут захватывать свободные задачи. 


Хоть они и подписываются как Е<номер> , А <номер> , но на деле не должно быть ограничения на то, кто выполняет по номеру. Если нейросеть аналитик / исполнитель свободны и есть свободная задача. У них должна быть возможность взять ее и закрепить за собой. Чтобы избежать простаивания. 
Задачи должны дробиться на как можно меньшие блоки, чтобы обеспечить возможность, как можно большему числу нейросетей участвовать в параллельной работе.

# 1. Главный принцип: роли не должны быть привязаны к номерам


Я предлагаю разделить три понятия:


| Понятие | Назначение |
|---|---|
| Идентификатор | Кто именно выполняет работу: E1, E2, A1 и т. д. |
| Функция | Что участник делает сейчас: исполняет, анализирует, проверяет, исследует |
| Полномочия | Какие действия ему разрешены системой управления |


Обозначения E1, E2, A1, A2 нужны для идентификации и истории работы. Они **не должны определять, какие задачи участник вправе захватывать**.


Например:


- A2 может взять свободную задачу по реализации.
- E3 может взять свободную задачу по анализу архитектуры.
- E1 может проверить работу другого исполнителя.
- A1 может самостоятельно выполнить техническую задачу, если обладает необходимыми возможностями.


При этом должна сохраняться независимость проверки: участник не может быть независимым проверяющим собственной работы.


Таким образом, мы отказываемся от закрепления нейросетей за постоянными должностями, но сохраняем разные функции внутри рабочего процесса.


# 2. Полномочия участников


Я бы закрепила следующие права.


## Исполнитель или аналитик


<badge color="success">Общие полномочия любого участника</badge>


Каждый участник имеет право:


- находить свободные задачи;
- самостоятельно захватывать подходящие задачи;
- сообщать о ходе выполнения;
- создавать запросы на проверку собственной работы;
- освобождать задачу с передачей результатов;
- обнаруживать и предлагать дробление крупных задач;
- сообщать о блокировках и конфликтах.


Дополнительно участник, выполняющий аналитическую или проверочную функцию, может:


**1. Создавать подзадачи для исполнителей.**


Например, исполнитель представил реализацию на проверку. Аналитик обнаружил три независимых недостатка. Вместо одного огромного задания на исправление он может создать три отдельных задачи с конкретными критериями приёмки.


**2. Создавать задачи для координатора.**


Когда обнаружена проблема, которую нельзя решить в рамках текущих полномочий:


- конфликт архитектурных решений;
- противоречие между несколькими задачами;
- невозможность выполнения исходного требования;
- необходимость изменить утверждённый scope;
- нехватка необходимых ресурсов или инфраструктуры;
- потенциальный риск для данных или безопасности;
- необходимость изменить приоритеты проекта.


Такая задача должна содержать не просто сообщение о проблеме, а описание ситуации, доказательства, возможные решения и вопрос, который должен решить координатор.


Я бы распространила право создавать такие запросы на любого участника, который обнаружил блокирующую проблему, а не только на того, кто называется аналитиком. Иначе исполнитель может обнаружить критическую проблему, но будет вынужден ждать посредника.


## Исполнитель: запрос на проверку


Это отдельное важное полномочие.


Когда участник завершает конкретную задачу, он может создать дочернюю задачу типа `REVIEW_REQUEST`.


Она должна содержать:


- ссылку на исходную задачу;
- описание выполненной работы;
- PR или commit;
- точный проверенный HEAD;
- список выполненных критериев;
- результаты тестирования;
- известные ограничения;
- конкретный объём требуемой проверки.


Затем любой свободный участник, подходящий для независимой проверки, может захватить эту задачу.


Исполнитель не должен самостоятельно объявлять работу принятой. Он сообщает о готовности и передаёт её на проверку. Это важное разделение, иначе получится система, в которой участники проверяют сами себя и дружно ставят галочки.


## Координатор


<badge color="info">Полные управляющие полномочия</badge>


Координатор обладает всеми полномочиями системы управления.


Он может:


- создавать, изменять, дробить и закрывать любые задачи;
- устанавливать и менять приоритеты;
- разрешать архитектурные конфликты;
- утверждать изменение scope;
- блокировать опасные или некорректные действия;
- перераспределять задачи;
- отменять и заменять устаревшие задания;
- принимать результаты;
- управлять интеграцией и слиянием PR;
- формировать следующие этапы развития проекта;
- решать кризисные ситуации;
- при необходимости менять саму систему управления.


Но есть одно дополнение: координатор должен оставлять проверяемый след своих решений. Полные полномочия не должны означать возможность бесследно переписывать историю.

Правила:


1. Любой свободный участник может выбрать любую открытую задачу, если она не имеет специальных ограничений по компетенциям, независимости или безопасности.
2. Захват осуществляется самостоятельно через `CLAIM`.
3. Подтверждение координатора не требуется.
4. После публикации CLAIM участник повторно проверяет комментарии задачи.
5. Если обнаружен параллельный CLAIM, действует установленный в Governance-протоколе арбитраж по наименьшему GitHub comment ID.
6. Один участник является ответственным владельцем одной задачи. Для параллельной работы создаются отдельные подзадачи.


**Важное следствие:** свободный аналитик не обязан ждать, пока освободится работа аналитика. Свободный исполнитель не обязан ждать, пока ему выдадут очередное задание.


Именно это позволит использовать доступные вычислительные ресурсы эффективнее.


# 4. Дробление задач: чем меньше независимые блоки, тем лучше


Здесь я бы сделала один из главных принципов системы.


**Каждая задача должна быть минимальной самостоятельной единицей работы, которую можно отдельно захватить, выполнить и проверить.**


Но есть оговорка: не нужно дробить работу до бессмысленного уровня. Одна задача на изменение каждой строки кода создаст больше управления, чем полезной работы.


Предлагаю правило:


> Дробить задачу до тех пор, пока дальнейшее разделение не создаёт самостоятельных, независимо проверяемых результатов либо приводит к опасному пересечению областей изменений.


Например, вместо одной задачи:


`Реализовать систему восстановления состояния`


создаём:


| Подзадача | Результат |
|---|---|
| 1 | Определить схему хранения состояния |
| 2 | Реализовать чтение состояния |
| 3 | Реализовать проверку целостности |
| 4 | Реализовать обнаружение незавершённой операции |
| 5 | Реализовать безопасное восстановление |
| 6 | Написать тесты повреждённого состояния |
| 7 | Проверить интеграцию компонентов |


Если задачи независимы, их могут одновременно захватить семь разных нейросетей.


Если одна задача зависит от другой, зависимость должна быть явно обозначена. Нельзя выдавать задачу как свободную для исполнения, когда необходимый результат ещё не готов.

### Ещё одно важное правило


Родительская задача не должна автоматически считаться выполненной, если выполнена одна из её подзадач.


Она завершена только тогда, когда:
- завершены обязательные дочерние задачи;
- выполнены интеграционные требования;
- получена необходимая проверка;
- результат принят;
- если требуется слияние, интеграция завершена.

# 5. Вводим типы задач


Я бы разделила задачи по назначению, чтобы участники понимали, какую именно работу они берут.


| Тип | Назначение | Кто может захватить |
|---|---|---|
| `IMPLEMENTATION` | Реализация или исправление | Любой подходящий свободный участник |
| `REVIEW` | Независимая проверка | Любой участник, не участвовавший в проверяемой работе |
| `ANALYSIS` | Исследование, аудит, диагностика | Любой подходящий участник |
| `COORDINATOR_DECISION` | Решение архитектурного или организационного вопроса | Координатор |
| `INTEGRATION` | Подготовка и объединение изменений | Координатор или явно уполномоченный участник |
| `CRISIS` | Срочное устранение опасного состояния | Координатор определяет порядок и исполнителей |


Особенно важны `REVIEW` и `COORDINATOR_DECISION`.


Они обеспечивают два самостоятельных маршрута:


- проблема решается в рамках текущей задачи;
- проблема выходит за рамки полномочий и требует решения координатора.


Не нужно отправлять координатору каждую техническую мелочь. Иначе он превратится в диспетчера, через которого проходит даже замена запятой.

# 7. Координатор должен управлять не просто задачами, а потоком проекта


Это, на мой взгляд, самое важное дополнение к твоей идее.


У координатора три основные функции.


## А. Управление интеграцией


Координатор должен следить, чтобы готовые результаты не накапливались в отдельных ветках.


Приоритет:
- готовые и проверенные PR;
- задачи, без слияния которых блокируется дальнейшая работа;
- синхронизация веток с `main`;
- необходимые интеграционные проверки;
- устранение конфликтов при объединении.


Но слияние не должно происходить в ущерб безопасности. Критический инцидент или риск порчи данных имеет более высокий приоритет.


## Б. Разрешение кризисных ситуаций


Кризисными считаются, например:


- потеря целостности данных;
- нарушение границ безопасности;
- архитектурный тупик;
- конфликт нескольких независимых реализаций;
- ситуация, в которой несколько участников не могут продолжить работу;
- ошибочное изменение общей инфраструктуры;
- критическая ошибка в уже объединённом коде.


Координатор определяет масштаб проблемы, приостанавливает затронутую работу, создаёт конкретные задачи на устранение и устанавливает порядок восстановления.


## В. Формирование продолжения проекта


Когда текущий этап подходит к завершению, координатор должен не просто ждать новых сообщений от аналитиков.


Он самостоятельно:
- оценивает текущее состояние проекта;
- определяет следующий архитектурный этап;
- выявляет незакрытые зависимости;
- формирует новые крупные цели;
- дробит их на рабочие задачи;
- создаёт достаточный запас свободных задач для параллельного исполнения.


Это предотвращает ситуацию, когда пять свободных нейросетей простаивают только потому, что никто не подготовил им работу.

# 8. Дополнительные механизмы, которые я настоятельно рекомендую


Есть несколько вещей, которые не следуют напрямую из твоего описания, но без них система начнёт ломаться при увеличении числа участников.


### 8.1. Контроль пересечения задач


Две задачи могут выглядеть независимыми, но затрагивать одни и те же файлы, интерфейсы или данные.


Поэтому при создании задачи нужно указывать:
- область изменений;
- затрагиваемые компоненты;
- связанные задачи;
- зависимости;
- потенциальные конфликты.


Если два участника собираются менять один и тот же критический интерфейс, координатор должен либо разделить работу по контрактам, либо не разрешать параллельное исполнение пересекающихся частей.


### 8.2. Запрет на расширение полномочий через декомпозицию


Аналитик может создать подзадачу для устранения найденного дефекта в рамках согласованного контракта.


Но он не может под видом исправления самостоятельно поменять архитектуру или разрешить новую функциональность.


Для этого нужна задача координатору.


Иначе через сотню маленьких подзадач можно незаметно реализовать совершенно другой продукт.


### 8.3. Контроль зависших CLAIM


Участник может исчезнуть посреди работы. Необходимо отслеживать не только статус задачи, но и последнее подтверждение активности.


Я бы ввела периодические комментарии `PROGRESS` с указанием:
- что сделано;
- что осталось;
- какие возникли препятствия.


Но не рекомендую автоматически освобождать задачу только по таймеру. Сначала необходимо зафиксировать отсутствие активности и дать возможность владельцу подтвердить продолжение или освободить работу. Координатор может принудительно переназначить задачу, оставив след решения.


### 8.4. Раздельный учёт выполнения, проверки и слияния


Это три разных события:


| Событие | Что означает |
|---|---|
| `IMPLEMENTATION_COMPLETE` | Исполнитель закончил работу |
| `REVIEW_ACCEPTED` | Независимая проверка пройдена |
| `MERGED` | Изменения объединены с основной веткой |


Не следует объединять их в один статус `DONE`.


Иначе координатор не сможет понять, где именно застрял проект: в реализации, проверке или интеграции.


### 8.5. Не допускать создания задач ради создания задач


Дробление необходимо, но у каждой задачи должен быть измеримый результат.


Минимальная карточка задачи должна включать:


```text
Task ID:
Parent:
Type:
Goal:
Scope:
Expected result:
Acceptance criteria:
Dependencies:
Affected components:
Priority:
Restrictions:
Evidence:
```


Если участник не способен объяснить, какой конкретный результат будет получен, вероятно, это ещё не задача, а идея или обсуждение.

## 4. Что пока не реализовано


Здесь есть принципиальная оговорка.


**Сейчас это протокол, исполняемый участниками через GitHub Issues, а не автоматический task manager.**


То есть пока нет программного механизма, который автоматически:


- создаёт `REVIEW_REQUEST` после завершения PR;
- назначает свободного аналитика на проверку;
- создаёт correction tasks по результатам review;
- автоматически возвращает исправления первоначальному исполнителю;
- распределяет свободные задачи между нейросетями;
- отслеживает простаивание и самостоятельно перераспределяет работу.


Участники делают это самостоятельно по правилам Governance v2.


Есть и ещё один нюанс: correction task после проверки становится самостоятельной свободной задачей. Протокол не требует автоматически возвращать её первоначальному исполнителю. Он может захватить её снова, но это не обязательное назначение.
