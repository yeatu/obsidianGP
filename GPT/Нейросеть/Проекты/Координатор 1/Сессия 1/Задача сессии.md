# Задача сессии: сформировать новый курс SFRA для работы с ChatGPT Web

**Тип:** COORDINATOR_DECISION / ARCHITECTURE_RECONCILIATION  
**Приоритет:** P1  
**Назначение документа:** передать следующему координатору цель проекта, исходный архитектурный контекст и известные риски, но не подменять его самостоятельный анализ текущего репозитория заранее подготовленным backlog.

## 0. Обязательное требование владельца проекта

**Нужен работающий интерфейс SFRA для ChatGPT Web. Local MCP stdio пользователю не нужен и не является целевым результатом проекта.**

Пользователь отдельно уточнил, что возможное согласие с архитектурой, в основе которой Local MCP, произошло либо из-за непонимания предложенного решения, либо из-за поверхностного просмотра длинного описания. Это согласие нельзя трактовать как осознанное решение отказаться от исходной цели ChatGPT Web.

Следствия:

- Не предлагать пользователю повторно выбирать между Local MCP и интеграцией с ChatGPT Web.
- Не делать Local MCP обязательным, основным или равноправным продуктовым интерфейсом.
- Не считать создание локального MCP stdio-сервера выполнением пользовательской цели.
- Не продолжать Local MCP-разработку по инерции только потому, что она уже описана в старых реестрах или частично реализована.
- Существующий MCP-код можно оценить на предмет повторного использования отдельных технических компонентов, но сам Local MCP не должен становиться целью, критерием успеха или причиной задержки Web-интерфейса.

Цель определена однозначно. **Конкретный технический курс и план реализации должен сформировать координатор после самостоятельного исследования текущего проекта.** Этот документ не должен заранее принимать за него все инженерные решения.

## 1. Поручение следующему координатору

Провести самостоятельный архитектурный и технический анализ SFRA и на его основе сформировать реалистичный, проверяемый курс достижения главной цели: ChatGPT Web должен иметь рабочий способ обращаться к SFRA, выполнять поиск по Vault и получать точные оригинальные фрагменты с проверяемым происхождением.

Координатору необходимо:

1. Изучить фактическое состояние репозитория: исходный код, пакеты, application services, адаптеры, конфигурацию, тесты, CI, документацию, ветки, PR и актуальную панель проекта.
2. Восстановить историю архитектурных решений по реестрам сессий, отдельно различая исходную цель, промежуточные предложения, принятые инженерные решения и последующие отклонения курса.
3. Самостоятельно проверить, какие способы интеграции действительно доступны ChatGPT Web в требуемом пользовательском сценарии. Не предполагать наличие локального доступа к процессам, файловой системе или stdio-серверу.
4. Оценить ранее обсуждавшуюся схему GitHub Issues + GitHub Actions как один из основных исторических вариантов Web-совместимого транспорта. Проверить её на соответствие текущему коду, возможностям ChatGPT Web, правам GitHub, ограничениям Actions, сохранению состояния и реальной стоимости эксплуатации.
5. При необходимости исследовать другие способы интеграции, но каждый кандидат обязан обеспечивать работу именно из ChatGPT Web. Local MCP stdio не является допустимой конечной заменой.
6. Отделить SFRA Core и application services от transport adapters. По возможности повторно использовать реализованное ядро, не копируя retrieval/source logic в новый интерфейс.
7. Выявить, какие существующие реализации и задачи полезны для Web-цели, какие требуют адаптации, какие относятся только к ненужному Local MCP направлению, а какие уже устарели или дублируют друг друга.
8. На основании анализа подготовить новое архитектурное решение, схему взаимодействия компонентов, последовательность реализации, карту зависимостей и предложения по декомпозиции на независимо проверяемые задачи.
9. До начала работ с общим архитектурным или операционным воздействием зафиксировать решение и провести необходимые governance/review-процедуры. Не менять чужие CLAIM и не приписывать себе полномочия роли C.
10. Не объявлять MVP завершённым, пока не доказан полный сквозной сценарий использования из ChatGPT Web.

**Не требуется механически продолжать старые планы, сохранять старую нумерацию этапов или подгонять новую реализацию под ранее созданные Issues.** История нужна для понимания причин и повторного использования работы, а не для ограничения анализа.

## 2. Исходная архитектурная идея, которую необходимо учитывать

В Сессии 2 обсуждалось изменение не самой модели SFRA, а способа запуска её функций и взаимодействия с ChatGPT Web. Основной исторический вариант выглядел так:

```
ChatGPT Web
    |
    | создаёт запрос к SFRA через доступный GitHub-интерфейс
    v
GitHub Issues / механизм приёма запросов
    |
    | событие запуска
    v
GitHub Actions / одноразовый worker
    |
    | вызывает Python application services
    v
SFRA Core
    |-- search_vault
    |-- read_source
    |-- Context Builder
    |-- проверка Node ID / Content Hash / SnapshotRef
    |
    v
Результат возвращается в канал запроса
    |
    v
ChatGPT Web читает результат и при необходимости отправляет следующий запрос
```

Это исторически обсуждавшийся вариант, а не приказ реализовать его без проверки. Координатор должен подтвердить его техническую пригодность либо предложить другой Web-compatible механизм. Но конечная точка неизменна: **пользователь работает с SFRA из ChatGPT Web, без обязательного локального MCP-процесса.**

### 2.1. Базовые операции SFRA

В исходном варианте были определены две главные операции:

- `search_vault` — поиск по Vault, отбор источников и сборка контекста.
- `read_source` — адресное чтение оригинального источника по идентификаторам и сведениям о версии, возвращённым предыдущим запросом.

Координатору следует проверить существующие контракты и сохранить эту семантику, если анализ не выявит обоснованной необходимости её изменить. Транспорт не должен создавать собственную альтернативную реализацию поиска или чтения.

### 2.2. Если будет выбран GitHub Issues + Actions

В старом предложении описывался следующий цикл:

1. ChatGPT Web создаёт запрос в структурированном JSON.
2. GitHub Actions принимает только запросы установленного формата и запускает разрешённую операцию.
3. Worker валидирует версию протокола, request ID, тип операции и payload. Содержимое запроса рассматривается как данные, а не код.
4. Worker вызывает SFRA application services и возвращает связанный с исходным запросом результат.
5. Для дополнительного чтения создаётся отдельный запрос `read_source`; комментарии с результатами не должны запускать новые циклы обработки.
6. Повторная обработка должна быть идемпотентной и не создавать конфликтующие результаты. Нужны однозначные статусы выполнения и обработка ошибок.

Координатор должен проверить детали этого дизайна, а не принимать все параметры ранней спецификации безусловно. В частности, необходимо отдельно исследовать разрешения GitHub Actions, защиту от повторных запусков, сериализацию обновления постоянного состояния, лимиты размера запроса и ответа, retries/recovery и способ, которым ChatGPT Web будет читать результат.

### 2.3. Постоянное и временное состояние

Исходная архитектурная идея разделяла:

**Постоянное состояние:**
- стабильные Node ID;
- сопоставление идентификаторов с документами и структурными узлами;
- история версий и перенаправлений;
- сведения, необходимые для проверки SnapshotRef и Content Hash между независимыми вызовами.

**Временные вычисления:**
- FTS5 и поисковые кандидаты;
- ранжирование;
- сборка конкретного Context Pack;
- временные файлы одноразового runner.

Координатор должен проверить, где и как сейчас реализовано это состояние, какие гарантии уже обеспечены и как сохранить непрерывность адресации между независимыми Web-вызовами. Ранее предлагалось sidecar-хранилище, в том числе отдельная Git-ветка; это вариант реализации, а не обязательное решение без повторного анализа.

## 3. Неизменные принципы SFRA Core

Независимо от выбранного Web-compatible транспорта должны сохраняться основные принципы проекта:

1. **Индекс не является первоисточником.** Он помогает находить материалы, но не заменяет оригинальный текст Vault.
2. **Provenance обязателен.** Возвращённые фрагменты должны сопровождаться достаточной информацией для установления источника, версии и точного места в документе.
3. **Node ID и Content Hash выполняют разные функции.** Node ID адресует структурный узел, Content Hash идентифицирует конкретную версию текста.
4. **Snapshot continuity обязательна.** Независимый последующий вызов должен проверить, что читает именно ту версию источника, к которой относится ранее полученный результат.
5. **Никакой молчаливой подмены.** Устаревший SnapshotRef, несовпадающий hash, удалённый или неоднозначный узел должны приводить к явному статусу, а не к выбору похожего фрагмента.
6. **Transport-independent Core.** Транспортный адаптер преобразует внешний запрос в application contract и возвращает результат. Он не дублирует поиск, ранжирование, чтение или сборку Context Pack.
7. **Stateless-вызовы допустимы, потеря адресуемости — нет.** Не требуется хранить состояние диалога в worker или сервере, если оно может передаваться через проверяемые идентификаторы и постоянное состояние SFRA.
8. **Качество должно измеряться.** Benchmark должен оценивать не только retrieval, но и полноту, точность, Source Fidelity, эффективность контекста и корректность адресного чтения.

## 4. История архитектурных решений и причина повторного анализа

### Сессия 2: исходный Web-compatible вариант

В реестре Сессии 2 подробно обсуждалось, что локальный MCP-подход не подходит для требуемого взаимодействия с ChatGPT Web. В качестве альтернативы была описана схема с GitHub Issues и GitHub Actions, вызывающими Python-модули SFRA. Там же зафиксированы две основные операции, отдельный запрос для адресного чтения, request ID, статусы, идемпотентность, постоянное sidecar-состояние и проблема нестабильных Node ID при пересоздании индекса между запусками.

Исторические эксперименты через GitHub подтверждали отдельные части идеи, но не должны автоматически считаться доказательством готовности полного MVP. Координатор должен перепроверить код, workflow и результаты на актуальном HEAD.

### Сессии 3–6: отделение ядра от способа подключения

В этих сессиях архитектура была разделена на независимые application services, non-production Issue Worker Core и отдельные транспортные/операционные этапы. В частности, были выделены SearchVaultService и ReadSourceService с типизированными контрактами. Такое разделение полезно для нынешней задачи: новое подключение ChatGPT Web должно использовать эти сервисы, а не переносить в адаптер бизнес-логику.

В тех же записях появились ограничения на публикацию содержимого Vault в GitHub. Координатор должен проверить происхождение и полномочия этих ограничений, их актуальность и точную область применения. Не следует выдавать их за пользовательское требование конфиденциальности.

### Сессии 8–9: Local MCP как промежуточный курс

В Сессиях 8–9 проект был переориентирован на Local MCP stdio и локальный retrieval interface. Пользователь теперь прямо уточнил, что не хотел этого как конечный результат, а возможное согласие с такой постановкой не было осознанным выбором отказаться от работы в ChatGPT Web.

Поэтому этот поворот важен как часть истории проекта и возможный источник уже написанного кода, но **не является подтверждением изменения цели владельцем проекта**. Координатор не должен продолжать этот курс как основной. Ему нужно самостоятельно оценить, какие части Local MCP реализации можно переиспользовать независимо от самого stdio-транспорта, а какие не имеют ценности для Web-цели.

## 5. Позиция пользователя по публичности и технической корректности

В Сессии 2 пользователь прямо сообщил: **«Публичность не имеет значения»**. В Сессии 7 он дополнительно написал: **«Мне плевать на безопасность, утечку данных, то, что данные будут в публичном доступе и тому подобное. Мне нужен результат.»**

Это означает, что публичность GitHub сама по себе не является основанием отвергать Web-compatible архитектуру или запрещать передачу необходимых исходных фрагментов через выбранный канал. Нельзя приписывать пользователю требование конфиденциальности, которого он не устанавливал.

При этом нужно разделять разные категории:

- **Конфиденциальность:** пользователь сообщил, что публичность и утечка данных не являются для него блокером.
- **Целостность и корректность:** точность оригинального текста, проверка хешей, стабильные идентификаторы, непрерывность SnapshotRef и отсутствие потери состояния нужны для работы продукта.
- **Операционные риски:** ошибочные workflow, повторное выполнение, порча или потеря sidecar, неконтролируемые записи и повреждение production state могут ломать продукт. Их нужно анализировать как инженерные риски, а не маскировать под требование секретности.

Не выводить из безразличия пользователя к публичности автоматическое разрешение на любую destructive-операцию. Текущие полномочия и governance-процедуры следует проверить и соблюдать, а спорные ограничения — пересматривать формально, не приписывая их пользователю.

## 6. Известный операционный инцидент, который необходимо проверить

В ходе одной из предыдущих интеграционных проверок публичный GitHub Actions log раскрыл имена/структуру путей Vault и производные метаданные. После этого real-Vault workflow `.github/workflows/sfra-e3-real-e1-integration.yml` был отключён в main коммитом `7a3808713a46f54a1cfd17c2df39ca9e581bc87f`.

В записи о containment указано:
- не повторять запуск этого workflow и эквивалентные реальные Vault checkout в публичных Actions до отдельного рассмотренного решения;
- для дальнейших CI использовать synthetic/disposable fixtures;
- в логах и артефактах оставлять только неидентифицирующие агрегированные результаты;
- ранее опубликованные лог и артефакт считать раскрытыми, пока не подтверждена отдельная проверка их удаления/retention.

Это известный факт истории проекта, а не утверждение о текущем состоянии всех workflow. Координатор обязан проверить актуальный репозиторий, Actions и доступные retention/remediation сведения самостоятельно. Не считать старый лог или артефакт удалённым без доказательства. Не запускать real-Vault workflow только ради повторного получения тестового результата.

## 7. Самостоятельный план анализа для координатора

Не начинать с редактирования backlog. Сначала получить целостную картину проекта.

### Этап A. Технический аудит

Проверить на актуальном состоянии репозитория:

- структуру исходного кода и границы модулей E1/E2/E3;
- индексатор, retrieval, Context Builder и source reader;
- application services и typed contracts;
- стабильность Node ID, Content Hash, SnapshotRef и sidecar persistence;
- тесты, benchmark, fixture sets, CI workflows и результаты последнего успешного прогона;
- transport adapters, включая незавершённые локальные интерфейсы и прежние предложения Web transport;
- README, архитектурные документы, handoff-файлы и оперативную панель.

Для каждого компонента установить фактический статус: реализован и проверен; реализован, но не принят; частично реализован; только спроектирован; заблокирован; устарел или дублируется. Подтверждать статусы ссылками на точные commit SHA, tests и PR, а не пересказом старых отчётов.

### Этап B. Проверка реального подключения к ChatGPT Web

Исследовать, каким способом ChatGPT Web сможет отправлять запрос в систему и получать ответ без локального MCP stdio. Проверить реальные доступные механизмы, права, ограничения и пользовательский flow. Не путать возможность локального запуска SFRA с возможностью вызова SFRA из Web.

Оценить ранее обсуждавшийся механизм GitHub Issues + Actions, но не считать его автоматически окончательным только потому, что он фигурировал в Сессии 2. Проверить:
- как именно ChatGPT Web создаёт запрос;
- как worker запускается и получает запрос;
- как worker возвращает результат;
- как ChatGPT Web получает и однозначно связывает ответ с запросом;
- как реализуются повторный запрос, ожидание, ошибки и тайм-ауты;
- как сохраняются Node ID, snapshot и sidecar между запусками;
- как предотвращаются повторная обработка и рекурсивные запуски;
- какие разрешения и secrets действительно необходимы;
- как избежать потери данных при параллельных обновлениях.

Кандидатная архитектура считается пригодной только после демонстрации полного пользовательского цикла, а не по наличию workflow или отдельного Python-модуля.

### Этап C. Сверка решений и активной работы

Изучить реестры всех предыдущих сессий и актуальное состояние GitHub: Issues, PR, ветки, коммиты, CLAIM, review requests, комментарии и CI. Использовать текущие записи как evidence, а не как готовый план.

Нужно понять:
- какие решения были предложениями, а какие получили формальное принятие;
- кто и на каком основании установил ограничения на transport/publication/production operations;
- какие задачи относятся к Local MCP и не приближают ChatGPT Web к рабочему результату;
- какие результаты можно переиспользовать;
- какие активные исполнители имеют подтверждённые CLAIM и не должны быть вытеснены;
- какие зависимости технические, а какие являются только родительскими связями.

Не требуется переносить в этот handoff длинный список номеров Issues. Координатор сам должен найти актуальные задачи и проверить их состояние.

### Этап D. Новая архитектура и план реализации

После анализа сформировать новый курс, который должен включать:

1. Целевую схему компонентов и последовательность вызовов именно для ChatGPT Web.
2. Точку входа, способ запуска, протокол запросов/ответов и способ получения ответа моделью.
3. Границы между транспортом, worker/runtime и SFRA Core.
4. Контракт поиска и адресного чтения, включая provenance и snapshot continuity.
5. Модель постоянного и временного состояния.
6. Retry, idempotency, timeout, concurrency и recovery semantics.
7. Ограничения прав, workflow и допустимые действия над Vault/sidecar.
8. Test strategy: unit, contract, integration, end-to-end, benchmark.
9. Этапы реализации с measurable acceptance criteria.
10. План декомпозиции на независимо полезные задачи с owner role, scope, deliverable, dependencies, files/components, conflict map и integration owner.

Предпочитать максимальную безопасную параллельность полезной работы, но не дробить задачи до бессмысленных микрошагов. Сначала согласовать общие контракты и границы, затем разделять независимые компоненты, тесты и документацию.

### Этап E. Формальное оформление и начало исполнения

После аудита координатор должен:
- опубликовать архитектурное решение с кратким сравнением рассмотренных вариантов и аргументами;
- отметить, какие прежние решения заменяются, а какие остаются действующими;
- привести в соответствие оперативную панель и связанные задачи, не удаляя историю;
- сохранить действующие CLAIM и независимость review;
- сформировать backlog, который прямо ведёт к Web-compatible MVP;
- начать работу в рамках имеющихся полномочий и передать независимые задачи свободным E/A-участникам.

Не приписывать себе Agent ID C. Полномочия координатора определяются действующим Governance Protocol и выдаются владельцем проекта.

## 8. Критерии готовности результата

Работа не считается выполненной только потому, что:
- локальный MCP stdio запускается;
- Python-модули проходят unit tests;
- GitHub Actions workflow существует;
- Issue или PR закрыты;
- отдельный тестовый запрос вернул ожидаемый результат.

Для подтверждения цели необходим полный сценарий:

1. Пользователь отправляет запрос из ChatGPT Web.
2. Web-compatible интеграция передаёт запрос SFRA.
3. SFRA выполняет поиск и возвращает контекст с provenance.
4. ChatGPT Web получает ответ и может запросить дополнительные исходные фрагменты.
5. Повторное чтение использует ранее полученные Node ID, Content Hash и SnapshotRef и корректно обнаруживает устаревание/несовпадение.
6. Весь цикл подтверждён тестами на точном commit HEAD и воспроизводимыми CI/e2e evidence.

**Критерий успеха — работающий пользовательский сценарий в ChatGPT Web, а не наличие конкретного локального транспорта.**
