# Задача сессии: восстановить целевую архитектуру SFRA для ChatGPT Web и скорректировать курс реализации

**Тип:** COORDINATOR_DECISION / ARCHITECTURE_RECONCILIATION  
**Приоритет:** P1  
**Цель:** привести фактический план реализации SFRA в соответствие с изначально задуманным способом работы через ChatGPT Web, сохранив уже реализованное ядро и не продолжая автоматически транспортную ветку, которая не решает исходную задачу пользователя.

> **Главное:** целевая схема взаимодействия с ChatGPT Web, обсуждавшаяся в Сессии 2, — `ChatGPT Web → GitHub Issues → GitHub Actions → SFRA Python modules → Issue Comment → ChatGPT Web`. Локальный MCP stdio-сервер не является способом подключения ChatGPT Web в требуемом сценарии и не должен оставаться обязательным входом в MVP.

## 1. Что требуется от координатора

1. Восстановить целевую архитектуру из реестров Сессий 2–9 и настоящей задачи, сопоставить её с текущим `main`, Issues и PR.
2. Разделить уже реализованное ядро SFRA и транспортные адаптеры. Не переписывать ядро ради смены транспорта.
3. Пересмотреть решение, зафиксированное в Issue [#35](https://github.com/yeatu/obsidianGP/issues/35), где основной продуктовый этап был переключён на Local MCP stdio. Проверить, решает ли этот путь исходную задачу работы именно с ChatGPT Web.
4. Подготовить и зафиксировать формальное координаторское решение о целевом транспорте, а затем скорректировать связанные Issues, зависимости, приоритеты и `PROJECT_TASKS.md` в соответствии с Governance Protocol.
5. Сохранить полезную работу по SnapshotRef, provenance, контрактам и benchmark. Не отменять задачи механически и не начинать реализацию заново.
6. До любых production-операций сначала определить безопасный проверяемый тестовый сценарий. Не запускать опасные workflow и не менять production-данные ради демонстрации активности.

Эта задача требует архитектурного решения, а не немедленного массового изменения кода. Координатор должен сначала проверить текущее состояние GitHub и действующие CLAIM/блокировки.

## 2. Целевая архитектура взаимодействия с ChatGPT Web

### 2.1. Общий поток

```text
ChatGPT Web
   |
   | Создаёт GitHub Issue с JSON-запросом SFRA
   v
GitHub Issues
   |
   | Событие открытия подходящей Issue
   v
GitHub Actions (одноразовый worker)
   |
   | Загружает Vault и постоянное sidecar-состояние
   | Вызывает Python application services
   v
SFRA Core
   |-- search_vault
   |-- read_source
   |-- Context Builder / проверка SnapshotRef и Content Hash
   |
   v
Комментарий к исходной GitHub Issue
   |
   | ChatGPT Web читает результат
   v
ChatGPT Web
```

Это не постоянный сервер и не локальное MCP-подключение. GitHub Issues служат очередью запросов и каналом передачи результатов; GitHub Actions — одноразовой средой исполнения Python-кода. Веб-модель взаимодействует с системой через доступные ей GitHub-действия: создать Issue, прочитать Issue и её комментарии.

### 2.2. Запросы и операции

На уровне внешнего протокола нужны две базовые операции:

- `search_vault` — поиск по Vault, отбор источников и сборка Context Pack.
- `read_source` — адресное получение оригинального фрагмента по ранее полученным идентификаторам и проверкам версии.

Запрос передаётся в теле новой Issue как структурированный JSON. В протоколе должны быть как минимум:

- версия протокола;
- уникальный `request_id`;
- имя операции из закрытого allowlist;
- типизированный payload операции.

Worker проверяет автора, репозиторий, заголовок/маркер запроса, версию и JSON-схему. Тело Issue является данными, а не исполняемым кодом. Ошибочный, неподдерживаемый или изменённый запрос должен завершаться явным отказом, а не частичным или приблизительным исполнением.

Результат публикуется комментарием к той же Issue и однозначно связывается с `request_id`. Нужны определённые статусы обработки (в ранней спецификации: `PENDING`, `RUNNING`, `DONE`, `FAILED`), идемпотентность и защита от повторной несовместимой обработки.

Для дополнительного чтения ChatGPT Web создаёт **новую отдельную Issue** с `read_source`, используя `Node ID`, `Content Hash` и соответствующий snapshot/version reference из предыдущего результата. Комментарии, которые публикует Actions, не должны запускать новые worker-запуски: иначе возможна рекурсивная цепочка.

### 2.3. Состояние и хранение

Необходимо различать постоянное состояние адресации источников и временные вычислительные данные.

**Постоянное sidecar-состояние:**
- стабильные `Node ID`;
- соответствие Node ID исходным документам и структурным узлам;
- история версий и сопоставление изменений;
- данные, необходимые для проверки SnapshotRef / Content Hash и продолжения адресного чтения между независимыми запусками.

В раннем варианте для sidecar предлагалась отдельная ветка GitHub, например `sfra-state`. Это состояние загружается worker-ом в начале задания и сохраняется после обновления. Конкурирующие записи должны сериализоваться или защищаться эквивалентным механизмом, чтобы параллельные Actions не затирали изменения друг друга.

**Временные данные:**
- поисковый FTS5-индекс и промежуточные таблицы;
- ранжирование и поисковые кандидаты;
- сборка конкретного Context Pack;
- временные файлы конкретного runner.

Их можно пересоздавать в одноразовой среде Actions. Нельзя делать Node ID случайными заново при каждом запуске: ранее выданный идентификатор должен оставаться адресуемым, пока это допускает история источника.

### 2.4. Ответ и provenance

`search_vault` должен возвращать не только краткое описание найденного, но и пригодный для анализа Context Pack с оригинальными фрагментами и provenance. В него входят:
- включённые фрагменты и дословный текст;
- Node ID, путь, heading path и Content Hash;
- сведения о SnapshotRef / версии источника;
- coverage: найденные и не найденные аспекты;
- deferred sources: найденные, но не включённые в текущий бюджет источники;
- параллельные / пересекающиеся источники без объявления их противоречиями без доказательств;
- статистика объёма и полноты пакета.

`read_source` возвращает точный оригинальный срез в запрошенном scope (например, node, parent, neighbors, document) либо явный статус, почему его нельзя вернуть. Несовпадение Hash, устаревший SnapshotRef или неоднозначная адресация не должны приводить к незаметной подмене похожим фрагментом.

Основной принцип SFRA остаётся неизменным: индекс — навигационное представление, а не вторая база знаний; доказательством служит первичный текст Vault с проверяемым происхождением.

## 3. Что не является целевой архитектурой

- **Локальный MCP stdio как обязательная точка входа ChatGPT Web.** В требуемом пользовательском сценарии такой способ подключения непригоден. Его нельзя считать выполнением цели только потому, что локальный MCP-сервер существует или проходит собственные интеграционные тесты.
- Постоянно работающий локальный сервер, который должен быть доступен ChatGPT Web.
- Перенос retrieval-логики внутрь GitHub Worker. Worker — транспортный/исполнительный адаптер; он вызывает SFRA application services.
- Переписывание Search, Source Reader или Context Builder под GitHub API.
- Новый retrieval algorithm, embeddings или vector search без доказанной benchmark-необходимости.

MCP может оставаться **дополнительным транспортным адаптером** для совместимых локальных клиентов. Его существующий код не нужно удалять или переписывать без необходимости. Однако функциональность ChatGPT Web должна иметь самостоятельный путь через Issues + Actions.

## 4. Контекст решений и расхождения между сессиями

### Сессия 2 — исходная альтернативная схема для ChatGPT Web

В реестре Сессии 2 прямо сформулировано, что меняется не основная архитектура SFRA, а способ запуска и взаимодействия с ChatGPT Web. Было предложено использовать GitHub Issues как очередь запросов и канал ответа, а GitHub Actions как одноразовый запуск Python-модулей.

В том же реестре зафиксированы:
- экспериментальный транспортный цикл через Issue [#3](https://github.com/yeatu/obsidianGP/issues/3): создание Issue, запуск Actions, публикация комментария и чтение результата;
- эксперимент поискового ядра через Issue [#4](https://github.com/yeatu/obsidianGP/issues/4);
- исторический тест на реальном Vault: 66 Markdown-файлов, 9 080 структурных узлов, проверка оригинального среза и SHA-256;
- обнаруженная проблема: временная SQLite с повторной генерацией UUID не сохраняет стабильные Node ID между независимыми runner-ами;
- решение разделить постоянное sidecar-состояние идентификаторов/истории и временный индекс/вычисления;
- две основные операции `search_vault` и `read_source`;
- дополнения к заданиям E1/E2/E3, чтобы сохранить существующие результаты и адаптировать их к Actions, а не начинать реализацию заново.

Реестр отдельно подчёркивает, что экспериментальный мост подтверждает техническую осуществимость направления, но сам по себе ещё не доказывает готовность полного MVP.

### Сессии 3–6 — разделение ядра и транспорта

Далее архитектура была декомпозирована на независимые этапы:
- V2.1 — transport-independent `SearchVaultService` и `ReadSourceService`, typed contracts и проверки;
- V2.2 — Issue Worker Core без реальных GitHub API/network-вызовов;
- V2.3 — GitHub transport, persistence, idempotency, leases, retries и recovery;
- V2.4 — отдельные readiness/security gates и controlled rollout.

Это разделение не опровергает GitHub transport. Оно позволяет сначала иметь устойчивое ядро и worker core, а затем подключить реальный транспорт отдельным этапом.

По текущей проверке GitHub:
- Issue [#13](https://github.com/yeatu/obsidianGP/issues/13) закрыта, PR [#14](https://github.com/yeatu/obsidianGP/pull/14) объединён: V2.1 находится в `main`;
- Issue [#15](https://github.com/yeatu/obsidianGP/issues/15) закрыта, PR [#16](https://github.com/yeatu/obsidianGP/pull/16) объединён: V2.2 non-production worker core находится в `main`;
- PR [#12](https://github.com/yeatu/obsidianGP/pull/12) с GitHub Issue Worker/Recovery на момент проверки остаётся Open / Draft / unmerged. Это предложение, а не работающий production worker.

### Сессии 3 и 5–6 — происхождение ограничений на публикацию

В реестре Сессии 3 под заголовком координаторских решений появилось правило `DENY BY DEFAULT` для публикации сырых Vault fragments/excerpts/titles/paths в Issues/comments. В более поздних записях это ограничение повторялось как действующий gate.

Важно: в найденной записи это сформулировано как координаторское решение. Это **не следует выдавать за требование пользователя о конфиденциальности**. Оно конфликтует с прямым пользовательским указанием из Сессии 2 о том, что публичность репозитория не имеет значения. Координатор должен установить происхождение, основания и актуальную силу этого gate и вынести вопрос на явное решение. Нельзя ни молча приписывать его пользователю, ни самовольно обходить действующее нормативное решение.

### Сессии 8–9 — поздний поворот к Local MCP

В Сессии 8 был утверждён этап `SFRA MVP — Local Retrieval Interface + Measured Quality` с Issues [#35](https://github.com/yeatu/obsidianGP/issues/35) и [#36–#43](https://github.com/yeatu/obsidianGP/issues). В нём локальный MCP stdio стал основным интерфейсом, а GitHub Issue Worker/Recovery был исключён из текущего этапа.

На момент проверки GitHub 18 ноября 2026 года:
- Issue #35 закрыта;
- Issue #37 (контракты MCP) закрыта;
- #36 и #38–#43 остаются открытыми;
- #38–#40 и #43 посвящены локальному MCP;
- #41–#42 посвящены benchmark и измерению качества.

Этот поворот зафиксирован в реестре и Issues, но он не доказывает, что Local MCP решает исходную задачу ChatGPT Web. Именно это расхождение и требуется разрешить координатору. Полезные задачи по SnapshotRef и benchmark нужно сохранить; MCP-специфичные задачи следует пересмотреть по scope и назначению, а не продолжать автоматически как будто пользовательская цель не менялась.

## 5. Позиция пользователя: публичность и техническая целостность — разные вопросы

В Сессии 2 пользователь прямо написал: **«Публичность не имеет значения.»** В ответном тексте того же реестра зафиксировано, что публичность репозитория не включается в риски транспортной схемы.

В Сессии 7 пользователь отдельно сформулировал два положения в одном сообщении:
- он не станет ради видимости прогресса запускать опасные workflow или трогать production-данные;
- ему безразличны безопасность/утечка данных и то, что данные могут оказаться в публичном доступе; ему нужен работающий результат.

Эти положения нужно читать по разным категориям риска:

1. **Конфиденциальность и публичность.** Это не пользовательский блокер. Нельзя отклонять GitHub Issues + Actions, запрещать возврат необходимых оригинальных фрагментов или обрезать Context Pack только потому, что Issues/comments публичны.
2. **Целостность и корректность.** Стабильность Node ID, проверка Content Hash/SnapshotRef, точность оригинального текста, защита от подмены и потери sidecar-состояния нужны самой функции SFRA. Они не являются требованием секретности.
3. **Операционный риск.** Запрет на опасный workflow и изменение production-данных ради формального прогресса был заявлен явно. Первые end-to-end проверки должны использовать контролируемый тестовый сценарий и не портить production state. Этот пункт не следует стирать фразой «пользователю всё равно на безопасность».

Следовательно, не вводить confidentiality-политику от имени пользователя. При этом технические проверки целостности и запрет на необоснованные destructive/production-операции должны оцениваться отдельно.

## 6. Действующие ограничения, которые координатор обязан разрешить формально

На момент проверки:
- Issue [#20](https://github.com/yeatu/obsidianGP/issues/20) открыта и содержит Governance Protocol v2.4.
- В §11 Issue #20 закреплено, что координаторские решения, подзадачи и CLAIM не могут обходить явно установленные safety/security gates, включая ограничения на публикацию содержимого Vault и production-операции.
- Issue #35 содержит отдельный запрет на production GitHub worker/API writes/event workflows и на публикацию source excerpts, raw_text, note titles/paths в публичных Issues/comments в рамках закрытого milestone.

Эти записи нельзя игнорировать. Эта задача не отменяет их автоматически. Координатор с надлежащими полномочиями должен:
1. проверить, кто и на каком основании установил эти ограничения;
2. сопоставить их с прямыми указаниями пользователя и исходной целью ChatGPT Web;
3. вынести отдельное решение: какие ограничения относятся к целостности/эксплуатации, а какие ошибочно ограничивают проект только из-за публичности;
4. при необходимости обновить Issue #20, #35 и зависимые задачи формальным решением, сохранив историю.

Не подменять решение координатора предположением и не приписывать себе Agent ID C. Идентификатор C выдаёт владелец проекта.

## 7. Рекомендуемый порядок пересмотра курса

1. **Проверить фактический HEAD и состояние работ.** Просмотреть `main`, PR #12, Issues #20, #35–#43, последние CLAIM/review/comments и реальные тесты. Исторические статусы выше не заменяют live-проверку.
2. **Зафиксировать архитектурное решение.** Основной пользовательский сценарий — ChatGPT Web через Issues + Actions. Core остаётся transport-independent. Local MCP может быть дополнительным интерфейсом для другого клиента, но не критерием доступа ChatGPT Web.
3. **Сохранить ядро.** Использовать существующие E1/E2/E3 и V2.1/V2.2 services/worker core. Не дублировать retrieval/source logic в transport adapter.
4. **Провести повторную декомпозицию.** Выделить отдельные задачи на протокол Issue, одноразовый worker, sidecar persistence/concurrency, публикацию результата и сквозной тест. Каждая задача должна иметь конкретную роль, deliverable, acceptance criteria, scope/out-of-scope, зависимости, границы файлов и интеграционного владельца.
5. **Пересмотреть текущие #36–#43.** Сохранить задачи SnapshotRef/provenance и benchmark, если они остаются актуальными. Решить, какие MCP-специфичные работы оставить как optional adapter, а какие заменить задачами GitHub transport. Не закрывать и не переназначать их без проверки владельцев и прогресса.
6. **Проверить end-to-end сценарий.** ChatGPT Web создаёт Issue для `search_vault`; Actions запускает модуль; ответ с Context Pack приходит комментарием; ChatGPT читает его; затем отдельная Issue запрашивает `read_source` по ранее возвращённым Node ID + Content Hash/SnapshotRef. Проверить повторный запуск, идемпотентность, сохранение sidecar и fail-closed при несовпадении версии.
7. **Не считать прототип завершённым MVP.** Исторический успешный транспортный тест и старые показатели Vault нужно повторить на актуальном коде и зафиксировать артефактами CI, тестами и проверяемыми commit SHA.

## Критерий завершения этой координаторской задачи

Следующий координатор должен оставить в GitHub однозначное, проверяемое решение, в котором:
- целевой способ работы ChatGPT Web явно определён;
- транспорт не смешан с SFRA Core;
- действующие governance gates формально пересмотрены, а не обойдены;
- существующий прогресс сохранён и задачи скорректированы;
- подготовлен проверяемый план end-to-end реализации через Issues + Actions;
- отсутствует ложное утверждение, что локальный MCP stdio сам по себе обеспечивает работу ChatGPT Web.

**Важно:** эта задача передаёт архитектурный контекст и требует пересмотра курса. Она сама по себе не утверждает, что GitHub worker уже реализован, не разрешает production rollout и не объявляет ранее открытые задачи выполненными.
