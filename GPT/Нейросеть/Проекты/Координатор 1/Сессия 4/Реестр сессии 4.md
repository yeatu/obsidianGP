Я изучила три реестра сессий, исходный промпт координатора и актуальный `PROJECT_TASKS.md` в репозитории `yeatu/obsidianGP`.


Проект, о котором идёт речь, — **SFRA (Search, Retrieval and Fragment Analysis)**: система поиска по Obsidian Vault с извлечением проверенных фрагментов первоисточника.


## 1. Роль координатора


Основные правила работы:


1. Пользователь ставит общую задачу.
2. Координатор определяет архитектурные границы, последовательность и независимые направления работ.
3. Исполнители E1, E2 и E3 выполняют независимые задачи. Они не должны зависеть от прямого взаимодействия друг с другом.
4. Аналитики A1, A2 и A3 независимо проверяют соответствующих исполнителей.
5. Аналитики ведут собственные чек-листы, фиксируют HEAD, CI и доказательства.
6. Координатор проводит пакетную проверку, принимает архитектурные решения и корректирует задания, когда для этого есть основания.


**Важное правило:** завершение отдельной задачи не означает автоматической приёмки координатором. Но и отсутствие координаторской приёмки не должно останавливать исполнителя от следующей уже согласованной задачи.

Главный архитектурный принцип:


**Индекс помогает найти информацию, но не становится самостоятельной базой знаний.**


Поисковые аннотации, ранжирование и метаданные не заменяют авторский Markdown. В Context Pack должны попадать исходные фрагменты с проверенными адресами, хешами и привязкой к конкретному snapshot.


Мой критерий качества будет не «модель получила красивый ответ», а «можно доказать, откуда взялся каждый использованный фрагмент».

## 6. Правила, которые принимаю как рабочие


- Не переписывать работающий функционал без доказанной необходимости.
- Не принимать тесты на fixtures за доказательство реальной интеграции.
- Не принимать успешный CI за автоматическую архитектурную приёмку.
- Не подменять исходный Markdown поисковыми аннотациями.
- Не считать `budget_limited` ошибкой, если система корректно обработала бюджет.
- Не переносить координаторское подтверждение на новый HEAD без проверки.
- Не заставлять аналитиков ждать моего разрешения для продолжения уже согласованной работы.


Самостоятельно запускать шесть отдельных нейросетей через этот чат я не могу. Моя зона ответственности здесь: постановка задач, проверка GitHub, аудит результатов и архитектурные решения. Передачу отчётов между участниками ты организуешь, как и предусмотрено исходным промптом.

### Аналитическое ревью — два блокирующих дефекта
Review [5944575778](https://github.com/yeatu/obsidianGP/pull/16#pullrequestreview-5944575778) вернул реализацию на доработку:

1. **First-seen body hash mutation guard обходится.** В `IssueWorkerCore.run()` digest вычисляется до metadata validation, но bind в status store выполняется после успешной metadata validation. Issue, впервые увиденный с неверным title/author/repository, остаётся без закреплённого hash; изменение body вместе с исправлением metadata может превратить подменённый payload в baseline. Исправление: закреплять точный hash первого наблюдения до metadata rejection; добавить тест: invalid metadata + body A → valid metadata + body B → permanent `request_body_changed`, без вызова application service.
2. **Необработанный JSON `RecursionError`.** Парсер ловит `JSONDecodeError`/`ValueError`, но не `RecursionError`. Глубоко вложенный JSON меньше 32 KiB может выйти из parser/worker без типизированного REJECTED status. Исправление: normalize recursion failure в `IssueRequestError("invalid_json")`; добавить adversarial test с глубиной около 10 000 пар скобок и размером <32 KiB.
