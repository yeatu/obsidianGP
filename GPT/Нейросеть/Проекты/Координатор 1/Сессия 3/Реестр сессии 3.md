## 2. Что представляет собой проект


Цель проекта — реализация **SFRA (Source-First Retrieval Architecture)** для Obsidian.


Главный принцип:


> Индекс указывает, источник говорит.


Это означает:


- Vault остаётся неизменным.
- Индексы и производные данные хранятся отдельно.
- Поиск обнаруживает оригинальные фрагменты, но не создаёт факты.
- Каждый фрагмент адресуется через Node ID и Content Hash.
- Система обязана сохранять различия между параллельными источниками.
- Экономия контекста не должна приводить к потере важных сведений.


Первоначальную архитектуру локального MCP-сервера скорректировали. Основным транспортом MVP теперь служат GitHub Issues и GitHub Actions. MCP остаётся возможным дополнительным интерфейсом.

## **4. Что ещё не готово**


Здесь находятся основные оставшиеся проблемы.


**Проблема №1. Отсутствует атомарность чтения одного scope.**


Сейчас `get_parent_by_id()` и `get_neighbors_by_id()` открывают несколько независимых SQLite-соединений.


Например, `get_neighbors_by_id()`:


1. Получает и проверяет целевой узел.
2. Отдельно загружает соседей.
3. Для каждого соседа повторно вызывает `get_node_by_id()`.


При этом `_relation_anchor_row()` сравнивает Hash узла, путь и родителя, но не сравнивает `documents.source_sha256` и `documents.generation`.


Это оставляет возможность смешать данные разных поколений при изменении индекса между операциями.


Требование E3: все фрагменты одной операции должны читаться из одной закреплённой SQLite read transaction.


**Статус:**&#x20;


Блокирует интеграционную приёмку






**Проблема №2. Нет Snapshot binding.**


Не реализованы:


- Входной `snapshot_id`.
- Возврат того же `snapshot_id`.
- Проверка соответствия закреплённого состояния manifest и Vault checkout.
- Явная идентификация версии индекса в результатах чтения.


Передача `db_path` и `vault_root` сама по себе не обеспечивает проверку SnapshotRef.


**Проблема №3. Нет&#x20;**`resolve_current_node()`**.**


B1 DependencyResolver получает только Node ID.


Существующий `get_node_by_id()` требует также `expected_hash`.


Следовательно, у E3 пока нет публичной операции, которая безопасно определяет текущую версию узла только по его Node ID.


**Проблема №4. Не передаются необходимые metadata.**


E3 ожидает:


- `preservation`;
- `required_with`;
- `parent_context_required`.


В `NodeRecord` этих полей нет. Более того, текущий Markdown-парсер формирует другую metadata: callout, параметры списков, ссылки. Три требуемых поля в нём не формируются.


Нужно определить единый источник этих метаданных. Просто экспортировать `metadata_json` недостаточно, если самих значений там нет.


**Проблема №5. Не определён бюджет чтения.**


В предложении E3 предусмотрен `budget_tokens`, а также запрет усечения оригинального текста.


У новых методов E1 такого аргумента и статуса `budget_exceeded` пока нет. Нужно согласовать, на какой стороне будет осуществляться бюджетирование.

### Блокер A. Проверка связей в E3

## **Главный нерешённый вопрос: формат API E1 и E3**


Здесь есть конкретная несовместимость, которую важно устранить до заявления о реальной интеграции.


E1 возвращает объекты `SourceScopeResult` и `CurrentNodeAddress`. Это dataclass-типы с методом `to_dict()`, но сами они не являются словарями `Mapping`.


E3 в `source_reader.py` непосредственно ожидает `Mapping`. Кроме того, E3 рассчитывает на такую структуру Source Scope:


- поле `target_source`;
- фрагменты с ролями `target`, `parent_context`, `previous_neighbor`, `next_neighbor` или `document`.


E1 сериализует результат иначе: `anchor`, `parent`, `previous`, `next`, `document`, а фрагменты представляет как записи `NodeRecord` без поля `role`.


Особенно показателен файл `run_real_e1_integration.py`: он передаёт в E3 непосредственно функции из `sfra_indexer`, без преобразующего адаптера. Поэтому реальная интеграция в текущем виде не сможет корректно обработать даже результат `resolve_current_node()`, не говоря уже о четырёх scope.


Это не косметическое расхождение имён. Нужно согласовать единый формат ответа или написать явный адаптер E3, который преобразует результаты E1 и назначает роли по структурированным полям E1.

### Что ещё необходимо исправить E3


**Первое. Структурные связи.** Нормализатор пока не проверяет точное равенство ID родителя, одинакового родителя у соседей и последовательность предыдущий → целевой → следующий. Нужны adversarial-тесты.


**Второе. Утечки диагностики между запросами.** `E1DependencyResolver.diagnostics` сохраняется в экземпляре, а pipeline не очищает его при следующем запуске. Ошибки предыдущего запроса могут попасть в следующий Context Pack. Нужен тест двух последовательных запусков одного pipeline.


**Третье. Документация.** README E3 всё ещё утверждает, что E1 предоставляет только `get_node_by_id()` и что реальная интеграция не доказана. Оба утверждения уже неверны.
