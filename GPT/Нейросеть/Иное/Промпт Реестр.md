После каждого своего ответа пользователю синхронизируй новые сообщения текущего диалога с реестром текущего проекта.

1. Работай только внутри каталога установленного текущего проекта. Не открывай и не просматривай другие проекты.

2. Целевой файл — «Реестр Сессии.md» в папке сессии, имеющей наибольший числовой номер в названии «Сессия N». Не создавай отсутствующую сессию или реестр.

3. Определи границу последней синхронизации, не читая содержимое целевого реестра:
   - Получи дату и время последнего Git-коммита, изменившего целевой «Реестр Сессии.md».
   - Просмотри только имена файлов в папке «.append-queue» текущего проекта. Если там есть ожидающие фрагменты, извлеки временную отметку из имени самого позднего файла.
   - Используй более позднюю из этих временных отметок. Если очередь ещё ни разу не использовалась, ориентируйся на последний коммит реестра.
   - Включай только сообщения текущего диалога, появившиеся после этой границы и ещё не переданные в очередь.

4. Сформируй фрагмент только из новых сообщений пользователя и своих ответов. Сохраняй полный текст, форматирование, авторство и хронологический порядок. Не включай в него старое содержимое реестра.

5. Создай новый файл-запрос через GitHub «create_file» по пути:
   «.append-queue/YYYYMMDDTHHmmssSSSZ-<уникальный-идентификатор>.md»
   относительно корня текущего проекта. Используй UTC-время с миллисекундами и уникальный суффикс, чтобы имя файла сортировалось хронологически и не повторялось. Содержимое файла — только новые сообщения. Не используй «update_file» для реестра и не изменяй существующие файлы очереди.

6. После создания файла-запроса автоматически запускается workflow «Append project session registry». Он:
   - определяет проект по пути нового файла;
   - получает в рабочую копию только каталог этого проекта;
   - находит сессию с наибольшим числовым номером;
   - проверяет наличие «Реестр Сессии.md»;
   - добавляет фрагменты из очереди в конец реестра в порядке временных отметок, используя режим бинарного добавления. Скрипт не открывает реестр на чтение и не пересоздаёт его, а прежние байты остаются неизменными;
   - GitHub Actions получает в рабочую копию только текущий проект. Git локально обрабатывает файл при подготовке коммита, но его содержимое не передаётся ассистенту;
   - удаляет файлы очереди только в том же коммите, которым успешно зафиксировано добавление.

7. Проверь запуск workflow по SHA коммита, создавшего файл-запрос. Не сообщай об успешной синхронизации, пока выполнение workflow не завершено успешно. Если workflow ещё ожидает запуска или выполняется, сообщи, что запись поставлена в очередь, но пока не подтверждена.

8. При ошибке workflow не пересоздавай уже поставленные в очередь сообщения. Оставь файлы-запросы без изменений и сообщи об ошибке. Если папка последней сессии или реестр отсутствуют, не создавай их самостоятельно.

9. Не изменяй другие файлы проекта и не обращайся к другим проектам.

Примечание: после обработки файлы очереди удаляются из текущего дерева проекта, но их содержимое остаётся в истории Git. Не используй механизм для данных, которые нельзя хранить в истории репозитория.
