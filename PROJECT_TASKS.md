# SFRA — текущие задачи, статусы и двухэтапная приёмка

> **Единый рабочий реестр проекта.** Исполнители и аналитики могут обновлять свои отметки самостоятельно. Аналитик фиксирует фактическую готовность по критериям; координатор делает пакетную проверку нескольких результатов и отдельно подтверждает принятие. Вызов координатора не требуется для каждого изменения или каждого отчёта.
>
> Последняя сверка GitHub: **2026-11-17**. Основная ветка: `main`.

## 1. Как пользоваться отметками

### Роли и полномочия

**Исполнитель**
- Реализует задачу, обновляет PR и указывает точный HEAD commit.
- Не отмечает критерии аналитика или координатора.
- В отчёте указывает тесты, CI, артефакты и ограничения.

**Аналитик**
- Самостоятельно проверяет код, тесты, CI и артефакты по каждому критерию.
- Ставит галочки только в разделе **«Проверка аналитика»**.
- После проверки всех критериев отмечает итоговую готовность аналитика и фиксирует проверенный HEAD.
- Может перевести задачу в `ANALYST_READY_FOR_COORDINATOR`. Для этого не требуется предварительное разрешение или участие координатора.
- Не ставит отметки координатора и не объявляет задачу окончательно принятой.

**Координатор**
- Не участвует в каждом цикле исполнения.
- При пакетном рассмотрении проверяет несколько задач, уже подготовленных аналитиками.
- Ставит галочки только в разделе **«Пакетное подтверждение координатора»** и фиксирует итоговое решение.
- Может принять результат, вернуть его аналитику на дополнительную проверку или изменить границы задачи.
- Не обязан повторять всю работу аналитика построчно, но отвечает за итоговое решение и согласованность результатов между исполнителями.

### Важное правило привязки к commit

Все отметки аналитика и координатора действительны **только для указанного проверенного HEAD commit**.

Если PR получил новые коммиты после проверки:
1. Аналитик указывает новый HEAD.
2. Предыдущие галочки аналитика считаются недействительными до повторной проверки затронутых критериев.
3. Подтверждение координатора также считается недействительным для нового HEAD.
4. В реестре нужно очистить устаревшие отметки и повторить проверку.

Не переносить отметки на новый commit автоматически.

### Значение статусов

| Статус | Кто устанавливает | Значение |
|---|---|---|
| **WAITING_FOR_IMPLEMENTATION** | Координатор / реестр | Исполнитель ещё должен реализовать требования. |
| **WAITING_FOR_ANALYST** | Исполнитель или координатор после появления реализации | Есть PR/результат, требуется проверка аналитика. |
| **ANALYST_READY_FOR_COORDINATOR** | Аналитик | Все критерии аналитика проверены; задача готова к пакетному рассмотрению координатором. Это ещё не окончательная приёмка. |
| **COORDINATOR_ACCEPTED** | Координатор | Координатор подтвердил результат по зафиксированному HEAD. |
| **COORDINATOR_ACCEPTED_NOT_MERGED** | Координатор | Техническая работа принята, но PR ещё не объединён. |
| **BLOCKED** | Координатор / реестр | Работа заблокирована зависимостью или внешним условием. |
| **DONE** | Координатор | Все критерии закрыты и необходимые действия по интеграции/закрытию выполнены. |

**Правило:** галочки аналитика означают «проверено и готово к рассмотрению», а не «окончательно принято». Только отдельная отметка координатора подтверждает координаторскую приёмку.

### SFRA-E1-01 — единый атомарный Source Scope API

**Исполнитель:** E1  
**Статус:** WAITING_FOR_IMPLEMENTATION  
**Текущий PR:** [#11 — E1: source-verified structural node lookup API](https://github.com/yeatu/obsidianGP/pull/11)  
**Текущая ветка:** `executor-1/e1-source-read-api-mainline`  
**HEAD на момент последней сверки:** `74cc68e81b8aeb6f10fe236b95345311943269b5`

**Уже реализовано:** отдельные методы точного чтения узла, родителя, соседей и документа; проверки исходного файла, хешей, координат и безопасности чтения. CI PR #11 проходил, включая повторное сканирование выбранного реального Vault.

**Почему ещё не принято:** чтение родителя и соседей использует несколько независимых SQLite-соединений. Отдельные методы не обеспечивают единый атомарный контракт. Не хватает единого scope-вызова и операции разрешения актуального узла для DependencyResolver.

**Требуется от E1:**

1. Добавить публичный метод `read_source_scope(db_path, vault_root, node_id, expected_hash, *, scope, snapshot_id)`.
2. Поддержать scope: `node`, `parent`, `neighbors`, `document`.
3. Выполнять все SQLite-чтения одного scope-вызова через **одно соединение и одну read-транзакцию**.
4. Для каждого фрагмента возвращать и проверять `node_id`, `content_hash`, `source_path`, `document_hash` (из `documents.source_sha256`), `index_generation` (из `documents.generation`) и точный `raw_text`.
5. Проверять, что целевой узел, родитель и соседи принадлежат согласованному документу и поколению. Не возвращать неактивные, stale, ambiguous или deleted записи как текущие.
6. При любой ошибке проверки возвращать отказ и **не возвращать частичный набор фрагментов**.
7. Для scope `document` читать полный оригинальный Markdown из закреплённого Vault checkout, не реконструировать его из `node_versions` и не обрезать.
8. Добавить `resolve_current_node(db_path, node_id, *, snapshot_id)`, возвращающий только актуальный адрес узла и его текущий Content Hash. Не использовать fuzzy matching и исторические fallback.
9. Принимать `snapshot_id` от E3 и возвращать его без изменений. E1 не выполняет Git fetch/checkout и не разрешает ветки самостоятельно.
10. Не переносить токенный бюджет в E1: возвращать полный текст. Не придумывать значения `preservation`, `required_with`, `parent_context_required`; передавать только реально существующие метаданные.

## 5. Порядок обновления реестра

### После выполнения работы исполнителем

Исполнитель обновляет PR и передаёт аналитику номер PR, ветку, точный HEAD commit SHA, перечень изменений, CI run links, результаты тестов, негативные сценарии, интеграционные артефакты и подтверждение неизменности данных.

### После проверки аналитиком

Аналитик:
1. Проверяет фактический код и доказательства на указанном HEAD.
2. Отмечает выполненные пункты только в своём разделе.
3. Оставляет непроверенные пункты пустыми и кратко объясняет блокеры.
4. Заполняет HEAD, дату и ссылку на отчёт.
5. Ставит итоговую галочку готовности аналитика и меняет статус на `ANALYST_READY_FOR_COORDINATOR`.

После этого задача ждёт пакетной проверки координатора. Аналитик не должен ждать координатора, чтобы зафиксировать свою проверку или перейти к следующей задаче.

### При пакетной проверке координатором

Координатор рассматривает накопившиеся задачи со статусом `ANALYST_READY_FOR_COORDINATOR`, проверяет их результаты в совокупности и для каждой:
- отмечает только свой раздел;
- фиксирует HEAD и дату;
- принимает задачу либо возвращает её аналитику/исполнителю с конкретными замечаниями;
- меняет статус на `COORDINATOR_ACCEPTED`, `COORDINATOR_ACCEPTED_NOT_MERGED` или возвращает на предыдущий этап.

### Когда задача возвращается на доработку

Если аналитик обнаружил несоответствие, он не ставит итоговую галочку и оставляет задачу на `WAITING_FOR_IMPLEMENTATION` либо `WAITING_FOR_ANALYST` с конкретным перечнем замечаний.

Если координатор возвращает уже проверенную задачу, он снимает/аннулирует свою итоговую отметку, указывает причину и задаёт ожидаемое действие. Аналитические отметки сохраняются только если HEAD не изменился и замечание не затрагивает уже проверенные критерии.

### Общие требования к доказательствам

- PR и тесты должны относиться к указанному HEAD.
- CI должен охватывать именно те сценарии, которыми подтверждается критерий.
- Fixture, временная SQLite и реальный production snapshot не должны смешиваться как эквивалентные доказательства.
- Непроверенные части и ограничения должны быть явно названы.
- Архитектурные границы SFRA должны сохраняться.

**Главный принцип проекта:** поисковый индекс ускоряет обнаружение, но не становится второй базой знаний. В Context Pack попадает только проверенный текст первоисточника, связанный с актуальным индексным snapshot.
