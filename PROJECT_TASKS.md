# SFRA — рабочий реестр задач и готовности

> **Реестр ведут аналитики. Координатор не обслуживает каждое обновление.** Аналитики самостоятельно обновляют статусы, результаты проверок, HEAD, ссылки на доказательства и отметки готовности. Они продолжают работу по утверждённому спектру задач без ожидания координатора.
>
> **Координатора вызывают только в двух случаях:** (1) аналитик завершил весь свой текущий спектр задач и сообщает, что готов передать его на пакетную проверку; (2) аналитик упёрся в ограничение, неоднозначность или решение за пределами утверждённого контракта и требует указания.
>
> Последняя сверка GitHub: **2026-11-17**. Основная ветка: ```main```.

## 1. Правила ведения реестра

### Что аналитики могут и должны делать самостоятельно

Аналитики являются владельцами текущего состояния реестра. Им не нужно ждать координатора, чтобы:
- отмечать проверенные критерии в своём чек-листе;
- фиксировать результат проверки PR, CI, тестов и артефактов;
- обновлять проверенный HEAD, дату и ссылки на доказательства;
- переводить задачу в статус `ANALYST_COMPLETE_UNREVIEWED` после выполнения всех критериев в рамках уже утверждённого задания;
- отмечать зависимость как снятую, если её критерии выполнены и доказательства приложены;
- продолжать следующую задачу своего утверждённого спектра;
- добавлять технические подзадачи, необходимые для выполнения уже согласованного контракта.

**Аналитик не должен вызывать координатора и ждать его отметки после каждого отчёта исполнителя или после каждой отдельной задачи.**

### Когда аналитик обращается к координатору

Аналитик самостоятельно ставит статус `ANALYST_SCOPE_COMPLETE`, когда весь порученный ему текущий спектр задач завершён, и передаёт сводный отчёт координатору.

Аналитик ставит статус `ANALYST_BLOCKED_NEEDS_COORDINATOR`, если:
- требования противоречат друг другу или допускают несколько архитектурно значимых трактовок;
- требуется изменить ранее утверждённый контракт или границы ответственности исполнителей;
- обнаружена проблема, которую нельзя устранить в рамках текущего задания;
- необходим новый приоритет, решение о компромиссе или новая задача за пределами уже согласованного спектра.

В этих случаях аналитик фиксирует конкретный вопрос, варианты и последствия, а не просто сообщает «заблокировано».

### Что аналитики не меняют без координатора

- Архитектурные инварианты SFRA и границы ответственности E1/E2/E3.
- Критерии, меняющие смысл уже утверждённого контракта.
- Приоритеты и зависимости между независимыми потоками работ.
- Решение об объединении PR в основную ветку, если оно отдельно не делегировано.

Если нужно изменить что-либо из этого, аналитик ставит блокировку и формулирует запрос на решение.

## 2. Статусы

| Статус | Кто устанавливает | Значение |
|---|---|---|
| `WAITING_FOR_IMPLEMENTATION` | Аналитик ведёт по плану | Исполнитель ещё должен реализовать требования. |
| `IMPLEMENTATION_IN_PROGRESS` | Аналитик ведёт по плану | Исполнитель работает над задачей. |
| `WAITING_FOR_ANALYST` | Аналитик ведёт по плану | Реализация/отчёт поступили, аналитик ещё не завершил проверку. |
| `ANALYST_REVIEW_IN_PROGRESS` | Аналитик | Аналитик проверяет код, тесты и доказательства. |
| `ANALYST_COMPLETE_UNREVIEWED` | Аналитик | Критерии конкретной задачи проверены; задача готова в рамках утверждённого контракта. Координатор ещё не проводил свой аудит. Это **не блокирует** продолжение зависимых работ, если ниже явно не указано иное. |
| `ANALYST_SCOPE_COMPLETE` | Аналитик | Завершён весь текущий спектр задач этого аналитика; требуется пакетный обзор координатора. |
| `ANALYST_BLOCKED_NEEDS_COORDINATOR` | Аналитик | Нужны решение, уточнение или изменение за пределами утверждённого контракта. |
| `COORDINATOR_REVIEWED_ACCEPTED` | Только координатор | Координатор провёл аудит и подтвердил результат. |
| `COORDINATOR_REVIEWED_RETURNED` | Только координатор | Координатор вернул результат с конкретными замечаниями. |
| `COORDINATOR_ACCEPTED_NOT_MERGED` | Только координатор | Техническая работа принята, но PR ещё не объединён. |
| `DONE` | Аналитик фиксирует выполнение; координатор подтверждает при пакетном аудите | Все критерии задачи закрыты и необходимые действия по интеграции/закрытию выполнены. |

**Важно:** `ANALYST_COMPLETE_UNREVIEWED` — полноценный сигнал аналитика, что конкретная задача исполнена в рамках утверждённых требований. Отсутствие координаторской галочки не заставляет исполнителя или аналитика ждать. Координаторская проверка — отдельный последующий контроль, а не ежедневный шлюз.

## 3. Привязка отметок к commit

Все проверки кода привязываются к точному HEAD commit.

Если PR получил новые коммиты после проверки:
1. Аналитик обновляет HEAD.
2. Аналитик повторно проверяет все затронутые критерии.
3. Галочки по затронутым критериям снимаются до повторной проверки. Незатронутые критерии можно сохранить с явным обоснованием.
4. Старое координаторское подтверждение не распространяется на новый HEAD автоматически.

Не переносить отметки на новый код без проверки.

## 5. Задачи E1

### SFRA-E1-01 — единый атомарный Source Scope API

**Исполнитель:** E1  
**Статус:** WAITING_FOR_IMPLEMENTATION  
**Текущий PR:** [#11 — E1: source-verified structural node lookup API](https://github.com/yeatu/obsidianGP/pull/11)  
**Текущая ветка:** `executor-1/e1-source-read-api-mainline`  
**HEAD на момент последней сверки:** `74cc68e81b8aeb6f10fe236b95345311943269b5`

**Уже реализовано:** отдельные методы точного чтения узла, родителя, соседей и документа; проверки исходного файла, хешей, координат и безопасности чтения. CI PR #11 проходил, включая повторное сканирование выбранного реального Vault.

**Почему ещё не принято:** чтение родителя и соседей использует несколько независимых SQLite-соединений. Отдельные методы не обеспечивают единый атомарный контракт. Не хватает единого scope-вызова и операции разрешения актуального узла для DependencyResolver.

**Требуется от E1:**

1. Добавить публичный метод:
   ```python
   read_source_scope(
       db_path, vault_root, node_id, expected_hash,
       *, scope, snapshot_id
   ) -> SourceScopeResult
   ```
2. Поддержать scope: `node`, `parent`, `neighbors`, `document`.
3. Выполнять все SQLite-чтения одного scope-вызова через **одно соединение и одну read-транзакцию**.
4. Для каждого фрагмента возвращать и проверять `node_id`, `content_hash`, `source_path`, `document_hash` (из `documents.source_sha256`), `index_generation` (из `documents.generation`) и точный `raw_text`.
5. Проверять, что целевой узел, родитель и соседи принадлежат согласованному документу и поколению. Не возвращать неактивные, stale, ambiguous или deleted записи как текущие.
6. При любой ошибке проверки возвращать отказ и **не возвращать частичный набор фрагментов**.
7. Для scope `document` читать полный оригинальный Markdown из закреплённого Vault checkout, не реконструировать его из `node_versions` и не обрезать.
8. Добавить:
   ```python
   resolve_current_node(db_path, node_id, *, snapshot_id)
       -> CurrentNodeAddress
   ```
   Метод возвращает только актуальный адрес узла и его текущий Content Hash. Не использовать fuzzy matching и исторические fallback.
9. Принимать `snapshot_id` от E3 и возвращать его без изменений. E1 не выполняет Git fetch/checkout и не разрешает ветки самостоятельно.
10. Не переносить токенный бюджет в E1: возвращать полный текст. Не придумывать значения `preservation`, `required_with`, `parent_context_required`; передавать только реально существующие метаданные.

### SFRA-E3-02 — реальная интеграция E2 → E3 → E1 → Context Pack

**Исполнитель:** E3  
**Статус:** BLOCKED_BY_SFRA-E1-01  
**Зависимость:** E1 должен реализовать публичный атомарный API и `resolve_current_node()`. После того как аналитик E1 отметит SFRA-E1-01 как `ANALYST_COMPLETE_UNREVIEWED`, зависимость считается технически снятой для начала интеграции. Координаторский аудит E1 не является обязательным ожиданием, если аналитик не обнаружил архитектурного отклонения.

**Что требуется:**

1. Подключить настоящий E1 API через публичный SourceReader port, не используя fixture вместо реального reader.
2. Проверить Snapshot binder: Vault commit совпадает с `manifest.source_commit`; sidecar commit соответствует используемому checkout `sfra-state`; SHA-256 manifest вычислен по точным байтам; manifest и SQLite относятся к одному snapshot.
3. Передавать один и тот же `snapshot_id` в resolver и все scope-вызовы, проверять echo.
4. Разрешать актуальный узел через `resolve_current_node()`, затем читать его по точному адресу и Content Hash.
5. Провести полный путь: **E2 SearchAdapter → retrieval → DependencyResolver → E1 Source Scope API → Context Builder → Context Pack**.
6. Проверить четыре scope на реальных данных: node, parent, neighbors, document.
7. Проверить source path, Content Hash, document hash, generation и полный точный исходный текст.
8. Проверить негативные случаи: wrong/stale hash, ambiguous/deleted узел, повреждённый источник, mismatch поколения/документа/snapshot.
9. Проверить, что budget exceeded обрабатывается E3 без обрезания исходного текста.
10. Сравнить контрольные суммы Vault и production SQLite до/после; использовать изолированную копию данных и не менять production.

#### Чек-лист аналитика E3 / реальная интеграция

- [ ] Сквозной тест использует реальный E2 runtime и реальный E1 Source Scope API, а не fixture E1.
- [ ] Все четыре scope проверены на индексном состоянии, соответствующем закреплённому Vault commit.
- [ ] Resolver возвращает актуальный адрес; subsequent source read подтверждает точный Content Hash.
- [ ] Snapshot ID совпадает на всех этапах, mismatch вызывает отказ.
- [ ] Поля source identity согласованы во всех возвращённых фрагментах и Context Pack.
- [ ] Отрицательные сценарии завершаются отказом без неподтверждённого или частичного контекста.
- [ ] Проверены полный документ и бюджет без truncation.
- [ ] CI и интеграционный прогон успешны; приложены логи/артефакты и commit SHA.

## 10. Процесс работы без постоянного участия координатора

1. Исполнитель присылает отчёт своему аналитику и обновляет PR.
2. Аналитик проверяет результат, отмечает свой чек-лист, записывает HEAD и выводы. Если нужно, возвращает исполнителю конкретные замечания.
3. Аналитик продолжает следующие задачи утверждённого спектра. Он не вызывает координатора после каждого ответа и не ждёт его галочки.
4. Когда весь спектр задач завершён, аналитик ставит `SCOPE COMPLETE` и передаёт один сводный отчёт. Если требуется решение за пределами контракта, ставит `BLOCKED` и формулирует вопрос.
5. Только после такого сигнала пользователь вызывает координатора. Координатор проверяет накопившийся объём работ и заполняет **свои отдельные чек-листы**.
6. Если координатор не согласен с результатом, он возвращает точечные замечания. Если согласен, фиксирует аудит и решение. Его отметки не подменяют и не стирают работу аналитика.

### Доказательства для каждой задачи

Аналитик указывает:
- PR, ветку и точный HEAD commit;
- CI run links и фактические результаты тестов;
- проверенные публичные интерфейсы и значимые изменения;
- негативные сценарии;
- интеграционные артефакты, если они нужны;
- подтверждение, какие данные использовались и что не было изменено.

**Главный принцип SFRA:** поисковый индекс ускоряет обнаружение, но не становится второй базой знаний. В Context Pack попадает только проверенный текст первоисточника, связанный с актуальным индексным snapshot.
