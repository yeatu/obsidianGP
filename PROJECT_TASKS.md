## 0. Как новой нейросети начать работу

Не требуется, чтобы пользователь или координатор вручную назначал тебе задачу. Прочитай эту панель, определи свою роль, выбери свободную задачу своей категории, самостоятельно зафиксируй CLAIM и приступай к работе.

### Ролевые категории

| Роль | Назначение и полномочия | Типы задач |
|---|---|---|
| **E — исполнитель** | Реализует код, тесты, исправления, техническую документацию и интеграционные действия в пределах утверждённого объёма | `IMPLEMENTATION`, `INTEGRATION` |
| **A — аналитик** | Исследует, диагностирует, формирует требования, проводит аудит и независимо проверяет результаты | `ANALYSIS`, `REVIEW_REQUEST` |
| **C — координатор** | Отдельная управляющая роль: приоритеты, область работ, архитектура, зависимости, переназначение, блокировки, отмена и закрытие задач, кризисы, интеграция и управление панелью | `COORDINATOR_DECISION`; управление задачами всех категорий |

Буква в Agent ID определяет роль. `E1`, `E2`, `E3` и другие `E<n>` — участники одной роли E. `A1`, `A2`, `A3` и другие `A<n>` — участники одной роли A. Цифра нужна только для уникальности участника: она не даёт старшинства, приоритета, исключительного права или запрета на захват задачи другим участником той же роли.

Идентификатор `C<n>` используется только координатором, назначенным владельцем проекта. Самостоятельно выбрать роль C или присвоить себе управляющие полномочия нельзя.

### Если у тебя ещё нет Agent ID

Сохрани Agent ID и роль, если они уже заданы средой или предыдущей договорённостью проекта. Если идентификатора нет, выбери роль E или A по типу подходящей задачи и зарегистрируй следующий номер выше максимального ранее использованного номера этой категории. Проверь историю CLAIM во всех известных Issues, включая завершённые: использованные номера не переиспользуются. Нумерация E и A независимая.

Роль C не выбирается самостоятельно. Идентификатор координатора выдаёт владелец проекта. Если два участника одновременно выбрали один номер E или A, первый по GitHub comment ID сохраняет его; второй публикует `AGENT_ID_REASSIGN` в своей Issue, выбирает следующий номер и использует его дальше.

### Порядок самостоятельного CLAIM

1. Найди в таблице активных задач ниже задачу, тип которой соответствует твоей роли.
2. Выбирай задачу без действующего владельца, без статуса BLOCKED и с выполненными зависимостями. Учитывай также требования к компетенциям, доступу и независимости.
3. Открой GitHub Issue. Проверь её состояние, описание, критерии приёмки, объём работ, последние комментарии и события CLAIM/RELEASE/BLOCKED/REVIEW. Проверь, не ведётся ли пересекающаяся работа в соседних Issues или PR.
4. Опубликуй в комментариях Issue:

   ```
   CLAIM
   Task: #<номер задачи>
   Agent: <E<n>|A<n>|C<n>>
   Role: <E|A|C>
   Scope: <что именно беру>
   Started: <время UTC>
   ```

5. Сразу повторно прочитай комментарии Issue. При одновременном захвате задачи действует корректный CLAIM с наименьшим GitHub comment ID. Если твой CLAIM проиграл, прекрати пересекающуюся работу и опубликуй `CLAIM_CONFLICT_YIELD`.
6. После успешной повторной проверки немедленно начинай работу. Для обычных задач E/A не требуется отдельное подтверждение координатора.
7. В ходе работы публикуй `PROGRESS`, фиксируй доказательства в Issue/PR/commit/Actions. После завершения E обязательно создай `REVIEW_REQUEST`, удали исходную реализационную задачу из активной таблицы и добавь строку новой задачи проверки для A. Если A отклонит результат, A сам создаёт correction `IMPLEMENTATION` Issue для E, удаляет строку завершённой проверки и добавляет строку исправления. После каждого перехода соответствующий участник сам обновляет панель через PR.

**Границы ролей:** E не захватывает задачи A, A не захватывает задачи E. Задачи C доступны только назначенному координатору. Исключение возможно лишь при явном делегировании координатора с записанными границами полномочий.

- MCP MVP ограничен локальным stdio и двумя инструментами только для чтения. Не добавлять произвольный доступ к файловой системе или инструменты записи.
- Обычный CI E1 должен работать только на тестовых данных. Не индексировать реальный Vault ради проверки задач.
- Не добавлять embeddings/vector search или менять алгоритм ранжирования до появления результатов эталонного тестирования.
- Бюджет контекста остаётся под контролем E3. Нельзя обрезать исходный текст и выдавать неполный результат за полный.

## 6. Обязательный цикл реализации, проверки и обновления панели

Реестр поддерживают сами нейросети, которые выполняют переходы между этапами. Пользователь не обязан редактировать `PROJECT_TASKS.md`, удалять строки, создавать записи или вручную передавать задачи между ролями.

### Шаг 1. Исполнитель E завершает реализацию

Когда E завершил `IMPLEMENTATION` или correction task:
1. публикует в исходной Issue результат, PR, полный commit SHA, команды и результаты тестов, известные ограничения;
2. создаёт связанную `REVIEW_REQUEST` Issue для роли A по шаблону из Governance Protocol §12;
3. публикует в исходной Issue `REVIEW_REQUESTED` со ссылкой на новую Issue и проверяемым HEAD;
4. оставляет исходную реализационную Issue открытой в состоянии `REVIEW`, но удаляет её строку из таблицы задач для захвата;
5. добавляет в таблицу новую строку `REVIEW_REQUEST` для роли A. В строке указываются исходная Issue, задача проверки и точный HEAD;
6. включает изменение панели в PR результата либо создаёт отдельный небольшой PR. E сам делает это обновление, не ожидая C или пользователя.

### Шаг 2. Аналитик A проверяет результат

A захватывает `REVIEW_REQUEST` и проверяет именно указанный HEAD: scope, критерии, diff, тесты/CI, регрессии и evidence. Проверять собственный вклад нельзя.

**Если результат принят:**
1. A публикует `REVIEW_ACCEPTED` с проверенным HEAD и доказательствами;
2. закрывает `REVIEW_REQUEST` и исходную реализационную Issue. Если это повторная проверка correction task, A закрывает также correction Issues, входящие в принятую цепочку;
3. удаляет строку `REVIEW_REQUEST` из активной таблицы;
4. если новых задач не требуется, цепочка завершена. Пользователь ничего вручную не убирает.

**Если обнаружены дефекты в пределах утверждённого scope:**
1. A публикует `REVIEW_CHANGES_REQUESTED` с точными дефектами, доказательствами, затронутыми критериями и проверенным HEAD;
2. создаёт одну или несколько correction Issues типа `IMPLEMENTATION` для роли E. Каждая задача содержит ссылку на исходную реализацию и текущий запрос проверки, конкретный дефект, требуемое исправление и критерии приёмки;
3. закрывает текущую `REVIEW_REQUEST` как выполненную проверку с отрицательным результатом. Исходная реализационная Issue остаётся открытой и ожидает исправления;
4. удаляет строку завершённой `REVIEW_REQUEST` из активной таблицы и добавляет строки созданных correction Issues для E;
5. E захватывает correction Issue и исправляет недостатки. После завершения E создаёт новый `REVIEW_REQUEST` на новый точный HEAD и повторяет Шаг 1. Цикл продолжается до принятия результата аналитиком.

Если дефект требует изменения исходного scope, архитектуры или публичного контракта, A не создаёт самовольную задачу на расширение. A создаёт `COORDINATOR_DECISION` для C и сохраняет строку решения в панели.

### Правила обновления реестра

- Участник, выполняющий переход, сам отвечает за соответствующее изменение панели: E обновляет её при передаче реализации на проверку; A — при принятии результата или создании задач на исправление.
- Реализационная задача, переданная на проверку, исчезает из списка доступных задач E. Вместо неё появляется `REVIEW_REQUEST` для A.
- Завершённая проверка исчезает из списка. Если результат отклонён, вместо неё появляются correction Issues для E.
- Исправление, переданное на повторную проверку, исчезает из списка E; вместо него появляется новый `REVIEW_REQUEST` для A.
- Удаляется только строка из `PROJECT_TASKS.md`. GitHub Issues, комментарии, PR, commits и доказательства остаются в истории.
- Изменения панели проходят через PR. Не редактировать `main` напрямую. Допускается PR с реализацией/исправлением либо отдельный небольшой PR по панели.
- E и A меняют только строки, относящиеся к переходу, который они выполнили. C может изменять весь реестр, приоритеты, роли, зависимости и чужие строки в рамках координаторских полномочий.
- Участник не ждёт ручного действия пользователя или C. Если технически не может изменить репозиторий, он фиксирует готовый патч в своей Issue/PR и сообщает о конкретном препятствии. Это исключение, а не штатный порядок.

## 7. Правила ведения панели

1. Панель — краткий снимок активной работы и точка входа для новых участников, а не хроника.
2. Для каждой задачи указываются Issue, приоритет, тип, целевая роль, следующий результат и зависимости.
3. Фактический владелец, состояние CLAIM, BLOCKED, REVIEW и DONE определяются по последним действующим событиям в GitHub Issue.
4. Подробные выводы, отчёты, результаты проверок, запуски CI, артефакты и доказательства для конкретного HEAD остаются в соответствующей Issue, PR, commit или Actions run.
5. Когда реализация переходит на проверку, её строка заменяется строкой `REVIEW_REQUEST`; когда проверка выявляет дефекты, строка запроса проверки заменяется correction задачами. После принятия результата соответствующая цепочка удаляется из активной таблицы. Все Issues и история Git сохраняются.
6. Если панель расходится с GitHub, приоритет имеет текущее состояние Issue/PR/commit/Actions. Панель исправляется, но не переопределяет источник истины.

---
