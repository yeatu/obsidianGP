## 1. Правила статусов

| Статус | Значение |
|---|---|
| **WAITING_FOR_IMPLEMENTATION** | Задача сформулирована и назначена исполнителю; ожидается реализация и обновление PR. |
| **BLOCKED** | Исполнение зависит от завершения другой задачи. До снятия зависимости нельзя заявлять о готовности. |
| **READY_FOR_ANALYSIS** | Реализация находится в PR и имеет заявленные результаты проверок; ожидается независимая проверка аналитиком. |
| **ACCEPTED_NOT_MERGED** | Техническая работа принята в согласованных границах, но PR ещё не объединён. Это не означает, что код уже находится в `main`. |
| **DONE** | Критерии приёмки проверены, результат принят, а все необходимые действия по закрытию задачи выполнены. |

**Обязательное правило:** статус задачи не повышается до READY/ACCEPTED/DONE на основании одного отчёта исполнителя. Аналитик проверяет указанный commit, содержимое кода, CI и артефакты, относящиеся к критериям задачи.

## 3. Активные задачи и ожидаемая реализация

### SFRA-E1-01 — единый атомарный Source Scope API

**Исполнитель:** E1  
**Статус:** WAITING_FOR_IMPLEMENTATION  
**Текущий PR:** [#11 — E1: source-verified structural node lookup API](https://github.com/yeatu/obsidianGP/pull/11)  
**Текущая ветка:** `executor-1/e1-source-read-api-mainline`  
**Проверенный на момент сверки HEAD:** `74cc68e81b8aeb6f10fe236b95345311943269b5`

**Что уже есть:** отдельные методы точного чтения узла, родителя, соседей и документа. Проверки исходного файла, хешей, координат и безопасности чтения реализованы. CI PR #11 проходил, включая повторное сканирование выбранного реального Vault.

**Почему задача ещё не принята:** методы родителя и соседей открывают несколько независимых SQLite-соединений. Набор отдельных методов не обеспечивает единый атомарный контракт. Также отсутствуют согласованный единый scope-вызов и операция разрешения текущего узла для DependencyResolver.

**Требуется от E1:**

1. Добавить публичный метод `read_source_scope(db_path, vault_root, node_id, expected_hash, *, scope, snapshot_id)`.
2. Поддержать scope: `node`, `parent`, `neighbors`, `document`.
3. Выполнять все SQLite-чтения одного scope-вызова через **одно соединение и одну read-транзакцию**.
4. Для каждого фрагмента возвращать и проверять `node_id`, `content_hash`, `source_path`, `document_hash` (из `documents.source_sha256`), `index_generation` (из `documents.generation`) и точный `raw_text`.
5. Проверять, что целевой узел, родитель и соседи принадлежат согласованному документу и поколению. Не возвращать неактивные, stale, ambiguous или deleted записи как текущие.
6. При любой ошибке проверки возвращать отказ и **не возвращать частичный набор фрагментов**.
7. Для scope `document` читать полный оригинальный Markdown из закреплённого Vault checkout, не реконструировать его из `node_versions` и не обрезать.
8. Добавить `resolve_current_node(db_path, node_id, *, snapshot_id)`, возвращающий только актуальный адрес узла и его текущий Content Hash. Не использовать fuzzy matching и исторические fallback.
9. Принимать `snapshot_id` от E3 и возвращать его без изменений. E1 не выполняет Git fetch/checkout и не разрешает ветки самостоятельно.
10. Не переносить токенный бюджет в E1: возвращать полный текст. Не придумывать значения `preservation`, `required_with`, `parent_context_required`; передавать только реально существующие метаданные.

**Условия, после которых задача считается исполненной:**

- [ ] Единый публичный API реализован и экспортирован; старые публичные методы по возможности работают как совместимые обёртки.
- [ ] Тест подтверждает одно SQLite-соединение и одну read-транзакцию на каждый scope-вызов.
- [ ] Все четыре scope проверены на содержимом, соответствующем реальным записям индекса.
- [ ] `resolve_current_node()` возвращает актуальный Node ID + Content Hash и корректно отказывает при отсутствии/неоднозначности.
- [ ] Позитивные проверки подтверждают соответствие source text, Content Hash, document hash, generation, path и координат.
- [ ] Негативные тесты покрывают wrong hash, stale, ambiguous, deleted, mismatch документа/поколения/пути/координат, повреждённый источник и snapshot mismatch.
- [ ] При отказе не возвращаются частичные fragments.
- [ ] Выполнена интеграционная проверка на **изолированной копии** production `sfra-state` SQLite и Vault checkout, соответствующем `source_commit` из manifest.
- [ ] До/после проверки подтверждено отсутствие изменений исходного Vault и production SQLite/ветки `sfra-state`.
- [ ] CI успешен на конкретном проверяемом HEAD; в отчёте указаны commit SHA, команды/результаты тестов и подтверждение неизменности данных.

**Решение до выполнения критериев:** PR #11 не объединять. Существующий прогресс не откатывать и не переписывать без технической необходимости; расширить текущую реализацию.

### SFRA-E3-02 — реальная интеграция E2 → E3 → E1 → Context Pack

**Исполнитель:** E3  
**Статус:** BLOCKED  
**Блокирующая зависимость:** SFRA-E1-01 — E1 должен предоставить принятый атомарный API и `resolve_current_node()`.

**Что требуется после снятия блокировки:**

1. Подключить настоящий E1 API через публичный SourceReader port, не используя fixture вместо реального reader.
2. Проверить Snapshot binder: Vault commit совпадает с `manifest.source_commit`; sidecar commit соответствует используемому checkout `sfra-state`; SHA-256 manifest вычислен по точным байтам; manifest и SQLite относятся к одному snapshot.
3. Передавать один и тот же `snapshot_id` в resolver и все scope-вызовы, проверять echo.
4. Разрешать актуальный узел через `resolve_current_node()`, затем читать его по точному адресу и Content Hash.
5. Провести полный путь: **E2 SearchAdapter → retrieval → DependencyResolver → E1 Source Scope API → Context Builder → Context Pack**.
6. Проверить четыре scope на реальных данных: node, parent, neighbors, document.
7. Проверить source path, Content Hash, document hash, generation и полный точный исходный текст.
8. Проверить негативные случаи: wrong/stale hash, ambiguous/deleted узел, повреждённый источник, mismatch поколения/документа/snapshot.
9. Проверить, что budget exceeded обрабатывается E3 без обрезания исходного текста.
10. Сравнить контрольные суммы Vault и production SQLite до/после; использовать изолированную копию данных и не менять production.

**Условия, после которых задача считается исполненной:**

- [ ] Сквозной тест использует реальный E2 runtime и реальный E1 Source Scope API, а не fixture E1.
- [ ] Все четыре scope успешно проверены на индексном состоянии, соответствующем закреплённому Vault commit.
- [ ] Resolver возвращает актуальный адрес; subsequent source read подтверждает точный Content Hash.
- [ ] Snapshot ID совпадает на всех этапах, mismatch вызывает отказ.
- [ ] Поля source identity согласованы во всех возвращённых фрагментах и Context Pack.
- [ ] Отрицательные сценарии завершаются отказом без неподтверждённого или частичного контекста.
- [ ] Проверены полный документ и бюджет без truncation.
- [ ] CI и интеграционный прогон успешны; приложены логи/артефакты и commit SHA.
- [ ] Подтверждено, что production Vault и production `sfra-state` не изменялись.

До снятия зависимости E1 не просить E3 повторно реализовывать фиктивную интеграцию. E3 может завершать C1 и поддерживать fixture-контракт, но не должен менять статус этой задачи на выполненную.

## 5. Общие правила для исполнителей и аналитиков

### Исполнитель передаёт

- номер PR и ветку;
- точный HEAD commit SHA;
- краткий перечень изменённых интерфейсов и файлов;
- CI run links и фактические результаты тестов;
- негативные сценарии и их результаты;
- интеграционные артефакты, если они требуются критериями;
- подтверждение, какие реальные данные использовались и что не было изменено.

### Аналитик проверяет

- что PR и тесты относятся к указанному HEAD;
- что код действительно реализует критерии, а не только описывает их;
- что CI успешен и охватывает нужные сценарии;
- что фикстуры, временная SQLite и реальный production snapshot не смешиваются в доказательствах;
- что ограничения и непроверенные части явно названы;
- что результат не нарушает архитектурные границы SFRA.

### Обновление этого файла

После каждого отчёта исполнителя или аналитика координатор обновляет этот файл: статус, HEAD, зависимости, результаты проверки, новые задачи и критерии приёмки. Если критерии или архитектурный контракт меняются, изменение фиксируется здесь до того, как исполнитель начнёт реализацию.

**Главный принцип проекта:** поисковый индекс ускоряет обнаружение, но не становится второй базой знаний. В Context Pack попадает только проверенный текст первоисточника, связанный с актуальным индексным snapshot.
