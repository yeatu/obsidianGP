## 0. Как новой нейросети начать работу

Не требуется, чтобы пользователь или координатор вручную назначал тебе задачу. Прочитай эту панель, определи свою роль, выбери свободную задачу своей категории, самостоятельно зафиксируй CLAIM и приступай к работе.

### Ролевые категории

| Роль | Назначение и полномочия | Типы задач |
|---|---|---|
| **E — исполнитель** | Реализует код, тесты, исправления, техническую документацию и интеграционные действия в пределах утверждённого объёма | `IMPLEMENTATION`, `INTEGRATION` |
| **A — аналитик** | Исследует, диагностирует, формирует требования, проводит аудит и независимо проверяет результаты | `ANALYSIS`, `REVIEW_REQUEST` |
| **C — координатор** | Отдельная управляющая роль: приоритеты, область работ, архитектура, зависимости, переназначение, блокировки, отмена и закрытие задач, кризисы, интеграция и управление панелью | `COORDINATOR_DECISION`; управление задачами всех категорий |

Буква в Agent ID определяет роль. `E1`, `E2`, `E3` и другие `E<n>` — участники одной роли E. `A1`, `A2`, `A3` и другие `A<n>` — участники одной роли A. Цифра нужна только для уникальности участника: она не даёт старшинства, приоритета, исключительного права или запрета на захват задачи другим участником той же роли.

Идентификатор `C<n>` используется только координатором, назначенным владельцем проекта. Самостоятельно выбрать роль C или присвоить себе управляющие полномочия нельзя.

### Если у тебя ещё нет Agent ID

Сохрани Agent ID и роль, если они уже заданы средой или предыдущей договорённостью проекта. Если идентификатора нет, выбери роль E или A по типу подходящей задачи и зарегистрируй следующий номер выше максимального ранее использованного номера этой категории. Проверь историю CLAIM во всех известных Issues, включая завершённые: использованные номера не переиспользуются. Нумерация E и A независимая.

Роль C не выбирается самостоятельно. Идентификатор координатора выдаёт владелец проекта. Если два участника одновременно выбрали один номер E или A, первый по GitHub comment ID сохраняет его; второй публикует `AGENT_ID_REASSIGN` в своей Issue, выбирает следующий номер и использует его дальше.

### Порядок самостоятельного CLAIM

1. Найди в таблице активных задач ниже задачу, тип которой соответствует твоей роли.
2. Выбирай задачу без действующего владельца, без статуса BLOCKED и с выполненными зависимостями. Учитывай также требования к компетенциям, доступу и независимости.
3. Открой GitHub Issue. Проверь её состояние, описание, критерии приёмки, объём работ, последние комментарии и события CLAIM/RELEASE/BLOCKED/REVIEW. Проверь, не ведётся ли пересекающаяся работа в соседних Issues или PR.
4. Опубликуй в комментариях Issue:

   ```
   CLAIM
   Task: #<номер задачи>
   Agent: <E<n>|A<n>|C<n>>
   Role: <E|A|C>
   Scope: <что именно беру>
   Started: <время UTC>
   ```

5. Сразу повторно прочитай комментарии Issue. При одновременном захвате задачи действует корректный CLAIM с наименьшим GitHub comment ID. Если твой CLAIM проиграл, прекрати пересекающуюся работу и опубликуй `CLAIM_CONFLICT_YIELD`.
6. После успешной повторной проверки немедленно начинай работу. Для обычных задач E/A не требуется отдельное подтверждение координатора.
7. В ходе работы публикуй `PROGRESS`, фиксируй доказательства в Issue/PR/commit/Actions. По завершении самостоятельно создай `REVIEW_REQUEST`; независимый проверяющий должен быть участником роли A и не должен участвовать в проверяемом результате.

**Границы ролей:** E не захватывает задачи A, A не захватывает задачи E. Задачи C доступны только назначенному координатору. Исключение возможно лишь при явном делегировании координатора с записанными границами полномочий.

## 5. Действующие ограничения

- [Issue #20](https://github.com/yeatu/obsidianGP/issues/20) — нормативный протокол v2.2: роли E/A/C, полномочия, CLAIM, декомпозиция, независимая проверка, обновление панели и решения координатора.
- [Issue #34](https://github.com/yeatu/obsidianGP/issues/34) — независимая проверка протокола v2.2 и порядка самостоятельной работы. Она не блокирует независимые инженерные задачи.
- Обработчик GitHub Issues и автоматическое восстановление, запись через GitHub API, удалённый MCP по HTTP/SSE/WebSocket, промышленная индексация/постоянное хранение и публикация содержимого Vault в публичных Issues/comments не разрешены текущим этапом.
- MCP MVP ограничен локальным stdio и двумя инструментами только для чтения. Не добавлять произвольный доступ к файловой системе или инструменты записи.
- Обычный CI E1 должен работать только на тестовых данных. Не индексировать реальный Vault ради проверки задач.
- Не добавлять embeddings/vector search или менять алгоритм ранжирования до появления результатов эталонного тестирования.
- Бюджет контекста остаётся под контролем E3. Нельзя обрезать исходный текст и выдавать неполный результат за полный.

## 6. Обновление панели после выполнения задач

`PROJECT_TASKS.md` содержит только активные задачи. Он должен оставаться пригодным для следующей нейросети после каждого завершённого действия.

### Что может сделать исполнитель или аналитик

После того как результат принят требуемой проверкой, а GitHub Issue закрыта, её владелец может:

1. **Убрать завершённую задачу** из таблицы активных задач.
2. **Добавить новую задачу**, если в ходе работы обнаружена необходимая самостоятельная подзадача в пределах утверждённого scope. Сначала создай GitHub Issue по правилам Governance Protocol, затем добавь её в таблицу с типом, ролью, приоритетом, ожидаемым результатом и зависимостями.
3. **Выполнить оба действия**, если завершённая задача заменена одной или несколькими новыми подзадачами.

Удаляется только строка из активной панели. Нельзя удалять саму GitHub Issue, комментарии, PR, commits или доказательства. Если задача ожидает проверки или Issue остаётся открытой, её строка остаётся в активном списке.

Изменения `PROJECT_TASKS.md` вносятся через PR: в составе PR с результатом задачи либо отдельным небольшим PR. Не меняй `main` напрямую. Это право обновить собственные строки не даёт права менять приоритеты, scope, роли, зависимости или состояние чужих задач.

### Что может сделать координатор C

C может добавлять и удалять любые строки активных задач, менять приоритеты, роли и зависимости в соответствии с принятыми решениями, создавать и дробить Issues, переназначать и блокировать задачи, закрывать/переоткрывать их и сливать PR в пределах своих полномочий. История GitHub остаётся неизменной и доступной.

## 7. Правила ведения панели

1. Панель — краткий снимок активной работы и точка входа для новых участников, а не хроника.
2. Для каждой задачи указываются Issue, приоритет, тип, целевая роль, следующий результат и зависимости.
3. Фактический владелец, состояние CLAIM, BLOCKED, REVIEW и DONE определяются по последним действующим событиям в GitHub Issue.
4. Подробные выводы, отчёты, результаты проверок, запуски CI, артефакты и доказательства для конкретного HEAD остаются в соответствующей Issue, PR, commit или Actions run.
5. Закрытые задачи удаляются из активной таблицы, но сохраняются в GitHub и истории Git.
6. Если панель расходится с GitHub, приоритет имеет текущее состояние Issue/PR/commit/Actions. Панель исправляется, но не переопределяет источник истины.

---

**Рабочее правило:** начни с этой панели, определи свою роль, выбери подходящую свободную задачу, проверь её состояние в Issue, зафиксируй CLAIM и приступай. После приёмки результата обнови активный список: убери закрытую задачу и при необходимости добавь созданную новую. Координатор C сохраняет управляющие полномочия и контроль слияния.
