## 0. Как новой нейросети начать работу

Не требуется, чтобы пользователь или координатор вручную назначал тебе задачу. Прочитай эту панель, определи свою роль, выбери свободную задачу своей категории, самостоятельно зафиксируй CLAIM и приступай к работе.

### Ролевые категории

| Роль | Назначение и полномочия | Типы задач |
|---|---|---|
| **E — исполнитель** | Реализует код, тесты, исправления, техническую документацию и интеграционные действия в пределах утверждённого объёма | `IMPLEMENTATION`, `INTEGRATION` |
| **A — аналитик** | Исследует, диагностирует, формирует требования, проводит аудит и независимо проверяет результаты | `ANALYSIS`, `REVIEW_REQUEST` |
| **C — координатор** | Отдельная управляющая роль: приоритеты, область работ, архитектура, зависимости, переназначение, блокировки, отмена и закрытие задач, кризисы, интеграция и управление панелью | `COORDINATOR_DECISION`; управление задачами всех категорий |

Буква в Agent ID определяет роль. `E1`, `E2`, `E3` и другие `E<n>` — участники одной роли E. `A1`, `A2`, `A3` и другие `A<n>` — участники одной роли A. Цифра нужна только для уникальности участника: она не даёт старшинства, приоритета, исключительного права или запрета на захват задачи другим участником той же роли.

Идентификатор `C<n>` используется только координатором, назначенным владельцем проекта. Самостоятельно выбрать роль C или присвоить себе управляющие полномочия нельзя.

### Если у тебя ещё нет Agent ID

Сохрани Agent ID и роль, если они уже заданы средой или предыдущей договорённостью проекта. Если идентификатора нет, выбери роль E или A по типу подходящей задачи и зарегистрируй следующий номер выше максимального ранее использованного номера этой категории. Проверь историю CLAIM во всех известных Issues, включая завершённые: использованные номера не переиспользуются. Нумерация E и A независимая.

Роль C не выбирается самостоятельно. Идентификатор координатора выдаёт владелец проекта. Если два участника одновременно выбрали один номер E или A, первый по GitHub comment ID сохраняет его; второй публикует `AGENT_ID_REASSIGN` в своей Issue, выбирает следующий номер и использует его дальше.

### Порядок самостоятельного CLAIM

1. Найди в таблице активных задач ниже задачу, тип которой соответствует твоей роли.
2. Выбирай задачу без действующего владельца, без статуса BLOCKED и с выполненными зависимостями. Учитывай также требования к компетенциям, доступу и независимости.
3. Открой GitHub Issue. Проверь её состояние, описание, критерии приёмки, объём работ, последние комментарии и события CLAIM/RELEASE/BLOCKED/REVIEW. Проверь, не ведётся ли пересекающаяся работа в соседних Issues или PR.
4. Опубликуй в комментариях Issue:

   ```
   CLAIM
   Task: #<номер задачи>
   Agent: <E<n>|A<n>|C<n>>
   Role: <E|A|C>
   Scope: <что именно беру>
   Started: <время UTC>
   ```

5. Сразу повторно прочитай комментарии Issue. При одновременном захвате задачи действует корректный CLAIM с наименьшим GitHub comment ID. Если твой CLAIM проиграл, прекрати пересекающуюся работу и опубликуй `CLAIM_CONFLICT_YIELD`.
6. После успешной повторной проверки немедленно начинай работу. Для обычных задач E/A не требуется отдельное подтверждение координатора.
7. В ходе работы публикуй `PROGRESS`, фиксируй доказательства в Issue/PR/commit/Actions. После завершения E обязательно создай `REVIEW_REQUEST`, удали исходную реализационную задачу из активной таблицы и добавь строку новой задачи проверки для A. Если A отклонит результат, A сам создаёт correction `IMPLEMENTATION` Issue для E, удаляет строку завершённой проверки и добавляет строку исправления. После каждого перехода соответствующий участник сам обновляет панель через PR.

**Границы ролей:** E не захватывает задачи A, A не захватывает задачи E. Задачи C доступны только назначенному координатору. Исключение возможно лишь при явном делегировании координатора с записанными границами полномочий.

## 6. Обязательный цикл E → A → E и автоматическое поддержание актуальности реестра участниками

Пользователь не редактирует `PROJECT_TASKS.md` и не передаёт задачи между нейросетями. Актуальность реестра поддерживают сами участники E и A, каждый после выполнения своего этапа. Координатор C контролирует общую целостность, приоритеты и слияние PR, но не требуется для обычной передачи между E и A.

### Шаг 1. Исполнитель E завершает реализацию

Когда E завершил реализационную задачу или correction task:
1. публикует в исходной `IMPLEMENTATION` Issue результат, PR, полный commit SHA, команды и результаты тестов, известные ограничения;
2. создаёт связанную `REVIEW_REQUEST` Issue для роли A, где указывает исходную задачу и точный проверяемый HEAD;
3. публикует в исходной Issue событие `REVIEW_REQUESTED` со ссылкой на запрос;
4. оставляет исходную реализационную Issue открытой в состоянии `REVIEW`, но удаляет её строку из таблицы активных задач;
5. добавляет вместо неё строку новой `REVIEW_REQUEST` для A;
6. сам включает обновление панели в PR с результатом либо создаёт отдельный небольшой PR. Не ждёт пользователя или координатора.

### Шаг 2. Аналитик A проверяет результат

A захватывает `REVIEW_REQUEST` и проверяет именно указанный HEAD: scope, критерии, diff, тесты/CI, регрессии и доказательства. Проверять собственный вклад нельзя.

**Если результат принят:**
1. A публикует `REVIEW_ACCEPTED` с проверенным HEAD и доказательствами;
2. закрывает `REVIEW_REQUEST` и только те реализационные/correction Issues, результат которых полностью покрыт проверенным HEAD. При нескольких correction Issues непроверенные исправления остаются открытыми и в активном списке;
3. удаляет строку `REVIEW_REQUEST` из активной таблицы;
4. исходную корневую реализационную Issue закрывает только после принятия всех обязательных correction Issues в её цепочке. Пока остаются другие исправления, корневая Issue остаётся открытой в состоянии `REVIEW`, но не возвращается в список задач для захвата;
5. если новых задач не требуется, цепочка завершена. Пользователь не редактирует список.

**Если обнаружены дефекты в пределах утверждённого объёма:**
1. A публикует `REVIEW_CHANGES_REQUESTED` с точными дефектами, доказательствами, затронутыми критериями и проверенным HEAD;
2. создаёт одну или несколько correction Issues типа `IMPLEMENTATION` для роли E. Каждая содержит ссылку на исходную реализацию и текущую проверку, конкретный дефект, требуемое исправление и критерии приёмки;
3. закрывает текущую `REVIEW_REQUEST` как выполненную проверку с отрицательным результатом. Исходная реализационная Issue остаётся открытой и ожидает исправлений;
4. удаляет строку завершённой `REVIEW_REQUEST` из таблицы и добавляет строки созданных correction Issues для E.

### Шаг 3. Исполнитель E исправляет недостатки

E самостоятельно захватывает correction Issue, устраняет перечисленные дефекты и публикует результат с новым точным HEAD. После завершения E создаёт новый `REVIEW_REQUEST`, удаляет строку correction task из активного списка и добавляет строку нового запроса проверки для A.

Цикл повторяется до тех пор, пока A не примет результат. После успешной повторной проверки A закрывает всю связанную цепочку и удаляет строку последнего `REVIEW_REQUEST` из активного списка.

Если для исправления требуется выход за утверждённый scope, изменение архитектуры или публичного контракта, A создаёт `COORDINATOR_DECISION` для C, а не придумывает расширение самостоятельно.

### Правила обновления реестра

- **E обновляет список после завершения реализации:** удаляет строку реализации/исправления и добавляет строку проверки для A.
- **A обновляет список после проверки:** при успехе удаляет строку проверки; при неуспехе заменяет её строками correction Issues для E.
- **E обновляет список после исправления:** удаляет строку correction task и добавляет новый запрос проверки для A.
- Удаляется только строка из `PROJECT_TASKS.md`. GitHub Issues, комментарии, PR, commits и доказательства сохраняются.
- Изменения панели проходят через PR. Не редактировать `main` напрямую. Можно использовать PR результата либо отдельный небольшой PR по панели.
- E и A обновляют строки перехода, который только что выполнили. C может менять весь список, приоритеты, роли, зависимости и любые строки в рамках своих полномочий.
- Участник не ждёт ручного действия пользователя или C. Если технические права не позволяют внести изменение, он публикует готовый патч в Issue/PR и указывает конкретное препятствие. Это исключение, а не штатный процесс.

## 7. Правила ведения панели

1. Панель — краткий снимок активной работы и точка входа для новых участников, а не хроника.
2. Для каждой задачи указываются Issue, приоритет, тип, целевая роль, следующий результат и зависимости.
3. Фактический владелец, состояние CLAIM, BLOCKED, REVIEW и DONE определяются по последним действующим событиям в GitHub Issue.
4. Подробные выводы, отчёты, результаты проверок, запуски CI, артефакты и доказательства для конкретного HEAD остаются в соответствующей Issue, PR, commit или Actions run.
5. После завершения реализации её строка заменяется строкой `REVIEW_REQUEST`; после отрицательной проверки строка запроса заменяется correction задачами; после исправлений E снова заменяет строку correction task строкой нового запроса проверки. После принятия результата A удаляет последнюю строку проверки. Все GitHub Issues и история Git сохраняются.
6. Если панель расходится с GitHub, приоритет имеет текущее состояние Issue/PR/commit/Actions. Панель исправляется, но не переопределяет источник истины.

**Рабочее правило:** начни с этой панели, определи свою роль и зафиксируй CLAIM. E завершает реализацию, создаёт задачу проверки и заменяет строку реализации строкой проверки. A проверяет результат: при успехе удаляет строку проверки, при дефектах создаёт correction задачи для E и заменяет строку проверки строками исправлений. E исправляет и передаёт на повторную проверку. Участники сами поддерживают реестр; пользователь его не редактирует. C сохраняет управляющие полномочия и контроль слияния.
