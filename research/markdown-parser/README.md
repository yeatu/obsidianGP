# Markdown parser research for SFRA

Исследование выполнено для репозитория `yeatu/obsidianGP`. Рабочая область исследования находится в корне репозитория: `research/markdown-parser/`. Исходные заметки не изменяются.

## Краткий вывод

Рекомендуемый первый выбор: **`markdown-it-py` для структурного разбора + собственная таблица смещений исходного файла**.

Не сериализовать AST обратно в Markdown. Сохранять исходный текст в неизменном виде и получать каждый фрагмент как `source[char_start:char_end]`. Координаты токенов markdown-it-py задаются диапазонами строк `token.map = [line_begin, line_end)`; точные символьные смещения вычисляются по заранее построенной таблице начал строк.

Для более строгой работы на уровне байтов можно отдельно оценить tree-sitter, но **не выбирать tree-sitter-markdown как единственный источник истины**: авторы грамматики прямо предупреждают о неточностях и не рекомендуют её там, где важна корректность.

## Сравнение библиотек

| Библиотека | AST / структура | Исходные координаты | Сложные конструкции | Оценка для SFRA |
|---|---|---|---|---|
| **markdown-it-py** | Поток вложенных block/inline tokens | У block-токенов есть `map=[start_line,end_line)`; это строки, не абсолютные смещения | Хорошо: вложенные списки, заголовки, цитаты, fenced code; таблицы включаются правилом; есть GFM-подобные alert-токены | **Лучший практический баланс** |
| **tree-sitter-markdown + py-tree-sitter** | Дерево синтаксических узлов | `start_byte/end_byte`, `start_point/end_point`; байтовые границы подходят для точных срезов UTF-8 | Иерархия и диапазоны детальны; Obsidian-диалект требует отдельной проверки; грамматика имеет известные ограничения | Полезен как дополнительный источник байтовых диапазонов, но не как безусловно надёжный Markdown-валидатор |
| **Mistune 3** | AST через `create_markdown(renderer="ast")` | В стандартном AST нет универсальных исходных диапазонов, пригодных для точного извлечения | Хороший расширяемый парсер, но координаты придётся восстанавливать самостоятельно | Не подходит как основа координатного слоя |
| **Python-Markdown** | ElementTree после нескольких стадий преобразования | В стандартном публичном дереве нет надёжных span-координат узлов; препроцессоры могут менять строки | Есть расширения для таблиц и другие расширения, но AST ориентирован на HTML-рендеринг | Не рекомендуется для этой задачи |

### Подробности

#### 1. markdown-it-py

- `MarkdownIt("commonmark")` даёт предсказуемую базу CommonMark.
- Block-токены имеют `map` с начальной и конечной строками, причём конечная строка не включается.
- Поток токенов сохраняет вложенность через `nesting` и типы `*_open` / `*_close`.
- Таблицы и зачёркивание можно включить явно: `enable(["table", "strikethrough"])`.
- Обычные Markdown-ссылки разбираются inline-парсером. Obsidian wiki-links и embeds не следует считать стандартными Markdown-ссылками: для первого этапа их достаточно сохранить в исходном тексте.
- Callout Obsidian вида `> [!NOTE]` синтаксически опирается на blockquote. Его тип можно определить по исходному тексту внутри диапазона цитаты. Это надёжнее, чем пытаться восстановить маркеры из HTML.

Недостаток: `token.map` даёт строки, но не абсолютные столбцы и не байтовые offsets. Это решается собственным индексом строк и UTF-8-пересчётом. Не использовать `token.content` как оригинальный текст: inline content может быть нормализован или отделён от маркеров.

#### 2. tree-sitter-markdown

Узлы Tree-sitter предоставляют байтовые границы и точки начала/конца. Python binding принимает исходник как UTF-8 bytes, поэтому можно напрямую выполнить:

```python
raw = path.read_bytes()
tree = parser.parse(raw)
fragment = raw[node.start_byte:node.end_byte].decode("utf-8")
```

Это сильнейшее свойство для точного извлечения. Однако в README самого `tree-sitter-markdown` есть предупреждение: грамматика имеет заметные неточности и не рекомендуется там, где корректность критична. Для SFRA это существенный минус. Кроме того, block и inline грамматики разделены, а Obsidian wiki-links, embeds и callouts требуют проверки на реальных заметках.

#### 3. Mistune

Mistune умеет возвращать AST-словари и хорошо подходит для преобразования и расширения Markdown. Но в стандартной структуре AST нет сквозных исходных byte/char диапазонов. Поиск текста узла обратно в документе неоднозначен при повторяющихся заголовках, повторяющихся фразах и одинаковых пунктах списка.

#### 4. Python-Markdown

Python-Markdown строит ElementTree в ходе нескольких стадий обработки. Препроцессоры и block processors могут преобразовывать список строк до формирования дерева. Стандартный ElementTree не хранит исходные диапазоны. Чтобы получить точные spans, пришлось бы внедрять собственную трассировку в pipeline и учитывать каждую модификацию текста. Это неоправданная стоимость для SFRA.

## Координатная модель

Хранить одновременно три системы координат:

- `line_start`, `line_end_exclusive`: строки, 1-based для интерфейса;
- `char_start`, `char_end`: индексы Python-строки, Unicode code points, 0-based, конец не включается;
- `utf8_byte_start`, `utf8_byte_end`: смещения в исходных UTF-8 байтах, 0-based, конец не включается.

Принцип пересчёта:

```python
line_starts = [0]
for i, ch in enumerate(source):
    if ch == "\\n":
        line_starts.append(i + 1)

char_start = line_starts[start_line0]
char_end = line_starts[end_line0] if end_line0 < len(line_starts) else len(source)

byte_start = len(source[:char_start].encode("utf-8"))
byte_end = len(source[:char_end].encode("utf-8"))
```

Для производительности байтовые offsets следует получать через заранее рассчитанную таблицу char-to-byte, а не кодировать префикс заново для каждого узла. В прототипе оставлен более простой вариант ради прозрачности.

### Кириллица, Unicode, CRLF/LF

- Индекс Python `str` — индекс Unicode code points, а не UTF-8 байт и не визуальная колонка редактора.
- Кириллическая буква обычно занимает 1 code point и 2 UTF-8 байта.
- Emoji и некоторые символы вне BMP занимают 1 Python code point, но 4 UTF-8 байта. В JavaScript такие символы могут занимать 2 UTF-16 code units.
- Комбинируемый знак может выглядеть как один символ, но состоять из нескольких code points. Не использовать графемные колонки как координату хранения.
- При открытии файла через `Path.read_text()` universal newline может преобразовать CRLF в LF. Прототип использует `open(..., newline="")`, чтобы не менять исходные окончания строк.
- Для байтовых координат самый безопасный источник — `Path.read_bytes()`. Для markdown-it-py строковые диапазоны переводятся в offsets по оригинальному тексту, прочитанному без newline conversion.
- Нельзя смешивать байтовый offset с индексом Python-строки.

## Практический прототип

Файл: [prototype.py](prototype.py)

Он:
- читает UTF-8 Markdown без нормализации CRLF;
- запускает markdown-it-py;
- извлекает диапазоны заголовков, list items, blockquotes, fenced/indented code и таблиц;
- различает Obsidian callout по исходному маркеру `> [!...]`;
- рассчитывает line, char и UTF-8 byte offsets;
- берёт фрагменты только срезом оригинального текста;
- проверяет точное равенство извлечённого фрагмента исходному срезу.

Установка:

```bash
python -m pip install -r research/markdown-parser/requirements.txt
```

Запуск на трёх контрольных заметках из `ГП/`:

```bash
python research/markdown-parser/prototype.py \
  "ГП/фракции/Рэддл.md" \
  "ГП/персонажи/ученики/Иное/Перси Уизли.md" \
  "ГП/персонажи/ученики/Молодая кровь/Генрих Фауст.md" \
  --output /tmp/sfra-markdown-spans.json
```

Проверка `all_round_trip_exact` должна быть `true` для каждого файла. Прототип проверяет точность среза, а не полноту грамматического распознавания: эти две проверки нельзя смешивать.

**Статус контрольных заметок:** сами заметки были просмотрены через GitHub. В доступной среде не удалось клонировать рабочую копию репозитория для запуска прототипа непосредственно на трёх файлах. Поэтому результаты выполнения на этих заметках не заявляются. Команда выше подготовлена для воспроизводимого запуска в рабочей копии. Исходные заметки не менялись.

## Поддержка требуемых конструкций

| Конструкция | markdown-it-py | Примечание |
|---|---|---|
| Вложенные списки | Да | Вложенность видна в токенах; диапазон родительского list item может включать дочерний список |
| Повторяющиеся заголовки | Да | Различаются по позиции, не по тексту; идентификатор узла должен включать путь/позицию |
| Таблицы | Да, включить `table` | GFM-таблицы |
| Блоки кода | Да | Fenced и indented code |
| Цитаты | Да | Blockquote с диапазоном строк |
| Obsidian Callout | Частично / практично | Определять как blockquote с маркером `[!TYPE]` в исходном диапазоне |
| Markdown-ссылки | Да | Inline token stream; точный фрагмент брать из исходного блока |
| Obsidian wiki-links / embeds | Не как стандартный Markdown | Не переписывать; добавить отдельное распознавание позже, если индексатору понадобится семантика ссылок |
| Смешанная структура | Да, на уровне block token stream | Сложные вложения требуют тестов на конкретном корпусе |

## Технические риски и меры защиты

1. **Границы блока не равны границам смыслового элемента.** Например, родительский list item содержит вложенный список. Сохранять вложенность токенов, а не пытаться сделать все spans непересекающимися.
2. **Повторяющийся текст.** Никогда не искать узел через `source.find(token.content)`: совпадение может быть не тем вхождением.
3. **Нормализация parser content.** `token.content` и HTML-render не использовать для восстановления оригинального Markdown.
4. **CRLF.** Не открывать оригинал в режиме, который нормализует окончания строк.
5. **Unicode.** В модели данных явно подписывать единицы измерения offsets.
6. **Стабильность индекса.** Координаты привязаны к конкретной версии файла. Для устойчивого внешнего ID хранить путь, hash исходных байтов и диапазон.
7. **Obsidian-диалект.** Не пытаться включить все расширения сразу. Callout обрабатывать как blockquote; wiki-links и embeds сохранять без потерь.
8. **Парсерные ошибки.** Сохранять возможность извлечь сырой фрагмент даже если часть синтаксиса не распознана.

## Рекомендации исполнителю №1

1. Считать исходные байты файла неизменяемым источником истины.
2. Разбирать текст через markdown-it-py, получать block tokens и их `map`.
3. Построить один индекс начал строк на файл. Не вычислять смещения повторным сканированием с начала для каждого узла.
4. Хранить для каждого узла как минимум `line_start/end`, `char_start/end`, `byte_start/end`, `node_type`, `parent_id` и hash файла.
5. Сохранять точный фрагмент только как `source[char_start:char_end]` либо `raw_bytes[byte_start:byte_end]`. Не сериализовать AST.
6. Не использовать текст заголовка как уникальный ID. Два одинаковых заголовка в одном документе — два разных узла.
7. Для callout не вводить отдельный парсер: сначала определить blockquote, затем проверить исходный префикс `[!...]`.
8. Проверять инвариант: `raw_bytes[start_byte:end_byte] == fragment.encode("utf-8")`. Важно, чтобы fragment получался из тех же байтов, а не из текста после newline normalization.
9. Добавить regression tests на реальных файлах: три заданные заметки плюс отдельные случаи CRLF, emoji, повторяющихся заголовков и вложенных списков. Не менять заметки ради тестов; тестировать чтение как есть.
10. На первом этапе не вводить tree-sitter как обязательную зависимость. Его можно подключить позже как экспериментальный источник точных byte spans и сравнивать расхождения с markdown-it-py.
