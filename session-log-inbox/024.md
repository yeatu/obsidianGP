### Пользователь

1. Загружается пользовательская инструкция.
2. Подключается `Промпт0`.
3. Система определяет, относится ли запрос к уже существующему проекту.
4. Если нет, работает по общим правилам.
5. Если пользователь явно начинает новый проект, запускается процедура определения необходимости сохранения контекста.



Думаю, было бы лучше, если бы промпт 0 использовался не по умолчанию, а лишь в случае отказа пользователя от сохранения контекста.

Если же пользователь соглашается, то алгоритм в первую очередь формирует файл инструкцию  в Проекты -> сохранение контекста -> название проекта (Промпт0 + дополнительные правила (если пользователь указал) +алгоритм действий (сохранение контекста) = актуальный промпт.

А затем используя его как основу применялось остальное. А при Новой сессии этот актуальный промпт бы заново подхватывался и восстанавливал контекст

### Ассистент

Это более логичная архитектура. Ты фактически предлагаешь отказаться от единого промпта, который всегда загружается первым, и перейти к **выбору рабочего режима с последующей сборкой инструкции под конкретный проект**.

Тогда `Промпт0` становится не универсальной инструкцией для всех случаев, а исходным шаблоном, из которого формируется постоянная инструкция проекта.

Здесь есть важное различие: `Промпт0` не должен просто копироваться в `Актуальный промпт`. Он должен объединяться с алгоритмом сохранения контекста и выбранными дополнительными правилами.

## 1. Обновлённая логика запуска

Пользовательские инструкции запускают определение режима работы и выбор нужного алгоритма.

Пользователь начинает новый проект → вопрос о сохранении контекста.

- **Нет:** обычный режим → `Промпт0` → работа по общей методологии без постоянной структуры проекта.
- **Да:** режим проекта → алгоритм сохранения контекста → название проекта и выбор дополнительных правил → сборка актуального промпта проекта.

После этого актуальный промпт становится основной инструкцией для дальнейшей работы и восстановления контекста.

## 2. Технические моменты

Пользовательские инструкции действительно применяются в новых чатах. Но если в них написано «прочитай `Промпт0`», это ещё не означает, что ChatGPT самостоятельно получит доступ к папке `Проекты`. Нужен механизм чтения файлов, например подключённый GitHub и явное обращение к нему по заданному алгоритму.

Пользовательская инструкция должна содержать порядок действий:
1. Определить, к какому проекту относится запрос.
2. Найти соответствующий `Актуальный промпт`.
3. Прочитать его из источника хранения.
4. Прочитать указанные в нём методологические и дополнительные файлы.
5. Проверить, что файлы доступны и прочитаны.
6. Только после этого приступать к работе.

Если чтение не удалось, ассистент обязан сообщить об этом, а не изображать загрузку контекста.

Вопрос о сохранении контекста не должен задаваться при каждом новом чате. Только при обнаружении намерения создать новый проект.

## 3. Иерархия правил

Предложены четыре уровня:
1. Пользовательские инструкции: глобальный механизм запуска.
2. `Промпт0`: общая методология работы.
3. Алгоритмы и дополнительные правила: процедуры и специализированные требования.
4. Актуальный промпт проекта: конкретные правила и указатели для данного проекта.

Нужно определить приоритеты на случай противоречий. Проектный промпт может дополнять общую методологию, но не отменять глобальные требования безопасности и достоверности.

## 4. Идентификация проекта

При нескольких проектах с сохранением контекста команда «новая сессия» сама по себе не определяет, какой проект восстанавливать. Возможные механизмы:
- пользователь явно указывает название проекта;
- ассистент определяет проект по запросу и предлагает подтвердить выбор, если есть неоднозначность.

Предпочтителен второй вариант с обязательным уточнением при неоднозначности.

## 5. Значение полного контекста

Предложено определить состав сохраняемых данных:
- история взаимодействия;
- принятые решения;
- текущие задачи и их статусы;
- методология и правила;
- рабочие материалы;
- ссылки на первоисточники;
- незавершённые операции и ограничения.

Это позволяет восстанавливать ход работы, а не только получать краткий пересказ предыдущей сессии.

## 6. Предварительная структура каталогов

```text
Проекты/
│
├── Промпты/
│   └── Промпт0.md
│
├── Сохранение контекста/
│   └── Алгоритм действий.md
│
├── Дополнительные правила/
│   ├── Правила исследования.md
│   ├── Правила разработки.md
│   └── ...
│
└── Проект А/
    ├── Актуальный промпт.md
    ├── Методология/
    ├── Материалы/
    ├── История/
    ├── Задачи/
    └── Архив/
```

Состав функциональных папок предварительный. История и материалы не должны дублировать друг друга: первая хранит последовательность событий, вторая содержит рабочие документы.

## 7. Предложенный порядок разработки

1. `Промпт0`: определить базовые принципы, границы и механизм маршрутизации.
2. `Алгоритм действий по сохранению контекста`: определить последовательность создания проекта.
3. `Дополнительные правила`: определить механизм выбора, подключения и разрешения конфликтов.
4. `Структура проекта`: определить состав папок и назначение каждого файла.
5. `Актуальный промпт`: определить его формат и правила обновления.
6. `Протокол новой сессии`: определить восстановление контекста и проверку источников.
7. Тестирование: проверить создание проекта, повторное открытие, переключение между проектами и отказ доступа к файлам.

Главный вывод: проектируется не коллекция промптов, а система управления режимами работы. Файлы будут её конфигурацией, алгоритмы будут определять последовательность действий, а пользовательские инструкции станут механизмом запуска.

Начать предложено с `Промпт0`, поскольку до определения его ответственности писать остальные алгоритмы преждевременно.
