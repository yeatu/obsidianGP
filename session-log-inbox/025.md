## Запись 025.

### Пользователь

Хорошее замечание, в таком случае Актуальный промпт должен быть набором ссылок на файлы, которые в нем участвуют. 
Реестр проектов тоже хорошая идея.
В таком случае при Новая сессия пользователя будут спрашивать, с каким проектом он на данный момент работает, список будет пронумерован, а сама позиция в нумерации будет зависеть от последнего изменения (новые как можно выше)

### Ассистент

Это уточняет архитектуру в правильную сторону. Тогда `Актуальный промпт` не будет копией нескольких инструкций и не станет ещё одним местом, где дублируются правила. Он будет **манифестом проекта: перечнем файлов, их назначением, версиями и порядком подключения**.

Это важное изменение. Оно позволяет обновлять отдельные алгоритмы и правила, не переписывая вручную каждый проектный промпт.

## 1. Актуальный промпт как манифест

Предлагаю заложить в него следующие сведения:

| Поле | Назначение |
|---|---|
| Название проекта | Идентификация проекта |
| Версия манифеста | Контроль изменений самого промпта |
| Список файлов | Ссылки на исходные инструкции и материалы |
| Версии файлов | Понимание, какие редакции использовались |
| Порядок подключения | Последовательность чтения |
| Назначение файлов | Какие правила или процедуры задаёт каждый файл |
| Правила разрешения конфликтов | Что делать при противоречиях |
| Алгоритм восстановления | Какие источники читать при новой сессии |

Например, структура может выглядеть так:

```yaml
project:
  name: "Название проекта"
  manifest_version: 1

instructions:
  - file: "Проекты/Промпты/Промпт0.md"
    version: "1.0"
    role: "Базовая методология"

  - file: "Проекты/Сохранение контекста/Алгоритм действий.md"
    version: "1.0"
    role: "Управление сохранением контекста"

  - file: "Проекты/Дополнительные правила/Правила исследования.md"
    version: "1.0"
    role: "Дополнительные правила исследования"

startup:
  - "Прочитать все обязательные инструкции"
  - "Восстановить состояние проекта"
  - "Проверить незавершённые задачи"
```

Это пока пример формата, не готовый файл. И ещё одно требование: ссылка должна вести именно на исходный файл, а версия должна позволять понять, соответствует ли прочитанное содержимое ожидаемой редакции. Иначе ссылка есть, а контроля фактически нет.

## 2. Реестр проектов и выбор при новой сессии

Согласна с нумерацией по дате последнего изменения. Тогда при команде **«Новая сессия»** порядок будет таким:

1. Проект, который изменялся последним.
2. Предыдущий по дате изменения.
3. Остальные в порядке убывания даты.

Например:

```text
С каким проектом будем работать?

1. Разработка плагина
   Последнее изменение: 12.11.2026

2. Оценка системы магии
   Последнее изменение: 10.11.2026

3. Исследование OpenCode
   Последнее изменение: 04.11.2026
```

Пользователь выбирает номер или название. После выбора ассистент открывает соответствующий `Актуальный промпт` и выполняет описанный в нём алгоритм восстановления.

Здесь есть два правила, которые я предлагаю сразу заложить:

- **Номер не является идентификатором проекта.** Это только текущая позиция в списке. После изменения активности проектов нумерация пересчитывается.
- У каждого проекта должен быть постоянный уникальный идентификатор, например `project_id`. Иначе ссылки на проект могут случайно начать указывать не туда после сортировки.

### Что считать последним изменением

Я предлагаю обновлять дату активности при содержательном изменении проекта: изменении рабочих материалов, решений, задач, методологии или истории. Простое открытие проекта не должно поднимать его на первую позицию. Иначе список будет отражать не ход работы, а количество приветствий.

В реестре можно хранить:

```yaml
projects:
  - id: "project-001"
    name: "Разработка плагина"
    path: "Проекты/Сохранение контекста/Разработка плагина/"
    prompt: "Актуальный промпт.md"
    last_modified: "2026-11-12T07:00:00"
    status: "active"
```

Время лучше хранить в едином формате с часовым поясом, а при показе пользователю преобразовывать в привычный локальный формат.
